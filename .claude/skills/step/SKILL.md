name: step
description: Build the next unchecked step of an in-progress deliverable on its lane branch — read the last push's CI run, implement, the step check green, one bounded diff review in a fresh context, one commit pushed to the lane's pull request. Use as "/step" for the next pending step of the one lane, "/step D<n>" to name the lane when more than one deliverable is in progress, or "/step D<n>.<step>" for a specific one.

# Build step $ARGUMENTS

One step, end to end, in this session: **one commit, pushed to the lane's pull request** ([ADR-0082](../../../docs/adr/0082-lanes-on-one-machine-and-one-main.md) §1, lanes on one machine and one `main`). The deliverable must be `in progress` in `docs/plan/README.md`; if it is `planned`, stop and ask the operator to open it (moving the row is their decision).

**Which lane.** More than one deliverable may be in progress when their records are disjoint, each a lane ([ADR-0079](../../../docs/adr/0079-parallel-lanes.md), parallel lanes; the open lanes are listed in [the ledger's window section](../../../docs/plan/README.md#the-window)). An argument of `D<n>` or `D<n>.<step>` names the lane; it must be one the window section lists. A bare call builds the next step of the one lane when exactly one row is `in progress`, and **is refused when more than one is** — stop and ask which lane rather than pick one. Stay in the named lane: never amend a record another lane lists.

**Which branch.** Every lane builds on a branch of its own from its first step, with one draft pull request from it to `main`: the branch the lane file's `- Branch:` line names (`docs/plan/lanes/D<n>.md`) — `lane/D<n>`, or the branch a cloud session was given. Work on it: in a local clone, a worktree of it (`git worktree add ../<repo>-D<n> <branch>`); in a cloud session, the session's checkout. If the checked-out branch is not the one the lane file names, stop and say so. **A lane on a cloud session's branch continues only from a session given that branch, or from a local clone**: a new cloud session is given a new branch and may write only to it, so it stops here and says which session or clone can continue the lane. Give the session the lane's own test database before anything runs the integration tier: `export TEST_DB_LANE=$(pnpm --silent db:lane)` (`/local-dev`, a lane's test database).

- **A step never merges to `main` and never pushes to it.** `main` moves when `/ship` merges the pull request, and not before.
- **`main` is merged in only when the plan needs something `main` has, or GitHub reports the pull request conflicting** (`gh pr view --json mergeable,mergeStateStatus`, or the pull request as the GitHub tools read it). `main` moving is never a reason on its own: the pull request's next run covers it. A conflict in a generated file — the lanes block in the ledger, a digest in `docs/rules/` — is resolved by running its generator (`pnpm lanes`, `pnpm rules:digest`), never by hand; the notes and the changelog merge by `union` and do not conflict.

1. **Read the last push's run first.** `gh run list --branch <lane branch> --workflow gate.yml --limit 3` and, when one failed, `gh run view <id> --log-failed`; in a cloud session without `gh`, the GitHub tools' workflow-run listing for `gate.yml` filtered to the branch, and the failed job's log. Read the run on the lane's last pushed commit (one cancelled by a later push is superseded, not failed).
   - **Green**: build.
   - **Red, or failed to finish**: fix forward first, in a commit of its own on the lane branch — the step check green, pushed — and then build this step. A failed file the run names is re-run in its set and alone before it is called a flake; one that passes in its set and alone twice is named in the note as a flake owed a hardening step, and needs no fix commit.
   - **No run for the lane's last pushed commit**: GitHub runs no `pull_request` workflow while the pull request conflicts with `main`, so read the pull request's state — `gh pr view --json mergeable,mergeStateStatus`, or the GitHub tools' pull-request read. `CONFLICTING` (`mergeStateStatus` `DIRTY`): merge `origin/main` in, regenerate every conflicted generated file (`pnpm lanes`, `pnpm rules:digest`) and resolve the rest, `pnpm step:check` green, push that merge as a commit of its own, and read again. Mergeable, or still `UNKNOWN` while GitHub computes it: the run is queued — treat it as still running.
   - **Still running**: build; do not wait. The next step, or `/ship`, reads it.
   - **Cannot be read** — no `gh`, no GitHub tools, no network: say so in the step's note and build. `/ship` cannot pass without a green head, so the gap is caught there.
2. **Orient**: read the step's entry in the deliverable's plan file — the plan, not its `.notes.md` sibling, which is the journal of earlier steps and is read only when a step names it — load [`docs/rules/process.md`](../../../docs/rules/process.md) and the digest for the area you are about to touch, open the capability's spec in [`docs/specs/`](../../../docs/specs/) for the behaviour you are about to change, then read every record the step's **ADRs:** line names. If the step's head accepts a `proposed` record, do that first: flip its status, move each superseded parent to `superseded by` with its delta stated, update the index row — then build.
3. **Implement.** Use the domain skills (`/api-conventions`, `/frontend-conventions`, `/new-api-module`, `/new-resource-ui`, `/ui-component`, `/db-schema-change`) and the builder agents where they fit. Where the plan or a record turns out to be wrong against reality, **amend it in place, labelled** `**Amended YYYY-MM-DD (D<n>.<step>).**` — while the deliverable is in progress its records may be amended ([the ledger](../../../docs/plan/README.md#the-window)); a corrected record is the system working, not a failure to report. **A behaviour change updates the capability's spec in the same diff** — the requirement, its scenario and the `Proved by:` test — or writes the spec when the capability has none (ADR-0068, behaviour specs); `pnpm docs:check` refuses a requirement without a scenario or a test that does not exist.
4. **The step check**: `pnpm check` is the inner loop while building; **the step ends green on the step check**, `pnpm step:check` (`CLAUDE.md` §Commands), not on the whole gate — CI runs the gate on the push. It needs Postgres when the change reaches an integration tier, and `TEST_DB_LANE` set. **Never pass `--force`**: a cached result is a proof ([ADR-0026](../../../docs/adr/0026-task-graph-caching-and-serialisation.md), the task graph), and a task suspected of impurity is fixed in its `inputs` or `env`, not run cold. A file the step check reports as a `FLAKE` is named in the note; any other red is the step's defect. New endpoints get integration tests and Postman entries; UI geometry gets structural assertions where the done-when names them.
5. **Review — one pass, bounded, in a fresh context**: with the step check green, hand the **diff** to one reviewer — `adr-reviewer` for a record-heavy step, `security-reviewer` for auth, session, config or deployment surfaces, otherwise `code-reviewer`. Correctness findings only, at most a handful, ranked. Fix what is confirmed and **re-run `pnpm step:check`**, which reaches what the fix reaches; log the rest in the commit body or the note. **No re-review round, no zero-finding requirement.**
   - **A builder that cannot run a reviewer** — no Agent tool, as when this skill runs inside a subagent — **does not review its own diff**: its own reading is not a review ([ADR-0082](../../../docs/adr/0082-lanes-on-one-machine-and-one-main.md) §2). It commits and pushes, says in the note and the commit body that the review is owed, and the orchestrating session runs the one review over the pushed commit. Confirmed findings land as a follow-up commit on the lane branch, `fix(<scope>): D<n>.<step> follow-up — the review's findings`, after `pnpm step:check` green, and the note gains the findings and their fates. That pass is the one review, not a second.
6. **Close the step**: tick its checkbox in the plan, then **append the build note to the deliverable's `.notes.md` beside the plan, never inline** (ADR-0068, the plan apart from its notes) — what was built, amendments, the run read in 1 and its conclusion, review findings and their fates (or that the review is owed), the step check's output, anything "pending operator acceptance" (browser-only geometry) recorded honestly. Commit by explicit path, one commit, with a conventional message naming the step and the review's findings in its body, and **push it to the lane branch** (`git push -u origin <lane branch>`, never a force push). Do not wait for CI. The step is closed when the lane branch on the remote carries it.
7. Report: what was built, the commit pushed, the step check's output verbatim, the run read in 1, review findings and their fates, what the operator should eyeball.

Never: start a step gated on an unaccepted record without accepting it at the head; batch several steps into one invocation unless the operator asked; loop reviews; review your own diff and call it the review; merge to `main` or push to it; merge `main` in because it moved; hand-merge a generated file; pass `--force`; wait on CI.

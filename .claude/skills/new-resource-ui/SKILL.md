# New resource UI — `$ARGUMENTS` (resource name, singular, camelCase)

Read [`docs/rules/frontend-and-platform.md`](../../../docs/rules/frontend-and-platform.md) first — the generated statement of the rules currently in force for this area, each line naming its record — then `/frontend-conventions` for the fuller working reference. **The architecture record is [ADR-0049](../../../docs/adr/0049-admin-app-architecture.md) (admin app architecture) as carried by [ADR-0051](../../../docs/adr/0051-platform-extraction.md) (platform extraction)** for what the `shared/` slices are — doors over packages, every layer rule unchanged. The slices you import from — `@/shared/{api,form,grid,resource,i18n,ui,auth,theme,density,lib}` — are **doors over the platform packages**: the import paths are exactly what they were, and a change behind one is a change to every consuming app at once. The eighth platform package, `@repo/account`, is the exception to the address and not to the rule: a feature package's door is the feature or entity slice that held its code (`entities/settings`, `features/{auth,profile-manage,theme,locale,density}` — [ADR-0077](../../../docs/adr/0077-shared-composition-second-wave.md), shared composition, second wave). A resource screen does not reach it, and the slices this checklist writes are the app's own code, not doors. Which amendment window is open, which records are frozen and which supersession is a delta is stated in one place — [the ledger](../../../docs/plan/README.md#the-window) — and never restated here. Mirror `entities/user` + `features/users-manage` + `pages/users` for exact style; for a **singleton** (no list endpoint, no `:id`) mirror `entities/profile` instead — it declares a `FieldConfigMap`, not a `ResourceConfig`, because a resource with no grid declaring `columns: {}` would be claiming an empty table exists.

The contract comes first: everything below is derived from `@repo/contracts`. If the endpoints do not exist yet, that is `/new-api-module`, not this.

## 0. Run the generator first

```
pnpm turbo gen resource-screen
```

It asks for the resource (singular, lower case), its plural, and whether it is owned by an organization (ADR-0067 §1, organizations).

**The templates in `turbo/generators/templates/resource-screen/` are the description of a resource screen** (ADR-0063 §3, typed resource configs and generators). When the shape changes, the template changes in the same step — a shape that lives only in this document decays, because nothing runs it.

The generator writes the entity slice, the feature slice, the thin page, the four record routes, the MSW handlers, the config and page tests, and a seeded catalogue per locale — each with the plural forms _its_ locale requires, so `pnpm i18n:check` is green on the first run. It also applies every enumeration a compiler or a test would redden: the namespace list, `EN_RESOURCES`, the `CustomTypeOptions` augmentation and the two hand-written `lv` fixtures. Then it runs prettier over what it wrote, rebuilds `routeTree.gen.ts` through the app's own Vite config, and prints the three edits it will not take for you.

**Everything below is what the generator deliberately does not do.** Sections 1–4 are the seeded files you now make true — the domain, the copy and the claims; section 3's nav entry and the policy row of ADR-0042 (client-side authorization) are the two it printed, and the policy row exists to be **transcribed from the `authorize(` calls that mount the endpoints** and from nothing else, so a generated guess would be the transcription lying.

## 1. Entity slice — `src/entities/<x>/`

- `<x>.keys.ts` — `all` / `lists()` / `list(params)` / `details()` / `detail(id)`. Never an inline key array at a call site.
- `<x>.api.ts` — `create<X>Api(client)` returning plain typed functions, `as const`. `list` reassembles the envelope into `Page<T>` (`meta.pagination`, `meta.sort`, `meta.filters` — the grid renders its own state from what the server said). Not hooks: a route loader and a test both need these without a React tree.
- `<x>.config.ts` — the `ResourceConfig`, **`as const satisfies ResourceConfig<XResource, CreateXBody, UpdateXBody>`** (ADR-0063 §1, typed resource configs): the three types come from `@repo/contracts`, columns are keyed by the row (plus the reserved `actions`), fields and `errorFields` by either body — so a misspelt column or a field the endpoint dropped fails `check-types` rather than rendering:
  - `grid` — how the grid _behaves_, and the whole of what v2 costs a resource beyond columns and fields:
    - `editSurface: "dialog" | "drawer" | "page"` (absent means `dialog`). The URL is identical across all three, so this line breaks no link and no test.
    - the capability flags `selectable` / `canCreate` / `canEdit` / `canDelete` / `canBulkDelete`. **These are not permissions** — they say what the surface offers, and `useAllowedCapabilities` conjoins them with the operator's role on the page. `canBulkDelete` without `selectable` is dead data and the config test refuses it.
    - `hotFilters` — the stances an operator presses many times a session, `enum` or `presence` only, declared **only** where `listQuerySchema` allow-lists the field and the operator. A filter that is a composition rather than a stance belongs in its column's header dialog instead, and a filter should not be both.
    - `pageSizes` if this endpoint wants other than the pager's defaults.
    - `searchable: true` where the endpoint implements `q` — the page reads it from here rather than passing a bare prop, so the claim is checkable (ADR-0063 §2, typed resource configs).
    - **A key outside this block's vocabulary is a compile error** (`satisfies` refuses it), and _adding_ one to `GridConfig` is a record's decision rather than a config edit: every capability has to be answered by ADR-0042's `can(action, resource)` or explicitly not be one, the way `hotFilters` and `searchable` are not.
  - `columns` in render order (declaration order **is** column order). `sortable` only where the endpoint's `sortable` allow-list has the field; `filter` only where `filterable` has the field **and** that operator; `formatter`/`cellRenderer` are registry keys. A `filter` renders a header icon and a dialog — declare one for the compositions, and let `grid.hotFilters` carry the stances.
  - a column whose `cellRenderer` is `rowActions` is **structural**: pinned last, never hidden, reordered, resized or offered in the Columns menu. So is the selection checkbox, which `AppGrid` injects and no config declares.
  - `fields` with `component`, `label`, `initialValue`, `variants` (`create` | `edit`), `nullable` where the update body allows `null`, `description` where the operator needs the consequence stated.
  - `errorFields` — domain codes the API reports with no path, mapped to the box an operator would change.
  - `export const <X>FormInput = createAppFormInput(<x>ResourceConfig.fields);`
- `<x>.queries.ts` — `use<X>List` (with `placeholderData: keepPreviousData`), `use<X>`, and one mutation per write. `meta: { success }` on every write; `meta: { errorToast: false }` on the ones a form hosts; `...CREDENTIAL_MUTATION` on any whose variables carry a plaintext password. Invalidate `lists()` and the touched `detail(id)` — and nothing, deliberately, when the write is to a different aggregate.
- `index.ts` — the public API. Everything above is reached through it.

## 2. Feature slice — `src/features/<x>-manage/`

- `types.ts` — the action union (`{ kind: "create" } | { kind: "edit", <x> } | …`) and its handler type.
- One component per interaction. Forms use `AppFormDialog` + `zodResolver(<body schema>)`; confirms use `ConfirmDialog` with copy written for _this_ action ("this cannot be undone" is a lie about a soft delete).
- `<x>-dialogs.tsx` — one switch over the union, mounting only the active dialog, so a form cannot keep the last row's values.
- `use-<x>-row-actions.ts` — the row menu as data for `table.options.meta`. Do **not** disable an entry on a rule the API owns (rank, invariants, self-targeting): offer it and render the server's refusal.
- `use-bulk-delete-<x>.ts` where the grid declares `canBulkDelete` — a `Promise.allSettled` fan-out over the same per-row delete, bounded in flight, stopping on `RATE_LIMITED`, reporting per-item refusals through `shared/api/bulk-outcome`. One confirmation with copy written for _this_ resource, one invalidation, one summary. The selection is cleared through the `GridToolbarContext` the handler is given, because the state lives inside `AppGrid`.
- Anything else the interaction invalidates goes here, not in the entity — this is the layer allowed to see two entity slices.
- `index.ts` — the public API.

## 3. Page and route

- `src/pages/<x>/index.tsx` — `useCarriedListState(useSearch({ from }))` → `toListQuery` → the list hook → `AppGrid`, one `useState` for the action, and the dialogs. Beyond the base grid props, v2 adds four and each is one line: `capabilities={useAllowedCapabilities(config.grid, "<resource>")}` — the second argument is ADR-0042's (client-side authorization) `ResourceName`, keyed by the **router path** and not by `config.name`: the users screen passes `"users"` while its config is named `"user"`, `createAction={<Button asChild><Link to="/<x>/new" state={openState}>…</Link></Button>}` (a link, not a handler — composing a record is addressable; `state`, not `search`, since ADR-0044, a record URL carries only the record), `hotFilters={config.grid.hotFilters}`, and `gridId={config.name}`. Plus `onBulkDelete` where the capability is declared. **The two shipped pages differ only in names and copy** — if this one needs to know something the other does not, that difference belongs in the config, and if it cannot go there it is a finding for the ADR rather than a special case here.
- **Four route files**, not one:
  - `_dashboard.<x>.tsx` — `validateSearch: listQuerySearchSchema`, `search: { middlewares: [stripSearchParams(listSearchDefaults)] }`, `staticData: { title, fullHeight: true }`. Under `_dashboard/` so the guard is inherited. **No `retainSearchParams`** (ADR-0044, a record URL carries only the record): a record URL carries only the record, and the list state travels as history state instead.
  - `_dashboard.<x>.index.tsx` — the **index leaf the grid does not live on**. The grid lives on the parent; putting it here unmounts it whenever a record surface opens, which is exactly what an overlay must not do. The corollary: "a record is open" is not a count of child matches, because the index is a child too.
  - `_dashboard.<x>.new.tsx` and `_dashboard.<x>.$<x>Id.tsx` — the record surfaces, the detail one loading through `ensureQueryData` on the entity's own `detail(id)` key. A loader has no hooks, so it reaches the API client through the router context. Its `errorComponent`'s way back uses `closeSearch`, so even a record that failed to load returns to the view it was opened from.
  - Every entry point spreads `openState` and every close passes `closeSearch`, both from `useRecordNavigation` — four call sites per resource, and forgetting one is an operator losing their page rather than a type error.
- **The two printed edits land here.** Add the nav entry in `widgets/app-sidebar` if it belongs there, with its `resource` so ADR-0042 (client-side authorization) can narrow it; and add this resource's row to `shared/auth/policy.ts` and its fixture in `shared/auth/__tests__/policy.test.ts`, then replace the generated page's `const capabilities = <x>ResourceConfig.grid` with `useAllowedCapabilities(config.grid, "<x>")`. The generated page passes the config's block **ungated** and says so where it does it, which is a screen that offers every capability to every role until the row exists.

## 4. Mocks and tests (ADR-0036, admin app testing strategy)

- `src/test/msw/handlers/<x>.handlers.ts` — `create<X>MockState()` + `create<X>Handlers(state)`, no module state. Parse every request with the contract schema; answer through `ok` / `listOk` / `fail`. Model each refusal the UI can meet, and name the service function it mirrors — a mock more permissive than the service certifies the opposite of production.
- `entities/<x>/__tests__/<x>.config.test.ts` — **one call of `assertConfigMatchesContract`** through the `shared/resource/config` door (ADR-0063 §2, typed resource configs), passing this endpoint's `listQuery`, both bodies, `samples` for the fields whose values the contract has an opinion about (an email, a password), and `optionLabelled` built from the app's `common` catalogue. It checks every `sortable` and every filter field-and-operator pair, the negative controls, every hot filter and each of its options, `q` in both directions, the required keys derived from the body's `shape`, the `nullable` fields, and `canBulkDelete` implying `selectable`. **Do not hand-write the claims**: hand-written they ran to several hundred lines per resource, and a suite nobody remembers to write checks nothing.
- `features/<x>-manage/__tests__/` — each write: the request the endpoint would have accepted, the refusal landing where the operator will look, the submit lock, the toast.
- `pages/<x>/__tests__/` — through `renderApp` on the real route tree: columns and rows, a header click writing the URL **in the API's own spelling** (`?sort=-email&filter[status]=active`, asserted as one whole string — a per-parameter check passes just as well on a JSON blob), the pager, a filter composed in its dialog and applied, a hot filter pressed, and the error panel with its retry. Assert a record opened from a filtered page has a **bare URL** and that the grid behind it still shows that page — on what the grid renders, not on `location.state`, or the assertion survives the grid ignoring the carrier. Clear `localStorage` in `beforeEach` — the grid persists its columns for real here — and close any overlay before unmounting.

## 5. Finish

- `pnpm check` while iterating (lint + check-types + test:unit, one cached parallel run — deliberately unfiltered, so a contracts change breaking another package surfaces here), then the gate (`CLAUDE.md` §Commands) once at the end — its lint, check-types and size links are cache hits at that point, so its cost is the integration tier (ADR-0026, task caching and serialisation) plus a prettier pass.
- Update the current plan's step notes in `docs/plan/`; if anything here forced a change under `src/shared/`, say so and say why — that is the machinery being wrong rather than this resource being special, and it is what an ADR amendment is for. That claim is load-bearing and has been measured twice: adding the second resource, and then putting both on the full v2 grid surface, and neither needed the machinery to change.
- **Walk it in a browser.** jsdom has no layout, so nothing above can see a column that will not narrow, a pager eaten by an `overflow-hidden`, or a toolbar that wraps badly at 900px. Every layout defect the grid work has found was found that way.

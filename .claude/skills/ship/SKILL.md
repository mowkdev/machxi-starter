name: ship
description: Close an in-progress deliverable on its lane's head — merge `main` in, run its definition of done under the lock, regenerate the digests, sync the records, remove the lane file, changelog, move the ledger row to shipped, push the ship commit, see the pull request's run green on it, merge the pull request with a merge commit, and tag the merge commit with the ledger's prefix. Use as "/ship" when one deliverable is in progress and every step is ticked, or "/ship D<n>" to name the lane when more than one is.

# Ship deliverable $ARGUMENTS

Closes one lane. More than one deliverable may be in progress, each a lane with disjoint records ([ADR-0079](../../../docs/adr/0079-parallel-lanes.md), parallel lanes; the open lanes are in [the ledger's window section](../../../docs/plan/README.md#the-window)). An argument `D<n>` names the lane and must be one the window section lists; a bare call ships the one `in progress` row and **is refused when more than one row is `in progress`** — ask which lane.

**`/ship` runs on the lane's head, never on `main`** ([ADR-0082](../../../docs/adr/0082-lanes-on-one-machine-and-one-main.md) §1, lanes on one machine and one `main`): on the branch the lane file's `- Branch:` line names, whose draft pull request carries every step as a commit. `main` takes the lane once, when the pull request merges below. **Check the branch first**: if the checked-out branch is not the one the lane file names, stop and say so — **a lane on a cloud session's branch ships only from a session given that branch, or from a local clone**, because a new cloud session may write only to the new branch it was given. Every step must be ticked in the lane's plan file; if one is not, stop and say which. The evidence per step is in the deliverable's `.notes.md` beside the plan (ADR-0068, the plan apart from its notes) — read it here, once, with the last pushed commit's `gate.yml` run (`gh run list --branch <lane branch> --workflow gate.yml`, or the GitHub tools); a red run is fixed forward on the branch before anything below.

1. **Merge `main` in**: `git fetch origin && git merge origin/main` on the lane branch, so the definition of done runs over the tree the pull request will make. A conflict in a generated file — the lanes block in the ledger, a digest in `docs/rules/` — is resolved by running its generator (`pnpm lanes`, `pnpm rules:digest`), never by hand; the notes and the changelog merge by `union`. `TEST_DB_LANE` set for the lane (`export TEST_DB_LANE=$(pnpm --silent db:lane)`).
2. **Definition of done, executed, under the lock**: every machine item of the plan's checklist verbatim — the gate (`CLAUDE.md` §Commands), the one time the whole tree runs on the machine for this lane, held under one lock across its links: `node scripts/with-lock.mjs tiers -- sh -c '<the gate>'`, so no other lane's tier runs between them — `pnpm test:unit` twice with the second run fully cached, `pnpm test:postman` where the deliverable touched endpoints, `pnpm test:scripts`, and a clean tree afterwards. Never `--force`.
3. **Operator items, named**: list every item only a human can check (browser walks, visual acceptance, a deployment, a repository setting) and record each as _accepted by the operator_ or _pending_ — never fold one into "shipped" silently.
4. **Regenerate the derived documents**: `pnpm rules:digest`, then `pnpm docs:check`. The digests are generated, never hand-edited; the hygiene check is what keeps the inherited documents free of this repository's step numbers and dates, and what refuses a behaviour spec whose record or test no longer exists (ADR-0068, behaviour specs).
5. **Records agree**: the deliverable's records read `accepted` with their amendments labelled; every superseded parent reads `superseded by` with its delta stated; the ADR index's topic table names the record now in force and its _Implemented_ cells name the steps; the plan's checkboxes are all ticked.
6. **The sweep**: the open lanes are stated in one place, [the ledger](../../../docs/plan/README.md#the-window) — delete the lane's file, `docs/plan/lanes/D<n>.md`, and run `pnpm lanes`, which rewrites that section's list and running paragraph from the lane files left, every other lane's file untouched — what moved goes in the ledger's `How D<n> closed` section, never in the generated paragraph — then read (do not restate) everything that links to it: `.claude/**`, `CLAUDE.md`, `README.md`, `docs/README.md`, `docs/specs/**` and the ADR index. A document that states the status instead of linking to it is the defect this list exists to catch.
7. **The ledger row** moves to `shipped YYYY-MM-DD` with a §How it closed note separating machine-verified from operator-accepted evidence.
8. **Changelog**: read the prefix from the ledger header's one `Tag prefix:` line (`pnpm docs:check` refuses a ledger without it); if the tag `<prefix>-D<n>` already exists, locally or on a fetched remote, stop and say so rather than move it. Write one entry in `docs/CHANGELOG.md` from the plan's goal line — number, name, ship date, goal — ending `Tag <prefix>-D<n>.` One entry per deliverable; not per commit, and not semver. The changelog is this repository's journal, like `docs/plan/`: it records this repository's deliverables only.
9. **The ship commit, pushed**: commit by path on the lane branch, with a message naming the deliverable's ship, and push it (`git push origin <lane branch>`, never a force push).
10. **The pull request's run green on that head**: wait for the `gate.yml` run on the lane's last pushed commit — `gh run watch <id>` after `gh run list --branch <lane branch> --workflow gate.yml`, or the GitHub tools' run for that commit — the one wait in the whole lane. Red: fix forward on the branch (`pnpm step:check`, commit, push) and wait again. **No run appears**: GitHub runs no `pull_request` workflow while the pull request conflicts with `main` — `main` moved after 1 — so read its state (`gh pr view --json mergeable,mergeStateStatus`, or the GitHub tools' pull-request read); `CONFLICTING`: merge `origin/main` in again, regenerate the conflicted generated files (`pnpm lanes`, `pnpm rules:digest`), resolve the rest, `pnpm step:check` green, push, and wait again. The pull request does not merge on a red or unread head.
11. **Merge the pull request with a merge commit**: mark it ready — `gh pr ready`, or the GitHub tools' pull-request update with `draft: false`, since a draft cannot be merged — and merge it — `gh pr merge <number> --merge`, or the GitHub tools' merge with the `merge` method — never squash, never rebase, so the per-step commits the ledger and the notes cite survive on `main`. Where `main` is protected with the gate required, the green run above is what lets it merge.
12. **Tag the merge commit**: take it from the pull request — `gh pr view <number> --json mergeCommit`, or the merge commit's SHA as the GitHub tools' pull-request read returns it — not from `origin/main`, which may have moved since; `git fetch origin main`, confirm that commit's second parent is the head the run above proved green (the ship commit, or the fix-forward after it), put an annotated tag `<prefix>-D<n>` on it — `starter-D<n>` in the starter, the fork's own prefix in a fork, so the two namespaces never meet ([ADR-0081](../../../docs/adr/0081-build-versions.md), build versions) — and push it (`git push origin <prefix>-D<n>`). Product release tags (`v<version>`) belong to whatever release tool the repository adopted, never to `/ship`. Then read `gate.yml`'s run on `main` for the merge commit, and record it. A session that cannot push a tag or read that run says so and names the commands for the operator.
13. **Clean up**: delete the lane branch, local and remote, and remove its worktree; the pull request's merge commit is what the ledger cites from here.
14. Offer `/scope` for the next `planned` row — opening it stays the operator's decision.

Steps 4 to 12 happen together or the deliverable is not closed: a merged pull request without its tag, or a tag on anything but the pull request's merge commit, is a ship to finish, not a ship.

Never: ship from `main`; merge the pull request on a red or unread run; squash or rebase it; move an existing tag; hand-merge a generated file; pass `--force`.

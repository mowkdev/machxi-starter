# .claude — project configuration for Claude Code

Everything in this directory travels into a fork ([ADR-0065](../docs/adr/0065-starter-lifecycle.md), the starter lifecycle), so it is written to survive one: citations carry a topic gloss, and no step number, ship date or record range appears here. `pnpm docs:check` enforces the last three, and refuses a relative link to a file that is not there — here, in `README.md`, `docs/*.md`, `docs/specs/` and `docs/rules/` — resolved from the file that holds it, so a skill's links start `../../../`; the gloss is a reading.

- `settings.json` — shared permission defaults (safe pnpm/docker/git commands allowed; destructive database and git operations ask; `.env` files never read). Personal overrides go in `settings.local.json` (git-ignored).
  - `git push`, `git merge`, `git worktree`, `gh pr` and `gh run` are allowed because a lane is a branch and one pull request ([ADR-0082](../docs/adr/0082-lanes-on-one-machine-and-one-main.md), lanes on one machine): an unattended step pushes its commit, reads the pull request's run, and merges `main` in when GitHub reports a conflict, without stopping to ask. Every form of force push — `--force`, `-f`, a `+` refspec — stays denied, because a lane's commits are what the ledger cites and the pull request proves; a push that rewrites them erases that record.
  - Recursive shell search (`grep -r`, `grep -R`, `find`, `rg`) is denied. Those commands ignore `.gitignore` and walk `node_modules` and `.turbo`, which is slow and floods the context. A plain single-file `grep` isn't denied but isn't allowlisted either, so it still stops an unattended run to ask for approval. Use Claude's Grep/Glob tools instead, for any search — they are ripgrep-backed, skip anything `.gitignore`d, and need no Bash approval at all.
- `rules/` — path-scoped loaders (`paths:` frontmatter). `api.md` loads with `apps/api` and the data packages, `frontend.md` with the SPAs, `@repo/ui` and the platform packages. Each one points at its generated digest in [`docs/rules/`](../docs/rules/) — the rules currently in force, each line naming its record — rather than restating them.
- `agents/` — subagents: `adr-reviewer`, `security-reviewer` and `code-reviewer` (all read-only; one of the three is the single bounded review pass a build step gets, in a fresh context — run by the orchestrating session when the builder has no Agent tool, never by the builder over its own diff), `module-builder`, `ui-builder`, `db-migrator`, `test-engineer`, `adr-author`, and `gate-runner` (haiku, low effort, Bash-only: runs `pnpm check`, the step check or the gate and returns a structured pass/fail). The reviewers stay on the strongest model; the mechanical agents are the ones to tier down.
- `skills/` — slash-command workflows, split by where the code lives:
  - API and data: `/api-conventions`, `/new-api-module`, `/add-endpoint`, `/db-schema-change`, `/postman-sync`.
  - The SPAs and the design system: `/frontend-conventions`, `/new-resource-ui`, `/ui-component`.
  - Process — **scope → step → ship**: `/scope` (a deliverable into a one-page plan whose done-whens are commands and test names), `/step` (the next step: read the last push's CI run, implement, update the capability's spec in [`docs/specs/`](../docs/specs/), the step check green, one bounded diff review, append the build note to the plan's `.notes.md` sibling, one commit pushed to the lane's pull request — ADR-0068, behaviour specs and the plan apart from its notes), `/steps` (an unattended repeat of `/step` that never waits on CI), `/ship` (on the lane's head: the definition of done, the digests, the ledger row, the pull request merged with a merge commit, the tag on it). Plus `/new-adr`, `/bootstrap` (a fork's day one: runs `pnpm bootstrap` for the empty ledger and changelog under the fork's prefix, and ends on `pnpm docs:check` and the script tests green; `docs/forking.md` opens with the whole fork-day checklist) and `/local-dev`. `/scope` on an empty ledger writes the first row, with the number and title the operator names.
  - **Lanes** ([ADR-0079](../docs/adr/0079-parallel-lanes.md), parallel lanes, as carried by [ADR-0082](../docs/adr/0082-lanes-on-one-machine-and-one-main.md), lanes on one machine and one `main`): more than one deliverable may be in progress when no record belongs to two of them; each is a lane, [the ledger's window section](../docs/plan/README.md#the-window) names every open one from its lane file, and `pnpm docs:check` refuses two lanes sharing a record or two owning the schema. While more than one lane is open, `/step`, `/steps` and `/ship` take the lane as `D<n>` and refuse a bare call. **Every lane has one shape**: `/scope` opens it with a documents-only commit on `main`, a branch of its own — `lane/D<n>`, or the branch a cloud session was given, named in the lane file — and a draft pull request; each step is one commit pushed to that branch, proved whole by `gate.yml` on the pull request and read by the next step before it builds; nothing merges to `main` until `/ship` merges the pull request with a merge commit on the lane's head. `main` is merged into a lane only when the lane needs it or GitHub reports a conflict. `/step`, `/steps`, `/ship` and `/scope` read CI and write pull requests with `gh` in a local clone and with the GitHub tools in a cloud session. `/steps` stays in its lane: it builds that deliverable's steps one after another, never opens or ships a deliverable, and never touches another.
- `../.worktreeinclude` — the untracked files Claude Code copies into a worktree it creates: `.env` and each SPA's own `.env`. A worktree without them starts an app that cannot reach the API.
- **The step check and the lock** ([ADR-0082](../docs/adr/0082-lanes-on-one-machine-and-one-main.md), lanes on one machine): `pnpm step:check` is what a step runs before it commits, sized to what its change reaches, and the gate is the whole tree's, a lane's; `CLAUDE.md` §Commands defines both, and `gate-runner` runs either. The tiers that contend for one machine — `test`, `test:int`, `size`, `test:e2e` — run inside `scripts/with-lock.mjs`, one lock in the git directory every worktree of a clone shares, so a second lane waits and prints who holds it instead of colliding; a cloud session is its own machine and holds its own. A worktree may point `TURBO_CACHE_DIR` at one shared cache — `export TURBO_CACHE_DIR="$(git rev-parse --path-format=absolute --git-common-dir)/turbo-cache"` — so a task another checkout already ran is a hit rather than a rebuild. The hit is correct because a cached task is a pure function of the tree and its declared `env` ([ADR-0026](../docs/adr/0026-task-graph-caching-and-serialisation.md), the task graph), which is also why nothing passes `--force`.

## How a lane runs — on one machine, and in the cloud

A lane has one shape wherever it runs ([ADR-0082](../docs/adr/0082-lanes-on-one-machine-and-one-main.md), lanes on one machine and one `main`). What differs is who else shares the machine, where the branch comes from, and what reads CI.

- **The tier** — `- Tier:` in the lane file and the plan's header. It declares what the lane expects to need. A `package` lane needs no Postgres beyond a harness's own tests and no SPA build, and any number may be open. An `api` lane takes a database of its own. A `schema` lane is the one open lane that adds migrations. The tier does not size the step check, which sizes itself to the diff: a lane that touches a test harness, or a package with an integration tier, needs Postgres whatever its tier, and a lane that reaches an SPA runs `size`. `pnpm docs:check` refuses a tier the plan does not name, and a second `schema` lane.
- **The database** — `export TEST_DB_LANE=$(pnpm --silent db:lane)` before anything runs the integration tier. It slugs the current branch, creates `machxi_<slug>_test` with `machxi_test`'s owner and grants (idempotent; it refuses `main`), and prints the slug. The harness then points both test URLs at that database, with the `_test` guard still underneath. `TEST_DB_LANE` is in `turbo.json`'s `env`, so one lane's cached run is never another's. `main` and CI run on `machxi_test` itself.
  - On one machine, every lane shares the one Postgres container and each lane has its own database in it.
  - In the cloud, the session's own Postgres on `localhost:5432` serves, with the roles and `machxi_test` that `docker/local/postgres/init/` creates. Both `.env.test` files are committed, so the tier needs no root `.env`, no Docker and no dev stack.
- **The step check** — `pnpm step:check`, the same command in both places. It is sized to the diff against the lane's merge base with `origin/main`, so fetch `origin` first. Never `--force`. On one machine, a worktree may share one turbo cache (above). A cloud session's cache is its own checkout's.
- **The lock** — the `tiers` lock is taken by `test`, `test:int`, `size` and `test:e2e`, and by `/ship` around the whole gate.
  - On one machine it sits in the git directory every worktree shares, so a second lane waits and prints the holder instead of colliding. A holder whose process is gone is taken over; a wait past the timeout stops with the holder's name, and the command does not run; a session never deletes the lock itself.
  - In the cloud the session is its own machine and holds its own lock. Nobody else contends for it, except the session's own interrupted run, which the next run takes over.
- **The pull request** — the branch the lane file names, one draft pull request to `main`, one commit per step pushed to it, never a force push. `gate.yml` proves each push whole; the next step reads that run first.
  - On one machine the branch is `lane/D<n>`, built in a worktree of its own (`git worktree add ../<repo>-D<n> lane/D<n>`). `gh` reads the runs and writes the pull request.
  - In the cloud the branch is the one the session was given, named in the lane file, and the GitHub tools stand in for `gh`. A cloud session may write only to its own branch, so a lane opened on one continues and ships only from a session given that branch, or from a local clone. Where the session cannot push to `main`, `/scope`'s scoping and opening commits ride with the pull request instead, which is safe only while no other lane is open.
- **What neither runs** — the dev stack is the operator's, attached to and never started (`CLAUDE.md`), so a session without one leaves the browser tier and the Postman run to the operator. Both sit beside the gate, never in it.

**There are no orchestration workflows.** An earlier generation — a three-stage decide → verify → build pipeline with multi-agent refutation gates — was removed after seventeen verification rounds against one deliverable's records burned millions of tokens converging on prose instead of building code. The post-mortem and the replacement rules are [ADR-0050](../docs/adr/0050-adr-lifecycle-and-verification.md) (the ADR lifecycle and verification): **machines gate** (the gate is defined once, in `CLAUDE.md` §Commands), **review is one bounded pass on a diff**, and **uncertain mechanics get a timeboxed spike in a worktree, not a debate**. The retired scripts are in git history if a future measurement wants the baseline.

Root `CLAUDE.md` is the always-loaded summary; the records in `docs/adr/` are the source of truth; which of them may still be amended in place is stated in [the ledger](../docs/plan/README.md#the-window) and nowhere else.

# D18 — Mail flows: build notes

The per-step build record of [D18](0018-mail-flows.md) — what was built, the amendments, the review findings and their fates, the gate's output, and what is pending the operator — kept apart from the executable plan so a builder opens the plan and not the journal ([ADR-0068](../adr/0068-behaviour-specs-and-plan-notes.md) §2, the plan apart from its notes). `/step` appends here; `/ship` and the close-out read it.

## `D18.1` — Accept ADR-0071; the table, the columns, the config, the sweep

**The head.** [ADR-0071](../adr/0071-mail-flows.md) moved `proposed` → `accepted` and [ADR-0017](../adr/0017-identity-model-populations-and-roles.md) moved to `superseded by` — its **second** partial successor, joining ADR-0067 — with the delta stated in both directions and its own paragraph in 0017. The other three parents (0018 at `D18.3`, 0027 at `D18.5`, 0057 at `D18.9`) are untouched, the `D10.5` precedent. The index gained a topic row for mail flows, both record rows were updated, and the "no window is open" sentence D17 left behind was replaced. The ledger's §The window records the acceptance and the amendments.

**Built.** `account_tokens` (`packages/db/src/schema/account-tokens.ts`) with `TOKEN_PURPOSES` declared once in `@repo/contracts` and consumed by `pgEnum` and by `z.enum` — the second half proved in `enums.test.ts` rather than asserted in prose. `users.email_verified_at`; `staff.password_hash` nullable, threaded through `StaffRecord`/`StaffRowWithRoles` with the null guard added to `verifyActorPassword`. Migration `0014_mail_flows` — generated, then extended by hand with the backfill, which no schema diff can produce. `RESTRICTED_SCHEMA_TABLE_IMPORTS` and `TRUNCATED_TABLES` grown, both checked by `enumerations.test.ts`; `schema.int.test.ts`'s two exact enumerations grown with them. `pruneAccountTokens` beside the other two sweeps, reported as a third count. Config: the two app URLs, four TTLs, `RATE_LIMIT_PASSWORD_RESET_MAX` — and, on the review, the window it is per. Logger: `payload`, `newEmail` and `link`. The dev seeds stamp every fixture but the pending one. `.env.example`, `docker/prod/.env.example`, `docker/prod/compose.yaml` and `docs/deploy.md` carry the new keys.

**Amendments — one record, one plan step, and a third correction that is the review's.** [ADR-0071](../adr/0071-mail-flows.md) §3 said the backfill stamps "accounts that existed before this record" verified, full stop. That is wrong for the one row it would matter on: a `pending_verification` account was not produced by ADR-0018's registration rule, it was put in that state deliberately — the `--dev` fixtures carry exactly one — and stamping it would make `email_verified_at` disagree with `status` on the very row the verification flow exists to move. §3 is amended in place, labelled; the migration's `WHERE` and the seeder match it. The **plan's step-1 done-when** is amended for the same reason plus two file names: it asked for "every dev fixture user `active` with `email_verified_at` set", which `DEV_USERS` cannot satisfy and should not, and it named `seed.int.test.ts` and a "unit test" where the tree has `seeds.int.test.ts` and `prune-sessions.int.test.ts`. §3 took a **second** amendment on the review, below.

**Not in the plan's list, and added anyway.** `docker/prod/compose.yaml`. The plan's constraint names the schema, both `.env.example` files and `docs/deploy.md`; the reference compose enumerates the API's environment explicitly, so two variables that are _required in production_ would otherwise have been unreachable in the one deployment description this repository ships.

**Review — `security-reviewer`, one pass, no re-review.** Five findings, all confirmed: four fixed in code, one fixed as documentation.

- **Fixed — the `3 / hour` budget had no hour** (medium). `RATE_LIMIT_PASSWORD_RESET_MAX` landed in `rateLimit`, whose only window is `RATE_LIMIT_WINDOW_MS`, a fixed fifteen minutes in `core/middleware/rate-limit.ts` shared by all four limiters — so `D18.2` would have reached for the only window there and deployed **twelve** messages an hour into a stranger's inbox, four times ADR-0071 §4's number, with nothing failing. `RATE_LIMIT_PASSWORD_RESET_WINDOW` (1h) lands here beside the count rather than in the step that builds the limiter, because a `3` with no window to be per is not a decision, it is a number.
- **Fixed — the production refusal was string equality against two constants** (medium). `http://localhost:3000`, `http://127.0.0.1:3002` and `http://[::1]:3002` all passed, each reproducing exactly the failure the refine exists to stop; and `originSchema()` permits `http:`, so `http://app.internal` would have mailed single-use, takeover-enabling tokens in cleartext URLs. Both refines now read the **parsed** URL through `isLocalOrInsecureAppUrl`: loopback hostnames refused, `https:` required. Four spellings and two http origins are asserted.
- **Fixed as documentation — the invariant was written before it was enforced** (medium). The column's comment said "every `active` user has a proven address … D19 may link by reading `status` alone", but registration and `POST /admin/users` still create `active` rows with an empty stamp until `D18.3`. An invariant documented ahead of its enforcement is how a claim becomes an account-takeover primitive, so both the column comment and ADR-0071 §3 now carry the date it becomes true — a **second** labelled amendment to §3.
- **Fixed, and one half declined with its reason — redaction covered the column, not the credential's travelling form** (low). The token is not logged as a column, it is logged as a URL with the raw token in its fragment, and the `log` transport writes a line per message; `link` and `*.link` are added ahead of use, the way `tokenHash` was. `url`/`*.url` were **declined**: `*.url` blanks `req.url` on every request log line in the repository, trading the observability of the whole HTTP layer for one hypothetical field name. A test asserts `req.url` survives, so the omission is deliberate and checkable rather than forgotten.
- **Fixed — the ESLint comment claimed more than the rule delivers** (low). `RESTRICTED_SCHEMA_TABLE_IMPORTS` feeds `noSchemaTables`, which covers services and controllers; a repository may still import `accountTokens`. "A service that could reach it could mint or consume a credential without going through `core/tokens`" described the `noAuditTable` shape instead. Reworded to say what the rule is — exactly `sessions`' protection — and to name what enforcing a single writer would take.
- **Also taken, from the residual list** — `RATE_LIMIT_PASSWORD_RESET_MAX` and its window joined `docker/prod/compose.yaml` as bare keys: this is the first limiter here whose default is an anti-abuse number rather than a capacity one, so an operator has to be able to reach it.

**Logged, not built — two residual risks for a later step or a record.**

- **No ceiling on `PASSWORD_RESET_TOKEN_TTL` or `EMAIL_CHANGE_TOKEN_TTL`.** ADR-0071 §1 argues the TTL _is_ the mitigation for a fragment-borne token, which is the same class of claim that earned the two impersonation windows their `.max()`. A 24h ceiling on the two flows that can take an account over is a record-level decision rather than a build step's; the schema comment states the deliberate absence.
- **`payload` is a very broad redact key.** It blanks any field named `payload` on any logger in the monorepo — a decoded JWT body among them. Safety-positive and deliberate; the docblock now says so, so the next reader does not narrow it.

**The gate — `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check`, exit `0` on the committed tree.** `lint` 17/17, `check-types` 16/16, `test` 15/15 **0 cached** (api unit + integration, admin, customer, the packages), `size` 4/4 inside every budget, `format:check` "All matched files use Prettier code style!". Beside it: `pnpm test:unit` twice — 15/15, then **`>>> FULL TURBO`** in 58ms; `pnpm docs:check` — inherited documents clean, behaviour specs clean (11 files).

**No behaviour spec changed, deliberately.** This step moves no request, response, status, header or side effect (ADR-0068 §1). `docs/specs/mail-flows.md` is begun at `D18.3`, the first step with wire behaviour to describe.

**Pending the operator.** Two things, neither blocking.

- **The dev database has not been migrated.** `0014` is applied by the integration harness on every run, so the gate proves it from nothing, but the developer's own database is still at `0013`. Run `pnpm db:migrate`, and `pnpm db:seed -- --dev` for the stamped fixtures, before the next dev-stack sitting; the backfill is idempotent and stamps nothing already stamped.
- **The two new production refusals change what an existing deployment accepts.** A deployment upgrading past this commit must set `CUSTOMER_APP_URL` and `ADMIN_APP_URL` to https, non-loopback origins or the API refuses to start — which is the intent, and `docs/deploy.md` and both `.env.example` files now say so, but it is a startup failure on upgrade rather than a silent default, and better known before the deploy than during it.

## `D18.2` — The token service, the templates, the limiters

**Built.** `core/tokens` — `createAccountTokens` (`mint`, `consume`) over `createAccountTokensRepository`, in `core/` for the audit writer's reason: the mechanism is infrastructure five flows borrow and the purposes belong to the features. The repository holds four statements and no `findByTokenHash`, the `impersonation_handoffs` precedent — a read followed by an update is the shape that lets two redemptions of one token both succeed. `core/mail/templates.ts` — six messages behind `createMailTemplates({ customerUrl, adminUrl })`, English with a `locale` on the seam and a copy table whose `lv` entry is the only thing Latvian needs. `createPasswordResetRateLimiter` and `createVerificationRateLimiter`, the first two limiters in that file with a window that is not `RATE_LIMIT_WINDOW_MS`. All three wired at the composition root, where the TTL map is a total `Record<TokenPurpose, number>` — nothing mounts them until `D18.3` and `D18.5`, and the wiring is what makes that map type-checked today rather than at the first flow.

**Amendments — the plan's step 2, five corrections, no record touched.** The three token assertions the done-when named are database properties, so they are proved in `apps/api/test/account-tokens.int.test.ts` and the unit file keeps what a fake can prove — `D18.1`'s correction about `prune-sessions.int.test.ts`, made again. `mint` takes no `ttl`: the four windows map one-to-one onto the four purposes, so the service is built with the map instead and no caller can hand the verification link's day to a password reset. `createVerificationRateLimiter` shares ADR-0071 §4's one budget in a counter of its own, because the record names one number and §3 asks only for "its own limiter". `rate-limit.test.ts` is a new unit file, since neither limiter has a mount for the integration tier to drive. And, on the review, `consume` takes an input object stating the **population**.

**Review — `security-reviewer` and `code-reviewer`, one pass each, no re-review.** Seven findings across the two; **the top two were found independently by both**, which is the strongest signal either pass produced. Five fixed, one declined with its reason, one logged.

- **Fixed — the consume was not scoped to a population** (medium, both reviewers). `reset_password` is minted for both segments (ADR-0071 §4), so a `where` on the hash and the purpose alone left an operator's reset token claimable at `/user/auth/password/reset` and a customer's at the admin segment's. Checking `row.principalType` afterwards is too late by construction: the update is atomic, so a mismatched consume would already have spent the token before any handler could object. `principalType` joins the `where`, `consume` takes `{ purpose, principalType, token }`, and an integration case presents a user's token as staff and asserts the row survives.
- **Fixed — two concurrent mints for one pair left two redeemable links** (low/medium, both reviewers). Under `read committed` each mint supersedes what its own snapshot can see, neither sees the other's uncommitted row, and both insert — so "one valid link, not a growing set" held only when nobody double-clicks resend. `lockPrincipalPurpose` takes `pg_advisory_xact_lock(hashtextextended(…))` on the pair at the head of the mint's transaction, contended only by a second mint for the same person and purpose.
- **Fixed, after the first attempt at it was thrown away — the concurrency test could not fail.** Two mints fired through `Promise.all` pass with the lock _and_ without it: the round trips happen not to interleave. That was caught by disabling the lock and re-running, which is the only reason it is not in the tree — a test that cannot fail is worse than no test, because it reads as coverage. What replaced it is deterministic: an outer transaction holds the pair's lock, a mint for that pair is started and asserted **not** to have completed 250 ms later, and it completes once the holder commits. Isolated both ways — it fails with `expected true to be false` when the lock is commented out.
- **Fixed — a test that asserted less than its name** (low, `code-reviewer`). "stores the hash and never the token" asserted only that the column differs from the token, which passes for a truncation, a reversal or a constant. It now asserts `sha256Base64url(token)`.
- **Fixed — the two new limiter prefixes were absent from the enumeration that guards them** (low, `code-reviewer`). On the memory store two limiters are separate by construction, so the unit case proving they count separately cannot fail; where separation is _earned_ is Redis, whose key space is the prefix the composition root passes. `password-reset` and `verification` join `store.test.ts`'s list, whose `new Set(prefixes).size` assertion is what fails if two names ever collide. The unit case is kept and renamed to what it proves.
- **Fixed — the verification copy told the reader to do something the record refuses** (low, `code-reviewer`). "If it has expired, sign in and ask for a new one" — but ADR-0071 §3 refuses login on a `pending_verification` account with `403 AUTH_EMAIL_UNVERIFIED`, so the affordance is `resend-verification` on the sign-in page and never a session.
- **Declined, with its reason — the mint's log line is written inside the caller's transaction** (low, `security-reviewer`). When registration passes its executor, a rollback leaves a line describing a mint that did not commit. Deliberate, and what every log line here does: the line records the _attempt_, the failure records itself through the error handler, and the request id joins the two. A line deferred until after a commit this service does not own is a line that never arrives when the commit fails, which is the worse trade. The docblock now says so.

**Logged, not built — one residual risk, routed to `D18.3`.**

- **Nothing bounds messages per sender across _distinct_ addresses.** `3 / hour / IP + email` stops one mailbox being flooded from one IP; it does not stop one IP walking a list of strangers' addresses, where the only remaining ceiling is the global limiter — on the order of a thousand messages an hour once `resend-verification` and `password/forgot` mount, and more under the committed development profile (ADR-0069). Symmetrically, one mailbox can still be flooded at `3 × N` from N addresses. The fix is a second limiter keyed on the address alone with its own hourly max, and it is **an ADR-0071 §4 amendment rather than a build step's invention**: §4 states the key and the number, and a step that added a knob the record does not name would be deciding policy on its own authority. The window is open, so the operator can take it at `D18.3` — the first step that mounts one of these two — at the cost of one env key through the schema, both `.env.example` files, `docker/prod/compose.yaml` and `docs/deploy.md`. Nothing is exposed today: neither limiter has a route.
- Two further notes from `security-reviewer`, neither a finding: an authenticated user picks both the recipient and the subject line once invitations send (§5 interpolates the organization name into `Subject:`, and nodemailer's header encoder strips CR/LF, so it is a volume question rather than an injection one); and `STAFF_ONBOARDING_TOKEN_TTL` is seven days for a credential that hands over an operator account, worth revisiting at `D18.11` against ADR-0057 §2's argument that the TTL _is_ the mitigation for a fragment that survives in browser history.

**The gate — `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check`, exit `0` on the committed tree.** `lint` 17/17, `check-types` 16/16, `test` 15/15 **0 cached** (api unit 652 + integration 638, admin, customer, the packages), `size` 4/4 inside every budget, `format:check` "All matched files use Prettier code style!". Beside it: `pnpm test:unit` twice — 15/15, then **`>>> FULL TURBO`**; `pnpm docs:check` — inherited documents clean, behaviour specs clean (11 files).

**No behaviour spec changed, deliberately.** This step moves no request, response, status, header or side effect (ADR-0068 §1) — it mounts no route at all. `docs/specs/mail-flows.md` is begun at `D18.3`, the first step with wire behaviour to describe.

**Pending the operator.** Nothing new, and one thing carried. `D18.1`'s note that the developer's own database is still at `0013` stands until `pnpm db:migrate` is run; this step adds no migration, and the integration harness migrates from scratch, so the gate proves the table either way. Nothing here is browser-visible, so nothing awaits a walk.

## `D18.3` — Address verification, the API

**The head.** [ADR-0018](../adr/0018-authentication-sessions-and-tokens.md) moved to `superseded by` — its **third** partial successor, joining ADR-0057 and ADR-0064 — with the delta stated in both directions and its own paragraph in 0018. The delta is registration's answer alone: `202` and no session where 0018 wrote `201` with one, plus the `403 AUTH_EMAIL_UNVERIFIED` that separates an unproven address from a disabled account once the password has verified. Everything 0018 decides about sessions, tokens, rotation and the hot path stands. The index's topic row and record row were updated and the ledger's §The window records the move.

**Built.** Registration creates a `pending_verification` user, mints its `verify_email` token **inside the same transaction** as the account and its personal organization, and mails the link **after** that commit — so there is no interval in which an account exists with no way to prove its address, and no message that names a token row a rollback took away. `POST /public/auth/verify-email` claims the token, activates the account, stamps `email_verified_at`, writes an `account.verified` audit row and issues login's body on login's transports, all in one transaction; every refusal throws, which is what rolls the claim back. `POST /public/auth/resend-verification` answers `202 { accepted: true }` for every address. Login's inactive branch splits on a new `PrincipalRecord.awaitingEmailVerification`, decided in the adapter where the status is and `false` on every staff row. `POST /admin/users` stamps the address it asserts, and — on the review — so does `PATCH /admin/users/:id` when it moves a row to `active`. `respond.accepted`, `AcceptedResource`, `AUTH_EMAIL_UNVERIFIED` with both apps' catalogue sentences in both locales, `verifyEmailBody`/`resendVerificationBody`/`mailLocaleSchema`, and `createVerificationRouter` mounted beside the gated register router. `docs/specs/mail-flows.md` begun; `auth-sessions.md`'s registration requirement rewritten; the `Public` Postman folder grown from two requests to eight.

**Amendments — the plan's step 3, four corrections, no record touched.** The token is read from a capturing `MailSender` rather than "the log adapter's capture", which does not exist and must not: the log transport writes the recipient and the subject and never the body, because the body is a single-use bearer credential. `buildContainer` therefore takes an optional `mail` port exactly as it takes `reporter`, and everything above the port — the templates, the links — is the real wiring. The two verification routes mount **unconditionally**, because `FEATURE_USER_REGISTRATION` is a decision about signing up and a deployment that closes sign-ups must not turn the link already in somebody's mailbox into a `404`. `POST /admin/users`' stamp lands in this step though the step's list does not name it, because the deliverable's own constraint does and half an invariant is how a claim becomes an account-takeover primitive. And the Postman collection was re-shaped rather than only grown: it cannot walk a mailed link, so the account the invitee signs in as and the account that closes itself are now the staff-created one, whose address is asserted.

**Review — `security-reviewer` and `code-reviewer`, one pass each, no re-review.** Nine findings across the two; eight fixed, one logged with its reasoning. The sharpest came from opposite directions — one reviewer found a third writer of `users.status` that the new invariant did not cover, the other found the client still writing a session out of a response that no longer carries one.

- **Fixed — a third path into `active` did not stamp the address** (medium, `security-reviewer`). This step is the commit that turns "every `active` user has a proven address" from documentation into an enforced fact, and it covered two of the three writers: the link and `create`. `PATCH /admin/users/:id { status: "active" }` — an operator clearing a stuck account from the grid — passed the status straight through and produced exactly the `status = 'active'` with an empty `email_verified_at` that `D18.1`'s backfill was rewritten to avoid creating. It matters because the declared consumers read _different_ columns: ADR-0067 §5's address-match acceptance and D19's linking rule read `status` alone, so a row an attacker made by registering somebody else's address becomes proof of that mailbox the moment an operator clears it. `updateColumns` now writes `coalesce(email_verified_at, at)` whenever the status becomes `active` — in the statement rather than in the service, so it holds for a transition this repository cannot see the previous status of, and an account that was already proven keeps the instant it was proven at. Two integration cases and the spec's two new scenarios.
- **Fixed — `client.register` hydrated the session store from a `202`** (`code-reviewer`). It still typed the answer as `AuthResource` and called `store.setSession({ accessToken: resource.accessToken, principal: resource.principal })`, so the customer SPA persisted `accessToken: undefined` and `principal: undefined` — not "no session" but a broken one, a shape the boot sequence has no branch for on a client that would then think it was signed in. Nothing went red because the MSW handler still answered `201` with a full resource: a mock that could only ever confirm behaviour the API no longer has. `register` now returns `Promise<void>` and writes nothing, the handler answers `202 { accepted: true }`, and `X-Auth-Transport: cookie` left `COOKIE_TRANSPORT_PATHS` for this call — the header exists to move a refresh token into a cookie and there is no longer a token in either place. The two `register-form` cases that asserted a landed session now assert the store stays empty; where the form _lands_ is deliberately not asserted, because today it navigates home and the dashboard guard turns it back to sign-in, which is honest but not the screen a person should meet. `D18.4` builds that screen.
- **Fixed — the delivery-failure log line could carry the address it was careful not to** (low, `security-reviewer`). The docblock promises "the purpose and no address", and the line interpolated `error.message` — but a relay rejects a recipient by quoting the envelope (`550 5.1.1 <someone@example.com> User unknown`), so a probed address would reach the logs from the endpoint whose whole shape is "reveal nothing". `describeTransportFailure` puts the error's class and the transport's own `code` on the line and never the message, which is `core/audit`'s `describeFailure` trade made for the same reason.
- **Fixed — `create` reached for `new Date()` where the module has an injected clock** (low, `security-reviewer`). Every other method in `users.service.ts` reads `now()`, and the one timestamp that bypassed it was the one written into `email_verified_at` — unreachable from a test that controls the clock.
- **Fixed — a spec's `Proved by` named a file that proved neither half of it** (`code-reviewer`). The staff-assertion requirement cited `users-admin.int.test.ts`, which asserted nothing about `email_verified_at` and nothing about the mail capture, so the only proof was a unit test over a fake repository. Both assertions now exist in that file, against the real `insert`.
- **Fixed — `docs/specs/organizations.md` still gated a scenario on registration's `201`.**
- **Fixed — a Postman request would `429` on the fourth run of an hour** (`code-reviewer`). `Ask for it for an address nobody holds` posted the fixed `{{unknownEmail}}` to an endpoint behind `3 / hour / IP + email`; the address is now generated per run like its sibling, and the README's rate-limit paragraph names the verification budget it spends.
- **Fixed — two test names promised more than their bodies** (`code-reviewer`). "and says so in the log" asserted no log line, and the harness logger is silent by design; the clause is gone and the comment says why. "leaves no account" asserted only the mail capture; it now counts the rows for that address.
- **Logged, not fixed, with its reasoning — `resend-verification` is byte-identical but not time-identical** (low, `security-reviewer`). The unknown branch is one indexed `SELECT`; the known branch adds a lock, a supersession, an insert, a commit and an awaited `mail.send`, which under `MAIL_TRANSPORT=smtp` is a network round trip inside the response. So the endpoint answers a narrower question than `register`'s `409` already does — "is there a _pending_ account here" — on a timing channel, and it is the only anonymous signal left where `FEATURE_USER_REGISTRATION` is off. The fix is to dispatch the send the way `audit.trail` dispatches its insert, and it is deliberately **not** taken here: `D18.5`'s `forgot` is the same shape against a much larger set (every live account, not only the pending ones), and "does a `202` mean sent or dispatched" is one decision for both endpoints rather than two. Routed to `D18.5`.

**Logged, not built — three residual risks for a later step or a record.**

- **Registration on somebody else's address is a pre-hijack primitive.** An attacker registers `victim@corp.com` with a password they choose; the victim receives "Confirm this address to finish setting up your account" and, if they follow it — plausible when they were separately expecting mail at that address — the account activates and they are signed into an account whose password the attacker still holds. The template's "If you did not ask for this, you can ignore this message" is the only mitigation, and ADR-0071's §Alternatives does not consider the class. The usual answers — clear the pending row's password on an unsolicited verify, or ask for the password again at verification — are **decisions rather than code**, so they belong to the operator and to §3 rather than to a build step. Raised by `security-reviewer` as a residual, not as a finding.
- **`verify-email` carries neither a limiter nor a CSRF guard.** Sound today: 256-bit single-use tokens with a day to live, the global limiter above, and cookie transport needs `X-Auth-Transport`, which forces a preflight against the CORS allow-list — so there is no cross-site forced sign-in. Worth stating as a decision somewhere durable before §6's `confirm-email` and §8's `onboarding/accept` inherit the same router and the same reasoning.
- **The `D18.1`→`D18.3` window.** An account self-registered between the two commits is `active` with a stamp the backfill wrote and an address nobody proved. §3 accepts that explicitly for rows that predate the record; whether the same acceptance covers rows created _inside_ the window is worth confirming before ADR-0067 §5 and D19 start leaning on `status`.
- Also carried forward, unchanged: **nothing bounds messages per sender across distinct addresses.** `security-reviewer` was asked not to re-raise it and agreed it did not become blocking here — `resend-verification` reaches a mailbox only for an address somebody already registered, a set `register`'s own `409` bounds — while `D18.5`'s `forgot` will reach every live account. The ADR-0071 §4 amendment is still owed before that step, and it is the operator's.

**The gate — `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check`, exit `0` on the committed tree.** `lint` 17/17, `check-types` 16/16, `test` 15/15 **0 cached** (api unit 667 + integration 660, admin, customer 188, the packages), `size` 4/4 inside every budget, `format:check` "All matched files use Prettier code style!". Beside it: `pnpm test:postman` — **173 requests, 528 assertions, 0 failed**, with the counts in `README.md` and `docs/postman/README.md`; `pnpm docs:check` — inherited documents clean, behaviour specs clean (12 files).

**Two specs changed, one of them new.** `docs/specs/mail-flows.md` is begun here, with the requirement "An account is usable once its address is proven" and eleven scenarios, plus "An address a staff member types is proven by that assertion" and its four; `auth-sessions.md`'s registration requirement is rewritten to the `202` and gains login's `AUTH_EMAIL_UNVERIFIED` scenario; `organizations.md` gains the corrected status.

**Pending the operator.** Three things, none of them blocking.

- **The customer app is one step behind the API, deliberately.** The register form still navigates home after a `202`, so a person who signs up now lands on the sign-in screen rather than on a check-your-mail screen, and the browser tier's `organizations.spec.ts` registration walk will fail until `D18.4` reads the link from Mailpit. That is the sequence the plan chose — API first, then the app — and the client was made _honest_ here (it writes no session) rather than left writing a broken one.
- **`D18.1`'s carried note is discharged.** The developer's database was migrated and re-seeded during this step: `0014` is applied, every `active` and `disabled` row carries `email_verified_at`, and the one `pending_verification` fixture carries null — which is the invariant, verified against the dev database rather than only against the harness.
- **Nothing is browser-visible yet**, so nothing awaits a walk. The first thing to eyeball is `D18.4`'s.

## `D20.3` — Node 24 and pnpm 12

**The head.** [ADR-0003](../adr/0003-api-runtime-express-typescript.md) moved to `superseded by` [ADR-0073](../adr/0073-review-hardening.md) for the **floor half** of its delta — the three server timeouts are `D20.4`'s and the blockquote says so. **[ADR-0002](../adr/0002-monorepo-layout-and-tooling.md) moved with it**, which this step's text did not originally name: §Toolchain versions is where `Node 22 LTS`, `engines.node: ">=22"` and `pnpm 10.x` were decided, so the floor move reverses a decision of 0002's rather than renaming an option the way `D20.2`'s `tsdown` case did. Frozen forbids amending 0002 in place; superseding it is the machinery that exists for exactly that, and 0073's `Supersedes:` line, its title, both index rows and the topic row now carry it. The step text was amended in place and labelled.

**Built.**

- **Node 24 in all seven places that state one**, moved together: `.nvmrc` (`24`), the root `engines`, `gate.yml`, `e2e.yml` and the three Dockerfiles (`node:24-bookworm-slim`). `engines.node` is **`>=24.15.0`**, not `>=24`: the tree's strictest constraint is `jsdom`'s `^22.22.2 || ^24.15.0 || >=26.0.0`, so a bare major would have repeated exactly the understatement the step was opened to close. - **pnpm 12.4.2** in `packageManager`, and with it four things the version brought that no plan text could have known:
  - **`package.json`'s `pnpm` field is no longer read.** `onlyBuiltDependencies` is now **`allowBuilds`** in `pnpm-workspace.yaml`, an answer per package, and pnpm 12 **refuses** the install rather than warning when a package it has no answer for wants to run a script. `argon2: true`, `esbuild: true`, and `msw: false` / `unrs-resolver: false` — the two decisions this tree had been running with unwritten since before they had to be written down.

  - **`.npmrc` is deleted.** pnpm 12 does not read it — `pnpm config list` has no `autoInstallPeers` key with the file present — and it held one line that `renovate.json`'s pinning register leans on as the reason `@vitest/coverage-v8` is pinned with `vitest`. It is `autoInstallPeers: true` in `pnpm-workspace.yaml` now, verified by `pnpm config get autoInstallPeers` answering `true`, and the register's sentence points at the new home.
  - **The lockfile gained a first YAML document** pinning pnpm itself and its per-platform binaries (158 lines, no deletions). Tool output, committed as such.
- **`pnpm deploy --legacy` is dropped, re-verified rather than assumed.** pnpm 12 does not refuse the deploy the flag existed to permit; a deploy without it links the four `@repo/*` packages out of the virtual store and leaves the image's two constraints true — **one** `pino@10.3.1` in the tree and `argon2`'s prebuilds present. The reason is in `apps/api/Dockerfile` beside the command, and the evidence is the image build below.
- **The two bundles target Node 24 too.** `apps/api/tsdown.config.ts` and `packages/db/tsdown.config.ts` said `target: "node22"` while every image that runs their output is now `node:24-bookworm-slim` — a place that states the floor and did not move with the step. **One deferral, stated rather than silent.** **`@types/node` stays at `^22.20.3`** in the catalog — a major behind the floor. It is `D21`'s with the other majors, one pull request each (ADR-0059 §3 and this plan's own constraint), and the effect until then is conservative in the right direction: nothing can reach for a Node 24-only API without the types refusing it. It is also the first bill the new cooldown presented — a `pnpm install` that had to re-resolve was refused over twelve _existing_ lockfile entries younger than a day, which is the protection working and the reason a major does not ride in on a floor move.

## `D20.4` — The API's budgets, key, timeouts and cap

**The head.** [ADR-0020](../adr/0020-security-baseline.md) and [ADR-0018](../adr/0018-authentication-sessions-and-tokens.md) both moved to `superseded by` [ADR-0073](../adr/0073-review-hardening.md) — 0020 for §1–§2 (the fifth limiter category its own §Residual risks has named as missing since D1, and a limiter key that can no longer degrade to one shared bucket), 0018 for §3 (a principal holds a bounded number of live sessions). [ADR-0003](../adr/0003-api-runtime-express-typescript.md)'s remaining half lands here too — the three socket deadlines — and its index row, which said the timeouts half "has not happened yet", now says what it built. The ADR index's topic rows for sessions and for the security baseline gained 0073, and four record rows were rewritten. The other parents stay where the plan puts them.

**Built.**

- **§1 — a fifth limiter, keyed on the account.** `createPrincipalHashRateLimiter` beside ADR-0020's four, `RATE_LIMIT_PRINCIPAL_HASH_MAX` (10) per `RATE_LIMIT_PRINCIPAL_HASH_WINDOW` (15m), **one instance from the composition root mounted seven times**. It closes two different things with one budget: the liveness hole — a handful of authenticated clients could make the `AUTH_MAX_CONCURRENT_HASHES` pool shed _login_ for everybody, because the only bound was a per-**address** global limit — and the oracle the `D2.3` security review found, where an operator's `403` on an administrative reset was an unbounded guess at their own credential. It mounts after `authenticate`, after `authorize` and after `refuseImpersonated` on every route, so nothing a guard is going to refuse is ever charged, and an impersonated request is never charged to the customer.
- **§2 — the key that cannot collapse.** `ipKey` falls back to `req.socket.remoteAddress` where the context middleware validated no address, and says so once per process. The failure it removes is not a loose limit but an outage with a counter: under a `TRUST_PROXY` stated one hop too many, every such caller keyed on `""` and the global limiter refused the whole world at 300. The fallback is a **key only** — `sessions.ip` still stays null, because a proxy's address recorded as a person's is worse than none.
- **§3 — the session cap.** `AUTH_MAX_SESSIONS_PER_PRINCIPAL` (10, `0` uncapped) enforced in `issueSession` rather than in `login`, which is the one design decision here worth stating: every path that puts a person into a session — login, registration's verify, the reset, the onboarding accept, the federated exchange — comes through that function, and a cap written at `login` would have been a cap five callers could be added without. The mint revokes the principal's **oldest** live sessions with `revoked_reason = 'session_cap'`; impersonated rows are counted and never chosen, and an impersonated mint is exempt entirely. `revokeOldestBeyondCap` reads live as _unrevoked and unexpired_, so a dead row never costs a real session its place.
- **§4 — the three socket deadlines**, from `HTTP_REQUEST_TIMEOUT` (30s), `HTTP_HEADERS_TIMEOUT` (10s) and `HTTP_KEEP_ALIVE_TIMEOUT` (65s), set synchronously after `listen` and before any socket is served. Node's own 300s/60s/5s are each wrong in a different direction, and the last one most visibly: a keep-alive **shorter** than the proxy's is the classic intermittent `502` in front of a perfectly healthy process, so the default is deliberately above a typical sixty rather than a round number.
- **The derived documents moved with them**: six new keys in `.env.example`, `apps/api/.env.test`, `docker/prod/.env.example`, `docker/prod/compose.yaml` and [`docs/deploy.md`](../deploy.md), which gains a row in the Coolify table for the keep-alive and three paragraphs; `docs/specs/auth-sessions.md` gains the cap's requirement with three scenarios and the limits requirement gains the per-account budget, and `users-and-profile.md` and `staff.md` gain the `429` on all four administrative routes.

**One deviation from the plan's own done-when, amended in place and labelled — the Postman half.** The collection gains **no `429`**, and the counts stay 207/631. This budget is keyed on an **account**, and the only account the collection can spend one with is the seeded super admin — a fixture, whose counter does not reset between runs the way every address-keyed limiter's does. A request that tripped it would leave that fixture refused for the rest of the window and fail the _next_ run in `Admin › Staff`, breaking the "it is repeatable" promise `docs/postman/README.md` opens with; it is also why no limiter's `429` has ever been asserted there. What the collection does carry is the consequence, which is real: **one pass drives eleven of these routes as that super admin**, so the committed development profile states `RATE_LIMIT_PRINCIPAL_HASH_MAX=100` — ADR-0069's shape applied to a second limiter, with the deployment's 10 untouched — and the README says what a pass spends and where the refusal is proved instead.

**Review — `security-reviewer`, one pass, five findings; four fixed, one fixed differently than proposed.**

# D4 — Data grid v2

- Status: **in progress**, opened 2026-08-20 — the day D3 shipped ([ADR-0025](../adr/0025-deliverables.md) rule 5: one at a time)
- Steps: `D4.1` – `D4.7`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: the second pass over the admin panel's largest surface. D3 proved the config-driven machinery — AppGrid on TanStack Table v9 in manual mode, one `ResourceConfig` per resource, the URL owning list state — and shipped with the seams this deliverable fills: two layout defects (a page-level horizontal scrollbar, a sidebar transition the content ignores), no viewport-height strategy, an always-visible filter row that inflates column widths, edit surfaces invisible to the URL, no row selection, no toolbar, and none of the column ergonomics ADR-0035 explicitly deferred "until a need names it". D4 names it. **`apps/admin` and `packages/ui` only — no API change anywhere in this deliverable**; the one place the requirements brushed the API (bulk delete) is deliberately answered client-side (ADR-0038).

Everything here builds on decisions that stand unchanged: the server owns data operations (ADR-0035), the URL owns view state (ADR-0034), configs are serializable data with functions in registries (ADR-0035), and the v9 features model means every new grid capability is an imported feature module, not a flag on dead code (ADR-0035, amended D3.6).

Each step names the ADRs that govern it. Read them before implementing — they carry the reasoning, this file carries the work. Every step ends green on `pnpm lint && pnpm check-types && pnpm test` and a conventional commit.

**Amendment window.** ADRs 0037–0042 were written for this deliverable (while D3 was still in progress — writing is not opening) and may be amended in place while D4 is in progress, labelled `**Amended YYYY-MM-DD (D4.N).**` at the point of change (ADR-0025 rule 2). **ADRs 0001–0036 are closed** — 0030–0036 shut with D3 on 2026-08-20 — so if the work below needs any of them to say something different, stop and write a superseding ADR (ADR-0024 rule 1). That is the live constraint for this deliverable rather than a formality: D4 rebuilds surfaces ADR-0034 and ADR-0035 describe, and those two are now frozen.

**Gate.** ADRs 0037–0042 are `proposed`, and opening the deliverable did not change that. Each is accepted before its own implementing step starts (ADR-0025 rule 3) — the stricter reading of the precedent D3 set by accepting all seven of its ADRs on one day, and the reason a step below is un-startable until somebody has read its ADR and agreed with it.

## Build order

### ~~1. Grid viewport layout — the shell fixes~~ — **done 2026-08-20**

**ADRs:** [0037](../adr/0037-grid-viewport-layout.md), [0031](../adr/0031-ui-design-system.md), [0032](../adr/0032-admin-app-architecture.md)

First because it fixes what is broken today and builds the frame every later region slots into. The root cause of both shipped defects is one CSS fact — flex items default to `min-width: auto`, and nothing in the chain from `SidebarInset` to the table says otherwise, so the inset is floored at the table's `whitespace-nowrap` min-content width. `min-w-0` lands on `SidebarInset` (an owned edit to `packages/ui`'s generated `sidebar.tsx`, under ADR-0031's regenerate-and-diff model) and on the dashboard page container; the doubled scroll wrapper goes (`@repo/ui`'s `Table` gains the container opt-out; AppGrid owns the one scroll element); grid pages become height-budgeted — static toolbar and filter-bar regions, a `flex-1 min-h-0 overflow-auto` scroll body with a sticky header, the pager as a static footer, a minimum-height floor, and the token-driven thin scrollbar utility from `@repo/ui`.

**Done when:** no page-level horizontal scrollbar at any viewport width with both resource grids rendered; collapsing/expanding the sidebar reflows the grid smoothly through the 200 ms transition; the grid fills the viewport with header and pager static while only rows scroll (custom scrollbars, both engines); a very short viewport degrades to page scroll at the floor rather than a crushed grid; profile and dashboard pages keep normal document flow.

**Closed.** ADR-0037 accepted at the head of the step, then built: `min-w-0` on `SidebarInset` and on the page container, a `container` opt-out on `@repo/ui`'s `Table` so AppGrid owns the one `overflow-auto` element, the flex height budget with a sticky header and a static pager, `min-h-64` as the floor, `.scrollbar-thin` in the design system, and full height as a per-page `staticData` opt-in.

Three things the browser found that neither the class lists nor the MSW tier could, each amended into ADR-0037 rather than worked around: **`min-h-svh` is a floor, not a ceiling**, so the budget needs one definite height (`h-svh` on the inset in full-height mode) or every `flex-1` below it resolves against the content it was meant to clip; **a sticky `thead`'s background does not travel** while `border-collapse: collapse` is in force, so the grid's table draws with separated borders at zero spacing and puts the borders and the opaque background on the cells; and **nothing on the grid path may clip**, because an `overflow-hidden` on the Card ate the pager on a short viewport instead of letting the page scroll.

Evidence, separated the way `D3.10` separated it. **Machine-verified:** `pnpm lint`, `pnpm check-types`, `pnpm format:check` clean; `pnpm test` green at `0 cached, 8 total` — 433 API, 267 admin (+7), 12 `@repo/ui` (+3). **Walked in Chrome against the dev stack**, which is the only tier that can see geometry: both grids viewport-filled with the header and pager static and only rows scrolling; no page-level scrollbar on either axis, in either sidebar state or across the transition; the scroll body flexing from 465px down to its 256px floor as the frame shrinks, and overflowing rather than crushing below roughly 560px; `/profile` and `/` with no height constraint and no pane scroller. **Not walked:** Firefox — the standard `scrollbar-width` / `scrollbar-color` half of the utility is written but only Chrome's rendering was seen.

### ~~2. Record routes and edit surfaces~~ — **done 2026-08-20**

**ADRs:** [0040](../adr/0040-record-routes-and-edit-surfaces.md), [0032](../adr/0032-admin-app-architecture.md), [0034](../adr/0034-server-state-and-notifications.md)

Second because it restructures the pages before more grid surface accumulates on them. Form surfaces become routes — `/staff/new`, `/staff/$staffId`, `/users/new`, `/users/$userId` — with list search params retained across open/close, detail data through the route loader (`ensureQueryData`, the first real user of the loader plumbing D3 threaded and left unused), and the three shells behind one config switch: `grid.editSurface: "dialog" | "drawer" | "page"` rendering the same ADR-0035 form in an `AppFormDialog`, a right-side `Sheet`, or a standalone page (grid unmounted). Destructive confirmations (delete, revoke-sessions, bulk delete) and the reset-password ceremony deliberately stay ephemeral component state — a URL must not reopen a "confirm delete".

**Done when:** opening edit puts the record id in the URL for both resources; reload restores the open surface with list state intact; Back closes it; an unknown id shows the error surface, not a blank overlay; flipping a resource's `editSurface` config renders the same form in all three shells with no other change; deep-linking `/users/$id` in a fresh session loads the record.

**Closed.** ADR-0040 accepted at the head of the step, then built: four route files per resource, detail routes loading through `ensureQueryData` on the entity's own `detail(id)` key, `retainSearchParams` on the list parent, `grid.editSurface` with three shells over one form frame, and the Action union shrunk to the three surfaces that must not be addressable — delete, revoke-sessions and the password ceremony. `staff` declares a dialog and `users` a drawer, so the switch is exercised rather than merely available.

Two amendments to ADR-0040, both things the implementation found rather than opinions about it. **The router context carries the ApiClient**: the ADR writes a loader's query as `getStaff(id)`, and this repository has no such expression — an entity's API is a `create<Entity>Api(client)` factory reached through a hook, and a loader has no hooks. That is ADR-0032 holding rather than bending (its decision is a context carrying "what guards and loaders need"), and `renderApp` still passes the test's own client. **The list route needs an index leaf the grid does not live on**: putting the grid there would unmount it whenever a dialog opened, which is exactly what an overlay must not do — and the corollary is that "a record is open" cannot be a count of child matches, since the index is a child too.

Evidence, separated as `D3.10` set the precedent. **Machine-verified:** `pnpm lint`, `pnpm check-types`, `pnpm format:check` clean; `pnpm test` green at `0 cached, 8 total` — 433 API integration unchanged (D4 touches no API surface), 272 admin (+5), and the two feature suites rewritten to enter through the router rather than by mounting a dialog. **Walked in Chrome against the dev stack:** a cold deep link to `/users/$id?limit=50` opening the drawer with the record loaded and the grid legible beside it; Escape closing it back to `/users?limit=50`, search intact; an unknown staff id rendering the error surface with its way back; and `staff` flipped to `"page"` and back, which is how the third shell was seen at all.

The flip is also how the step's two real defects surfaced, both of them in the `page` branch that no resource declares and therefore no test could reach: `useMatchRoute` compares search params unless told not to, so the grid stayed mounted under a surface that had replaced it, and a `??` where `||` was meant left `/staff/$staffId` permanently unrecognised. The `adr-reviewer` pass then made the same point the defects had: a shell that is specified, implemented and shipped but never exercised is where the next one will live too. `shared/form/__tests__/app-form-surface.test.tsx` now runs the same assertions against all three by accessible name — the form, the Cancel path, the submit lock, a real submit — plus the one requirement only the page owns, that a navigation out of a pending form is refused. It found a fourth thing on its first run: the page shell titled itself with `CardTitle`, a styled `div`, where the other two use Radix titles that are real headings — so "the same form in three shells" was false for a screen reader.

**Still recorded rather than glossed:** no _resource_ declares `page`, so the shell has coverage but the config path into it does not; `D4.6` is where a resource that actually declares it would close that.

### ~~3. Selection, capabilities and the toolbar~~ — **done 2026-08-20**

**ADRs:** [0038](../adr/0038-grid-selection-and-capabilities.md), [0042](../adr/0042-client-side-authorization.md), [0028](../adr/0028-account-deletion.md), [0034](../adr/0034-server-state-and-notifications.md)

`ResourceConfig` gains the `grid` capability block (`selectable`, `canCreate`, `canEdit`, `canDelete`, `canBulkDelete`); AppGrid registers the v9 row-selection feature and injects the checkbox column when selected-for; `GridToolbar` becomes a real region — search left, capability-driven actions right (Create moves in from the page's `CardAction`, wired to the `new` route from D4.2), with `toolbarStart` / `toolbarEnd` / `renderToolbar` as the JSX extension seams. Bulk delete is a feature-owned `Promise.allSettled` fan-out over the existing per-row deletes: one confirmation with honest per-resource copy, one invalidation, one summary toast with per-item refusals (the ADR-0028 rules — rank, last super admin, self-delete — surface per item, which is the semantic a transactional endpoint could not give).

[ADR-0042](../adr/0042-client-side-authorization.md) lands with it, because the two answer different halves of the same question and shipping one without the other reproduces the defect that motivated both: a capability says _this surface offers the action_, `can(action, resource)` says _this operator's role may perform it_, and an affordance needs both. `shared/auth` gains the policy table and the predicate; the narrowing is applied once per screen so `shared/grid` never learns a resource name. This is the D3.8 deferral — a `manager` reaching `/admin/users` and being refused by every write it offers — answered at the layer that draws the affordances. **Answered, not eliminated**: ADR-0042 deliberately leaves the containment actions (reset password, sign out everywhere, and edit while disabling lives inside it) rendering for everyone, because a hidden break-glass control during an incident is worse than a refused one. Two of the five affordances disappear for a `manager`; the other three still `403`, on purpose, and the ADR says why.

**Done when:** selection is keyed by row id and survives page and filter navigation; the header checkbox toggles the current page and the count reads "N selected" across pages; capability flags provably add/remove the toolbar buttons and row-menu items; a `manager` is offered neither Create nor Delete on `/admin/users` while an `admin` is offered both, and the three containment actions render for both because ADR-0042 refuses to hide them — neither assertion is a security claim, the API still answers; a mixed bulk delete (some refused) reports both outcomes and leaves the grid consistent after one refetch; toolbar slots append and `renderToolbar` replaces.

**Closed.** ADR-0038 and ADR-0042 accepted together at the head of the step — the plan said they are halves of one question, and building either alone would have rebuilt the defect that motivated both. Then built: `GridCapabilities` on the `grid` block D4.2 opened, `rowSelectionFeature` registered and a built-in checkbox column injected when `selectable`, `GridToolbar` as a named region with its three JSX seams, `shared/auth` (policy table, `can`, `allowedCapabilities`, the bound hooks), a `Promise.allSettled` bulk delete per feature over `shared/api/bulk-outcome`, and the sidebar's explicit `resource` join. Create moved out of the page's `CardAction` into the toolbar and stayed the `<Link>` D4.2 made it. Both resources declare the full capability block, so the `manager`/`admin` split on `/users` is a real difference between two screens rather than a fixture.

Five amendments to ADR-0038, all of them things the implementation or its reviews found rather than opinions about it — three from building it, and two below from the security pass. **`onCreate` cannot exist**: the ADR gives Create a `() => void`, and a handler can only render a `<button>` — where D4.2 made composing a record addressable and made the `link` role the assertion. It is a `createAction: ReactNode` gated by the capability, which is the division the ADR already draws for `toolbarStart` / `toolbarEnd`, one prop further along. **`onBulkDelete(ids)` cannot clear the selection** the same ADR says must clear when the fan-out settles, because the selection lives inside `AppGrid`; it takes the same `GridToolbarContext` that `renderToolbar` already gets. And **`grid` is `GridConfig`, not `GridCapabilities`** — the ADR's snippet would have dropped D4.2's shipped `editSurface`, so capabilities are the subset the grid reads and `editSurface` stays a routing decision `AppGrid` never sees.

Two smaller findings recorded in the ADR rather than worked around: the v9 page-scoped selection getters read `getPaginatedRowModel()`, which returns the _pre_-paginated model under `manualPagination` — so "the current page" is the server page in hand, which is the only scope this grid may honestly claim; and the header checkbox is **two-state**, because Radix's `indeterminate` draws the same tick as `checked` in the shadcn primitive and a mixed state indistinguishable from "all selected" is a worse lie than no third state, with the toolbar's "N selected" as the disclosure.

**The review round found one thing worth the step being longer for**, and it was in the paragraph of ADR-0038 that sounded most settled. The ADR's cost bullet says N requests are "fine at admin scale, where a selection is tens of rows, not thousands" — an assumption with nothing enforcing it. `GridPager` offers 100 rows a page and selection deliberately survives paging _and_ filtering, so three "select all on this page" clicks stage 300 targets, which is the whole of ADR-0020's `300 / 15 min / IP` budget in one confirm; the limiter does not set `skipFailedRequests`, so continuing past the first `429` spends the remainder on requests guaranteed to fail; it is mounted above `/auth`, so what it sheds is `login` and `refresh` **for every operator behind the same egress IP**; and a `401` mid-fan-out meets ADR-0033's single-flight refresh, which replays all N — 2N+1 requests for one click. The fan-out is now five in flight, stops dead on `RATE_LIMITED`, and reports what it never attempted as its own outcome rather than as more refusals, since "you may not" and "try again in a few minutes" have opposite remedies. What that does not fix is the limiter's granularity — a per-IP budget shared with authentication is the wrong shape for an authenticated bulk operation, `users.routes.ts` already records a per-principal budget as the missing category, and D4 does not take an API decision.

Four smaller review fixes, each closing a gap between a claim and the code: `allowedCapabilities` named its keys instead of spreading, because the spread copied ADR-0040's `editSurface` into the object handed to `AppGrid` and made "the grid never sees it" true of the type only; the row-action hooks' `capabilities` parameter became required, because optional made _hiding a containment control_ the behaviour of a forgotten argument — the direction ADR-0042 calls the worse one, and one the compiler could not see; the sidebar's `resource` join gained the principal-parameterised tests ADR-0042 said it would have, including the two-sided assertion that Dashboard and Profile survive (deny-by-default over a derived resource name would hide both); and a config test that could not fail — `some(key.includes("role"))` over a type with no such key — became an exact key-set assertion.

Evidence, separated as `D3.10` set the precedent. **Machine-verified:** `pnpm lint`, `pnpm check-types`, `pnpm format:check` clean; `pnpm test` green at `0 cached, 8 total` — 433 API integration unchanged (D4 touches no API surface), 328 admin (+41), 12 `@repo/ui`. The new admin coverage is ADR-0038's three non-negotiables and ADR-0042's three: selection keyed by id surviving a real page change (a navigation, a new query key, a refetch — not a `rerender`); capability flags adding and removing the toolbar's buttons and the menu's entries; a mixed fan-out reporting "1 deleted, 1 refused" with the refusal named per item from the `ErrorCode` map, one list refetch, selection cleared; a `manager` on `/users` offered neither Create nor Delete while Edit, Reset password and Sign out everywhere all remain; an `admin` offered both back; and the policy table pinned against the `authorize(` calls transcribed from `admin.router.ts` and `users.routes.ts`.

**Recorded rather than glossed**, in the shape `D4.2` used. The `canEdit: false` branch of the row-action hooks has no config path into it and cannot get one from a role: ADR-0042 never narrows `canEdit` (the disable path runs through the edit form), and both resources declare it `true`. The branch is unit-covered through `allowedCapabilities` and unreachable from any screen — which is correct, not a gap, but it is the same shape as D4.2's unexercised `page` shell and is written down for the same reason. Second: the policy table's `?? []` deny-by-default fallback has no live case, because every action is listed for both resources; the test pins that _completeness_ instead, since completeness is what makes the fixture a transcription. Third: **not walked in a browser** — every assertion above is from the MSW tier, and the toolbar's wrap behaviour at narrow widths is geometry only `D4.6`'s manual walk can see.

Three behaviours left as they are, amended into ADR-0038 §Selection so they are decisions rather than oversights: a row deleted through the **row menu** stays staged, because pruning it would mean `shared/grid` learning which rows died; a selection **survives a filter change**, so an operator can confirm a count whose rows are no longer on screen — `D4.4` rebuilds the filter surface and is where that should be decided if it is going to be; and `selectable` is **not** narrowed by `can()`, so a `manager` on `/users` gets checkboxes with no bulk action reachable from them, which is the shown-but-leads-nowhere shape one notch quieter and stops being visible the day selection has a second consumer.

### ~~4. Filter UX — dialogs, hot filters and the applied-filters bar~~ — **done 2026-08-20**

**ADRs:** [0039](../adr/0039-grid-filter-ux.md), [0014](../adr/0014-pagination-filtering-sorting.md), [0034](../adr/0034-server-state-and-notifications.md)

The filter row dies. Filterable columns get a header filter icon (active state when applied) opening a per-column dialog that reuses the four existing control kinds — text, enum, dateRange, presence — with explicit Apply/Clear. Resources may declare **hot filters** (`grid.hotFilters`): toolbar button groups for the stance-like filters — staff status, role, "deleted only" — one press to apply, one to release, writing through the same `withFilters` channel and tested against the same contract allow-lists. Above the table, the applied-filters bar renders one removable chip per applied filter plus `q`, and Clear all; the bar reads the URL's validated filters, **not** the column configs, so a deep-linked filter on a field no column owns still shows and clears — the same lesson `withFilters`' `owned` argument already encodes — while a chip currently displayed by a pressed hot-filter button is suppressed, keeping every filter visible and removable in exactly one place. ADR-0014's operator allow-list is the unmoved boundary: no dialog or button offers an operation the contract cannot answer.

**Done when:** no always-visible filter row remains and dateRange columns return to content width; each filter kind round-trips through its dialog (Apply commits, Clear removes, the icon's active state tracks the URL); a declared hot-filter group renders, presses on and off, agrees with the same field's header dialog, and is cleared by Clear all; a deep-linked unowned filter renders a chip and is clearable; Clear all resets filters and `q`, returns to offset 0, and leaves sort and limit alone; all asserted in the MSW tier.

**Closed.** ADR-0039 accepted at the head of the step, then built: the filter row deleted, a `ColumnFilterDialog` behind a header icon wherever a column declares a `filter`, `grid.hotFilters` with its two kinds rendered in the toolbar's left cluster, and an `AppliedFilters` bar over `chipsForState` / `withoutFilter` / `clearedFilters`. The debounce moved out with the row into `grid-search.tsx`, which is now the only control that live-commits — `q` still narrows under an operator's fingers, and a commit-on-Apply dialog has nothing to debounce. Staff declares one stance (`status`), users declares two (`status`, and the "Deleted only" toggle ADR-0039 predicted would be the first `presence` one), so the chip-suppression rule is exercised by a real config rather than a fixture.

**The step's first finding was in the ADR's own example.** ADR-0039 §Hot filters declares `status` _and_ `roles` for staff, and `listStaffQuery.filterable` has no `roles` entry — `staff_roles` is a join table, which §Context of the same ADR says two screens earlier about the columns. The config-versus-contract tests the ADR promises were written before the configs, and this is the first thing they refused, which is the whole argument for declaring hot filters as data instead of composing them per page. Amended rather than quietly dropped, and the same test now runs _every_ declared option through the endpoint rather than only the first — a group is one button per option, and only the first was ever sampled.

Six amendments to ADR-0039 in all, each a thing the implementation found rather than an opinion about it. **The icon's active state travels in its accessible name** (`"Filter by Email (filtered)"`), because the ADR pins the name _and_ asks for the state, and on a control that opens a dialog the name is the only honest channel — `aria-pressed` declares a toggle that toggles nothing, `data-active` is CSS a screen reader never hears. **`kind`, not `control`**, since the snippet's own comment says it mirrors `FilterControlConfig` and then picks the other word. **`hotFilters` is not a capability**: it sits on `GridConfig` beside `editSurface` and reaches `AppGrid` as its own prop, because ADR-0042 narrows _capabilities_ by role and nobody's role decides whether a list may be looked at through a smaller window. **The bar renders on what is applied, not on what has chips** — once hot filters suppress the chips they display, a pressed "Deleted only" is one applied filter and zero chips, and a bar keyed to chips would take Clear all off screen exactly when it was the only way to release the stance. **"Displays" is all-or-nothing**, defined as "could pressing these buttons have produced exactly this?": an `in` group holding one declared option and one foreign one must show _nothing_ pressed, or half of what the server was asked is represented by nothing at all — the invisible filter this ADR opens on, rebuilt inside the fix for it. And **`renderToolbar` suppresses nothing**, because a screen that replaces the toolbar replaced the hot filters with it.

**The `security-reviewer` pass found nothing above LOW and four things worth the step being longer for**, all of them the same defect wearing different clothes: a bar whose whole justification is that it says honestly what the server was asked can say it wrongly. **`unescapeContains` is a lossy inverse** — exact for what `containsPattern` writes, a guess for anything else — so a deep link carrying `like: "ada"` unwrapped to "Email contains “ada”" over an empty grid, when what was actually asked is an _exact_ match; the term is now round-tripped and the chip falls back to the raw form when it does not reproduce the pattern. **A range bound was formatted in the operator's timezone** by the same formatter the cells use, which moves an end-of-day bound forward a day east of UTC and a start-of-day bound back a day west of it — the chip and the dialog naming different days for one filter, deterministically and not only under a crafted URL. **`filterSchema` bounds neither a filter's `field` nor a scalar `value`**, harmless while nothing rendered an unowned filter and not harmless once this bar did, so labels are clamped and the schema's own bound goes on the index's Planned list. And **chip suppression was by resemblance rather than by entry**: a group renders from the first `field:op` entry it finds, so a URL holding two would press one and suppress both, leaving the second invisible and unremovable — the invariant failing inside the code that keeps it. Each is amended into ADR-0039 and each has a test that fails without the fix; the date one needed the _test_ fixed first, since asserting through the app's own formatter agreed with itself no matter what the timezone was.

One related thing is recorded rather than fixed: the dialog's _draft_ is seeded by the same lossy inverse, so opening a hand-written `like` filter and pressing Apply rewrites it to a containment pattern. That path ends in an explicit Apply, so it is something the operator does rather than something that happens to them.

**The `adr-reviewer` pass found the step's one real defect, and it was inside the sentence that sounded most settled.** ADR-0039 and the file both say focus trapping, Escape and return-of-focus "come free with the Dialog primitive — none of it is rebuilt here", and neither was true: the icon was a `Button` with an `onClick` rather than a `DialogTrigger`, and Radix's modal content _replaces_ the default focus restore with `triggerRef.current?.focus()` — so with no Trigger mounted the ref is null, the restore is suppressed rather than falling back, and Apply, Clear and Escape all dropped focus onto `<body>`. A keyboard operator was ejected to the top of the page by the act of filtering one column. The ADR is right here and the code was wrong, so the fix is a `DialogTrigger` rather than an amendment; `shared/ui` gains the export, which is the first time the door has needed one — this is the app's first in-place, button-opened dialog, the record surfaces of ADR-0040 being route-driven. It has a test, and the test was checked against the broken version rather than assumed to bite.

The same pass caught that **the timeout raise had undone the fix its own neighbour documents**. `vitest.config.ts` pins `testTimeout` at fifteen seconds and says why — the test ceiling has to sit _above_ `asyncUtilTimeout`, or a failing `findBy*` races it and reports "Test timed out" instead of naming the element it could not find. Raising `asyncUtilTimeout` to the same fifteen re-created exactly that race, and made this file's own claim that a broken assertion "costs the ceiling before failing" false. It is ten, and the gap is now written down as the constraint on anything raised there later.

Three smaller findings, each a gap between a name and what the code does: **the live region unmounted with the bar**, so clearing the _last_ filter — the change most worth hearing — was the one change the bar announced nothing for, and the region is now a sibling of the row rather than a child of it (`sr-only` is `position: absolute`, so it is out of flow and costs no `gap` in ADR-0037's budget); **the `renderToolbar` carve-out had no test**, which for a branch whose failure is an invisible filter is the wrong thing to leave to a comment; and **a config test named "and no more" asserted one direction**, while its option probe always used the `eq` shorthand and would have validated an `in` group against the wrong operator. The name now says what it checks and why the other direction is not checkable from outside the schema, and the probe goes through the same builder the rest of the file uses.

A seventh is a naming detail with a real failure behind it: a hot-filter group is named `"<label> filter"`, not `<label>`. A group called "Status" is indistinguishable from the _form field_ called "Status" the moment a record surface opens over the grid — which ADR-0040 made the normal case, since the grid stays mounted underneath — and four suites found it at once.

Evidence, separated as `D3.10` set the precedent. **Machine-verified:** `pnpm lint`, `pnpm check-types`, `pnpm format:check` clean; `pnpm test` green at `0 cached, 8 total` — 433 API integration unchanged (D4 touches no API surface), 377 admin (+49), 12 `@repo/ui`. The new coverage is this step's six "done when" clauses plus the pure seams ADR-0039 names: no control left in the header and one `thead` row where there were two; every kind round-tripping through its dialog with Apply committing once and only once, Clear touching one column, and a range writing both bounds in one navigation; a hot-filter group pressing on, off, and agreeing with the same field's header dialog; a chip suppressed while a button displays it and standing when the value is one the group cannot represent; a deep-linked filter on a field no column owns rendering `ownerId eq u-9` and clearing; Clear all dropping filters and `q`, resetting the offset and leaving sort and limit alone. `filter-chips.test.ts` and `hot-filters.test.ts` are new unit suites beside `list-state`, and the two config suites now run each declared hot filter — and each of its options — through the real contract schema. The two review rounds added six more, one per finding below.

**One thing changed that the step did not set out to change**, recorded because it is a test-harness edit made under a filter-UX step. `apps/admin/src/test/setup.ts` raises `asyncUtilTimeout` from five seconds to fifteen. The first `findByRole` in `staff-page.test.tsx` and `users-page.test.tsx` — the two files that mount the whole route tree and then wait for a list — began failing consistently under full-suite load on this machine. ### ~~5. Persisted grid preferences~~ — **done 2026-08-20**

**ADRs:** [0041](../adr/0041-grid-preferences.md), [0033](../adr/0033-browser-api-client-and-session.md), [0032](../adr/0032-admin-app-architecture.md)

The third state owner, with its boundary written down: the URL owns view state, preferences own ergonomics. Column sizing (header-edge drag), order and visibility (the "Columns" toolbar menu with reset) land as controlled v9 feature state backed by `createGridPreferences({ gridId, storage })` — a closure-based store over a storage-adapter seam, `localStorage` adapter now, the future user-settings API later without touching AppGrid. Values are versioned, zod-validated on read (corrupt → silently discarded), and reconciled against the current config (vanished columns dropped, new ones appended at defaults). The `actions` and selection columns are exempt from hiding and reordering by construction.

**Done when:** resize, reorder and hide/show each persist across a reload, independently per grid (`staff` and `users` prove isolation); a corrupted or stale-versioned stored value falls back to config defaults without an error; removing a column from config strands nothing; Reset returns to config defaults; nothing but column names and numbers ever enters storage.

**Closed.** ADR-0041 accepted at the head of the step — the last of the D4 six, so every ADR of this deliverable is now `accepted`. Then built: `createGridPreferences` over a three-function `PreferenceStorage`, with `createLocalStorageAdapter` and `createMemoryStorage` as its two implementations; `useGridPreferences` binding it to React through `useSyncExternalStore`, the shape ADR-0033's session store established; three v9 column features registered and controlled from it; a resize handle on the sticky header; and a Columns surface in the toolbar seat ADR-0038 reserved. Both pages pass `gridId={config.name}` and nothing else.

**The taxonomy is the deliverable here, and it holds.** The URL owns _view_ state, the store owns _ergonomics_, and the table owns nothing durable — which on this grid turned out stronger than the ADR asked for: with the transient resize slice unregistered (below), the table owns nothing at all. Nothing of sizing, order or visibility reaches a link, which is the point: a shared view must not impose the sender's column widths on the receiver.

Six amendments to ADR-0041, every one a thing the implementation found. **v9 splits sizing into two features and only one is registered**: `columnSizingFeature` holds the durable widths, `columnResizingFeature` holds the drag and `header.getResizeHandler()` — and that handler takes its start width from `column.getSize()`, which for a column nobody has sized is the engine's 150px default, while this grid's real default is whatever the content needed. Using it would snap a wide email column to 150px on the first pixel of the first drag. The alternatives were to freeze every column's width at mount, ending content-based auto-layout for the benefit of columns nobody has touched, or to read the start width off the header cell; `AppGrid` does the second in fifteen lines of pointer events and still writes through `table.setColumnSizing`, so the path in and out is the one every other control takes. **A width also has to be applied to a block _inside_ the cell**, because `@repo/ui`'s table cells are `whitespace-nowrap` and under `table-layout: auto` a cell's own `width` is a suggestion its content can overrule — a narrowed column simply refused to narrow. It is rendered only for columns somebody has actually sized, so an unsized grid keeps exactly the markup and the layout it had. **The handle is a named, keyboard-operable button**, because the ADR described a pointer drag and nothing else, which would have made column width the one affordance in this panel a keyboard cannot reach. **`structural` lives in `columnMeta`** rather than as v9's `enableResizing`, which belongs to the feature this grid does not register — and it keys off the `rowActions` _registry key_ rather than a column called `actions`, because `shared/grid` may not hold a column name (ADR-0032). **The Columns "menu" is a `Popover`**: a Radix menu treats each item as one actionable unit under a roving tabindex and closes on activation, while a row here is three controls used in sequence. **And a grid with no `gridId` persists nothing, unconditionally** — the supplied adapter is ignored rather than pointed at a placeholder key, because a shared fallback id reproduces the exact collision `gridId` exists to prevent.

One smaller amendment closes a gap between a promise and its owner: **the store guards the adapter as well as the other way round.** "Corrupt preferences must never break a grid" was, as written, a promise kept by the shipped `localStorage` adapter and by nothing else — a future server-backed adapter letting a network failure escape would have taken the grid down with it. The read path and both writes are guarded in the store, so the guarantee belongs to the store rather than to a convention adapters are asked to honour.

**The step's sharpest finding was in a test, and it cost six hundred seconds to notice.** The first full run after the page-level test landed showed one unrelated case — "says so when the list is refused" — taking **614 923 ms**, which `testTimeout: 15_000` should have made impossible; a synchronous storm that starves the timer is the only thing that can. Run alone it took 768 ms. The cause was the new test's own hygiene: it opened the Columns popover, then unmounted the tree without closing it, leaving a Radix dismiss layer and its focus guards mounted at teardown, mutating the document forever — and every `findBy*` in every later test in that file re-scanning a tree that never settles. Closing the overlay first, which is what an operator would do, took the file from 656 s to 32 s. Recorded because the shape generalises: **a test that unmounts with an overlay open does not fail, it makes the tests after it slow**, which is the hardest kind of failure to attribute.

**The two review rounds found eight things, none above MEDIUM, and the useful half were about what a _well-formed_ stored value can do.** The `security-reviewer` set the threat model first and it is worth restating: `localStorage` for this origin is writable only by same-origin script or by the operator with devtools, so "attacker-controlled storage" means post-XSS or a shared workstation, not a remote attacker. Nothing found is remotely exploitable. What it did find is that "corrupt preferences must never break a grid" had a gap on its other side — a value that passes the schema and still takes the grid away from the person using it. **`order` was neither de-duplicated nor length-bounded**, and both matter: the Columns menu keys its rows by id, so a repeat gives two rows one React key and one `<label for>`; and an unbounded array — `localStorage` holds megabytes — renders hundreds of thousands of menu rows and hangs the tab on the one surface that contains "Reset to defaults". **Widths were validated only as finite and positive** while the write path clamps to 64–2000, so a hand-edited `1` or `1e12` was accepted and applied. **An operator could uncheck every column**, leaving a blank rectangle whose undo is inside the menu that produced it. Bounds, dedupe and a disabled last checkbox; the ADR's promise is now the stronger one, that a well-formed entry cannot break a grid either. Two smaller ones: `preferences.sizing[id]` was an unguarded prototype-chain read, so a resource column named `constructor` would have yielded a _function_ as a width — not reachable from storage, reachable from a config; and the `movable` memo key was being split back into an array, making "no config key contains a newline" an invariant nothing enforced, which is now only a comparison.

The `adr-reviewer` found one behavioural slip and three places the prose had drifted. **The Columns surface was passed to the toolbar as a component that renders `null`**, and the toolbar's empty-region check asks whether a slot was _given_ something — so a grid whose every column is structural got back the dead band ADR-0038 spent a step removing. It is `null` now, with a test. The prose: the index row said "four v9 column features" where three are registered and the fourth is the one refused; the ADR's schema snippet still read `z.number()`; and "selection is pinned first and actions last by `buildColumns`" was left standing next to the amendment that supersedes it. One hazard is documented rather than fixed, because it cannot be: **`preferenceStorage` must be referentially stable**, since the store is memoised on it and a store rebuilt every render hands `useSyncExternalStore` a new snapshot every render — an infinite loop rather than a slow path. No call site does it; the prop now says so. And the drag's `window` listeners are torn down through an `AbortController` on unmount, because ADR-0040 made navigating away from a grid mid-interaction ordinary.

**One shipped behaviour changed that no step asked to change.** ADR-0038's "a toolbar region with nothing in it renders nothing" now has no live case on a grid that has columns, because every such grid has a Columns control. The rule stands and is still the reason a future control cannot assume the region exists; the test that pinned it now asserts what is true instead of being deleted.

Evidence, separated as `D3.10` set the precedent. **Machine-verified:** `pnpm lint`, `pnpm check-types`, `pnpm format:check` clean; `pnpm test` green at `0 cached, 8 total` — 433 API integration unchanged (D4 touches no API surface), 411 admin (+34), 12 `@repo/ui`. The new coverage is ADR-0041's own enumerated list, over an in-memory `PreferenceStorage` because the adapter seam is also the test seam: the round trip per `gridId`; a corrupt, wrong-versioned, wrong-shaped or zero-width value falling back to defaults without an error; reconciliation dropping a vanished id, appending a new one at its defaults, and absorbing a rename as a reset of that column alone; Reset removing the entry rather than writing today's defaults into it; a hostile adapter that throws on all three functions leaving the grid working; and the stored payload asserted key by key, so "column names and numbers only" is a test rather than a promise. Above that, through the component: hiding a column takes the header _and_ the cells (`getVisibleCells`), reordering moves the header, the arrangement survives a remount, two grids keep separate entries, the structural columns are absent from the menu and stay at the ends whatever the operator does, Reset is disabled until something deviates, the keyboard resizes, and a grid with no id writes nothing at all. `pages/staff` adds the one assertion only a screen can make: the real `gridId={staffResourceConfig.name}` wiring persists across a reload and leaves the users entry untouched.

**Recorded rather than glossed.** **Not walked in a browser** — every assertion is from the jsdom tier, which has no layout, so the _geometry_ of this step is unverified: whether a dragged edge tracks the pointer, whether a narrowed column truly truncates rather than overflowing, and whether the handle is reachable on the sticky header at the right edge of the scroll container are all things only `D4.6`'s manual walk can see. The keyboard path is what the tests drive, and the measured start width there is `0` because jsdom reports no rectangle, so what they pin is the clamp rather than the arithmetic. Second: **multi-tab is last-write-wins**, as the ADR accepts, and the `storage` event it notes as a cheap future sync is not built. Third: `ColumnConfig` gained no optional `size`, so default sizing is still the engine's until a need proves otherwise — the ADR's escape hatch, unused.

## The walk

Against the running dev stack — real API, real database, real `localStorage` — and it is the tier that has caught every layout defect in this deliverable, so what it did _not_ see is listed as carefully as what it did.

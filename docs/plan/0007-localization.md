# D7 — Interface localization

- Status: **in progress**, opened 2026-08-22 — the day D6 shipped ([ADR-0025](../adr/0025-deliverables.md) rule 5: one at a time). Its ADR, [0046](../adr/0046-interface-localization.md), was **written ahead on 2026-08-22** while D6 was in progress (writing is not opening — the D4 precedent) and was **accepted 2026-08-22 at the head of `D7.1`**. The window on ADR-0046 is open; **ADRs 0001–0045 are frozen**.
- Steps: `D7.1` – `D7.7`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: **every operator-facing string in `apps/admin` moves into a typed dictionary**, the locale switch lands and persists through D6's settings, and — the part that makes this a strategy rather than a chore — the i18n foundation is **designed for two SPAs and the shared packages between them**, because D8 extracts machinery into packages and builds the customer app on them, and that app must be _born_ localized. The ADR index's Planned list has carried "Internationalization" since D1; this is that entry becoming a deliverable.

## Why before the customer app

Retrofitting i18n is the expensive half — sweeping an app for hardcoded strings, restructuring copy into keys, threading formatters through every date and count. That price is paid **once**, for `apps/admin`, which already exists. Sequenced after the customer app it would be paid twice. And D8's extraction then moves components that are already dictionary-fed, so the packages never exist in a hardcoded state that would need its own sweep.

## Strategy requirements (the constraints ADR-0046 satisfies)

- **Typed keys.** A missing or misspelled key is a type error, not a runtime fallback — the same lint-mechanized posture ADR-0002 takes everywhere else.
- **ICU-grade formatting**: plurals, interpolation, and locale-aware dates and numbers (the grid's timestamp formatters become locale consumers).
- **Lazy per-locale bundles.** A locale costs its user, not every user.
- **Packages can declare strings without owning dictionaries.** Shared machinery (grid chrome — "No results", pager copy, form errors) ships its keys, likely namespaced per package; the apps own the dictionaries that satisfy them. This constraint exists so D8's extraction has a rule to follow.
- **Lint enforcement.** An ESLint rule (restricted-syntax on literal JSX text, in the ADR-0002 "lint half of the ADRs" tradition) makes a hardcoded string fail `pnpm lint` rather than depend on review.
- **The two-catalogue rule evolves rather than breaks.** D3 settled that operator copy has exactly two catalogues: error _codes_ in `shared/notifications/messages.ts`, field _rules_ in the contracts schemas. The first becomes a dictionary namespace mechanically. The second turned out to be simpler than it looked: the contracts schemas carry almost no hand-written messages — field rules surface as **zod's own default messages**, which the API copies into `VALIDATION_ERROR` details and the admin renders (a D3.9 decision whose comment already names the mechanism: _"localising the latter is zod's own error map on the contracts package"_). So the answer is zod's error map, switched with the locale on the client. Zod 4 ships locale maps but **no Latvian one**; ours lives in `@repo/contracts` as zod-only code, which ADR-0023 permits. The API keeps its developer-facing English (ADR-0013) and is untouched.

## Decisions (taken 2026-08-22, recorded in ADR-0046)

Made by the operator after a comparison of react-i18next, FormatJS/react-intl, Lingui and Paraglide; the ADR carries the reasoning and the trade-offs, this file carries the outcome.

- **react-i18next** — the boring choice on purpose: ubiquity and hiring outweighed Lingui's smaller runtime and built-in pseudo-locale. No ICU plugin: `Intl.PluralRules` through i18next's `_zero` / `_one` / `_other` keys covers Latvian's three forms.
- **Validation copy is localized on the client; the API stays English.** No frozen ADR is touched, no envelope change; a server detail that matches a rendered field is re-derived from the same contracts schema under the active locale.
- **`@repo/ui`'s hard-coded a11y strings** (`Close`, `Previous`, `Toggle Sidebar`…) go through a `UiStrings` context with English defaults — six owned, commented edits to generated files under ADR-0031's existing rule, and no i18n dependency in the design system.
- **Latvian is machine-drafted in D7 and marked `pending native review`** until the operator signs it off — a real second locale with an honest status, rather than a catalogue waiting for a translator.
- **`en` means en-GB**: British spelling for the source copy (the repository's own voice) and European date order through Intl; `lv` maps to `lv-LV`.
- Typed keys by declaration merging over the `en` catalogue; one `locales/` tree with a namespace per slice; `en` eager, other locales lazy per namespace; locale precedence settings → `localStorage` → `navigator.languages` → `en`, and `Accept-Language` used nowhere; `eslint-plugin-i18next` as the mechanical half; `i18next-parser` extraction with a drift check in `pnpm check`; a dev-only pseudo-locale behind `VITE_I18N_PSEUDO`; and an i18n factory rather than a singleton, so D8 lifts it into a package unchanged.

## Locales (decided 2026-08-20)

- **English is the source language; Latvian (`lv`) is the second locale, named by the operator** — the deliverable ships both, so the pipeline is proven by a real translation, not just infrastructure. Latvian is also a usefully demanding second locale: three plural forms (the `21 ieraksts` / `2 ieraksti` / `11 ierakstu` split), which is exactly what the ICU-plurals requirement above exists for — an i18n layer that survives Latvian counts survives most of Europe.
- **A pseudo-locale still ships as a dev-only verification tier** (accented-and-widened English in the `en-XA` tradition): it catches extraction gaps mechanically, which a real translation cannot — a missed hardcoded string looks fine in Latvian review only until someone reads every screen. It is excluded from the production locale enum.

Seven things the step found, recorded rather than folded into "done":

**The option that makes `init` synchronous was renamed, and the wrong spelling is silent.** ADR-0046 §14 rests the whole harness on "`en` loaded synchronously" — it is what keeps `test:unit` a pure function of the tree and therefore cached (ADR-0026). The option that buys it is `initImmediate: false` in every recipe written before i18next 26 and `initAsync: false` in i18next 26, which is what this repository installed. The two are not merely renamed spellings: the default is `true` either way, an unknown key in the options object is ignored rather than refused, and the failure mode is that the instance initialises on a `setTimeout` and the first render of every localised component misses its copy — which fails nothing today, because there is no copy. `check-types` caught it, and only because the options object is passed as a literal. Amended into ADR-0046 §13 so the next reader does not pay for it twice.

**`<html lang>` had two readings and the ADR only meant one.** "Follows the active locale" is satisfied by `lang="en"` and by `lang="en-GB"`, and the attribute is read by things that tell them apart — a screen reader picks a voice from it, a browser hyphenates by it, `:lang()` matches it. §5 had already decided that `en` **means** en-GB here, so the bare enum member would have been the one place that decision was not honoured. It carries `INTL_TAGS[locale]`; ADR-0046 §4 amended.

**Latvian needed a directory before it needed a translation.** The lazy loader is a template-literal `import()` over `./locales/<locale>/<namespace>.json`, which Vite compiles into a fixed map of what is on disk — so a locale with no directory is not an untranslated locale at runtime, it is a chunk that does not exist. `locales/lv/` therefore ships at `D7.1` holding the same four `{}` files as `en`, which is what let this step drive `changeLocale("lv")` end to end, assert `<html lang="lv-LV">` and the device cache write, and prove the whole lazy path with nothing to translate in it. `D7.6` fills the files; it does not have to create them.

**Keeping the precedence pure cost one module and bought the table.** ADR-0046 §4 writes `resolveInitialLocale` as taking `stored` and `navigator` as arguments, and the temptation is to have it read them. Splitting the two `localStorage` accessors into `locale-storage.ts` is what let the precedence be tested as a seven-row table with no browser in it — including the two cases the record names, `lv-LV` matching `lv` by primary subtag and an unmatched tag falling through to `en` rather than being guessed at. `preferredLocale(settings)` in `index.ts` is the two impure lines that join them, and it is the only thing outside `shared/i18n` that needs to exist.

**`TranslationKey` is `never` today, and that is the correct answer.** The catalogues land empty, so the declaration merge over `en` produces a union with nothing in it — which reads like a bug and is the property working: nothing may claim to carry a key before there is one. The same merge already makes an unknown key a compile error, which the factory's own suite had to leave the type system deliberately (one cast, commented) in order to ask what happens at runtime. So `D7.4`'s "a typo'd key fails to compile" is not a thing to build later; it is a thing that is already true and currently has no keys to be true about.

**Suspense had to be turned off, and the reason is a switch rather than a load.** react-i18next suspends a component whose namespace has not arrived, and every locale but `en` arrives through a dynamic `import()`. Left at the default that means a `<Suspense>` boundary above every translated component — and worse, a locale _switch_ unmounting and remounting whole subtrees, which is a grid losing its scroll position and an open dialog closing itself because somebody changed language. `react: { useSuspense: false }` costs one render in the `en` fallback, which is the fallback a missing `lv` key would have shown anyway. Amended into ADR-0046 §13.

**i18next 26 ships the mechanism D8's package rule was going to need.** `ResourceNamespaceMap` exists precisely so several packages can each declare their own namespace without their declaration merges colliding on `CustomTypeOptions.resources` (TS2717) — which is the failure the second extracted package would have hit. Both feed `TypeOptions['resources']`, so nothing about `TranslationKey` changes. `D7.1` uses `CustomTypeOptions` because there is exactly one declarer; ADR-0046 §13 now names the other for D8.

Six things the step found, recorded rather than folded into "done":

**"`messageForError` keeps its signature" is satisfiable, and not by keeping the export.** ADR-0046 §2 writes `messageForError(error)` surviving unchanged with `t()` behind it, and §13 forbids the module-level instance that a module-level function would have to read it through. Both hold only if the function that keeps the signature is one that is **produced**: `createMessageForError(t)` returns it, `useMessageForError()` is the hook every component uses, and the eight `applyServerErrors` call sites and the two fan-outs take it as an argument. The requirement was about the _shape a caller sees_, not about which identifier the module exports, and reading it the other way would have meant a singleton in the one place the ADR most wanted none.

**The global toast handler is older than the i18next instance, and neither end should move.** ADR-0034 gives one query client to the whole app and `app/index.tsx` builds it at module scope; `D7.1` put the instance _inside_ `SettingsProvider`, because that is where the account's locale is known and starting in it beats switching to it. So the handler cannot be handed a `t` at construction and the instance cannot be hoisted without undoing a step-1 decision. `createDeferredErrorMessage()` is the join: a stable lookup the client closes over, and a `bind(t)` called by a null-rendering component mounted as a sibling of `<AppRouter>` — which is already inside `I18nProvider`, because `SettingsProvider` renders its children there. The suite needs none of it: `renderWithProviders` builds the client _from_ the render's own instance, because there the two are born together.

**The boot screen is the honest floor of "the app is localized".** `AppLoader` is the fallback of both boot gates and both sit above the provider, so `useTranslation` there does not degrade to English — it warns and returns the key, and an operator would have read `loading.starting` while the app started. There is no ordering that fixes it: the account's locale needs the settings query, the settings query needs the client, and every locale but `en` is a dynamic `import()` that has not been asked for at first paint. It reads `I18nContext` and falls back to the bundled `en` catalogue, which keeps the string in one place and the key extractable. The first paint is in the source language, and that is a property of boot rather than a gap in the sweep.

**`Intl` had to become app-wide state, and ADR-0035 is why.** The plan's own sentence — "rebuild on `languageChanged` by closing over a holder the listener swaps, so the registry entries stay `(value) => string`" — is not a stylistic preference, it is the only shape available: a formatter registry entry takes a value and nothing else, so there is no parameter an instance could arrive through. `shared/i18n/intl.ts` is therefore the one module-level mutable thing in a directory built around a factory, and the cost is real and bounded — two instances at two locales in one test file share it, last writer wins. Naming it in ADR-0046 §5 is cheaper than having a future locale test fail only when it is run second.

**The seam between this step and `D7.4` is a namespace, not a folder.** `src/shared` and `src/widgets` finished at zero operator-facing literals. `src/app` did not, and deliberately: what is left there is eight `staticData.title`s, the two shell fallbacks behind them, and two "Back to <resource>" links — every one of which ADR-0046 §7 assigns to `D7.4` by name, and every one of which needs a namespace (`auth`, `dashboard`, `profile`, `staff`, `users`) that `D7.4` creates. Doing them here would have pulled half of `D7.4` forward into the step that was supposed to own the cross-cutting four.

**Two things the plan named do not exist to be moved.** There is no unsaved-changes prompt: `AppFormSurface`'s page shell blocks navigation while a mutation is in flight and shows nothing, so the copy the plan lists has never been written. And the plural of the bulk summary's noun is only half solved — `grid:bulk.deleted` carries `_one` and `_other`, so English forms its own plural in the catalogue rather than in TypeScript, but the noun itself is still a caller's string (`"staff account"`), which a language that declines it cannot use. `D7.4` turns that noun into a key, which is where the rest of the answer is.

**Evidence.** Machine-verified: `pnpm lint`, `pnpm check-types`, `pnpm test` and `pnpm format:check` all green — `admin` **497 across 45 files** (up from 485 across 42), `@repo/contracts` 167, `@repo/db` 56 unit and 44 integration, `api` 461 unit and 469 integration, `@repo/ui` 12, `@repo/crypto` 39, `@repo/logger` 14. ### 3. `@repo/ui`'s six strings

### 4. The configs carry keys

**ADRs:** [0046](../adr/0046-interface-localization.md) §7, [0035](../adr/0035-config-driven-resource-ui.md), [0043](../adr/0043-readable-list-search-params.md), [0032](../adr/0032-admin-app-architecture.md), [0036](../adr/0036-admin-testing-strategy.md)

The second half of the sweep, and the one that tests whether ADR-0035's "config is serializable data" survives contact with i18n. It does, because **a key is data**: every operator-facing string in a `ResourceConfig` becomes a `TranslationKey` — column `header`, field `label`, `description` and `placeholder`, `emptyMessage`, hot-filter and filter-operator labels — resolved by the rendering machinery with `t()`, and a config still diffs, snapshots and deep-merges with no function in it. The same rule covers the three places beside the configs where copy travels as data: route `staticData.title`, mutation `meta.success` — the follow-up ADR-0043 §Consequences explicitly left for D7, made as an additive type narrowing of one field beside a frozen record, with nothing moving about where `meta` is read or who delivers it — and confirm-dialog copy. The remaining namespaces land, each named for the slice that owns it: `auth`, `dashboard`, `profile`, `staff`, `users`, `settings`. The FSD boundary here is a review rule and this plan says so rather than pretending the lint can hold it: ADR-0032's import lint cannot enforce a string prefix, so a key under `staff:` appearing in `features/users-manage` is a finding with a name, not a failed build.

**Done when:** `as const satisfies ResourceConfig` fails to compile on a typo'd key, which is the property the registries already have for formatter names; both resource screens render every label, description, placeholder, empty message and filter label through `t()`; a success toast's copy is a key the one global handler resolves; both resource suites are green; the gate is green.

### 5. Validation copy, and the switch

**ADRs:** [0046](../adr/0046-interface-localization.md) §6, [0023](../adr/0023-shared-contracts-package.md), [0011](../adr/0011-middleware-pipeline.md), [0013](../adr/0013-error-model.md), [0033](../adr/0033-browser-api-client-and-session.md), [0045](../adr/0045-user-settings.md)

The plan's subtle half, and the one `D3.9` already named the mechanism for. `packages/contracts/src/locales/lv.ts` mirrors the shape of zod's own locale modules — a default-exported factory, a `Sizable` table, a `FormatDictionary`, one `switch` over `issue.code` — and **depends on zod alone**, which is what ADR-0023 permits word for word; it is exported through the `@repo/contracts/locales/lv` subpath so a consumer that never switches to Latvian never bundles it and the root export stays what it is. `applyZodLocale(locale)` calls `z.config({ localeError })` at `createI18n` time and on every `languageChanged`, with zod 4's shipped `en` map used as-is. The schemas' **custom** messages — `passwordSchema`'s policy text, a `.refine()` with its own sentence — become `params: { i18n: "<key>" }` on the issue and resolve through the `form` namespace, so contracts holds a locale map and still ships no sentence in any language but the source one. `applyServerErrors` stops echoing a matched `VALIDATION_ERROR` detail verbatim and **re-runs the form's resolver on the current values under the active locale**, preferring its own issue message for that path: the same schema, caught a second time, in the operator's language. The `D3.8` residual — a detail whose key the controls never held, which the resolver cannot produce an issue for because the form's state is not its body — keeps the API's English as its fallback and is now an **un-localised** residual, the same narrow case with one more property, not a new one. The **locale switch** lands on the settings page beside `D6.3`'s theme control, writing through `useUpdateSettings` and the `localStorage` key in that order of importance and the reverse order of time. **The API is untouched**, and that is checked as a diff rather than assumed.

**Done when:** a field the API refuses renders its rule in the active locale without a reload; the `lv` map has a unit test per issue code it translates; `apps/api/src` has no diff since D6 and the Postman collection's 102 requests and 314 assertions are unchanged; switching the locale changes the document language and the grid's formatters live; a second client of the same account finds the first one's language; the gate is green.

### 6. The mechanical half, and Latvian

**ADRs:** [0046](../adr/0046-interface-localization.md) §8 §9 §10 §11 §14, [0002](../adr/0002-monorepo-layout-and-tooling.md), [0004](../adr/0004-configuration-and-environment.md), [0026](../adr/0026-task-graph-caching-and-serialisation.md), [0036](../adr/0036-admin-testing-strategy.md)

The step that turns the sweep from believed into checked, and the one that can only run here: a rule that fires on every literal is red until the app has none, so it lands after the app has none. `eslint-plugin-i18next`'s `no-literal-string` goes into `@repo/config-eslint`'s admin config — where `apiConfig` lives, and for `apiConfig`'s reason: D8's customer app applies the same export, and a second copy is where two apps' rules diverge — scoped to `apps/admin/src/**`, off for the test directories and for `src/shared/i18n/**`, which is literals by definition. `pnpm i18n:extract` runs `i18next-parser` over the source and rewrites `en/*.json` from the `t()` calls, which is what keeps the catalogue from rotting: the code is the source of truth for which keys exist and the catalogue is derived. `pnpm i18n:check` joins `pnpm check` and is red on three things — the extractor would change any `en` file, an `lv` namespace is missing a key `en` has (runtime falls back silently and correctly, which is exactly why the gap needs somewhere else to become visible), or a `toLocaleString(` / `toLocaleDateString(` appears outside `shared/i18n`; it is a pure function of the tree, so it is cached under ADR-0026. `VITE_I18N_PSEUDO` arrives as a new admin variable through ADR-0004's one reader — `shared/config`'s zod schema, `apps/admin/.env.example`, and `turbo.json`'s `env` on the tasks that read it, the way `VITE_API_URL` is declared — behind which `i18next-pseudo` post-processes `en` into `[Šàvé çhàñgéš ∙∙∙]`, accented so a literal stands out and widened so a truncation shows. It is **not** a member of `LOCALES`: the enum is the production set and lives in a database column, and a pseudo-locale is a lens over `en`, not a language an account can have. The `lv` catalogues are machine-drafted here and **marked `pending native review`** — a real second locale with an honest status rather than a claimed translation — with the plural forms written correctly from the start, because `_zero` / `_one` / `_other` is grammar and not style. And §14's suite renders **every route under the pseudo-locale** and asserts that no rendered text node or operator-read attribute survives unaccented, over the route tree rather than a hand-kept list, so a page added later is covered on arrival.

**Done when:** a literal JSX string fails `pnpm lint` and a dropped key fails `pnpm i18n:check`, both proved by a deliberate break and reverted; every route passes the pseudo suite; the plural categories are tested for both locales; `pnpm check` still reports the cache hit ADR-0026 asks for; the gate is green.

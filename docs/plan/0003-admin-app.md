# D3 — Admin panel

- Status: **in progress**, opened 2026-08-19
- Steps: `D3.1` – `D3.10`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: build `apps/admin` — the staff-facing panel ADR-0022 configured — against the API surface D1 and D2 shipped, plus the two prerequisites the app cannot exist without: the `packages/ui` design system and the `GET /auth/csrf` bootstrap endpoint. **`apps/web` is not in this deliverable.** The ledger's old D3 row said "frontend apps"; the two apps share almost nothing beyond `@repo/ui` — different framework, different segments, different session model — so `web` is staged as D4 and this deliverable stays one app deep. No new API surface beyond ADR-0030.

The feature surface is exactly what the admin segment already exposes: login/logout/logout-all/refresh on cookie transport, staff CRUD with administrative password reset, users CRUD (soft delete) with reset, and the caller's own profile with password change. Two resources and a profile page are deliberately the whole product — they are the proof of the config-driven machinery, not a feature backlog.

Each step names the ADRs that govern it. Read them before implementing — they carry the reasoning, this file carries the work. Every step ends green on `pnpm lint && pnpm check-types && pnpm test` and a conventional commit.

**Amendment window.** ADRs 0030–0036 were written for this deliverable and may be amended in place while it is in progress, labelled `**Amended YYYY-MM-DD (D3.N).**` at the point of change ([ADR-0025](../adr/0025-deliverables.md) rule 2). ADRs 0001–0029 belong to shipped D1/D2 and are closed: if the work below needs one of them to say something different, stop and write a superseding ADR ([ADR-0024](../adr/0024-adr-lifecycle.md) rule 1).

**Gate.** ADRs 0030–0036 were written `proposed` and accepted 2026-08-19, before any implementing step started — [ADR-0025](../adr/0025-deliverables.md) rule 3 keeps "agreed" and "built" as separate facts, and the acceptance un-gates every step below. A future amendment that changes a decision re-gates only the steps that build it.

### 2. ~~`GET /auth/csrf` — the bootstrap endpoint~~ — **done 2026-08-19**

**ADRs:** [0030](../adr/0030-csrf-bootstrap-endpoint.md), [0029](../adr/0029-browser-token-transport.md), [0012](../adr/0012-response-envelope.md), [0020](../adr/0020-security-baseline.md) §Rate limiting

**Closed.** `GET /api/v1/{user,admin}/auth/csrf` is the first route on each auth router, above `authenticate(population)` and under the router-wide `noStore`. `auth.cookies.ts` gained one CSRF writer behind two policies — `setCsrfCookie` (mints, for `setAuthCookies`) and `ensureCsrfCookie` (echoes, for the bootstrap) — plus the shared `csrfAttributes` the clearer needs too. `CsrfResource` is a hand-written type in `@repo/contracts` `auth/`, and `respond.ok<CsrfResource>` is what pins the controller's literal to it. No request schema, no new error code, no new environment variable, no `turbo.json` change. `apps/api/test/auth-csrf.int.test.ts` is new (27 tests); both Postman auth folders gained the request.

Two things the step decided that the plan above did not, both recorded in ADR-0030, **amended 2026-08-19 (D3.2)**:

- **The cookie's `Max-Age` had no owner.** ADR-0030 says the bootstrap writes "the same attributes ADR-0029 gives it", and ADR-0029 §CSRF never names `Max-Age` — its row for that attribute belongs to the refresh cookie, and the CSRF cookie inherited the value only because D2.5 wrote both from one variable. So the ADR's parameterless `setCsrfCookie(res)` sketch would have issued a _session_ cookie from the bootstrap and a thirty-day one from login: one code path, two different cookies, and a reloaded browser finding nothing exactly when it needs it. The writer takes `maxAgeSec`, and ADR-0030 now states the attribute ADR-0029 left unstated — which is the "adds a decision ADR-0029 declined to make" move its own §Context licenses.
- **The bootstrap echoes rather than rotates, and that came out of the security review.** ADR-0030 §Rotation reasoned that last-write-wins was fine, which held while only `login` and `refresh` rotated — neither is triggerable by a third party. This endpoint is different in kind: unauthenticated, no input, a plain `GET`, so a page the operator never meant to visit can make their own browser call it. Rotating unconditionally would replace a signed-in operator's cookie, strand the value their tab holds in memory, and turn their next refresh into a `403 CSRF_TOKEN_INVALID` — a cross-site forced logout, which is the class of thing the CSRF token exists to prevent. `ensureCsrfCookie` re-sends what the caller already holds and mints only when there is none, so an unintended call is a no-op; `login` and `refresh` still rotate, which is where rotation is worth having.

**What was not established, deliberately.** Both reviews asserted that a cross-site `fetch` or `<img>` would land the `Set-Cookie`; that is doubtful — RFC 6265bis gates _storing_ a `SameSite=Strict` cookie on the request's same-site status, not only sending it — and an attempt to settle it in a real browser was inconclusive, because Chrome answers `127.0.0.1 → localhost` itself and a faithful test needs two registrable domains and TLS (`Secure` and `__Host-` do not survive a plain-HTTP alias). What is not in doubt is that a cross-site **top-level navigation** reaches the endpoint, as does any host under the registrable domain — the sibling ADR-0029 already refuses to allow. The idempotent bootstrap closes the vector without needing the answer, which is why it was preferred over pushing "re-bootstrap once on `403`" into a client that does not exist yet. The idempotence also falsified a decision in a sibling ADR, and that was reconciled rather than deferred: [ADR-0033](../adr/0033-browser-api-client-and-session.md) §Boot listed `CSRF_TOKEN_INVALID` among the codes that end a session, on the grounds that the client had nothing fresher to present and that a retry would spend the refresh budget. The first is untrue now that a re-bootstrap echoes the cookie's current value; the second was untrue already, since ADR-0029's D2.5 amendment narrowed that limiter to count only `401`. It is now recoverable — re-bootstrap once, retry once, second failure terminal — which matters because an ordinary two-tab login rotates the shared `Path=/` cookie and would otherwise end a session for no reason. ADR-0033 and [ADR-0036](../adr/0036-admin-testing-strategy.md), which enumerated the same list, are both **amended 2026-08-19 (D3.2)**; `D3.4` builds the recovery.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green (API 446 unit, 433 integration). `pnpm test:postman` green on 84 requests and 260 assertions, with the two new requests' cookie-matches-body assertion confirmed to execute rather than pass vacuously. Cross-origin readability — the property the whole endpoint exists for, and one supertest cannot see because it sends no `Origin` — was checked by hand against the dev API: with `Origin: http://localhost:3001` the response carries `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials: true`, and the cookie comes back `Max-Age=2592000`, matching `REFRESH_TOKEN_TTL`.

The one API change in this deliverable, and it lands before any client code depends on it — the same sequencing D2.5 used. Unauthenticated `GET /api/v1/{user,admin}/auth/csrf` on the existing auth routers: sets/rotates `__Host-machxi.csrf` and returns the value as `respond.ok({ csrfToken })` via a new `CsrfResource` in `@repo/contracts`. Use `/add-endpoint`; integration tests cover cookie set + body echo for both segments, the guard-matrix test gains the route as unauthenticated, and the Postman collection gains the request (`/postman-sync`).

**Done when:** both segments answer with the cookie and the body copy agreeing; the refresh limiter provably does not count the call; `pnpm test:postman` green.

### 3. ~~Admin app skeleton — FSD, router, layouts, test harness~~ — **done 2026-08-19**

**ADRs:** [0032](../adr/0032-admin-app-architecture.md), [0031](../adr/0031-ui-design-system.md), [0036](../adr/0036-admin-testing-strategy.md)

**Closed.** The FSD tree is `src/{app,pages,widgets,shared,test}` — `features` and `entities` arrive with their first slice, since an empty directory is not a layer. TanStack Router v1 file-based under `src/app/routes` with `autoCodeSplitting`, the two pathless layouts (`_auth` on the login-01 shell, `_dashboard` on sidebar-07 with `collapsible="icon"`), placeholder pages behind them, and the ADR-0036 harness in `src/test/`. `--passWithNoTests` is gone from both scripts.

Four things worth keeping from the doing of it:

- **The boundaries lint enforced nothing at all, and looked like it did.** `pnpm lint` was green with the whole config in place; it was green because the plugin resolves every import to the element that owns it, and an import it cannot resolve is "unknown" and passes. Elements matched, imports did not, so an upward `shared` → `widgets` import linted clean. `eslint-import-resolver-typescript` in `settings["import/resolver"]` is what makes the rule real. The lesson is the one D2.2 already recorded about a weak assertion: **the enforcement claim is only worth what a deliberate violation says about it**, so all three — upward, cross-slice, and past a slice's public API — were probed, and each fails the gate. A second hole came from the same shape: `boundaries/dependencies` says nothing about a dependency matching no element, so a file dropped outside the six folders was importable from everywhere and checked by nothing until `no-unknown-files` and `no-unknown-dependencies` were added. ADR-0032 is **amended 2026-08-19 (D3.3)** with all of it, including that the rule is now `boundaries/dependencies` (the plugin renamed it in v6 and folded `entry-point` and `no-private` into it in v7).

This is ADR-0036's role-and-label discipline paying for itself on day one: a control the suite cannot query is a control a screen reader cannot name.
- **The session stub has an address and an expiry date.** It lives at `shared/api/session-store.ts` under the names ADR-0033 gives it (`createSessionStore`, `SessionStore`), so `D3.4` replaces a body rather than a path and neither `__root.tsx` nor `providers/router.tsx` has to be rewired. It carries a `?anon` escape hatch, because with both guards real and the stub answering `true`, `_auth`'s mirror redirect makes the login screen unreachable under `pnpm dev` — half of what this step builds could not be looked at. It is gated behind `import.meta.env.DEV`: a URL-controlled guard bypass is harmless only while nothing sits behind the guard. **`D3.4` deletes the file and the hatch with it.**
- **Two conflicts between code and ADR were resolved in opposite directions**, which is the point of asking the question each time. `widgets` importing a sibling `widget` — the shell reaching for the sidebar — was a sideways import ADR-0032 forbids, so the _code_ changed: `DashboardLayout` takes the sidebar as a prop and the `_dashboard` route file composes them, which leaves the frame a pure frame. `lucide-react` as a dependency of the app was forbidden by ADR-0031's "runtime deps live in `packages/ui`", and there the _ADR_ changed (**amended 2026-08-19, D3.3**): that rule is about the design system's own dependencies, and re-exporting every icon through the door would make adding a nav item a two-package change. ADR-0036 is amended in the same window to record that colocated `__tests__` sit outside the boundaries lint.

### 4. ~~Browser session — API client, token store, login~~ — **done 2026-08-19**

**ADRs:** [0033](../adr/0033-browser-api-client-and-session.md), [0030](../adr/0030-csrf-bootstrap-endpoint.md), [0029](../adr/0029-browser-token-transport.md), [0013](../adr/0013-error-model.md)

**Closed.** `shared/config` parses `import.meta.env` once with zod and freezes it; `shared/api` holds `api-error.ts`, `session-store.ts`, `client.ts`, `bootstrap.ts` and `context.tsx`; `app/providers/session.tsx` wires the singletons behind the boot gate; the guards read the real store; `features/auth` is the app's first feature slice, with login and logout. `apps/admin/.env.example` is new and `VITE_API_URL` is declared on admin's `build` and `dev` tasks. 30 tests, all in the cached loop.

Four things worth keeping from the doing of it:

- **The tests caught two gaps in the client, and the security review caught five more.** The suite's own finds were the ones that mattered most: a second `401` after a retry, and a second `CSRF_TOKEN_INVALID`, both left the session looking alive where [ADR-0036](../adr/0036-admin-testing-strategy.md) §What must be covered and [ADR-0033](../adr/0033-browser-api-client-and-session.md) §Boot say they must end it. The review then found that `GET /auth/csrf` was not exempt from either recovery branch — and because `fetchCsrfToken` builds a fresh config each time, the retry flags could not bound it, so a `403` there recursed without limit and a `401` raised inside a refresh's own retry awaited the promise it was running inside and deadlocked the boot gate. Neither is reachable from this API, both are reachable from a proxy in front of it. Also fixed: an absolute URL passed to `client.instance` would have carried the bearer and the cookies off-origin while silently missing the CSRF header rules; a transport failure during recovery logged the operator out over a dropped connection, which is no evidence the session died; and an offline logout raised an unhandled rejection on the one path the design deliberately supports.
- **The `redirect` fence was not a fence.** `D3.3` validated it as `^\/(?!\/)` and the comment claimed it stopped "anything with a scheme or a `//` prefix". Checked against `new URL(value, origin)` rather than reasoned about, three values passed and resolved off-origin: `/\evil.com`, because the WHATWG parser treats `\` as `/` in special schemes, and `/<TAB>/evil.com` and its LF and CR variants, because the parser strips those characters before parsing. The router's own `pushState` refuses a cross-origin result today, so the live effect was a failed navigation rather than a landing — but that is a browser check, not the fence the ADR asked for, and it disappears the moment the value reaches `location.assign` or an `href`. The schema now rejects all three and `.catch(undefined)` keeps a hostile value from replacing the login screen with a router error.
- **The boundaries lint refused a design before a reviewer had to.** `useApiClient` started in `app/providers/session.tsx`, and the login form importing it was `features` → `app` — upward, which [ADR-0032](../adr/0032-admin-app-architecture.md) forbids. The React context moved to `shared/api/context.tsx`, where it belongs: hooks that reach the client are part of the client's surface, and `app` keeps constructing singletons and deciding readiness. ADR-0033's file map is **amended 2026-08-19 (D3.4)** to list the fifth module and say why it is there.
- **Two more amendments record what ADR-0033 left to this step.** The code for envelope-less failures is `SERVICE_UNAVAILABLE`, with `status: 0` as the discriminator between "no answer" and a real `503` — a distinction the client then uses to decide _not_ to end a session over a dropped socket. And the boot sequence has a third outcome: a failed _refresh_ is `anonymous`, but a failed _bootstrap_ means the API is unreachable, and swallowing that would send an operator to a login screen that cannot work either.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green across the workspace, `format:check` clean; admin's 30 tests are in the cached `test:unit` loop. The boot sequence was driven against the **real API** in dev — `GET /auth/csrf` 200, a genuine CORS preflight on refresh 204, `POST /auth/refresh` 400 with no cookie (ADR-0029 §Contracts), landing anonymous, and `/staff` redirecting to `/login?redirect=%2Fstaff`. Two incidental confirmations: `D3.2`'s idempotent bootstrap means React's `StrictMode` double-boot in dev returns the same token rather than rotating it, and a `useRef` latch now stops the second call entirely.

**Outstanding, deliberately.** The credential half of the done-when — sign in, reload, sign out against the real API — is **operator-verified rather than agent-verified**: it needs the seeded super admin's password typed into the form, and the assistant does not enter passwords into fields. Everything below the form is covered: login, logout, single-flight refresh, terminal codes and the CSRF recovery all run against MSW at the HTTP boundary with the real client. `D3.5` should not treat that leg as closed until it has been walked.

**Housekeeping:** `@tanstack/router-plugin` moved from `^1.170.31` back to `^1.168.34`. `D3.3` aligned it with `@tanstack/react-router` on a reviewer's suggestion, but the plugin publishes on a slower cadence and `1.170.x` does not exist for it — the range was unsatisfiable and would have failed `--frozen-lockfile`.

`shared/config` (zod-validated `import.meta.env`, `VITE_API_URL`, `apps/admin/.env.example`), `shared/api` (axios instance, envelope unwrap, branded `ApiClientError` + `isApiClientError`, in-memory session store, single-flight 401 refresh), the boot sequence (`GET /auth/csrf` → `POST /auth/refresh` behind a loading gate), real route guards in `_dashboard`/`_auth` `beforeLoad`, and the login feature on the login-01 screen with fields disabled while the mutation is pending. Logout wired in the dashboard shell. MSW suites cover bootstrap, single-flight refresh with queued retries, every terminal auth code landing on `/login`, and the one code that is **not** terminal — a `403 CSRF_TOKEN_INVALID` re-bootstraps and retries once, and only a second one ends the session (ADR-0033 §Boot, amended D3.2).

**Done when:** login → dashboard → reload keeps the session → logout → guarded routes redirect, against the real API in dev; the session flows are green in the cached unit loop against MSW.

### 5. ~~Server state and notifications~~ — **done 2026-08-20**

**ADRs:** [0034](../adr/0034-server-state-and-notifications.md), [0014](../adr/0014-pagination-filtering-sorting.md)

**Closed.** `createQueryClient` carries the decided defaults and the notifying `MutationCache` / `QueryCache`; `shared/api/query-meta.ts` types `meta`; `shared/api/list-params.ts` is the one place a list query becomes a query string; `shared/notifications/messages.ts` is `Record<ErrorCode, string>`; `entities/{staff,user}` hold key factories, plain API functions and hooks with one invalidation rule. The staff and users routes validate their search params, and `@repo/contracts` gained `listQuerySearchSchema`. 50 tests.

Four things worth keeping, three of them mistakes caught in review:

- **The retry rule retried nothing.** `isApiClientError(error) ? false : failureCount < 2` reads exactly like ADR-0034's snippet and is dead on arrival, because `D3.4`'s amendment to [ADR-0033](../adr/0033-browser-api-client-and-session.md) made _every_ rejection out of the client an `ApiClientError` — a dead socket included. So the predicate was constantly false, "network failures and 5xx get up to 2 retries" was unimplemented, and the only things that could reach the live branch were bugs, which it then retried twice. It discriminates on `status` now. **ADR-0034 is amended (D3.5)**: its snippet predates the ADR it depends on, which is the specific hazard of writing a decision set together and implementing it in sequence.
- **`validateSearch: listStaffQuery` could not survive its own output.** The per-endpoint builder parses the _wire_ form and outputs the _parsed_ one, and TanStack Router round-trips validated output back into the URL on every navigation — so the first pager click would have written a search the schema rejects, and the `.catch` I had added would have turned that into a silent reset to page one. That is the "state dies on navigation" failure ADR-0034 §Context exists to prevent, arriving through the fix for it. Verified rather than argued: `listStaffQuery.safeParse(listStaffQuery.parse({}))` fails on `sort` and on an unrecognised `filters`. `@repo/contracts` now exports `listQuerySearchSchema` for the parsed shape, and ADR-0034 is **amended (D3.5)** because its §47 and §61 could not both be true.
- **A date filter serialized as a JS date string.** `listStaffQuery` declares its date fields `z.coerce.date()`, so a parsed filter value really is a `Date`, and `String(value)` wrote `Thu Jan 01 2026 12:20:30 GMT+0200 (…)` where ADR-0014 specifies an ISO-8601 instant. The round-trip test missed it because it hand-built `value: "2026-01-01"`, which `ListQuery`'s `unknown` value accepts and the contract never produces — the test is now driven from `listStaffQuery.parse(…)`, which is the only version of it worth having.
- **Two accepted ADRs disagreed about where mutation hooks live.** [ADR-0032](../adr/0032-admin-app-architecture.md) says entities own reads and features own writes; ADR-0034's snippets put `useUpdateStaff` in the entity slice. ADR-0034 is right and **ADR-0032 is amended (D3.5)**: the line is the _cache surface_, not reads versus writes. "Invalidate `lists()` and the touched `detail(id)`" is a rule about keys and belongs where the keys are; a mutation hook in a feature would import a key factory across a slice boundary and the rule would have as many homes as callers. Features own the interactions that call those hooks.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green across the workspace, `format:check` clean; admin's 50 tests are in the cached loop. The list serializer's output is parsed back by the real `listStaffQuery` rather than compared to a fixture, so the two halves cannot drift apart quietly. One test failure was left in place long enough to read: the positive query-toast case timed out until it used a `4xx`, which is the corrected retry rule doing its job on a `5xx` and is now recorded in the test.

**Note for `D3.6`:** the query client is threaded through the router context (ADR-0032's `{ queryClient, session }`) but no loader uses it yet. `entities/user` has no suite of its own — it is generated from the same template as `entities/staff` and covered by that one; the first behaviour that differs needs its own.

The QueryClient with its decided defaults, per-entity query-key factories and API functions in `entities/{staff,user}`, list state validated into the URL by the `@repo/contracts` list schemas through TanStack Router search params, and the notification layer: `<Toaster>` mounted once, `MutationCache`/`QueryCache` global handlers reading typed `meta`, the error-code → message map over the contracts union.

**Done when:** a list hook driven from URL search params refetches on param change; a mutation with `meta.success` toasts without any call-site `toast()`; an `ApiClientError` code renders its mapped message; all covered by MSW tests.

### 6. ~~Resource UI machinery — AppGrid and config-driven forms~~ — **done 2026-08-20**

**ADRs:** [0035](../adr/0035-config-driven-resource-ui.md), [0031](../adr/0031-ui-design-system.md), [0034](../adr/0034-server-state-and-notifications.md)

**Closed.** `shared/resource` holds the `ResourceConfig` vocabulary (`types.ts`, type-only) and its runtime helpers (`config.ts`); `shared/grid` holds the registry, the URL-to-engine translation (`list-state.ts`, `column-filters.ts`), the filter controls, the pager and `AppGrid`; `shared/form` holds the field registry, the two nested contexts, `AppFormInput`, `createAppFormInput`, the server-error mapping and `AppFormError`. Proved against a demo resource config in `src/test/fixtures/` rather than a demo page — a route and a nav entry for a fictional resource would be scope this step does not have and D3 would then have to delete. 130 tests, 74 new.

Five things worth keeping:

- **The engine is TanStack Table v9, and ADR-0035 is amended (D3.6).** The ADR named v8, verified 2026-08-19; `pnpm add` resolved v9 the next day, and v8's `useReactTable` survives there only under the `/legacy` entry point. Taking v8 anyway would have been adopting the previous major, on its compatibility path, into a package with no code in it yet — the "technical debt at birth" the ADR's own §Alternatives refuses for shadcn's legacy `<Form>` wrapper. Nothing the decision rested on changed: headless, MIT, `manual*` + `rowCount` + controlled `state`, the same instance API. What changed is `useTable` in place of `useReactTable`, `table.FlexRender` in place of `flexRender`, per-table `tableMeta` / `columnMeta` type slots in place of global declaration merging — and features being _imports_, which turns out to strengthen this ADR's own argument: a fully manual grid imports no row model, so the code that could sort or paginate the fetched page locally is **absent from the bundle** rather than suppressed by a flag. The manual flags are still set, and now they describe something structural.
- **The filter row's cells are `td`, not `th`.** Caught by a test, and it was a real defect rather than a test to adjust: `th` claims the `columnheader` role, so a six-column grid announced twelve column headers and every `getAllByRole("row")` query got the filter row before the first data row. Those cells hold controls and label nothing. This is ADR-0036's role-and-label discipline earning its keep on the first grid it met — "a control the suite cannot query is a control a screen reader cannot name", read from the other direction.
- **`dirtyValuesOf` cannot test `=== true`.** ADR-0035 prunes edit submits to RHF's `dirtyFields`, and RHF mirrors the _value's_ shape there: a scalar is flagged `true`, an array field (`roles`, any `multiCheckbox`) is flagged as an array of booleans. The obvious predicate passes on every scalar field and silently drops exactly the array ones — so an operator changing only the roles would have submitted an empty body and met the contracts' "provide at least one field" refinement as a validation error. Fixed before it shipped, and the test says why it exists.
- **`react-hooks/refs` is a false positive on RHF's `field`, and the carve-out says so.** The React Compiler rule treats `ControllerRenderProps` as a ref because it carries a `ref` property — but that is a ref _callback_ to attach, not a ref object with a `.current`, and reading `field.value` during render is what the API is for. Probed rather than assumed: the warning follows the object through direct access, destructuring, aliased and inline prop types alike, so no spelling of the adapters satisfies it while still using `Controller`. One file-scoped disable in `fields.tsx`, in the shape ADR-0031 §Consequences set for the generated primitives — name the rule at the point of change and say what forced it. The sibling finding needed no carve-out: the debounced input's re-sync moved from an effect to React's documented in-render adjustment, which is better code and not a workaround.
- **`shared` stays free of domain knowledge by erasing the row type exactly once.** ADR-0032 forbids `shared/grid` knowing what a staff member is, but a feature declaring `onSelect: (staff) => …` should still get a `StaffResource`. `AppGrid` is generic at its door and untyped on the inside, with one commented cast in between — so D3.7 and D3.8 pay nothing for the rule.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green across the workspace, `format:check` clean.

**Note for `D3.7`:** the config-versus-contract tests ADR-0035 asks for (`listStaffQuery.safeParse({ sort: "email" })` for each column that declares `sortable`, and the same for each filter's field and operator) belong to the first _real_ config and are not written yet — the demo resource has no endpoint to check against. `shared/form/server-errors.ts` takes an optional `codeFields` map so a domain code the API sends without `details` (`STAFF_EMAIL_TAKEN` is a `409` with no field path) still lands on its field; staff is the first resource that needs it. The `q` toolbar renders only when a page passes `searchable`, which both list endpoints are.

The machinery both resource steps consume: the `ResourceConfig` shape (columns + fields declared once per resource), the grid registry (formatters, cell renderers by key) and `AppGrid` — TanStack Table in manual mode (`manualPagination`/`manualSorting`/`manualFiltering`, `rowCount` from `meta.pagination.total`) rendered with `@repo/ui` `Table` primitives, state controlled from the URL search params per ADR-0014/0034, a real pager including the stranded-offset and `total: null` branches, sort and filter controls only where the contract allow-lists them; the field-component registry, `AppFormProvider` (RHF `FormProvider` + config context, `zodResolver` over the contracts schema), `AppFormInput`, and the submit lock (mutation `isPending` → `useForm` `disabled` + `fieldset` + button state). Registry resolution, `fieldName` typing, submit-lock behaviour and server-error `setError` mapping all get unit tests.

**Done when:** a demo resource config renders a themed grid and a working form entirely from config; every field provably disables during a pending mutation; a config typo on `fieldName` is a compile error.

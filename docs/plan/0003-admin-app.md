# D3 — Admin panel

- Status: **shipped 2026-08-20** (opened 2026-08-19)
- Steps: `D3.1` – `D3.10`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: build `apps/admin` — the staff-facing panel ADR-0022 configured — against the API surface D1 and D2 shipped, plus the two prerequisites the app cannot exist without: the `packages/ui` design system and the `GET /auth/csrf` bootstrap endpoint. **`apps/web` is not in this deliverable.** The ledger's old D3 row said "frontend apps"; the two apps share almost nothing beyond `@repo/ui` — different framework, different segments, different session model — so `web` is staged as D4 and this deliverable stays one app deep. No new API surface beyond ADR-0030.

The feature surface is exactly what the admin segment already exposes: login/logout/logout-all/refresh on cookie transport, staff CRUD with administrative password reset, users CRUD (soft delete) with reset, and the caller's own profile with password change. Two resources and a profile page are deliberately the whole product — they are the proof of the config-driven machinery, not a feature backlog.

Each step names the ADRs that govern it. Read them before implementing — they carry the reasoning, this file carries the work. Every step ends green on `pnpm lint && pnpm check-types && pnpm test` and a conventional commit.

**Amendment window — shut.** ADRs 0030–0036 were written for this deliverable and were amendable in place while it was in progress, labelled `**Amended YYYY-MM-DD (D3.N).**` at the point of change ([ADR-0025](../adr/0025-deliverables.md) rule 2). Every one of them carries at least one such amendment, which is the window having been used rather than merely granted. **It shut when D3 shipped on 2026-08-20**: ADRs 0001–0036 are now closed, and a change to any of them is a superseding ADR that carries the whole decision ([ADR-0024](../adr/0024-adr-lifecycle.md) rule 1).

**Gate.** ADRs 0030–0036 were written `proposed` and accepted 2026-08-19, before any implementing step started — [ADR-0025](../adr/0025-deliverables.md) rule 3 keeps "agreed" and "built" as separate facts, and the acceptance un-gates every step below. A future amendment that changes a decision re-gates only the steps that build it.

### 2. ~~`GET /auth/csrf` — the bootstrap endpoint~~ — **done 2026-08-19**

**ADRs:** [0030](../adr/0030-csrf-bootstrap-endpoint.md), [0029](../adr/0029-browser-token-transport.md), [0012](../adr/0012-response-envelope.md), [0020](../adr/0020-security-baseline.md) §Rate limiting

**Closed.** `GET /api/v1/{user,admin}/auth/csrf` is the first route on each auth router, above `authenticate(population)` and under the router-wide `noStore`. `auth.cookies.ts` gained one CSRF writer behind two policies — `setCsrfCookie` (mints, for `setAuthCookies`) and `ensureCsrfCookie` (echoes, for the bootstrap) — plus the shared `csrfAttributes` the clearer needs too. `CsrfResource` is a hand-written type in `@repo/contracts` `auth/`, and `respond.ok<CsrfResource>` is what pins the controller's literal to it. No request schema, no new error code, no new environment variable, no `turbo.json` change. `apps/api/test/auth-csrf.int.test.ts` is new (27 tests); both Postman auth folders gained the request.

Two things the step decided that the plan above did not, both recorded in ADR-0030, **amended 2026-08-19 (D3.2)**:

- **The cookie's `Max-Age` had no owner.** ADR-0030 says the bootstrap writes "the same attributes ADR-0029 gives it", and ADR-0029 §CSRF never names `Max-Age` — its row for that attribute belongs to the refresh cookie, and the CSRF cookie inherited the value only because D2.5 wrote both from one variable. So the ADR's parameterless `setCsrfCookie(res)` sketch would have issued a _session_ cookie from the bootstrap and a thirty-day one from login: one code path, two different cookies, and a reloaded browser finding nothing exactly when it needs it. The writer takes `maxAgeSec`, and ADR-0030 now states the attribute ADR-0029 left unstated — which is the "adds a decision ADR-0029 declined to make" move its own §Context licenses.
- **The bootstrap echoes rather than rotates, and that came out of the security review.** ADR-0030 §Rotation reasoned that last-write-wins was fine, which held while only `login` and `refresh` rotated — neither is triggerable by a third party. This endpoint is different in kind: unauthenticated, no input, a plain `GET`, so a page the operator never meant to visit can make their own browser call it. Rotating unconditionally would replace a signed-in operator's cookie, strand the value their tab holds in memory, and turn their next refresh into a `403 CSRF_TOKEN_INVALID` — a cross-site forced logout, which is the class of thing the CSRF token exists to prevent. `ensureCsrfCookie` re-sends what the caller already holds and mints only when there is none, so an unintended call is a no-op; `login` and `refresh` still rotate, which is where rotation is worth having.

**What was not established, deliberately.** Both reviews asserted that a cross-site `fetch` or `<img>` would land the `Set-Cookie`; that is doubtful — RFC 6265bis gates _storing_ a `SameSite=Strict` cookie on the request's same-site status, not only sending it — and an attempt to settle it in a real browser was inconclusive, because Chrome answers `127.0.0.1 → localhost` itself and a faithful test needs two registrable domains and TLS (`Secure` and `__Host-` do not survive a plain-HTTP alias). What is not in doubt is that a cross-site **top-level navigation** reaches the endpoint, as does any host under the registrable domain — the sibling ADR-0029 already refuses to allow. The idempotent bootstrap closes the vector without needing the answer, which is why it was preferred over pushing "re-bootstrap once on `403`" into a client that does not exist yet. The idempotence also falsified a decision in a sibling ADR, and that was reconciled rather than deferred: [ADR-0033](../adr/0033-browser-api-client-and-session.md) §Boot listed `CSRF_TOKEN_INVALID` among the codes that end a session, on the grounds that the client had nothing fresher to present and that a retry would spend the refresh budget. The first is untrue now that a re-bootstrap echoes the cookie's current value; the second was untrue already, since ADR-0029's D2.5 amendment narrowed that limiter to count only `401`. It is now recoverable — re-bootstrap once, retry once, second failure terminal — which matters because an ordinary two-tab login rotates the shared `Path=/` cookie and would otherwise end a session for no reason. ADR-0033 and [ADR-0036](../adr/0036-admin-testing-strategy.md), which enumerated the same list, are both **amended 2026-08-19 (D3.2)**; `D3.4` builds the recovery.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green (API 446 unit, 433 integration). `pnpm test:postman` green on 84 requests and 260 assertions, with the two new requests' cookie-matches-body assertion confirmed to execute rather than pass vacuously. Cross-origin readability — the property the whole endpoint exists for, and one supertest cannot see because it sends no `Origin` — was checked by hand against the dev API: with `Origin: http://localhost:3001` the response carries `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials: true`, and the cookie comes back `Max-Age=2592000`, matching `REFRESH_TOKEN_TTL`.

The one API change in this deliverable, and it lands before any client code depends on it — the same sequencing D2.5 used. Unauthenticated `GET /api/v1/{user,admin}/auth/csrf` on the existing auth routers: sets/rotates `__Host-machxi.csrf` and returns the value as `respond.ok({ csrfToken })` via a new `CsrfResource` in `@repo/contracts`. Use `/add-endpoint`; integration tests cover cookie set + body echo for both segments, the guard-matrix test gains the route as unauthenticated, and the Postman collection gains the request (`/postman-sync`).

**Done when:** both segments answer with the cookie and the body copy agreeing; the refresh limiter provably does not count the call; `pnpm test:postman` green.

**Closed.** The FSD tree is `src/{app,pages,widgets,shared,test}` — `features` and `entities` arrive with their first slice, since an empty directory is not a layer. It is gated behind `import.meta.env.DEV`: a URL-controlled guard bypass is harmless only while nothing sits behind the guard. **`D3.4` deletes the file and the hatch with it.**

### 4. ~~Browser session — API client, token store, login~~ — **done 2026-08-19**

**ADRs:** [0033](../adr/0033-browser-api-client-and-session.md), [0030](../adr/0030-csrf-bootstrap-endpoint.md), [0029](../adr/0029-browser-token-transport.md), [0013](../adr/0013-error-model.md)

**Closed.** `shared/config` parses `import.meta.env` once with zod and freezes it; `shared/api` holds `api-error.ts`, `session-store.ts`, `client.ts`, `bootstrap.ts` and `context.tsx`; `app/providers/session.tsx` wires the singletons behind the boot gate; the guards read the real store; `features/auth` is the app's first feature slice, with login and logout. `apps/admin/.env.example` is new and `VITE_API_URL` is declared on admin's `build` and `dev` tasks. 30 tests, all in the cached loop.

Four things worth keeping from the doing of it:

- **The tests caught two gaps in the client, and the security review caught five more.** The suite's own finds were the ones that mattered most: a second `401` after a retry, and a second `CSRF_TOKEN_INVALID`, both left the session looking alive where [ADR-0036](../adr/0036-admin-testing-strategy.md) §What must be covered and [ADR-0033](../adr/0033-browser-api-client-and-session.md) §Boot say they must end it. The review then found that `GET /auth/csrf` was not exempt from either recovery branch — and because `fetchCsrfToken` builds a fresh config each time, the retry flags could not bound it, so a `403` there recursed without limit and a `401` raised inside a refresh's own retry awaited the promise it was running inside and deadlocked the boot gate. Neither is reachable from this API, both are reachable from a proxy in front of it. Also fixed: an absolute URL passed to `client.instance` would have carried the bearer and the cookies off-origin while silently missing the CSRF header rules; a transport failure during recovery logged the operator out over a dropped connection, which is no evidence the session died; and an offline logout raised an unhandled rejection on the one path the design deliberately supports.
- **The `redirect` fence was not a fence.** `D3.3` validated it as `^\/(?!\/)` and the comment claimed it stopped "anything with a scheme or a `//` prefix". Checked against `new URL(value, origin)` rather than reasoned about, three values passed and resolved off-origin: `/\evil.com`, because the WHATWG parser treats `\` as `/` in special schemes, and `/<TAB>/evil.com` and its LF and CR variants, because the parser strips those characters before parsing. The router's own `pushState` refuses a cross-origin result today, so the live effect was a failed navigation rather than a landing — but that is a browser check, not the fence the ADR asked for, and it disappears the moment the value reaches `location.assign` or an `href`. The schema now rejects all three and `.catch(undefined)` keeps a hostile value from replacing the login screen with a router error.
- **The boundaries lint refused a design before a reviewer had to.** `useApiClient` started in `app/providers/session.tsx`, and the login form importing it was `features` → `app` — upward, which [ADR-0032](../adr/0032-admin-app-architecture.md) forbids. The React context moved to `shared/api/context.tsx`, where it belongs: hooks that reach the client are part of the client's surface, and `app` keeps constructing singletons and deciding readiness. ADR-0033's file map is **amended 2026-08-19 (D3.4)** to list the fifth module and say why it is there.
- **Two more amendments record what ADR-0033 left to this step.** The code for envelope-less failures is `SERVICE_UNAVAILABLE`, with `status: 0` as the discriminator between "no answer" and a real `503` — a distinction the client then uses to decide _not_ to end a session over a dropped socket. And the boot sequence has a third outcome: a failed _refresh_ is `anonymous`, but a failed _bootstrap_ means the API is unreachable, and swallowing that would send an operator to a login screen that cannot work either.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green across the workspace, `format:check` clean; admin's 30 tests are in the cached `test:unit` loop. The boot sequence was driven against the **real API** in dev — `GET /auth/csrf` 200, a genuine CORS preflight on refresh 204, `POST /auth/refresh` 400 with no cookie (ADR-0029 §Contracts), landing anonymous, and `/staff` redirecting to `/login?redirect=%2Fstaff`. Two incidental confirmations: `D3.2`'s idempotent bootstrap means React's `StrictMode` double-boot in dev returns the same token rather than rotating it, and a `useRef` latch now stops the second call entirely.

**Outstanding, deliberately.** The credential half of the done-when — sign in, reload, sign out against the real API — is **operator-verified rather than agent-verified**: it needs the seeded super admin's password typed into the form, and the assistant does not enter passwords into fields. Everything below the form is covered: login, logout, single-flight refresh, terminal codes and the CSRF recovery all run against MSW at the HTTP boundary with the real client. `D3.5` should not treat that leg as closed until it has been walked.

**Housekeeping:** `@tanstack/router-plugin` moved from `^1.170.31` back to `^1.168.34`. `D3.3` aligned it with `@tanstack/react-router` on a reviewer's suggestion, but the plugin publishes on a slower cadence and `1.170.x` does not exist for it — the range was unsatisfiable and would have failed `--frozen-lockfile`.

`shared/config` (zod-validated `import.meta.env`, `VITE_API_URL`, `apps/admin/.env.example`), `shared/api` (axios instance, envelope unwrap, branded `ApiClientError` + `isApiClientError`, in-memory session store, single-flight 401 refresh), the boot sequence (`GET /auth/csrf` → `POST /auth/refresh` behind a loading gate), real route guards in `_dashboard`/`_auth` `beforeLoad`, and the login feature on the login-01 screen with fields disabled while the mutation is pending. Logout wired in the dashboard shell. MSW suites cover bootstrap, single-flight refresh with queued retries, every terminal auth code landing on `/login`, and the one code that is **not** terminal — a `403 CSRF_TOKEN_INVALID` re-bootstraps and retries once, and only a second one ends the session (ADR-0033 §Boot, amended D3.2).

**Done when:** login → dashboard → reload keeps the session → logout → guarded routes redirect, against the real API in dev; the session flows are green in the cached unit loop against MSW.

### 5. ~~Server state and notifications~~ — **done 2026-08-20**

**ADRs:** [0034](../adr/0034-server-state-and-notifications.md), [0014](../adr/0014-pagination-filtering-sorting.md)

**Closed.** `createQueryClient` carries the decided defaults and the notifying `MutationCache` / `QueryCache`; `shared/api/query-meta.ts` types `meta`; `shared/api/list-params.ts` is the one place a list query becomes a query string; `shared/notifications/messages.ts` is `Record<ErrorCode, string>`; `entities/{staff,user}` hold key factories, plain API functions and hooks with one invalidation rule. The staff and users routes validate their search params, and `@repo/contracts` gained `listQuerySearchSchema`. 50 tests.

Four things worth keeping, three of them mistakes caught in review:

- **The retry rule retried nothing.** `isApiClientError(error) ? false : failureCount < 2` reads exactly like ADR-0034's snippet and is dead on arrival, because `D3.4`'s amendment to [ADR-0033](../adr/0033-browser-api-client-and-session.md) made _every_ rejection out of the client an `ApiClientError` — a dead socket included. So the predicate was constantly false, "network failures and 5xx get up to 2 retries" was unimplemented, and the only things that could reach the live branch were bugs, which it then retried twice. It discriminates on `status` now. **ADR-0034 is amended (D3.5)**: its snippet predates the ADR it depends on, which is the specific hazard of writing a decision set together and implementing it in sequence.
- **`validateSearch: listStaffQuery` could not survive its own output.** The per-endpoint builder parses the _wire_ form and outputs the _parsed_ one, and TanStack Router round-trips validated output back into the URL on every navigation — so the first pager click would have written a search the schema rejects, and the `.catch` I had added would have turned that into a silent reset to page one. That is the "state dies on navigation" failure ADR-0034 §Context exists to prevent, arriving through the fix for it. Verified rather than argued: `listStaffQuery.safeParse(listStaffQuery.parse({}))` fails on `sort` and on an unrecognised `filters`. `@repo/contracts` now exports `listQuerySearchSchema` for the parsed shape, and ADR-0034 is **amended (D3.5)** because its §47 and §61 could not both be true.
- **A date filter serialized as a JS date string.** `listStaffQuery` declares its date fields `z.coerce.date()`, so a parsed filter value really is a `Date`, and `String(value)` wrote `Thu Jan 01 2026 12:20:30 GMT+0200 (…)` where ADR-0014 specifies an ISO-8601 instant. The round-trip test missed it because it hand-built `value: "2026-01-01"`, which `ListQuery`'s `unknown` value accepts and the contract never produces — the test is now driven from `listStaffQuery.parse(…)`, which is the only version of it worth having.
- **Two accepted ADRs disagreed about where mutation hooks live.** [ADR-0032](../adr/0032-admin-app-architecture.md) says entities own reads and features own writes; ADR-0034's snippets put `useUpdateStaff` in the entity slice. ADR-0034 is right and **ADR-0032 is amended (D3.5)**: the line is the _cache surface_, not reads versus writes. "Invalidate `lists()` and the touched `detail(id)`" is a rule about keys and belongs where the keys are; a mutation hook in a feature would import a key factory across a slice boundary and the rule would have as many homes as callers. Features own the interactions that call those hooks.

Seven things worth keeping, three of them found by the review rather than by the build:

- **The engine is TanStack Table v9, and ADR-0035 is amended (D3.6).** The ADR named v8, verified 2026-08-19; `pnpm add` resolved v9 the next day, and v8's `useReactTable` survives there only under the `/legacy` entry point. What changed is `useTable` in place of `useReactTable`, `table.FlexRender` in place of `flexRender`, per-table `tableMeta` / `columnMeta` type slots in place of global declaration merging — and features being _imports_, which turns out to strengthen this ADR's own argument: a fully manual grid imports no row model, so the code that could sort or paginate the fetched page locally is **absent from the bundle** rather than suppressed by a flag. The manual flags are still set, and now they describe something structural.
- **The filter row's cells are `td`, not `th`.** Caught by a test, and it was a real defect rather than a test to adjust: `th` claims the `columnheader` role, so a six-column grid announced twelve column headers and every `getAllByRole("row")` query got the filter row before the first data row. Those cells hold controls and label nothing. This is ADR-0036's role-and-label discipline earning its keep on the first grid it met — "a control the suite cannot query is a control a screen reader cannot name", read from the other direction.
- **`dirtyValuesOf` cannot test `=== true`.** ADR-0035 prunes edit submits to RHF's `dirtyFields`, and RHF mirrors the _value's_ shape there: a scalar is flagged `true`, an array field (`roles`, any `multiCheckbox`) is flagged as an array of booleans. The obvious predicate passes on every scalar field and silently drops exactly the array ones — so an operator changing only the roles would have submitted an empty body and met the contracts' "provide at least one field" refinement as a validation error. Fixed before it shipped, and the test says why it exists.
- **`react-hooks/refs` is a false positive on RHF's `field`, and the carve-out says so.** The React Compiler rule treats `ControllerRenderProps` as a ref because it carries a `ref` property — but that is a ref _callback_ to attach, not a ref object with a `.current`, and reading `field.value` during render is what the API is for. Probed rather than assumed: the warning follows the object through direct access, destructuring, aliased and inline prop types alike, so no spelling of the adapters satisfies it while still using `Controller`. One file-scoped disable in `fields.tsx`, in the shape ADR-0031 §Consequences set for the generated primitives — name the rule at the point of change and say what forced it. The sibling finding needed no carve-out: the debounced input's re-sync moved from an effect to React's documented in-render adjustment, which is better code and not a workaround.
- **`shared` stays free of domain knowledge by erasing the row type exactly once.** ADR-0032 forbids `shared/grid` knowing what a staff member is, but a feature declaring `onSelect: (staff) => …` should still get a `StaffResource`. `AppGrid` is generic at its door and untyped on the inside, with one commented cast in between — so D3.7 and D3.8 pay nothing for the rule.

- **The filter loop was lossy, and the case it loses is `D3.8`'s.** `onColumnFiltersChange` rebuilds the whole filter set from the grid's own controls, and the first version then replaced `state.filters` wholesale — so a filter on a field no _column_ declares a control for was erased the moment the operator touched any column filter. Latent against the demo config, which routes everything through columns; it detonates on the users list, where "show deleted" is exactly such a filter arriving from a deep link. `withFilters` now takes the fields the grid owns and leaves the rest alone: a filter the grid did not put there is not the grid's to remove. Silently widening what someone is looking at is a worse failure than not filtering at all, which is why this was the one finding worth blocking `D3.7` on.
- **Two mechanisms were written, commented, and never read.** Cell renderers took `meta` as a closure baked into each `ColumnDef` while `useTable({ meta })` and the v9 `tableMeta` slot sat unused — so the columns memo depended on `meta`, and a caller passing an inline `meta={{ rowActions }}` rebuilt every column def on every render, which is the precise cost `table.options.meta` exists to avoid and the thing the D3.6 amendment cites as an improvement. Both are load-bearing now — renderers read `table.options.meta`, the pager reports through `setPageIndex`/`setPageSize` and takes its last page from `getPageCount()`. The general lesson is the one the review put plainly: where code and comments disagreed, **the comments were the ones that were wrong**, and a comment claiming a mechanism is in use is worth exactly as much as a test that it is.
- **Four smaller defects, each a plausible line that is wrong.** `{...config.props}` spread _after_ the wiring let a config declare `disabled: false` and defeat the submit lock from data. `initialValuesFor` seeded `""` for `checkbox` and `switch`, whose adapters test `value === true` — so the control rendered unchecked and submitted `""` into a `z.boolean()`; the demo config set both explicitly, so no test caught it. `getRowId` was spread away when absent, making TanStack fall back to the row _index_ and `key={row.id}` positional. And every row's action menu was called "Row actions", which is what the role-and-label discipline exists to prevent and what forced the test to index positionally; the label carries the row id now.

**Closed.** `entities/staff/staff.config.ts` declares the resource once — eight columns, six fields, `errorFields` — and `StaffFormInput` is the typed door onto it. `features/staff-manage` owns the five interactions (create, edit, administrative reset, sign-out-everywhere, delete) plus the row menu; `pages/staff` is ~100 lines of arrangement over `AppGrid` and one `useState`. What the step actually taught, most of it found by the two reviews rather than by the build:

- **The config-versus-contract tests ADR-0035 promised exist now, and they are the reason `email` filters on `like` rather than `eq`.** `filterable.email.value` is `emailSchema`, so an `eq` control would refuse every partial term an operator types; ADR-0014 exempts `like` from the field's value schema because a pattern is not a value of the column's type. Every `sortable`, every filter field-and-operator pair, and both form variants are run through the real `listStaffQuery` / `createStaffBody` / `updateStaffBody`. The negative controls matter as much: `roles` and `actions` are asserted **not** sortable, because a column that claims a sort it cannot have costs an operator a broken feature rather than a missing one.
- **`applyServerErrors` must be given the _variant's_ field names, not the resource's whole map — and the first version got it wrong.** It reads the list as "fields this form renders", which is what makes its guarantee true: a detail it cannot place falls through to `root.server` and is shown. Handed `status` on a create form, it called `setError` on a control that is not on screen, counted that as landed, and skipped the fallback — a submit that failed and said why to nobody, which is the exact failure the function's own header says every path avoids. Latent today (both bodies are strict, so the API cannot emit those paths) and it would have been copied twice more in `D3.8` and `D3.9`. ADR-0035 amended; regression test written.
- **A silent query channel is a promise about the surface, not about the query.** ADR-0034 makes queries silent because "a failed list has an error panel in the place the data would have been" — and the first grid shipped without one. `AppGrid` rendered its loading skeleton whenever it had no page, and the retry policy short-circuits a `4xx`, so a `403` from the segment's `authorize` mount resolved to five placeholder rows, forever, with no message. The one refusal the client deliberately does not pre-guess was therefore the one an operator could not see. `AppGrid` now takes the query's `error` and renders it with a retry; ADR-0034 is amended to make the panel a requirement rather than an assumption.
- **A password box holding somebody else's credential must not say `new-password`.** `new-password` beside `current-password`, or beside an `email`, is the signature browsers read as "this person is changing their own password" — and the "Save password?" prompt that follows would file the _subject's_ credential into the acting admin's password manager and sync it off the machine, which is precisely the reach ADR-0033 spends the whole session design avoiding. Both are `autoComplete: "off"` now, on the create form's initial password and the reset dialog's new password; only the actor's own re-presented password may claim `current-password`. **Residual:** `off` is a hint a browser may ignore on a password field. Closing it properly (separate `<form>` elements, or accepting the prompt as unavoidable) is a decision for the D3 close-out, and `/admin/users/:id/password` in `D3.8` asks the same question.
- **A credential in a mutation's _variables_ outlives the form that collected it.** TanStack Query keeps a settled mutation, variables included, for `gcTime` — five minutes by default — so `{ password, currentPassword }` survived `form.reset()` and the unmount, reachable from the mutation cache. Nothing reads it; the point is that nothing can. `gcTime: 0` on the two credential-carrying mutations, and ADR-0034 amended so the next one inherits the rule.
- **`useRevokeStaffSessions` invalidates nothing, and that is the invalidation rule holding rather than bending.** It writes `sessions`, a different aggregate that this app does not cache; the `staff` row is untouched. Its sibling `POST /:id/password` _does_ invalidate, because the password write sets `updatedAt`. The test ADR-0034 now records: does the response of any cached query change because of this write?
- **A field map that is not a resource's belongs to the feature that owns the interaction.** `{ password, currentPassword }` are two credentials belonging to two different people and neither is an attribute of a staff member — which is exactly why ADR-0027 makes that endpoint a sub-resource. `AppFormProvider` is keyed on a `FieldConfigMap` rather than a `ResourceConfig`, so no machinery was needed; what the map owes is the same contract test a resource config owes, and it has one. `FieldVariant` gained `action`, because rendering a password reset as `variant="create"` was a claim the vocabulary could not make.
- **The suite flaked in the gate and passed per file.** The first render in a file that mounts the whole route tree lands either side of Testing Library's one-second `findBy*` default under `vitest run`'s parallelism. `asyncUtilTimeout` is 5s and `testTimeout` 15s — the ceiling has to sit above the query's, or a genuine failure reports "Test timed out" instead of naming the element it could not find, which cost one debugging round here.

### 8. ~~Users resource~~ — **done 2026-08-20**

**ADRs:** [0035](../adr/0035-config-driven-resource-ui.md), [0028](../adr/0028-account-deletion.md), [0027](../adr/0027-credential-self-service-and-reset.md)

**Closed, and the bar held.** `git diff --stat 7e268a8..e041039 -- apps/admin/src/shared` was empty on the implementing commit — verified independently by `adr-reviewer` rather than asserted here. The step is one config, one thin page, and a feature slice of five dialogs; every difference between users and staff is declared as data and invisible in the page. 216 admin tests, 40 new.

The four differences, all of them the contract's rather than a style choice: `deletedAt` is a column, because deletion here is soft and `USER_STATUSES` has no `deleted` member — the timestamp is the only thing on the row that distinguishes disabled from deleted; names are nullable and seeded `null`; `status` appears in both variants because `createUserBody` takes one; and `roles` is a column but **not** a field, because `USER_ROLES` has one member in v1 and `userRolesSchema` requires at least one when the key is present, so a control could only ever be used to make the form invalid.

Three findings, each escalated to an ADR amendment rather than worked around, which is what this step's "where it is not thin" clause asked for:

- **A form validates the _request body_, not the form state — and until this step the machinery assumed they were the same object.** True for `createStaffBody`, where every field is required. False the moment one is optional: "the operator left this blank" has to arrive as an **absent key**, `""` is refused by `nameSchema.trim().min(1)`, `null` is refused because only the _update_ body is nullable, and no HTML control can hold absence. So a blank optional field was failing the resolver on a request that would never have been sent. The create dialog now converts state → body _before_ parsing and returns that as the resolver's values, so `handleSubmit`, the mutation variables and the wire carry one object. The conversion is config-driven both ways: `nullable` is why an emptied name arrives as `null`, and `component` is what makes an empty value mean _unanswered_ (a `select` at its placeholder, a `multiCheckbox` at `[]`) rather than _answered with empty_ — which is what lets a blank **required** box still fail with `emailSchema`'s own message instead of zod's complaint about a missing key. ADR-0035 amended; the converter stays local until a second create form needs it.
- **It is "Deleted only", not "Show deleted".** ADR-0035 had described this control as "a 'show deleted' toggle" since it was written, and that is not a request the endpoint can answer: `filter[deletedAt][null]=false` compiles to `isNotNull` (`core/http/list-query.ts`), and the users repository drops its default live-only scope as soon as a filter names `deletedAt` — so checking the box **replaces** the live accounts rather than adding to them. `deletedAt` is allow-listed for `null` alone, so "both" does not exist. The general lesson is the one worth keeping: **a label is the one part of a config no schema can check**, which is exactly why it was the part that stayed wrong through two ADRs and a `presence` doc comment. Amended in ADR-0035 and in `shared/resource/types.ts`.
- **The frame has to carry the pair of types.** Making the form's real shape honest (`CreateUserFormValues` ≠ `CreateUserBody`) needed `AppFormDialog` and `AppFormProvider` to take `<TValues, TSubmitted = TValues>`. Two-parameter signatures were the machinery assuming state and body coincide, and a caller with a transform could satisfy them only by casting `defaultValues` — asserting away the very distinction the transform exists to make. **This is the one `shared/` change in the step, and it is a follow-up to the review rather than part of the bar**: the implementing commit met the bar, and the fix is the machinery being wrong rather than this resource being special, which is precisely what the plan says to escalate. The default keeps every untransformed form unchanged.

What the reviews found, beyond the above:

- **The MSW `DELETE` handler was the one write that did not model `USER_DELETED`** — it re-stamped the timestamp and answered `204` where the service refuses a second delete with `409`. Both reviewers flagged it, and it mattered more than a normal mock gap: `useUserRowActions` deliberately leaves **Delete** enabled on a row carrying `deletedAt`, on the argument that the API is the enforcement point, so the mock was certifying the opposite of production on precisely the flow that argument rests on. Fixed, with a test.
- **The reset handler checked the subject before the actor**, inverting an order the service takes deliberately: verifying the actor's own password first means a wrong one answers the same `403` whether or not the id exists, and no argon2 hash is bought for a request about to be refused (ADR-0027, ADR-0020). The staff mock had it right and the two had drifted apart.
- **The config-versus-contract tests were weaker here than for staff, for a contract reason.** `createStaffBody` has no optional fields, so one strict parse proves both directions; `createUserBody` has four, so a config that dropped `status` would still pass. The required keys are now **derived from `createUserBody.shape`** rather than named by hand, so any future required field nobody built a control for is a red test.

**Deferred, with reasons — none of these is in this step's scope and all of them are now concrete:**

- **A `manager` sees write actions they cannot perform.** `/admin/users` is mounted `authorize("admin", "manager")` with the five writes narrowed to `admin`, so a manager legitimately reaches this page and gets a `403` from every row action and the create button. That is a decision, not an implementation detail, and inventing it inside a step whose bar was "no new machinery" would be the wrong way to make it. `D3.9` is the step that first puts the principal on screen; the ADR belongs at or before `D3.10`.

Nothing there decides what a field _is_: fields from the config, controls from the registry, validation from the contract.
- **`QueryError` came out of `AppGrid` on its second caller.** The profile is a silent query (ADR-0034) with no table to put a failure inside, and two hand-written apologies drift the moment one of them gains a retry.
- **No API change, so no Postman change.** All three endpoints have shipped since `D2.3`, and the collection already carries "My session survived my own password change" — which, with `staff-profile.int.test.ts`'s "rotates the password, keeps this session and ends the others", is where the server half of this step's _Done when_ is actually proven.

What the two reviews found, all of it addressed rather than recorded:

- **The profile write left the operator's own staff row stale, and the reason given for not fixing it was wrong.** `entities/profile` genuinely cannot reach `staffKeys` — ADR-0032 lets an entity import from `shared` and nowhere else — but a **feature** may import any entity slice, and the feature is already the layer that owns the interaction. `features/profile-manage/use-invalidate-own-staff-row.ts`, three lines, called after both writes. The general rule, amended into ADR-0034: **the mutation invalidates its own entity; the feature invalidates whatever else its interaction touched.**
- **"Only zod sets a detail `path`" was true and enforced by nothing.** Both reviewers landed on it independently, and the security one was right that a doc block is not an invariant: `AppError` takes arbitrary `details`, and one that grew a path colliding with a rendered field name would have reached an operator as raw copy, past the ADR-0034 catalogue. `applyServerErrors` now gates the verbatim branch on `error.code === "VALIDATION_ERROR"`, with the negative case tested. The one residual the argument still does not cover is written down rather than glossed: a form whose state is not its body (the D3.8 transform) can be handed zod's own type message for a key its controls never held.
- **`gcTime: 0` was a security property written three times and observable nowhere.** Consolidated to `shared/api/credential-mutation.ts` — the layer every entity may reach, since ADR-0032 stops them sharing one entity's copy — and `renderWithProviders` now returns the query client, so the test asserts the mutation cache is empty once the dialog has settled. A property no test can see is a comment.
- **A change-password form with no username gives a password manager nothing to key the update on.** With two saved credentials for one origin — a personal account and a break-glass one is normal here — managers update the wrong entry or save a duplicate, and the operator ends up with a vault entry that no longer opens the account. A hidden `autoComplete="username"` input carrying the principal's email, as `login-form` already does with a visible one.
- **The principal writer was wider than the app it serves.** Now typed to `StaffPrincipalResource`, and it refuses to write when the store holds no access token — logout lives in the sidebar, outside the form's `fieldset`, so ending the session mid-save was reachable and the `onSuccess` would have written the operator's name and address back into a store that had just been cleared.
- **The page had hand-rolled the status and roles badges, and they had already drifted:** `invited` read destructive on the profile and secondary in the grid. `StatusBadge` and `RolesList` are resource-agnostic by ADR-0035's own rule, so they take a `value`-only prop type now and the page uses them. ADR-0035 amended: resource-agnostic also means usable off the grid.
- **The mock recorded a refused change-password as one the endpoint accepted.** `seen.changed` now means accepted and `seen.refused` means refused — the D3.8 fidelity lesson, in the direction that would have let an assertion pass on a `403`.
- **ADR-0032's slice tree still said `profile-edit` and listed no `entities/profile`.** Amended to what shipped, including the note that a singleton entity is still an entity.

**Verified:** `pnpm lint && pnpm check-types && pnpm test` green across the workspace, `format:check` clean, admin's 260 tests run three times without a flake. Reviewed by `adr-reviewer` (1 MAJOR, 5 MINOR) and `security-reviewer` (1 MEDIUM, 5 LOW); every finding is addressed above or carried below.

The client half is covered by tests and the server half by the integration tier and newman; the walk itself is D3 acceptance steps 4–5, on a fresh clone, which is where it belongs.

**Carried, with reasons:** the `PATCH /profile` handler models no `404` — the branch exists in the service (the row can be deleted while a session lives) and there is no UI flow that reaches it, so a mock for it would be untested code; and the store's `roles` now come from the database while authorization runs off the token's claims, which is stated in ADR-0033 and is a difference with no consequence until something gates on them.

**Two decisions this step was left to make, and it made them differently.**

- **The client-side authorization vocabulary is written and assigned to D4.** `D3.8` found a `manager` being offered five writes the API refuses on `/admin/users`, and handed the decision here. It is [ADR-0042](../adr/0042-client-side-authorization.md), `proposed`, its index cell reading `D4 (not yet built)` — the state ADR-0025 rule 3 exists for. The distinction it turns on belongs in this file too, because it is what makes the decision safe: the API's authorization has a **static** half (mount-level role guards — a table of resource × action → roles that depends on nothing but the principal) and a **dynamic** half (the rank rule, the last super admin, self-targeting — state the client does not hold). D3.7's rule that the client does not pre-guess a refusal is not overturned, it is given its scope: the static half may be answered, the dynamic half never. It lands in `D4.3` beside ADR-0038's capabilities, because the two are halves of one question — a capability says _this surface offers the action_, `can()` says _this role may perform it_ — and shipping either alone rebuilds the defect.

  The security review of the ADR changed its shape in one way worth carrying forward, because it makes the fix **smaller** than D3.8's wording promised. Three of the six actions are incident-containment controls — reset password, sign out everywhere, and disabling, which today lives inside the edit form — and hiding one of those is silent, with no error, at the moment an operator most needs to find it. So `can()` never hides them; they render, and the server answers. A `manager` on `/admin/users` will lose Create and Delete and keep the other three, still meeting a `403`. That is a deliberate trade of the D3.8 affordance complaint against the worse failure, and the day disabling gets an affordance of its own is the day to revisit which side Edit is on.

- **The soft-deleted PII gap is recorded and deliberately not decided.** `D3.8` made deleted accounts — email and both names — browsable in one click by anybody with `manager` or above, and asked for an ADR before D3 ships. Writing one here would mean choosing a retention window, a redaction shape and whether restore exists, from a repository with no product input; and ADR-0028 is frozen, so it is a supersession rather than an amendment either way. What this step could usefully contribute it did: the entry in the index's _Planned_ list is sharpened from a storage question into an access one, which is what changed.

**The `autoComplete` residual from `D3.7` is closed as accepted, not fixed.** `off` on a password box holding somebody else's credential is a hint a browser may ignore, and both candidate fixes are worse: separate `<form>` elements inside one dialog break the submit lock and the RHF context that make the dialog what it is, and no attribute exists meaning "this credential is not the user's". What `D3.9` added is the half that actually mattered — a `username` anchor on the _self-service_ form, so a password manager keys the update to the right account instead of guessing. The residual stands, and the operational instruction is one line: an administrator resetting somebody else's password may be prompted to save it, and should decline.

**ADR-0036 gained the enforcement `D3.8` asked for.** Derivation from contracts bounds the _shapes_; three findings across `D3.8` and `D3.9` were the _refusals_ drifting, every one of them in the permissive direction, because a handler gets written from the happy path a test needed. A handler that models a refusal now names the service function it mirrors, in a comment at the branch — a naming requirement rather than a machine check, since nothing in `apps/admin` may import `apps/api`, and it puts the burden where the drift happens.

## Definition of done

D3 is closed when every step above is closed and this checklist passes on a fresh clone:

1. `pnpm i && cp .env.example .env && pnpm docker:up && pnpm db:setup && pnpm db:seed -- --dev` — Postgres healthy, fixtures seeded.
2. `pnpm lint && pnpm check-types` clean, and `git status` clean afterwards.
3. `pnpm test` green, twice, uncached both times for the API; `pnpm test:unit` twice hits cache the second time — admin's suites among the cached.
4. `pnpm dev --filter api` and `pnpm dev --filter admin`; sign in as the seeded super admin at `http://localhost:3001`.
5. The walk: staff grid pages/sorts from the URL → create a staff member → edit → reset their password re-presenting your own → delete; users grid → edit → soft-delete → the row stays listed as deleted → re-register the address; profile → change password → a second browser context is signed out; every mutation toasts, every form locks while pending.
6. Reload mid-session — the app bootstraps from the cookie and stays signed in. `pnpm test:postman` green, untouched by the frontend.

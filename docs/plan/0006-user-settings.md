# D6 — User settings

- Status: **in progress**, opened 2026-08-22 — the day D5 shipped ([ADR-0025](../adr/0025-deliverables.md) rule 5: one at a time). The amendment window is open on **ADR-0045 only**; ADRs 0001–0044 stay frozen.
- Steps: `D6.1` – `D6.4`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: server-persisted per-account settings — **theme, locale, and per-grid preferences** — as one new API module exposed on **both** population segments, and the admin app consuming it. The theme stops being a device fact and becomes an account fact; the grid arrangement an operator built on one machine follows them to the next; the locale slot exists before D7 has anything to put in it. **The first new API module since D2** — `apps/api`, `packages/db`, `packages/contracts` and `apps/admin` all move, which makes this the first deliverable since D2 whose gate is a target on every tier rather than a regression check on most of them.

## Why this is first after the grid deliverables

Three reasons, in order of weight:

1. **ADR-0041 pre-paid the design.** The grid-preferences store ships behind a three-function `PreferenceStorage` adapter precisely so that "a server-backed user-settings adapter slots in later without touching the store or AppGrid" — and its §Consequences names the claim this deliverable holds it to: _"when it lands, the store and AppGrid do not change."_ Neither D4's later steps nor D5 touched the adapter, so the seam is the freshest contract in the repository, and building on it is the cheapest possible falsification of that claim.
2. **D7 (localization) needs a locale to persist.** A locale switch that forgets itself on the next device is a toy; sequencing settings first means D7 wires into a slot that already exists instead of building persistence as a side quest.
3. **It is the smallest of the planned deliverables** — one module, two mounts, no new app, no new package — and it re-exercises `/new-api-module` and the whole ADR-0009 layering on a body of code that has only been maintained, not extended, for three deliverables.

**Both populations get settings from day one.** Taken as the default when the deliverable was scoped and standing at opening: the customer app (D8) inherits account-portable theme and locale for free, and one settings model beats two arriving a deliverable apart. Reversing it later costs exactly one mount in `user.router.ts`.

Everything here builds on decisions that stand unchanged: two populations as separate aggregates in separate tables, free to grow attributes without adding nullable columns to each other ([ADR-0017](../adr/0017-principals-and-roles.md)) — which is exactly why the settings tables come in a pair; the layering, envelope and error model every module follows ([ADR-0009](../adr/0009-functional-layering.md), [ADR-0012](../adr/0012-response-envelope.md), [ADR-0013](../adr/0013-error-model.md)); enums declared once in `@repo/contracts` and consumed by `pgEnum` and zod ([ADR-0023](../adr/0023-shared-contracts-package.md)); the query cache, invalidation and notification rules ([ADR-0043](../adr/0043-readable-list-search-params.md)); `localStorage` permitted for non-credential display state and nothing else ([ADR-0033](../adr/0033-browser-api-client-and-session.md)); and the adapter seam and versioned, bounded value of [ADR-0041](../adr/0041-grid-preferences.md).

**Gate.** [ADR-0045](../adr/0045-user-settings.md) was written `proposed`, and opening this deliverable did not change that. It was **accepted 2026-08-22**, at the head of `D6.1` (ADR-0025 rule 3) — the per-step acceptance D4 and D5 ran on — and governs `D6.1`–`D6.3`; `D6.4` names no ADR of its own. It is additive: nothing in it supersedes a frozen record, and ADR-0041 anticipated it by name.

Each step names the ADRs that govern it. Read them before implementing — they carry the reasoning, this file carries the work. Every step ends green on `pnpm lint && pnpm check-types && pnpm test` and a conventional commit; `pnpm check` is the loop inside a step.

Five things the step found, recorded rather than folded into "done":

**The re-export is what keeps `app-grid.tsx` at zero diff.** `MIN_COLUMN_WIDTH` and `MAX_COLUMN_WIDTH` moved to contracts with the schema, and `app-grid.tsx` imports both from `shared/grid/preferences` — so the honest choice was between editing a second file above the seam and re-exporting the two names from the module that always published them. Re-exporting, because the ADR-0041 claim `D6.3` is scheduled to falsify is about files above the seam changing, and a mechanical import rewrite would have spent the claim on a rename. `git diff` on `app-grid.tsx` is empty; `preferences.ts` shows the import, the re-export and the deleted schema body, which is definition-of-done item 2 already half-satisfied.

**`@repo/db`'s root barrel had to grow, and the integration suite is what said so.** `src/schema/index.ts` alone is not the package's surface — `src/index.ts` re-exports each table by name and `src/types.ts` derives its row pair — so the two tables were invisible to anything importing `@repo/db` until both were updated. The schema integration test failed with `Cannot read properties of undefined`, not with a type error, because it imports through the root the way a repository will. `TRUNCATED_TABLES` in `src/testing.ts` was the third place: `cascade` on `staff` and `users` already empties the pair, so nothing was broken — but that list is read as “every application table”, and a table cleaned only as a side effect of another one's constraint is a leak waiting for the day that constraint changes, so both are named.

**Drizzle's generated names are not the repository's names, in two places.** `drizzle-kit generate` proposed `0003_sturdy_proteus.sql`, against three predecessors named for what they do; regenerated with `--name settings`. And the first draft's unnamed `.unique()` produced `staff_settings_staffId_unique` — the one camelCase identifier in a snake_case database, which is precisely the trap `sessions.ts` documents for `sessions_refresh_token_hash_unique`. Both were caught by reading the generated SQL, which is the whole reason ADR-0008 makes generate-then-review a step rather than a formality.

**The migration got its own assertions at the schema tier, seven of them.** `packages/db/src/__tests__/schema.int.test.ts` goes from 37 to 44: the two exact-list assertions — every table, every enum with its label order — had to learn six new names, which is those pins doing their job, and a `migration 0003` block covers the defaults, a `jsonb` round trip, one row per principal in each population, a staff and a user sharing an address holding separate rows, the hard-delete cascade, a soft-deleted user keeping theirs, and an orphan being refused outright. The cascade is `D6.2`'s to assert through the API as well; asserting it here first is cheap and puts the claim next to the constraint that makes it true.

**A hazard `D6.2` does not have to defend against, checked rather than assumed.** `mergeGrids` deletes on `null`, so it has to assign per key rather than spread — and `merged["__proto__"] = entry` sets the merged object's prototype instead of adding an entry to it. `JSON.parse('{"__proto__": …}')` produces an **own** property, so the key survives transport as an ordinary string and a bounded `z.string().min(1).max(64)` has no reason to refuse it. The step went as far as adding a reserved-id refusal before measuring what actually happens: `z.record` drops the key outright, the parsed body has no such entry, and the result's prototype is untouched — while a refinement on the key schema never even runs for that name (it fires for `constructor` and `prototype`, neither of which is dangerous to assign). The guard was removed and replaced by a test pinning the behaviour, because a defence against something that cannot happen is a defence nobody maintains, and the property `D6.2`'s merge relies on should fail loudly if a zod upgrade ever changes it.

**ADR-0045 amended twice (D6.1)**, both on questions the record left to whoever wrote the schema: an empty `PATCH` body is accepted rather than refused, because the caller is a coalescing writer and not a person; and "moved intact" includes the moved schema staying `z.object`, since a strict _entry_ would discard a whole arrangement over one field a newer client added, which is the opposite of the version tolerance the same section asks for.

### 2. The `settings` module on both segments

**ADRs:** [0045](../adr/0045-user-settings.md), [0009](../adr/0009-functional-layering.md), [0010](../adr/0010-request-context.md), [0011](../adr/0011-validation.md), [0012](../adr/0012-response-envelope.md), [0015](../adr/0015-route-segments.md), [0019](../adr/0019-authorization.md), [0021](../adr/0021-testing-strategy.md), [0028](../adr/0028-account-deletion.md)

`apps/api/src/modules/settings` via `/new-api-module`: routes → controller → service → repository, one controller and one service serving both mounts, the service selecting the repository's `staff` or `user` half — same signatures over the two tables — by `ctx.principal`'s population. `GET /settings` returns the defaults when no row exists — never a `404`, a principal always has settings. `PATCH /settings` is `.strict()` and partial: `theme` and `locale` replace, `grids` merges per key, and the row is upserted. Mounted beside `/profile` on both `admin.router.ts` and `user.router.ts`, under `authenticate` and with no `authorize`, for the reason both routers already give for `/profile`. The hard-delete paths (ADR-0028) need no settings code: the foreign key cascades, which is the constraint `sessions` could not have; a soft-deleted user keeps its row because its `users` row stays. The integration test asserts the cascade rather than trusting it. Unit tests over a fake repository; integration tests on both segments — defaults, upsert, per-key merge and delete, every bound, a second principal's row invisible, `401` without a session; Postman requests on both segments via `/postman-sync`.

**Done when:** both segments answer `GET` and `PATCH /settings` per ADR-0045; a staff account and a user account sharing an email address read and write different rows; a grid entry above the bounds is a `VALIDATION_ERROR` with its path; hard-deleting a staff account leaves no settings row; `pnpm test` green on both tiers, `pnpm test:postman` green with the new requests, and the collection's previous counts otherwise unchanged.

**Closed.** `apps/api/src/modules/settings/` in ADR-0009's fixed shape — `routes` (one factory, called once per segment with its population), `controller` (one, for both mounts: neither handler takes an id, so there is nothing a second factory would withhold), `service` (`tableFor(ctx)`, the pure `mergeGrids`/`applyPatch`, and the merged-row bound), `repository` (two halves over one signature, built from a `TableSpec`), `schemas`, `mapper`, `index` — wired in `core/container.ts` and mounted beside `/profile` on both segment routers, under `authenticate` and with no `authorize`. Fifteen unit tests, thirty-two integration tests parameterised by population, and eighteen Postman requests. There is no `settings.errors.ts`, as ADR-0045 predicted: nothing in this module can fail in a way `VALIDATION_ERROR` does not already name.

Five things the step found:

**ADR-0045's concurrency promise was false for the first write, and the fix is one statement.** §Endpoints reads the row `FOR UPDATE` — _“or finds none”_ — and upserts, then promises that two tabs patching different grids “serialise on the row and both land”. `select … for update` locks the rows it **finds**, so a principal's first-ever `PATCH` locks nothing: two of them merge against an empty row and the second erases the first's grids, which is the exact outcome per-key merging exists to prevent. Inserting the defaults row with `on conflict do nothing` **before** the locking read closes it — Postgres makes a conflicting insert wait for the uncommitted one, so the lock always finds exactly one row — and needs no retry loop and no advisory lock. `findForUpdate` became `lockForUpdate` to stop the name claiming otherwise, and ADR-0045 is amended.

**One type cannot be written twice when it is on both sides of the wire.** `GridPreferencesV1` was hand-written in `D6.1` with `readonly` members, like every other resource type here. It is also the value a `PATCH` body carries, and zod infers mutable arrays — so a client could not send back a value it had just been given, and `D6.1`'s test that pinned the two “agreeing” only ever checked the direction that happened to work. The service's unit tests failed on the other direction within minutes of being written. It is now `z.infer<typeof gridPreferencesSchema>`, with `Readonly` applied where the type is used. The same argument produced `DEFAULT_THEME` and `DEFAULT_LOCALE` in contracts: the column default and the mapper's no-row answer were two spellings of one fact, and a drift between them would have been invisible — both paths answer a valid resource, and only the values differ.

**Drizzle's `column.name` is the physical name, and TypeScript will not say so.** The repository's two halves are built from a `TableSpec`, and the first draft inserted with `.values({ [principalColumn.name]: principalId })` — which compiles, because a computed key widens to `string`, and which writes `staff_id` where `.values()` wants the TypeScript property `staffId`. The row would have been inserted with no principal at all. The spec now carries a `newRow` closure per half, which cannot be spelled wrongly without failing to compile.

**Two of this step's own integration tests were wrong before they were right, and the second kind is the dangerous one.** The ceiling test built fifty grids into a row the tests above it had already put grids in, so it failed loudly — fine. The “keeps a staff member and a customer with the same address apart” test generated _one_ address, used it for the staff account and compared against the **seeded** customer: two different addresses, dressed as one. It failed only by accident (the seeded customer's theme had already been set by the parameterised block), and had it passed it would have proved that different accounts differ. It now creates both sides at the same address, which is the claim ADR-0017 actually makes.

**Postman went from 84 requests and 260 assertions to 102 and 314**, with all 84 previous requests byte-identical — verified by comparing the parsed collections, not by reading the diff, since inserting a folder rewrites the array and git shows the shift as deletions. The two `Settings` folders are the same nine requests twice, and they are the first in the collection that act on an account the run does not create: only a hard delete removes a settings row, so each folder clears the two grid ids it uses on the way in as well as on the way out. `pnpm test:postman` green **twice in a row** against the same database, which is what makes that claim real.

**ADR-0045 amended four times (D6.2)**: the create-then-lock sequence, the derived `GridPreferencesV1`, the single declaration of the defaults, and `no-store` on the router.

Six things the step found:

**The first-sync rule cannot be a sweep, because the seam has nothing to sweep.** ADR-0045 says "when the settings query resolves, for each grid key" — and a sweep needs the local cache's key list. `PreferenceStorage` is `read`, `write`, `remove`, and none of them enumerates; adding a fourth function would have widened the interface ADR-0041 cut, on the one step scheduled to prove it did not need widening. So adoption is answered where it is asked: the first `read` of a key the mirror cannot answer consults the cache, adopts a well-formed entry and queues it, once per grid id per session. Same outcome for every grid an operator opens, and strictly more conservative for one they never do — a device that has never shown the users grid does not push its stale arrangement of it. The "well-formed" is checked rather than assumed: an entry the schema refuses stays on the device and is never uploaded, so a corrupt local cache cannot become the account's corruption.

**The writer cannot hold the mutation, and React's lint said so before the code ran.** ADR-0045's sketch builds `createSettingsWriter({ patch })`, and `patch` is `useUpdateSettings().mutateAsync` — a render-time value belonging to a component. Captured at construction it is whichever one was first; kept fresh in a ref, `react-hooks/refs` refuses the read outright, and it is right to — a value read during render is a value that does not cause the render. The writer now takes no sender at all and exposes `subscribe(send)`, the observable shape ADR-0033's session store established and every store here has copied, installed from an effect and returning its remover. One consequence had to be designed rather than found later: a grid can be adopted in the render _before_ that effect runs, so a flush with no subscriber keeps its pending payload rather than dropping it, and `subscribe` flushes on arrival. There is a test for exactly that ordering.

**"A settled query" has a reading that hangs the login screen forever.** The natural spelling of the gate is `isSuccess || isError`, and an anonymous visitor reaches neither: `enabled: false` leaves a query `isPending` with an idle `fetchStatus` for as long as the app runs. The gate is therefore "nothing is in flight for us to wait on". The same paragraph produced a second pin: the query carries `staleTime: Infinity` and `refetchOnWindowFocus: false` against the app's defaults of thirty seconds and refetch-on-focus, because the mirror is the working copy and a background refetch on focus would re-seed it mid-session — a column snapping back under an operator who has just dragged it.

**The theme has been an account fact nobody could change.** `applyTheme` and `preferredTheme` ship since `D3.1` and are called from `main.tsx` and from **nowhere else**; the file's own header deferred a toggle to `D3.9` "once there is a header to put it in", and `D3.9` built the header and not the toggle. "Writes both on toggle" therefore had no toggle to write from, and §Definition of done item 3 — two browsers, one account — had no way to be walked. `features/theme` adds the control as a three-option radio group in the account menu, built from the `THEMES` tuple so a value D7 appends cannot leave a control behind. That placement is what moved `theme.ts`: a feature and a widget may not import from `app` (ADR-0032), so the pure half is now `shared/theme` and the _provider_ is still `app/providers`', rendered by `SettingsProvider`. Two names — `DropdownMenuRadioGroup`, `DropdownMenuRadioItem` — join the `shared/ui` door, which is the visible line in a diff ADR-0031 asks for; no new component, no new dependency.

**One property was asserted in the wrong direction first, and the corrected version is the interesting one.** A local entry the schema refuses was expected to make `adapter.read` answer `null`. It does not, and should not: the writer declines to adopt it, and the adapter then falls through to the local cache exactly as it does for any key it does not own — so the device keeps its own corruption and the _store_ discards it on read, which is the guard ADR-0041's `D4.5` amendment made the store's own. The test now pins both halves: the account never hears about it, and the grid renders at config defaults. Asserting `null` would have pinned a behaviour where a corrupt cache silently stopped being readable at all.

**A disabled query is not an emptied one, and the signed-out claim was decided by the wrong fact.** The provider read `const account = settings.data`, so "is there an account?" was answered by the query cache rather than by the session. `useSettings({ enabled: isAuthenticated })` only stops a _fetch_ on logout; the entry it already has stays, and this step's own `staleTime: Infinity` guarantees it is never refetched — so after a sign-out in the same tab the previous principal's row was still the answer, and both branches that hang off it kept running on the login screen: the server adapter stayed under `PreferenceStorageProvider`, and `writer.setTheme` stayed as the theme's publisher. ADR-0045 §The server adapter says the opposite in one sentence — "Signed out, the app uses the local adapter alone, unchanged" — so this is the code being wrong, not the record: `const account = isAuthenticated ? settings.data : undefined` restores it and **no amendment is owed**. Found by `review-step`, not by the eight provider tests, because every one of them rendered a session that never ended; the ninth ends one and pins both halves — the grid falls back to the device entry, and a toggle afterwards writes `localStorage` and sends nothing.

**ADR-0045 amended five times (D6.3)**: the per-key first sync, the subscribed writer, the gate's spelling with the query's two pins, the diff item 2 actually gets, and the theme's missing control with the `shared/theme` move it forced.

**Not walked — pending operator acceptance.** Everything above is jsdom and MSW. §Definition of done item 3 in a real browser (two browsers, one account, a width changed in one and reloaded in the other), item 4's second half (a row hand-edited to garbage in Postgres rendering the grid at config defaults), the pre-paint apply of a `"system"` theme against a real `prefers-color-scheme`, and the coalescing window under a real pointer drag are all `D6.4`'s to walk. `apps/customer` does not exist, so `/user/settings` has no client and this step built none.

## Definition of done

1. **A fresh clone** runs `pnpm i`, `pnpm docker:up`, `pnpm db:setup`, `pnpm db:seed -- --dev`, `pnpm dev --filter api` and `pnpm dev --filter admin`, and the `settings` migration is among those applied.
2. **The seam held.** `git diff D5..HEAD -- apps/admin/src/shared/grid/preferences.ts apps/admin/src/shared/grid/app-grid.tsx` shows the schema import and nothing else.
3. **One account, two browsers.** Sign in as the same staff account in a second browser: the first browser's theme and column arrangement are there. Change a width in the second; reload the first; it followed.
4. **The defaults are the floor.** A `PATCH` with a hand-made grid entry outside the bounds is refused with a `VALIDATION_ERROR` naming the path; a row edited in the database to garbage renders the grid at config defaults with no toast.
5. **Both segments.** `pnpm test:postman` green, with `GET` and `PATCH /settings` on `admin` and `user` among the requests and every previous request's assertions unchanged.
6. **Green and cached.** `pnpm lint && pnpm check-types && pnpm test` green; `pnpm test:unit` twice, the second `FULL TURBO`; `pnpm format:check` clean; a clean tree afterwards.

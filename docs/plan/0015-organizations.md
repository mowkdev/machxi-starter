## Goal

Every user belongs to organizations and every tenant-owned table is scoped by one; staff stay above all of them. Every path that creates a user creates a personal organization in the same transaction, so no query anywhere has a "no organization" branch; a user may belong to many, each membership with a role, and a second member arrives by invitation — the flow without the email. The active organization is in the URL and a membership guard resolves it per request. The admin app manages organizations as a resource, the customer app switches between them and gains the self-service sign-up ADR-0055 §5 deferred. Row-level security is designed in and not enabled.

## Constraints

- **`security-reviewer` runs on every step**, beside the ordinary bounded pass — this is the feature where a missed filter is a cross-tenant leak. A BLOCKER stops the step.
- **Shared schema; `organization_id not null` and a tenant-led composite index per order on every tenant-owned table** (ADR-0067 §1). The bare `(column, id)` pairs the D14.11 template declared beside them are dropped, and `indexCoverage` learns the scope — the decision ADR-0063 §3 left to this deliverable.
- **Staff are never members** (ADR-0067 §3); `/admin/organizations` mounts `authorize("admin", "manager")` with writes narrowed to `admin`, exactly as `/admin/users` does (ADR-0019 as carried by 0067).
- **Resolution is the URL** — `/api/v1/user/orgs/:orgId/...` and `requireMembership(...roles)`; a non-member is `404`, never `403` (ADR-0067 §4). Self-scoped routes stay outside the prefix.
- **Unscoped is a compile error** (ADR-0067 §5): a tenant-owned repository takes the organization id as a required parameter, and the hand-maintained tenant-table list is checked by the enumeration test of ADR-0061 §4, negative case included.
- **The exclusion list grows** (ADR-0057 §5 as carried by 0067 §8): membership and ownership writes, organization deletion and leaving, and inviting are refused under impersonation with `AUTH_IMPERSONATION_REFUSED`; name and slug edits stay allowed and audited.
- **Nothing here changes the envelope, the error shape, the auth flows or the session model** (ADR-0012, ADR-0013, ADR-0018 as carried by ADR-0057). Registration's response is login's, as it always was.
- **Every list is ADR-0014's language as carried by ADR-0060**: allow-lists with their indexes in the same step, `count` honoured, the `::text` cast on searched columns.
- **The gate** — `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check` (`CLAUDE.md` §Commands) — green at the end of every step; new endpoints get integration tests and Postman; a new variable means a schema entry and `.env.example`.
- **The window**: ADR-0067 may be amended in place, labelled, while this row is `in progress` ([the ledger](README.md#the-window)). Every earlier record it touches takes a **delta** and stands for everything not named.

## Decisions taken at scoping (operator, 2026-09-04)

Offered as options with a recommendation, the operator choosing; each is written into ADR-0067 rather than left here.

- **Indexes on a tenant-owned table are tenant-led only, and the checker learns the scope** (ADR-0067 §1, resolving ADR-0063 §3's recorded tension). `indexCoverage` gains a `scopedBy` option: on a table scoped by `organization_id`, an index that leads with the scope covers its second column. One change in `@repo/db/testing` with its own negative case; the template drops the bare set.
- **The personal organization is created on every path, backfilled, and carries two invariants** (ADR-0067 §2): `register`, `POST /admin/users` and the seeders create it in their own transaction; the migration backfills one per existing user; an organization always has at least one owner, and a personal organization cannot be deleted on its own — it is soft-deleted inside the user's own deletion transaction.
- **Membership and ownership writes are refused under impersonation** (ADR-0067 §8, a delta on ADR-0057 §5). Not the recommendation's alternative — "allow everything, audited" — because an operator could otherwise grant a third party `owner` of a customer's organization, which is takeover of the tenant rather than the account.
- **A second member arrives by the invitation flow, minus delivery** (ADR-0067 §2) — chosen over the recommendation (staff add members; the user side only manages). Invitations are created by email on the user segment, listed by the invitee, accepted or declined; **no email is sent**, and the mail deliverable adds the send at one marked call. Enumeration-safe by construction: an invitation names an address, not an account, so the response is identical whether or not the address has one (ADR-0020 §Enumeration), and acceptance is by the authenticated account whose email matches.

## Not in D15

Invitations' **delivery** (the send through ADR-0066 §1's port, the token link a non-account holder can accept, the templates — the mail flows deliverable, which finds one marked call to fill); a sweep for expired invitation rows (a small table; the day it is not, it joins `db:sessions:prune`'s batched shape); billing, plans, SSO, per-organization settings beyond name and slug; transferring a personal organization to `team`; **enabling row-level security** — its shape is fixed in ADR-0067 §5 and it is a migration and a middleware once these tables exist; email verification (registration still creates `active` accounts, as ADR-0018 decided).

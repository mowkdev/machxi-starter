# Deliverables

The ledger of staged work in this repository. A **deliverable** is the unit defined by [ADR-0025](../adr/0025-deliverables.md): it is what a plan file describes, what a step number is scoped to, and what opens and closes an [ADR-0024](../adr/0024-adr-lifecycle.md) amendment window.

Read this file first; open a plan only when you are working in it.

Tag prefix: `starter`

`/ship` tags each shipped deliverable `<prefix>-D<n>` from the line above, and `pnpm docs:check` refuses a ledger without it. The namespace is this repository's: a fork's `/bootstrap` writes the fork's own, so a tag fetched from the starter never meets one of the fork's ([ADR-0081](../adr/0081-build-versions.md) §5).

## Rules

- **More than one deliverable may be in progress when their records are disjoint** ([ADR-0079](../adr/0079-parallel-lanes.md), a delta on ADR-0025 rule 5): no record — written, superseded or amended in place — belongs to two open deliverables, each of which is a **lane**, and at most one open lane adds migrations. [The window](#the-window) names every open lane with its records; a deliverable whose records overlap an open lane's waits for that lane to ship.
- **Steps are written `D<n>.<step>`** — `D1.7`, `D2.3`. Inside a plan file they are numbered plainly; the prefix is how they are cited from the ADR index and from commits.
- **An ADR may be amended in place only while its deliverable is in progress** (ADR-0025 rule 2, as carried by [ADR-0065](../adr/0065-starter-lifecycle.md)). Which windows are open, which records are frozen and which supersession is a delta is stated in [The window](#the-window) below and nowhere else — every rule file, skill and agent links to that section rather than restating it.
- **A deliverable closes on an executable acceptance checklist** (ADR-0025 rule 4), the ledger row moves to `shipped YYYY-MM-DD`, and the amendment window shuts. All three or it is not closed.

## The window

**One place to be right; nowhere else to be wrong.** This is the only section in the repository that states which amendment window is open, which records are frozen, and which supersession is a delta ([ADR-0065](../adr/0065-starter-lifecycle.md) §5, a delta on [ADR-0025](../adr/0025-deliverables.md) for _where_ that state is written). `CLAUDE.md`, every file under `.claude/`, [`docs/README.md`](../README.md) and the generated digests in [`docs/rules/`](../rules/) link here instead of repeating it; when the open lanes as this section states them — the lane files and the block generated from them — and one of them disagree, the lane files are right and the other is the defect. [The history after this section](#the-windows-history-frozen-at-d344) is a record of earlier states and says nothing in force.

- **A window belongs to a deliverable this ledger's table marks `in progress`, and to its records only.** Those may be amended in place, labelled; every other record changes by supersession (ADR-0025 rule 2). More than one window may be open — one per lane, their records disjoint ([ADR-0079](../adr/0079-parallel-lanes.md) §1) — and opening a lane reopens nothing.
- **The open lanes** are files, one each, under [`lanes/`](lanes/): `lanes/D<n>.md`, in one shape — the deliverable and its plan, the date it opened, the branch it builds on, its tier (`package`, `api` or `schema`, as its plan's `- Tier:` line names it), whether it adds migrations (`schema: yes`, at most one lane, and that lane's tier is `schema`; ADR-0079 §3), and its records — the ones it writes, every parent they supersede, and every record it amends in place ([ADR-0082](../adr/0082-lanes-on-one-machine-and-one-main.md) §4 and §5, a delta on ADR-0079 §2). `/scope` creates the file when a lane opens and `/ship` removes it when the lane ships. ## Executing a step

`/step` builds the next unchecked step of an in-progress deliverable (`/step D8.3` for a specific one; `/step D<n>` names the lane when more than one row is in progress, and a bare call is refused then): it reads the last push's `gate.yml` run and fixes forward if it is red, reads the step, reads the ADRs it names, implements, ends green on the step check, takes one bounded diff review, and pushes one commit to the lane's branch and pull request, never to `main` ([ADR-0050](../adr/0050-adr-lifecycle-and-verification.md) as carried by [ADR-0082](../adr/0082-lanes-on-one-machine-and-one-main.md) §1–§2); `main` takes the lane when `/ship` merges the pull request. Every step below names the ADRs that govern it precisely so that it can be handed to an agent without further context.

**Revised 2026-09-30 while `proposed`, before opening, on the operator's decision.** The operator reported the bottleneck the review had named from the inside: agents re-ran the whole gate every time `main` moved, so a faster lane's landings kept restarting a slower lane's gate. - One review per step. No close-out step in any plan `/scope` writes after this; D34 keeps its own as the last.
- The shape is the same in a cloud session and in a worktree: the branch, the pull request, the step check, the lane's database; the lock is the machine's own, and a session that cannot read CI state says so and is caught at ship.

So the server was interrogated before it was trusted — `http://localhost:3001/src/shared/theme/index.ts` resolves to `packages/app-services/src/index.ts`, which is proof the running app is the extracted one rather than a survivor. Then: the shell, the account menu in its header and the dark theme (`@repo/app-services`); `/staff?limit=10&sort=-lastName&filter[status]=active` answering **1–7 of 7** correctly sorted with the hot filter engaged, sticky header and static pager (`@repo/grid`, `@repo/resource`, `@repo/api-client` — D5's headline property, re-run); the row-action menu offering all four actions to a `super_admin` (`can()` through the door); the edit dialog over `RecordSurface` with its four field kinds, its breadcrumb carrying the record label, and **Cancel** — the one key `D9.5` moved from the app's `common` into `@repo/form`'s namespace — rendering correctly; Escape closing it and the list state returning through ADR-0044's history carrier; and the users grid, a second resource config, scrolling inside its own pane. **No console error or warning on any of it.**

The single most fragile thing the extraction built was checked directly rather than by looking at a screen: `@repo/grid`'s and `@repo/form`'s `loadCatalogue("lv")` were called in the running page and both returned their real Latvian catalogues (`form.actions.cancel` is `"Atcelt"`). That is the exact failure `D9.2` and `D9.4` each hit — a relative specifier resolving against the module that writes it, pointing at a package with no `locales/` — proven closed in the app rather than in a test.

**What is not certified, stated plainly.** Three things, and none of them is a claim this deliverable made. The **locale switch was not flipped**: it writes an account setting, and changing one uncorrectedly is not a walk's business — the loaders were exercised instead, which is the part D9 could have broken. The **D8 geometry items stay where D8 left them** — both modal and drawer at every size token, the shell at mobile width, the spacing `D8.9` and `D8.11` moved, and whether `aria-busy` reaches the accessibility tree under `display: contents`. D9 moved no geometry, so re-walking them would be re-accepting D8's work under D9's name; they remain pending operator acceptance against ADR-0048, whose window is shut. And `pnpm test` has a **flake worth knowing before the next deliverable**: under CPU contention vitest's forks pool times out starting workers and reports `Test Files no tests` rather than an error, which once took a whole 14-task run down. It did not reproduce idle — `pnpm test` 14/14 with `TURBO-EXIT=0`, `pnpm test:unit` twice at 14/14 with the second `>>> FULL TURBO` in 54ms, the ADR-0026 property — but a suite that never started should not read as a suite with nothing in it.

**Five amendments to one record, and none is a reversal.** `D9.4` changed a shipped default in ADR-0051 §Strings — a package's bundles are composed into `createI18n` at `init` rather than registered onto a live instance — and it was found by a suite rather than by a reading: seven grid tests lost a row selection between a click and its assertion, with nothing failing to type-check and no error logged. `D9.5` added two: a package's namespace may hold a word an app also has, and an installer travels with the copy it names. `D9.6` added three. The bounded review pass earned its place at `D9.5` and `D9.6` — the first caught a frozen-record regression that had made a package's Latvian a static import and undone ADR-0046 §3's per-locale chunking with the gate green; the second caught `useCan` inferring its action vocabulary from the policy table's _literal keys_, which would have turned ADR-0019's deny-by-default hole into a compile error in a file nobody had changed. Both were verified by probe in both directions rather than taken on the reviewer's word.

## How D8 closed, and on what evidence

**D8 shipped 2026-08-27**, twelve steps built, and ADR-0025 rule 4's three parts happened together: the checklist was run, this row moved, and the window on [0047](../adr/0047-ui-package-scope.md), [0048](../adr/0048-app-shell-and-record-surfaces.md), [0049](../adr/0049-admin-app-architecture.md) and [0050](../adr/0050-adr-lifecycle-and-verification.md) shut. **Twelve steps is the most any deliverable here has taken** — against D3's ten and D7's seven — and the window itself was one day, the same as D3's, D4's and D5's. What is unusual is not the window but the four days in front of it: D7 shipped 2026-08-22 and D8 did not open until 2026-08-26, the first gap in this ledger since D3, and §How D8 opened tells what happened in it.

Five things about it are worth more than the numbers.

**The package never learned anything behavioural, and that is checkable rather than asserted.** `packages/ui/package.json`'s `dependencies` block is byte-identical to D7's closing commit `f2ddfdf` — the only edit anywhere in that file is the `"./compositions/*"` `exports` entry — so no `react-hook-form`, no `@tanstack/react-router` and no i18n dependency entered `@repo/ui`, and the boundary ADR-0047 draws is enforced by the dependency graph rather than by review. **The generated-primitive carve-out held under twelve steps of pressure.** `packages/ui/src/components/` took exactly five edits across the whole deliverable and every one is the same comment-only correction — striking a stale count from an existing owned-edit comment — which ADR-0047 regime 1 rules is not a new divergence. `src/hooks/` took none. The shell, the container and `Banner` are all in `src/compositions/`, the path `D8.1` opened, under the ordinary code regime; the byte-identical rule never had to be argued about because the path is what selects the regime.

**Eleven amendments across four records, and the one that took none is the interesting one.** Four to [0047](../adr/0047-ui-package-scope.md), five to [0048](../adr/0048-app-shell-and-record-surfaces.md), two to [0049](../adr/0049-admin-app-architecture.md), and **none at all to [0050](../adr/0050-adr-lifecycle-and-verification.md)** — the first record in this ledger to pass through its own window untouched, and it is the one that governs the process the deliverable ran under. Against D7's twenty-two to one record and D6's twelve, eleven across four is a quiet window; the reason is that three of the four were written and re-written across four days before the deliverable opened, which is the cost D8's opening paid up front. **None of the eleven is a reversal.** Two are worth naming because they are the same shape: `D8.8` found that the `page` variant needed a `Card` rather than a `div` or the adoption would have stripped the shipped surface's border and rhythm, and `D8.11` found that `DialogContent`'s `gap-4` was a real header-to-fields distance that the inversion made inert — both invisible to jsdom, both found by reading the primitive against the shipped tree, and the second one corrected a sentence in 0048 §4 that had asserted the opposite in as many words.

**The bounded review pass earned its place three times, and once it was wrong.** ADR-0050 replaced seventeen rounds of multi-agent refutation with one reviewer per diff, and across twelve steps that reviewer produced findings that mattered on `D8.7`, `D8.10` and `D8.11` — the second of those is a commit titled for them: a focus ring clipped by the dialog's new scroll container on every field of all three ceremonies, an assertion that could not fail because the routed drawer can never unmount, and a docblock that attributed the drawer's defect to the dialog. It also proposed a fix that was itself wrong — asserting `event.defaultPrevented` to prove the Escape refusal, which Radix sets on both branches — and the step caught that by mutating the container and watching the assertion stay green. That is the regime working as 0050 describes it: the review proposes, the machine decides, and no round is spent arguing.

**And the nine-document check found nothing out of step, for the first time in five close-outs.** D4 through D7 each found one — this file records D6's as the third in a row and D7's as the fourth — and D7's found the error in this file's own window rule — which is why D7's close-out enumerated the list and D8's plan carried it forward as nine. Here the predicate held over all nine before close-out touched them. ## How D8–D13 were re-scoped

**Re-scoped 2026-08-22, at the desk, after D7 shipped.** The ledger ran extraction-with-the-customer-app → impersonation → marketing; it now runs **shell and surfaces → extraction → grid follow-ups → customer app → impersonation → marketing**, and what was D8–D10 is now D11–D13. Three operator judgements produced it.

- **The extraction moves ahead of the app that was going to force it.** The old D8 bundled extraction and customer app on the argument that "an extraction with one consumer is speculation with extra folders". That argument is answered rather than ignored: the second consumer's requirements are known now — a collapsing nav drawer, header chrome placed differently, create/edit surfaces in three shells — so the extraction is generalising against named needs rather than guessing. `docs/plan/0008-app-shell-and-record-surfaces.md` carries the rule that keeps it honest: every slot and variant must answer a need this repository can name today.
- **Design comes before the move, and they are separate deliverables.** `apps/admin` is a working consumer with a full test tier; generalising the shell and the surfaces against it, in place, is the cheapest verification available, and it leaves D9 mechanical enough that its "no behaviour change" claim is a matter of comparing test totals. That also makes D9 the first row in this ledger genuinely suited to an unattended run.
- **The remaining grid and admin work is real, and belongs after the extraction** — a grid capability added before D9 is added to code that is moving, and one added after D11 is added twice. D10 is a placeholder with a candidate list drawn from the index's _Planned_ entries; its scope is the operator's to name.

Two design decisions were taken at the same desk and are recorded in the D8 file rather than here: the compositions live in **`@repo/ui`**, which means superseding frozen [ADR-0031](../adr/0031-ui-design-system.md) and carrying the whole of it (ADR-0024 rule 1) — the accepted price of one door per app; and the shell ships **header slots, breadcrumbs, a page header and a banner slot** — the banner added to the scope on 2026-08-22 as a region a shell of this shape should have anyway, dumb by construction, with [D12](0012-impersonation.md)'s impersonation banner as its named consumer and the principal field it reads left to that deliverable.

## Goal

Two lanes on one machine stop competing for one database, one CPU and one `main`. A lane is one pull request and a step is one commit to it, checked locally for what it reaches and proved whole by CI on every push; `main` moves once per lane, at ship, where the whole gate runs on the machine once; a lane's test database is derived from its branch and never named by hand; the shared documents stop conflicting. It lands before the fork so machxi-ship's carrier lanes inherit the rule with the records rather than the failure with the memory.

## Constraints

- Window and supersession state is written in the ledger's window section and nowhere else, and after `D34.4` the lane entries are files that section links (ADR-0065 §5 as carried; ADR-0082 §4).
- A cached task is a pure function of the tree and the declared environment; `TEST_DB_LANE` is declared in `turbo.json` for `test` and `test:int` (ADR-0026 §The rule).
- The `_test` suffix guard on the test database stays underneath every lane database (ADR-0008, `@repo/db/testing`).
- `.claude/**` carries no step number, no date and no bare record range; `pnpm docs:check` enforces it (ADR-0065 §5).
- A superseding record states its delta and each parent's status line names it at the step that makes the delta true; the parent's body is untouched (ADR-0050 rule 1 as carried by ADR-0065).
- The browser tier stays beside the gate, never in it (ADR-0052, ADR-0059 §1).
- D34 opens alone: D29 and D32 have shipped before it opens (ADR-0079 §1 — its records meet theirs).
- D34 itself runs in the shape it builds: on the lane branch its lane file names, from `D34.1`, one pull request, no step merged to `main`. Steps 1–4 close on the whole gate locally, because the step check does not exist until `D34.2` and `/step` does not use it until `D34.5`; from `D34.5` the step check and the pull request's run are the proof; `/ship` merges the pull request.
- The shape fits a cloud session as it fits a worktree: the branch may be the one the session was given, the lane file names it, CI state is read with `gh` or the GitHub tools and its absence is said in the note, and the lock is the machine's own.

## Decisions taken at scoping (2026-09-30)

Taken in the review sitting of the same day (the review is kept in the project's Claude space as `parallel-lanes-review`) and confirmed by the operator there; recorded here so a builder does not re-open them.

- **CI is the authority for `main`.** ~~A step lands through the merge queue; the local `--ff-only` path is an operator-chosen fallback (`/step --local`), never the agent's answer to a failed push.~~ **Revised 2026-09-30, before opening, on the operator's decision:** GitHub's merge queue is not offered for a private repository on a personal account, and the day's record showed the step's cost was verification that proved nothing new, not the landing. A lane is **one pull request**; a step is **one commit** pushed to it, checked locally with the step check (the fast loop plus the integration files the change reaches) and proved whole by `gate.yml` on the push; the next step reads that run first and fixes forward if it is red. `main` takes the opening commit and the merge at `/ship`, where the whole gate runs on the machine once. There is no landing script and no local fallback.
- **Nothing re-runs what is proved** (added with the revision). `main` moving never re-runs anything; a review fix re-runs the step check over what the fix reaches; a red run re-runs the failed files and logs a flake by name; `--force` is never passed. One review per step; no close-out step in any plan `/scope` writes from here on.
- **Every lane is a branch from its first step.** The lone-lane-on-`main` allowance is withdrawn.
- **One commit per step**, on the lane branch, titled with the step's conventional message, review findings in its body; the pull request merges with a merge commit so the ledger's step citations survive on `main`.
- **Derive, don't validate.** `TEST_DB_LANE` comes from the branch name; `pnpm db:lane` takes no argument.
- **Union merge for notes and the changelog only.** The ledger and the records never union; they stop conflicting by becoming per-lane files and a generated paragraph.
- **`merge=ours` is applied on the command line for the starter merge**, not as a standing attribute.
- **Recorded, not asked:** steps within a lane stay sequential; no record is shared by agreement; no human approval is required on `main`; one Postgres container.

## Definition of done

Run at `D34.6` and again by `/ship` on the lane's head with `main` merged in.

1. The gate green by `gate.yml` on the pull request's head, and locally, under the lock: `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check`.
2. `pnpm test:unit` twice, the second `FULL TURBO`.
3. `pnpm rules:digest` writes nothing on a second run; `pnpm lanes` writes nothing on a second run; `pnpm docs:check` clean; `pnpm test:scripts` green.
4. Every step of D34 a commit on the lane branch its lane file names, none merged to `main` before the pull request; the pull request merged with a merge commit and `gate.yml` green on `main` after it.
5. A clean tree afterwards.

### The rate-limit wall

**`pnpm test:e2e` cannot be green on a stock profile, and this is a measurement rather than an opinion.** Each suite alone in a clear window, on 2026-09-05: `apps/admin` **37 passed, 299 → 124 = 174 requests**; `apps/customer` **12 passed, 299 → 164 = 134**. The root script is `turbo run test:e2e --concurrency=1`, so they run back to back through one in-memory limiter: **308 against [ADR-0020](../adr/0020-security-baseline.md)'s global 300 per fifteen minutes**. The first full-tier run of the day failed exactly there — the admin suite green, then the customer's worker fixture refusing with 79 left against a floor of 126.

**Neither suite is at fault and neither floor was trimmed to make the sum work.** The admin's 168 was measured at `D11.11` and its suite has not changed since `D11.12`; what grew is the app under it. This suite's 77 was measured at `D13.9`; `D15.5` then put a `GET /user/orgs` behind every protected screen and this step added a spec, so it is 134 — re-measured whole rather than added to. Both floors now state what was measured, and the customer's moves 90 → 147.

**The fix is known, is named in three places in this repository, and is not a build step's to apply.** A larger `RATE_LIMIT_GLOBAL_MAX` for the dev profile is the first of the two candidates `D11.6` recorded; `D11.11` took the second (the probe) and left this one, both times with the same sentence — _the limit is ADR-0020's_. ADR-0020 is frozen: only 0067 and 0068 are amendable today, so its number moves by supersession. `security-reviewer` was asked the question directly and agreed, on four grounds: 0020 decides the number and not only the knob; the number is load-bearing in 0020's own §Residual risks, where the global 300 is what bounds an argon2 hash burst, so raising it moves the premise of a recorded risk acceptance rather than an operational preference; `.env.example` is the deploy template and this repository's own `KNOWN_PUBLIC_SECRETS` rows exist because committed dev values get copied forward; and a fourth step reversing a judgement three earlier ones recorded would be the edit-rather-than-supersede that ADR-0065 treats as erasure.

**For the operator, three options with a recommendation. A was taken on 2026-09-05.**

- **A — supersede ADR-0020's rate-limit row for the dev profile** (recommended): a short record saying the _committed development_ profile carries a larger `RATE_LIMIT_GLOBAL_MAX`, the schema default stays 300 so a deployment that sets nothing is unchanged, and the reason is that the repository's own browser tier is now a legitimate consumer of 308. Cost: one record and a `.env.example` line. It is the only option that leaves a stock clone able to run `pnpm test:e2e`. **Taken 2026-09-05 — §The record, and what it decided, below.**
- **B — leave the limit and make the tier fit**, by cutting about a dozen requests of coverage — the four cold-URL account boots, or this step's registration reload. Cheap today and wrong in a month: the next screen puts it back over, and the thing being trimmed is coverage. **Declined.**
- **C — leave both and document the tier as two commands**, one suite per window, with `pnpm dev --filter api` restarted between them. Costs nothing and admits that `pnpm test:e2e` is a command a clone cannot run green, which is a poor property for a starter's own definition of done. **Declined.**

### The record, and what it decided

**[ADR-0069](../adr/0069-development-rate-limit-profile.md), written and accepted 2026-09-05 at this step's head**, on the operator's decision — option A as it was offered, B and C declined. It joins the open D15 window at the step that needs it (the `D12.12`/0056 and `D15.7`/0068 precedent), and [ADR-0020](../adr/0020-security-baseline.md) moves to `superseded by` there: its **third** partial successor after 0059 and 0066, standing for everything none of the three touches.

**The delta is one file.** The root [`.env.example`](../../.env.example) — the development template, the one that sets `NODE_ENV=development` — carries `RATE_LIMIT_GLOBAL_MAX=1000`. The schema default stays 300, so a deployment that states nothing is exactly as 0020 decided and [ADR-0004](../adr/0004-configuration-and-environment.md)'s sketch stays true, which is why 0004 is not a parent. `docker/prod/.env.example` carries no value at all, so the development number is not on the path a deployment copies forward — the answer to the `KNOWN_PUBLIC_SECRETS` ground the first sitting's security pass raised, and the reason the record adds no production refusal: unlike a signing key, a request budget carries no secret, and refusing a number in production would refuse a capacity decision only the deployment can make. The window, the login, refresh and impersonation limiters, their keys and `skipSuccessfulRequests` do not move.

**1000 has a reason, and it is not 308 plus slack.** It is what one address legitimately spends on this repository's own verification in one window, twice over: the browser tier (308) and the Postman collection (165) are 473 together, and a run that fails and is run again is 946. A window that cannot hold a failed run **and its retry** produces a second, false failure on the diagnosis attempt — the class of defect the probe was built for at `D11.11`. It stays a limit rather than an off switch: 1000 in fifteen minutes is about 1.1 requests a second, so a client stuck in a render loop still spends it — under a minute at twenty requests a second — and a developer still meets the `429` envelope, the `Retry-After` and the tier's own refusal on a machine where they can be read. **And the wall was never only a clone's**, which the second sitting found while checking where the development template travels: `.github/workflows/e2e.yml` copies this same `.env.example` and runs `pnpm test:e2e` as one command, so the nightly browser tier was on it too. Both workflows copy the root template — `gate.yml` for the SPA builds `pnpm size` needs — and both run at `NODE_ENV=development`; `docker/prod/compose.yaml` passes no `RATE_LIMIT_*` at all, so a deployment following the reference gets the schema's 300 whatever the root template says. The test profile's 100000 was deliberately not reused — a development stack that never refuses anything is one on which ADR-0020's most visible behaviour is never once observed.

**0020's residual-risks premise is restated rather than left standing**, which is what made this a supersession rather than a preference. §4 of the new record: at 1000 the burst is three times larger and the drain three times longer — about thirty seconds rather than ten, at the argon2 capacity 0020 measures — while the sustained rate stays an order of magnitude below that capacity, so it remains a burst-recovery problem. And the acceptance 0020 recorded was made about a deployed posture, which this record does not move: a deployment inherits 300 unless it decides otherwise.

**Measured on the profile, in one window** (2026-09-05, a fresh API at 1000). `pnpm test:e2e` as one command: admin **37 passed** (57.7s), customer **12 passed** (34.0s), `organizations.spec.ts` among them; the window went 998 → 689, so **309** including the two probes. `pnpm test:postman` in the same window took it to 528, so **161** more. **471 spent, 528 left** — a second full tier run fits, which is the headroom the number was chosen for, now measured rather than argued. **What the tier says now.** Both `e2e/support/app.ts` files read the quota off `RateLimit-Policy`'s `q=` field instead of stating 300, because 300 has become a diagnosis: it means an `.env` copied before this record, and the failure is then the stale line rather than the run. ### A third defect, found by the close-out again

**`api#test:unit` was red on a forced cold run of the parallel loop at the second sitting**, and the failure had nothing to do with this step's diff: `health.service.test.ts`'s "runs indicators in parallel, not one after another" gave three 40 ms indicators and asserted the whole call finished inside **120 ms** — the serial time exactly, so the entire margin was the difference between parallel and serial, and any machine that adds scheduling delay to a timer closes it. ## D15.6 — Registration in the customer app

**Built 2026-09-05.** No record moved at this head: every ADR the step names was already in force. It closes a deferral rather than making a decision — [ADR-0055](../adr/0055-customer-app.md) §5 left self-service registration unwritten, and [ADR-0067](../adr/0067-organizations.md) §6 made it required, because sign-up is what creates the personal organization. **No wire behaviour changed**, so [`docs/specs/auth-sessions.md`](../specs/auth-sessions.md) is untouched: its "Self-registration is public, optional, and never an oracle" requirement already states everything this screen consumes, down to the flag-off answer being `404 ROUTE_NOT_FOUND` rather than a `403`. That is ADR-0068's altitude rather than an omission.

**The endpoint is on a segment this client is pinned away from, and that is the step's one structural fact.** `POST /api/v1/public/auth/register` is for somebody who has no population yet, so it cannot live under `/user` — and `@repo/api-client` builds one axios instance whose `baseURL` _is_ the segment, deliberately, so "a path that escapes the segment is a bug the base URL makes impossible to write by accident." The escape is a per-request `baseURL` override on the one call, which keeps every path-keyed rule working (the request's own `url` is still `/auth/register`, so `COOKIE_TRANSPORT_PATHS` and the CSRF list match on it) and is now itself fenced to this client's host. `register` lives beside `login` for `login`'s reason: the response's whole purpose is to start a session, and the module that owns the session's memory is the one that writes it.

**`/auth/register` had to join three lists, and the step found two of them.** Cookie transport is the one that is invisible when you get it wrong: without `X-Auth-Transport: cookie` the API answers with the refresh token in the body and sets no cookie (ADR-0029 §Opt-in), so an account somebody has just created is signed in until the first reload — the `D13.7` failure one endpoint along, and asserted at the wire in both suites because no response shows it. `UNAUTHENTICATED_PATHS` is the second. The third is the `401` recovery exclusion, and both reviewers found it independently; it is finding 1 below.

**The flag travels on the router's context, because its first reader is a guard.** `/register`'s `beforeLoad` answers `notFound()` when registration is off, and a `beforeLoad` is not a component, so no provider can reach it — `RouterContext` gains `features` beside `session`, and `createAppRouter` takes an override the way it takes a store. The sign-in screen's link then reads the _same_ value through `useRouteContext`, so the route and the link into it cannot disagree. `notFound()` rather than a redirect to `/login`, which is the client's echo of the API's own choice: a redirect would tell whoever typed the address that something is behind it. **The API's flag stays the control** — this one can only subtract — and the case where the two disagree (client on, API off) is a `404 ROUTE_NOT_FOUND` the `errors` catalogue turns into a sentence, which has its own test.

**Two reviews, `code-reviewer` and `security-reviewer` (the D15 constraint). No BLOCKER; nothing above LOW from the security pass. Five findings, all five taken; both reviewers found the first independently.**

1. **`/auth/register` joined two of the client's path lists and not the third**, so the `401` recovery exclusion had silently diverged from `UNAUTHENTICATED_PATHS`. A `401` on the public register path — which this API cannot produce, but edge auth, a WAF or a staging reverse proxy in front of it can, exactly the justification already written for `/auth/csrf` — would have fired a refresh nobody asked for, signed an anonymous visitor out of a session they never had, and rendered _the refresh's_ sentence over their sign-up. Fixed by deleting the second enumeration rather than extending it: the branch asks `matches(UNAUTHENTICATED_PATHS, …)`, which is the property it was always spelling out by hand. The test pins its refresh handler on the **user** segment, because counting on the file's shared `admin` handlers would have left the assertion true whether the refresh happened or not.
2. **The absolute-URL fence did not cover `baseURL`, and `register`'s own comment claimed it did.** The interceptor tests `config.url`; a `baseURL` is an absolute URL arriving by a key it never reads, and this step made the override a supported pattern. Nothing builds one from server data today — the fence exists to keep that true — so a second caller would otherwise have carried the cookies, and off `UNAUTHENTICATED_PATHS` the bearer, to any origin. The interceptor now refuses a `baseURL` outside this client's own host, and the comment says what is true.

## D15.3 — The API surface, both segments, the exclusions, Postman

**Built 2026-09-05.** [ADR-0015](../adr/0015-route-segments-and-versioning.md) and [ADR-0057](../adr/0057-impersonation-sessions.md) moved to `superseded by` [ADR-0067](../adr/0067-organizations.md) at the head — 0015 for a prefix _within_ the `user` segment (`/orgs/:orgId`; the three segments, their guards and the version stand) and 0057 for §5's list alone (the mint, the handoff, the actor claim, the fixed session life and the attribution stand). 0057 is the fifth record here to carry more than one partial successor, and **all four of 0067's parents have now moved**.

Built: `@repo/contracts/organizations` — three resources, the params and bodies, and the three list allow-lists; the module's mapper, schemas, three controllers and three routers; the service's whole HTTP surface; the repositories' list surfaces; `ORGANIZATION_INVITATION_TTL` through the config schema and `.env.example`; a pending invitation in the dev fixtures whose token is minted per run; three Postman folders with their environment variables; and three integration suites plus the list-index tests.

Nineteen endpoints across three mounts. `/user/orgs` — the switcher's list and a team create outside the prefix, then get, patch, delete, `/members` (list, role, remove-or-leave) and `/invitations` (create, list, revoke) under it, each route naming the membership roles it admits. `/user/invitations` — the invitee's list, accept and decline, self-scoped by the caller's **address**, which is read from their account because no principal carries one. `/admin/organizations` — the users resource's shape exactly, `admin` or `manager` to read with every write narrowed to `admin`, plus a memberships sub-resource that adds by user id.

**Two reviews, `code-reviewer` and `security-reviewer` (the D15 constraint). No BLOCKER. Nine findings, all nine taken.**

1. **HIGH — a second member could be put into a `personal` organization**, from either segment: the caller holds `owner` on their own, so `requireMembership("owner","admin")` admits them, and staff reach the same row by id. ADR-0067 §2 bounds the accepted "a uuid and a creation timestamp in a URL" exposure precisely with _"only its owner and staff ever see the slug, and no surface a second party reads may carry one"_ — and this step built that surface. Worse followed: ownership could then be granted away, so `findPersonalFor`'s `created_by` key and the derived slug would name different accounts and `ensurePersonalOrganizationFor`'s idempotence proof would fail; and the creator closing their account soft-deletes the organization, silently evicting anybody else. Both paths now refuse `409 ORGANIZATION_PERSONAL_CLOSED`. **The invariant was a fact of the record with nothing in the code holding it up.**
2. **MEDIUM — an address could be invited without bound.** An invitation has no natural key, so nothing in the schema stops a second one while the first is outstanding, and the cost lands on somebody else: the invitee's own list is deliberately unpaged, so an unrelated account's list could be made arbitrarily long from an address the inviter never controlled — and the day the mail deliverable fills §2's marked call, the same loop is a mail bomb at a third party. One live offer per address per organization now, `409 ORGANIZATION_INVITATION_PENDING`, revocable and then repeatable.
3. **`findByEmail` counted a closed account's membership**, so an address could become permanently un-invitable: team memberships survive a soft delete while `users_email_active_unique` releases the address, so the dead row would match by email forever and the owner would be told "already a member" about somebody who is not. It now filters `deleted_at`, the same clause `countOwnersExcept` carries.
4. **`GET /admin/organizations/:id/memberships` answered `200` with an empty page** for an id nothing holds, while `GET /:id` on the same prefix answers `404` — nothing on that segment having proved the organization exists. It reads first now, through a `listMembersForStaff` distinct from the user segment's, which is already behind the guard.
5. **`acceptInvitation` read the organization and the membership after its transaction committed**, so a concurrent removal could produce a `200` reporting `role: null` for a membership the same request had just created. Both reads moved inside.
6. **The dev seeder's "already pending" probe omitted the expiry**, so a re-seed a month later would find the expired row, skip the insert, and leave the invitee's surface with nothing to answer.
7. Three smaller ones: `inviteeAccessToken` was a `default` Postman variable where every other token in the file is `secret`; `callerAccount` answered "Organization not found" on routes that name no organization; and the `get` handler was typed against the patch schema.
8. **A dead test and a dead script.** The impersonation role-grant case invited somebody and never accepted, then granted against the _owner's_ own membership — an operation the last-owner invariant would refuse anyway, so the case did not exercise what it was named for. It now brings a real second member in and promotes them to `owner`, with the account's own owner doing the same thing successfully afterwards. A `qaInviteNonce` prerequest that nothing read was removed.

**Two notes taken as written rather than fixed.** The members list's default sort (`-createdAt` with an ascending tiebreaker) is a mixed-direction order no single btree scan serves — the repository-wide convention rather than this table's problem, and the comment that claimed the `ORDER BY` matched the composite now says what actually happens. And `GET /user/orgs` ships **without** ADR-0014's list language, against this step's own plan line: it is the switcher's query over a handful of rows, so a pagination language there would be a query string no client sends. That is a labelled amendment to the plan entry rather than a silent divergence.

**Gate green** — `lint` 17/17, `check-types` 16/16, `test` 15/15 (API 36 unit files, 24 integration), `size` 4/4, `format:check` clean — plus `pnpm test:scripts` 28/28, `node scripts/docs-hygiene.mjs` clean over 11 specs, `node scripts/rules-digest.mjs --check` up to date, and **`pnpm test:postman` 165 requests / 504 assertions / 0 failures** against the dev stack.

**The spec grew six requirements** ([`docs/specs/organizations.md`](../specs/organizations.md)): the caller's own organizations and the create; name and slug as the whole of an organization; the members list with removal-or-leaving; the invitation create and its three `409`s; the invitee's surface and its single use; the admin resource; and the impersonated session's refusals. Two new error codes entered the enum with all four dictionaries, which the apps' compile-time completeness check over `ErrorCode` made unskippable.

**Two reviews, `code-reviewer` and `security-reviewer` (the D15 constraint). No BLOCKER. Six findings, all six taken.**

1. **The one that mattered most, and the gate could not see it.** `invitations.listPendingForEmail` used the relational query builder with a **correlated** `exists` subquery. It caught this and finding 2 on its first run.
2. **The last-owner invariant counted closed accounts as owners.** Both deletion paths leave an account's **team** memberships in place — only the personal organization goes with it — and `user_id` cascades on a hard delete only, so a soft-deleted account still held its `owner` row. Two-owner team, owner A closes their account, owner B leaves: the count saw A and allowed it, leaving an organization with no owner who can sign in, no path to grant one and no path to delete it. `countOwnersExcept` now joins `users` and filters `deleted_at is null`.
3. **The owner lock was taken after the read it was meant to cover.** `assertOwnerSurvives` locked only once a role read said `owner`, which leaves the non-owner path unserialised — and a non-owner path can still empty an organization: a removal reads `member`, skips the lock, and by the time it deletes, that member has been promoted and the previous sole owner removed by a request that counted this one as the survivor. Two writes, each correct against what it read, no owner left. The lock is now the first statement of both membership writes, in a `lockedMembershipWrite` helper, which is the ordering `staff.service.ts` had all along. The unit test that pinned the weaker ordering (`lockOwnerInvariant === 0` for a non-owner removal) asserted the bug as if it were the requirement, and now asserts the fix.
4. **Both new test fakes recorded calls nothing read**, so the claim their docstrings made was unproved at the unit tier. One assertion added per path: `register` and `POST /admin/users` ensure the organization, both deletion paths delete it with the account's own `at`.
5. **The tenant scope was spread-overridable** in `invitations.create` — the scope was spread over by `input`. Structural typing only excess-checks object literals, so a wider variable could have put an `organizationId` over the required parameter. The scope now goes last.
6. **The whole `UserRecord`, `passwordHash` included, was handed to the organizations service** for a call that needs four fields. The auth service already built the object by hand at its own call site; the users service now matches it.

Two smaller corrections went in with them: the "a duplicate leaves the organization count unchanged" tests carried a comment claiming they proved a rollback, when today the transaction returns before the organization is ever written — the comment now says what the assertion is really guarding against, and the assertion stays; and `organizations.findBySlug` gained a note that it carries no membership scope, because a slug is an existence oracle exactly as an id is.

# D8 — App shell and record surfaces

- Status: **planned** — opens when the previous deliverable ships (D7 has: 2026-08-22); per the ledger, opening is a decision, not a formality. Its three ADRs — [0047](../adr/0047-ui-package-scope.md), superseding frozen [0031](../adr/0031-ui-design-system.md), and [0048](../adr/0048-app-shell-and-record-surfaces.md), both **written ahead on 2026-08-22**, plus [0049](../adr/0049-admin-app-architecture.md), superseding frozen [0032](../adr/0032-admin-app-architecture.md), **written ahead on 2026-08-26** — are all `proposed` (writing is not opening, the D4 precedent). 0047 and 0048 are accepted at the head of `D8.1`; 0049 at the head of `D8.4` (§Gate below)
- Steps: `D8.1` – `D8.12`
- Ledger: [`docs/plan/README.md`](README.md)

Scope: the two compositions every screen in both SPAs is built from — **the application shell** and **the record surface** — designed as generic, slotted components in `@repo/ui`, with `apps/admin` adopting them as the first consumer. Nothing behavioural moves in this deliverable: the grid, the API client, the resource config and the form machinery stay exactly where they are (that is [D9](0009-platform-extraction.md)). What moves is presentation, and what changes is that two hardcoded layouts become two designed ones.

**This is design work, not a move**, and that is why it comes before the extraction. `apps/admin` is a working consumer with a full test tier and a browser walk; generalising the shell and the surfaces **against it, in place** is the cheapest verification available. D9 afterwards is then a mechanical relocation whose "no behaviour change" claim is checkable by test totals.

## Why now rather than with the customer app

The scope document these two deliverables were split out of made the opposite argument — _"an extraction with one consumer is speculation with extra folders; the second app is the forcing function."_ That argument stands in general and is answered specifically here: **the second consumer's requirement this deliverable actually designs against is nameable** — header chrome placed differently from the admin panel's — and both compositions are ones the customer app cannot be written without. Only that one requirement is cited below, because only that one is owed to a step: `D8.5` writes it into [`docs/plan/0011-customer-app.md`](0011-customer-app.md), whose file today states its needs only generically. The risk the old argument names is speculative generality, and the plan carries a rule against it rather than a hope:

> **Every slot and every variant must answer a need this repository can name today** — a screen in `apps/admin`, a stated requirement of the customer app ([D11](0011-customer-app.md)) written into D11's own file in the same change, or an invariant a frozen ADR already imposes. A slot added because it "might be useful" is a review failure.

That rule has already cost this deliverable five slots. [ADR-0048](../adr/0048-app-shell-and-record-surfaces.md) §2 struck `brand`/`nav`/`sidebarFooter` as separate drawer regions (the drawer arrives as one node), and struck `headerStart` and `pageActions` outright — nothing in `apps/admin` fills either.

## What is wrong with today's two layouts

Both gaps are real and were read out of the code rather than assumed.

**The record surface scrolls the wrong thing, in two different shapes.** On the drawer and page paths, `apps/admin/src/shared/form/app-form-surface.tsx` puts `overflow-y-auto` on the drawer's entire `SheetContent`, so the title scrolls away with the fields, and the footer is a `FOOTER` class string rendered inside the scrolling body, so Save scrolls away too. The dialog path is a separate file, `app-form-dialog.tsx`, with the mirror-image defect: `DialogContent` carries **no `max-h` at all**, so a long form grows the modal past the viewport instead of scrolling inside it, and the modal has exactly one width. A form long enough to scroll therefore loses both its title and its Save button, which is the case the operator most needs them.

**The shell has no slots.** `apps/admin/src/widgets/dashboard-layout/index.tsx` hardcodes its header as `SidebarTrigger + Separator + <h1>{title}</h1>`. There is nowhere to put an action, a breadcrumb or a status control, which is why theme, locale and logout live in the _sidebar footer_. ADR-0048 §Context records that this was a deliberate placement (D6.3/D7.5) rather than an accident, so moving them is a reversal the records argue — and a divergence from frozen ADR-0032, which is what [ADR-0049](../adr/0049-admin-app-architecture.md) exists to carry.

## The shell

A composition over `@repo/ui`'s `sidebar-07` primitives, which **knows nothing about routing or authorization**: navigation arrives as JSX, so the `can()` join (ADR-0042) and the typed route links stay in the app that owns them.

- **`sidebar`** — the whole drawer as one node. `apps/admin`'s `AppSidebar` **is** the `<Sidebar>` with its header, content, footer and rail; ADR-0049 keeps it whole in the `widgets` layer and has the `_dashboard` route file hand it in. `collapsible="icon"` and the mobile `Sheet` swap stay the primitive's, inside the app's node.
- **`headerEnd`** — the fix for the stranded chrome. The trigger stays the shell's; the account menu mounts here.
- **`breadcrumbs`** — JSX the app composes, not data. `packages/ui/src/components/breadcrumb.tsx` has been in the package since D3.1 and no admin screen has ever composed one.
- **The page header** — a second `shrink-0` row below the existing `h-16` header and above the page container, carrying the single `<h1>`; its height is content-driven, and a full-height grid gives up roughly one line of viewport for it.
- **`banner`** — a region above the header spanning the content column (it lives inside `SidebarInset`, which is the `main` landmark, so it sits beside the drawer rather than across the window), and a standard shell region rather than a speculative one: every app of this shape eventually needs somewhere to say something about the whole session. It is **dumb by construction** — it renders what it is handed and reserves no space when handed nothing. The shell must not learn _why_ a banner is showing, because a shell that read the principal would drag the session store and `@repo/contracts`'s principal type into `@repo/ui`, which ADR-0047's dependency rule and [ADR-0023](../adr/0023-shared-contracts-package.md) both exist to prevent.

  It comes with a generic **`Banner`** component beside it — the variants **`info`** and **`warning`** (one per consumer the repository can name today: `info` for the pseudo-locale notice, `warning` for D12’s impersonation banner), a message, an action slot, and a **`dismissible`** flag, because that first real consumer needs `dismissible={false}`. `Banner` is **hand-written in `compositions/`, not built on shadcn's `alert`** (ADR-0048 §3; ADR-0047 §What-code): the package carries no `alert`, and generating one as a substrate would put the banner's base under the regenerate-and-diff rule for no upstream benefit. `dismissible` exposes an `onDismiss` callback and the component holds no dismissed state of its own — whether a dismissal sticks is a session question, and answering it would make the component the opposite of dumb.

  **The named consumers, in order of certainty**: [D12](0012-impersonation.md)'s impersonation banner, which reads `principal.impersonatedBy` and renders into this slot — the field on the principal and the banner itself are D12's to add, not this deliverable's; then offline, maintenance and read-only notices. In `apps/admin` today the honest consumer is the dev-only pseudo-locale notice: `VITE_I18N_PSEUDO` (D7) is on and nothing says so on screen, which is a real if small need and makes the slot _exercised_ rather than merely offered. A slot with no consumer at all is the defect this repository recorded twice about the `page` edit surface, and the deliverable should not add a third.

- **The page container**, carrying [ADR-0037](../adr/0037-grid-viewport-layout.md)'s height contract unchanged. That contract is a **two-element chain and the shell must own both ends**: `min-w-0` always on the container; in full-height mode `h-svh` on the **`SidebarInset`** and `min-h-0` on the **page container**. Collapsing them onto one element drops `h-svh` and breaks the chain every grid divides — and jsdom lays nothing out, so no test would say so. This is the part of the shell most easily broken by a redesign; the definition of done says so explicitly.

**Deliberately out of scope, each with its consequence stated rather than left to be discovered:**

- **Navigation as a typed data array.** Nav stays inside the app's sidebar node: a data-driven nav would pull the `can()` filtering and the route-tree types into the shell, and ADR-0042's containment carve-out means "which entries render" is a per-app judgement, not a shell rule.
- **`headerStart` and `pageActions`.** No admin screen fills either, and the record's own slot rule forbids shipping them unexercised. Each is one prop wide when a screen names it.
- **Command palette, global search, tenant switcher.** Named so that nobody wonders whether they were forgotten.

## The record surface

One container in three variants — `dialog`, `drawer`, `page` — replacing the shells inside `app-form-surface.tsx` and `app-form-dialog.tsx`:

```
┌─ Header ─────────────┐  fixed: title, description, close
├─ Body ───────────────┤  scrolls: overflow-y-auto, min-h-0
└─ Footer ─────────────┘  fixed: slot — submit, cancel, destructive actions
```

Three decisions [ADR-0048](../adr/0048-app-shell-and-record-surfaces.md) §4 makes explicitly, each because it has a wrong answer that looks right:

1. **The `<form>` wraps header, body and footer; only the body scrolls** — and it gets there by **inversion**, not by nesting. `AppFormFrame` keeps the `<form>` (ADR-0035's one form frame, `handleSubmit` still attached to it) and supplies it to the container through a **`column` render prop**; the container calls it with its geometry classes and its three rows. The obvious reading — the container wrapping the frame — puts the footer outside both the `<form>` and the locked `FieldSet` and breaks `type="submit"` and the submit lock in one move. The mechanism is a render prop and deliberately **not `asChild`**: Radix `Slot.Root`, which is every `asChild` in this repository, clones its child and merges props but does not render the parent's children inside it.
2. **The container is content-agnostic** (§4). Container and RHF frame are fused today; split, the same surface serves a detail view, a confirmation with a long body, or a future wizard — none of which hand in a `<form>`, and for those the container renders its own `div` as the column.
3. **Sizes are a token set** (§4, §5), not free values: `sm | md | lg | xl | full`, mapped per variant to a class string merged through `cn`. For the `dialog` variant that class **carries the `max-h` onto `DialogContent` itself** — the element has none today, so a bound on the inner column would bound nothing.

Everything already decided about these shells carries over unchanged and is the surface's job to preserve: the URL is identical across all three variants and closing is a navigation ([ADR-0044](../adr/0044-record-routes-without-list-state.md)); the submit lock refuses dismissal while a mutation is in flight, including the page variant's navigation blocker; and the record's title is always exactly one real heading — rendered by the surface in `dialog` and `drawer`, and by the shell's `<h1>` under `page`, where the surface renders none (§4: `staff:create.routeTitle` and `create.title` are the same string, so a `page` surface with its own heading is two headings with one name).

### 2. `Banner`, and the fourteenth `UiStrings` key

**ADRs:** [0048](../adr/0048-app-shell-and-record-surfaces.md) §1 §3, [0047](../adr/0047-ui-package-scope.md), [0046](../adr/0046-interface-localization.md) §12, [0023](../adr/0023-shared-contracts-package.md)

### 3. The shell composition, geometry only, in the package

**ADRs:** [0048](../adr/0048-app-shell-and-record-surfaces.md) §2 §3, [0047](../adr/0047-ui-package-scope.md), [0037](../adr/0037-grid-viewport-layout.md)

The shell before the record surface because its adoption carries the deliverable's riskiest contract — ADR-0037's height chain under every grid — and building the composition alone first is what makes that adoption a small, legible diff. `compositions/app-shell.tsx` (`"use client"`) composes the `sidebar-07` primitives and **knows nothing about routing or authorization**: `sidebar` as one node, `headerEnd` beside the trigger (which stays the shell's), `breadcrumbs`, `banner`, `title` as the page-header row **the single `<h1>` lives in**, `fullHeight`, and `children` inside the page container.

The shell owns **both ends** of ADR-0037's chain: the `SidebarInset` (`h-svh` in full-height mode) and the page container (`min-w-0` always, `min-h-0` in full-height mode), keeping **`data-slot="page-container"` and `data-full-height` on the same element**, `data-full-height` **an empty string when on and absent when off** — the form the three routing tests' valueless `toHaveAttribute` would also accept a `"true"` for, which is why the step pins it. The page-header row and the `banner` region are both **`shrink-0` in-flow siblings above the page container**, not children of it: a row inside the `min-h-0` box silently takes height from every grid, and jsdom would not say so. The banner region **renders nothing at all — not an empty `div` — when handed nothing.**

Package tests only, within the harness's reach (a desktop-only `matchMedia` stub and cleanup — no router, no form, no MSW, no `user-event`): roles, accessible names, slot presence, the attribute pair in both modes, the two geometry classes, the empty banner's absence. The admin does not adopt it here; `apps/admin`'s only edit is the named `shared/ui` re-export.

**Done when:** `@repo/ui`'s suite asserts, per mode, the two attributes on one element with `data-full-height` empty-when-on and absent-when-off; full-height mode renders `h-svh` on the inset element and `min-h-0` on the `data-slot="page-container"` element (both readable as class strings in jsdom); the page-header and banner rows are siblings of the page container carrying `shrink-0`; the empty `banner` slot leaves no node in the DOM; `title` renders as exactly one element with `role="heading"`; each slot's content is reachable by role or accessible name; `app-shell.tsx` opens with `"use client"` and adds no dependency; `apps/admin`'s diff is the one re-export line; the gate is green.

### 5. The account menu moves to the header

**ADRs:** [0049](../adr/0049-admin-app-architecture.md) §The-shell-adapter, [0048](../adr/0048-app-shell-and-record-surfaces.md) §2, [0046](../adr/0046-interface-localization.md)

Separated from the adoption because it is a different kind of risk — four shipped assertions and a public-API widening, not geometry — and because ADR-0049 makes three decisions about it that each have a wrong answer:

### 6. Breadcrumbs, and the record-label channel

**ADRs:** [0048](../adr/0048-app-shell-and-record-surfaces.md) §2, [0046](../adr/0046-interface-localization.md) §8, [0044](../adr/0044-record-routes-without-list-state.md), [0036](../adr/0036-admin-testing-strategy.md)

The first of two slot-proving steps, and the one `D8.9` depends on. The adapter composes the long-exported breadcrumb primitives into their first rendered screen, on the record routes, where the surface's URL gives the trail its meaning (ADR-0044). The trail is **JSX the app builds, not data the shell takes** — `Breadcrumb*` from the `shared/ui` door with `asChild` over the router's typed `Link`, because a shell rendering `href`s would emit plain anchors and reload the document.

Ancestor crumbs come from route `staticData`, read by the existing `shared/lib/route-meta.ts`; **the record's own crumb needs a channel that does not exist yet** — `route-meta.ts` reads `staticData.title` and `fullHeight` and nothing else — so this step adds the one ADR-0048 §2 specifies: a third optional `staticData` field, **`recordLabel?: (loaderData: unknown) => string | undefined`**. Its *type* is added to the `StaticDataRouteOption` augmentation in **`app/providers/router.tsx`**, where the other two already live; the callback is written by the two `$id` routes (`_dashboard.staff.$staffId.tsx`, `_dashboard.users.$userId.tsx`), which own the type of their own loader data and are the only place the narrowing can be justified. The two `new` routes declare none and fall back to `staticData.title` — a record being created has no label yet. It is read by **a third hook, `useRouteRecordLabel(): string | undefined`**, beside the untouched `useRouteTitle`: a label is loaded data rather than a `TranslationKey`, so it must bypass the `t()` wrap `useRouteTitle` applies, and it scans for the deepest match declaring `recordLabel` independently of the one declaring `title`. The channel and its consumers are separate — the breadcrumb's last crumb reads the label unconditionally, while the shell's `title` takes it only on the `page` branch, and the adapter is what decides, passing `recordLabel ?? routeTitle`. This is the same channel `D8.10`'s `page`-variant heading needs, which is why it is built once, here.

Ancestor labels are `TranslationKey`s (ADR-0046 §8); the record's own label is loaded data, not copy. **No door widening** for a trail that never collapses — `shared/ui` has exported six breadcrumb symbols since D3.3 and the `breadcrumb`/`more` keys already have a `t()` call site and an `lv` entry; a collapsing trail would need `BreadcrumbEllipsis` as a seventh export, owed by the first trail that collapses and not by this step. The stale "never reached the `shared/ui` door" comment in `app/providers/ui-strings.tsx` is corrected here, the step ADR-0048 assigns it to: whichever first renders one.

**Done when:** a breadcrumb renders on the record routes and is reachable as a navigation landmark; **clicking an ancestor crumb in the memory router changes the active route without unmounting the shell** — the observable form of "in-app, not a reload", since jsdom cannot see a document reload; **a test asserts the trail's last crumb on `/staff/$staffId` renders the loaded record's own label**, which is what proves the channel end to end; `recordLabel`'s type is declared in the `StaticDataRouteOption` augmentation in `app/providers/router.tsx` and supplied by the two `$id` routes — typed at the declaration rather than cast at the read — and read by a new `useRouteRecordLabel()` with `useRouteTitle`'s signature unchanged; ADR-0048:63 cites `D8.6` as the breadcrumbs slot's proving screen; the stale provider comment is gone; the gate is green.

### 7. The banner's consumer: the pseudo-locale notice

**ADRs:** [0048](../adr/0048-app-shell-and-record-surfaces.md) §3, [0046](../adr/0046-interface-localization.md) §10 §14, [0036](../adr/0036-admin-testing-strategy.md)

The second slot-proving step, separate because it shares nothing with the trail but the slot-honesty rule — the defect this repository has recorded twice about the `page` edit surface, and the plan carries a rule against a third.

The dev-only pseudo-locale notice renders a `Banner variant="info"` into the slot, and **its visibility is a prop with the channel ADR-0048 §3 names** — a `PseudoNoticeProvider` whose context lives in `shared/` and is mounted from `app/providers`, the way `app/providers/settings.tsx` mounts `shared/theme`'s `ThemeProvider`; its default is `config.VITE_I18N_PSEUDO`, `_dashboard.tsx` is its only reader, and it reaches the adapter as a prop. Tests override it through a **new `renderApp` option named `pseudoNotice`**. It must be a new name: `renderApp`'s existing `pseudo` already means the pseudo-locale *lens* and reaches only `createI18n`, and `createAppRouter`'s context is exactly `{session, queryClient, client}`, which no record here may widen. **`renderApp` builds its provider tree by hand** (`src/test/render.tsx`), so the provider is added to that tree explicitly — mounting it only in `app/index.tsx` would never reach a test. Gated on the config variable directly the notice would render in no test in the repository, because the admin vitest config pins the variable to `"false"` for the whole suite on purpose. The notice's copy is the app's — keys in the admin's catalogues, never the package's — so ADR-0046 §14's pseudo-locale route suite stays green over it.

**Done when:** the pseudo-notice context is defined in `shared/`, mounted from `app/providers` **and added to `renderApp`'s hand-built tree**, with `config.VITE_I18N_PSEUDO` as its default; a test passing `renderApp`'s new `pseudoNotice` option sees the notice inside the banner region while the suite's default renders no banner node at all; the pseudo-locale route suite is green with the notice's keys in both catalogues; the gate is green.

### 8. The record-surface container, in the package

**ADRs:** [0048](../adr/0048-app-shell-and-record-surfaces.md) §4 §5, [0047](../adr/0047-ui-package-scope.md), [0035](../adr/0035-config-driven-resource-ui.md), [0044](../adr/0044-record-routes-without-list-state.md)

The surface's package half, separated from its adoption for the same reason the shell's was — and after the shell because nothing in it depends on the surface, while both adoptions depend on their compositions existing. `compositions/record-surface.tsx` (`"use client"`): one content-agnostic container in three variants — `dialog` | `drawer` | `page` — fixed header, scrolling body (`overflow-y-auto min-h-0`), fixed footer as a slot.

**The `<form>` wraps header, body and footer with only the body scrolling**, which fights the primitives' own layout — `DialogContent` is `grid … gap-4 p-6`, `SheetContent` is `flex flex-col gap-4`, both laying out their direct children — so wrapping collapses them to a single child, and that child is the element carrying the row template and the body's `min-h-0`. The container gets that element rather than supplying it: **the `column` render prop is ADR-0048 §4's inversion** — `column({ className, children })` is called with the container's geometry classes and its three rows, and the app returns its `<form>`. **Not `asChild`**: Radix `Slot.Root` (every `asChild` in `packages/ui`) clones its child and merges props but does not render the parent's children inside it, `Slot.Slottable` has no precedent in this repository, and the element handed over is a React component rather than a DOM node. With no `column` given the container renders its own `div`, which is the detail-view and long-confirmation case.

**Geometry only**: neither `react-hook-form` nor `@tanstack/react-router` enters the package — the form-state reads and the navigation blocker are the app's thin wrappers, next steps. Sizes are the `sm | md | lg | xl | full` token set, mapped per variant to a class string merged through `cn` — and for `dialog` that class carries the **`max-h` onto `DialogContent` itself**, which has none today, so a bound on the column would bound nothing; `SheetContent` is already `inset-y-0 h-full` on the `left`/`right` side variants the `drawer` uses, so it needs no equivalent. Both merge `className` already, so sizes cost **zero generated-file edits**. Both mounts are the container's API: `open` / `onOpenChange` for the three shipped controlled dialogs, defaulted always-open for the routed mount; `dismissible={false}` refuses Escape, overlay and close alike. The structural pins are built in rather than approximated: `dialog` renders a Radix Dialog (`role="dialog"`), `drawer` the primitive `SheetContent` with `data-slot="sheet-content"` and still modal, `page` neither; the title is a real heading in `dialog` and `drawer` and **absent under `page`, where the shell's `<h1>` carries the record's label** (§2); the close button is the primitive's own, already localized — no new string. `ConfirmDialog` is not touched: it stays on `AlertDialog`, named by the ADR as the future candidate for a confirmation with a long body.

**Done when:** the package suite asserts, per variant, the structural pin, the title's heading role in `dialog`/`drawer` and its absence under `page`, and header and footer as siblings **outside** the element carrying `overflow-y-auto`; each size token maps to a distinct class on the right content element, and the `dialog` variant's bound is asserted **on the `DialogContent` element**; the controlled mount renders its content under `open` and removes it after a rerender with `open={false}`, with the routed mount needing neither (the callback firing from a gesture is the app's suite to assert — the package harness has no `user-event`); no record still describes the inversion as `asChild` — ADR-0047 §What-code and ADR-0048 §4 both read `column` render prop; `packages/ui/src/components/` and `src/hooks/` carry no new uncommented divergence; no dependency is added; the gate is green.

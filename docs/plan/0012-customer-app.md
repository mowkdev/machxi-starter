# D12 — Customer app

> **Renumbered from D11 on 2026-08-29**, when the design foundations and account area ([D11](0011-design-foundations-and-account-area.md)) were inserted ahead of it — a ledger decision, the D5 precedent; see `docs/plan/README.md` §How D11 was inserted.

- Status: **shipped 2026-09-01** — opened 2026-08-31, the operator's decision, the day D11 shipped. The window covers [ADR-0055](../adr/0055-customer-app.md), `proposed` at opening and **accepted 2026-08-31 at the head of `D12.1`**, where [ADR-0022](../adr/0022-frontend-apps.md) moved to `superseded by` (a delta: the roster; every stack decision stands)
- Steps: `D12.1` – `D12.12` (`D12.12` added 2026-09-01 at the operator's post-close review, out of finding 6 — the D11.12 precedent)
- Ledger: [`docs/plan/README.md`](README.md)

Scope: **`apps/customer`** — a Vite + React SPA over the `/user` segment, dev port 3002, the same shape as `apps/admin` — built as the **second consumer** of the shell, surfaces, machinery and design language that D8–D11 designed, extracted and settled. It ships self-service v1: sign-in on the ADR-0033 session model, profile, credential self-service ([ADR-0027](../adr/0027-credential-self-service-and-reset.md)'s rules with the account as actor), settings (D6, density included), and account deletion ([ADR-0028](../adr/0028-account-deletion.md)'s user semantics, self-served), localized in `en` and `lv` from the first screen and drawn in Instrument ([ADR-0054](../adr/0054-design-language-instrument.md)) from the first pixel.

**The app was the forcing function; now it is the proof.** This deliverable was originally scoped as one with the extraction, on the argument that "an extraction with one consumer is speculation with extra folders". The operator split them because the second consumer's requirements were already known well enough to design against — so the burden this deliverable carries is the other half of that bet: **anything `apps/customer` cannot build from the packages without changing them is a finding against D8–D11**, recorded as such in this file rather than patched silently. A package diff in this deliverable is either a named finding or a defect in the step that made it.

## The sharing decision (settled in scoping, 2026-08-20)

**Separate apps, not one merged app.** The population boundary is the app boundary: [ADR-0017](../adr/0017-identity-model-populations-and-roles.md) split `staff` and `user` into separate tables, flows and segments, and the [ADR-0033](../adr/0033-browser-api-client-and-session.md) session machine — in-memory token, single-flight refresh, CSRF bootstrap — is built around one population per client. A merged app would run two session models in one SPA, ship the admin panel's code in every customer's bundle, and put the customer-facing attack surface in the same origin as staff sessions. Impersonation ([D13](0013-impersonation.md)) also gets _cleaner_ with separation: the staff session and the impersonated customer session never coexist in one client.

## The decisions, taken 2026-08-31

All in [ADR-0055](../adr/0055-customer-app.md), written at opening and deliberately mostly by reference: the roster (customer joins at 3002; `apps/web` is marketing only, its architecture D14's — the supersession of frozen 0022 the 2026-08-22 re-scoping deferred to "the day an app actually changes"); the architecture as the admin's records applied through the app's own `shared/` doors; the `/user`-segment deltas — **no roles and no policy table** (configs offer, the API refuses; ADR-0042 stays an admin record), the slim account control in `headerEnd` (the slot's promised second consumer), 0053's account-area shape with **deletion in the security section**, **no grid until a domain entity arrives**, and the bundle budget from first build; and the **three self-service endpoints the segment lacks** — profile read/write, password change with 0027's re-auth and session-revocation rules, and self-deletion with 0028's semantics plus password re-auth and every-session-revoked. Email change, registration and password reset stay deliberately unwritten (the Planned list).

## Assumptions (revisable while in progress)

- **Self-service v1 only.** No customer-ownable domain entity exists; the grid, real navigation and list screens arrive with the first one the operator names. If one is named mid-deliverable, it folds in here and this file gains the scope.
- **The e2e smoke stays read-and-restore.** Self-deletion is never run against the dev database (it would consume a seeded fixture with no registration endpoint to replace it); its proof is the integration tier and the MSW tier. The tier's ADR-0020 request budget grows with the customer specs and the probe's floor moves with it.
- **The i18n tooling pattern is the admin's** (`i18n:check`/`i18n:extract`, the type-source `en`, the drift check in `pnpm check`), instantiated per app.

### ~~4. API — self-deletion~~ — **done 2026-08-31**

**ADRs:** [0055](../adr/0055-customer-app.md) §4, [0028](../adr/0028-account-deletion.md), [0013](../adr/0013-error-model.md)

`DELETE /api/v1/user/profile`: current password required, soft delete with 0028's user semantics carried exactly, **every** session revoked including the caller's. Integration tests prove the refusals, the soft row, the dead tokens and the email's post-deletion state under the partial index; Postman entries.

**Done when:** `pnpm test:int --filter api` green on the new cases; `pnpm test:postman` green; the gate green.

**What was built.** `deleteProfileBody` in `@repo/contracts` — one `currentPassword` on `presentedPasswordSchema`, declared in `users/` rather than beside `changePasswordBody` in `auth/` because that file holds shapes _both_ populations send and ADR-0028 rule 4 means no staff mirror of this will ever exist. Then `deleteProfileSchema`, `usersService.deleteProfile`, `createUserProfileController`'s `remove` and `router.delete("/")` — the same four files the module's other two self endpoints run through.

Three decisions worth naming, none of which the records had already made:

- **A `DELETE` with a body**, which is unusual. ADR-0055 §4 spelled the path and required the re-authentication, and a body is the only place a presented credential can go: a password in a query string is logged by every proxy between the browser and the process. The admin `DELETE /admin/users/:id` keeps its empty body for the opposite reason — the actor there is staff acting on somebody else, already fenced by a role guard.
- **A second delete answers `404`, not the admin segment's `409 USER_DELETED`.** The self view filters `deleted_at`, so every other `/user/profile` endpoint already answers `404` for a deleted row and this one agrees with them. It is unreachable from a real client anyway: the first call revoked the session that could ask, so the repeat is refused by `authenticate` with `401 AUTH_SESSION_REVOKED`, and the integration tier asserts that rather than the `404` no browser can see.
- **The response clears the auth cookies**, which no ADR asked for and the endpoint is wrong without. `clearAuthCookies` is what `logout` calls, for a reason that applies here with nothing left to argue: revoking the session server-side while leaving a thirty-day refresh cookie in the browser makes "signed out everywhere" true of the database and false of the device in the person's hand, and the browser would spend a `RATE_LIMIT_REFRESH_MAX` failure on the dead cookie at every boot. It is the one cross-module import the step added (`users.controller.ts` → `../auth/index.js`, beside the service's existing two), and it is what `D12.8`'s "the client lands on `/login`" rests on.

**Probed rather than assumed**, as `D12.3` was. Deleting the whole re-authentication block fails exactly the two cases that name it — the wrong password and the `null` `password_hash` — and the other twenty-eight stay green. Sparing the caller's session (`exceptSessionId: principal.sessionId` on the in-transaction sweep, which is what `changePassword` does) fails the unit case that pins it and **no integration case**, because the post-commit straggler sweep carries no exception and ends the session a moment later anyway. That is the endpoint still being correct and the tier being unable to see _where_ it became correct; the rule lives in `users.service.test.ts` because that is the only place it is visible.

**The review found three, all fixed.** A sentence in the controller docblock had lost its verb. The router's docblock accepted a hash-cost risk in the name of `change-password` alone, and there are two endpoints on that pool now — the note says so, and says the new one is smaller in degree (one hash, not two, and callable at most once per account because it ends the session that called it). And the cookie-clearing integration case signed in as a cookie client and then deleted with a _body_-transport token: clearing is unconditional, so it passed either way and proved nothing about the name on it. It now deletes with the cookie session'''s own access token.

Eleven integration cases and eight unit ones. `pnpm test:int --filter api` green (486, up from 475); `pnpm test:postman` green (105 requests, 323 assertions) — the collection's last account now closes itself through the customer's own door instead of being closed by staff, which is the run's only behavioural change and leaves it, as before, with nothing behind.

3. **An unrecognised error code degrades to "check your connection", not to the catalogue's fallback** (`D12.2`). 6. **One `__Host-machxi.csrf` cookie at `Path=/` now serves two populations** (`D12.2`, from the step's security review). Refresh cookies are correctly per-segment — `authCookiePath` scopes them to `/api/v1/{admin,user}/auth` — but the CSRF cookie is deliberately host-wide (`apps/api/src/core/http/cookies.ts`: `__Host-` requires `Path=/`, and the app's own pages have to read it). `setAuthCookies` rotates it on **every** login and refresh. Until this deliverable exactly one SPA could hold a session against a given API host, so rotation was always the rotating client's own. It is not any more: with the admin panel and the customer app open against the same host, an admin refresh strands the customer's in-memory CSRF token and vice versa. The client recovers with one re-bootstrap (ADR-0030's endpoint echoes rather than rotates, which is why `CSRF_TOKEN_INVALID` stopped being terminal at `D3.2`), but a second `403` inside that window **is** terminal — a forced sign-out caused by unrelated traffic in another tab.

   **Extended `D12.4`.** `DELETE /api/v1/user/profile` joins the endpoints that _clear_ that cookie rather than rotate it, because it calls the same `clearAuthCookies` `logout` does. Clearing is not a new failure mode — every `logout` in either app has always removed the other app's CSRF cookie host-wide — and the client recovery is identical, one re-bootstrap. It is recorded here so the successor ADR weighs the whole set: the cookie is written by login and refresh, and removed by logout, logout-all and now self-deletion, in whichever of the two apps acts last.

   The first finding here that is neither a duplication nor a bug in one app: it is a property of the _deployment_ that only a second SPA could expose, which is precisely what this deliverable was split out to find. It is also **not amendable** — [ADR-0029](../adr/0029-browser-token-transport.md) is frozen and decided this cookie's shape — so it needs a superseding record rather than a patch, and that record has to weigh a per-population cookie name against `__Host-`'s `Path=/` requirement. Unreachable in dev today only because nobody runs both apps signed in at once; the browser tier (`D12.10`) is where it would first bite.

   **Closed 2026-09-01 by `D12.12`.** [ADR-0056](../adr/0056-per-population-csrf-cookie.md) is the superseding record this paragraph asked for, and the weighing came out the way the paragraph guessed it might: `__Host-` constrains `Path` and `Domain` and **not the name**, so `__Host-machxi.csrf.admin` and `__Host-machxi.csrf.user` keep `Path=/` and the whole prefix guarantee while ending the sharing. It is **the only one of the eleven that became a build step**, which is the distinction worth keeping — the other ten are duplications and gaps whose cost is paid by whoever changes them next, and this one was a defect with a window in it. It stayed a finding for ten steps and became a step at the operator's post-close review, on the `D11.12` precedent.

7. **The account control and the sidebar footer are Instrument geometry with a second consumer and no composition** (`D12.5`). `AppShell` is a package and took this app's nodes unchanged — that is the step's headline and it holds. What is _inside_ those nodes did not travel: the account trigger's `h-auto px-2 py-1.5 has-[>svg]:px-2` and the three-line `tailwind-merge` argument beside it, the 232px/`rounded-xl` popover ADR-0054 §7 measures, the monogram block, the active nav item's `inset 2px` shadow over `--primary-tint`, and the 48px mono version footer are all now written twice, near-identically, in two `widgets/app-sidebar` files. It is finding 2's shape a second time and for the same reason: ADR-0048 §2 gave the shell a `headerEnd` _slot_ and deliberately did not say what goes in it, because what goes in it is app content — a principal, a route to the account area, a session to end.

   The finding is therefore not "extract it now" but the precondition: the parts that are pure geometry (the trigger's size overrides, the popover's width and radius, the footer band) are §7 and §5 assignments that a third consumer, or a §7 change that must land twice, would have to apply in two places and could apply in one. The parts that are content (which items hang there, what they say, where they go) must stay app code. Splitting those two apart is a `@repo/ui` API decision, and this deliverable's rule is that such a diff is named before it is made.

8. **ADR-0034's notification policy is written twice, and the second copy holds no app knowledge at all** (`D12.6`). `app/providers/query-client.ts` is `apps/admin`'s file with not one line of its own: the mutation cache that turns `meta.success` into a toast and suppresses the error toast a form will render inline, the query cache that stays silent unless a query asks, `staleTime: 30_000`, and no retry on a 4xx — that last one discriminating **on status rather than on `isApiClientError`**, which is a real trap ADR-0034's own snippet fell into and which is now available to be fallen into twice. `shared/ui/query-error.tsx` is the same story one file down, and `shared/notifications/messages.ts`'s `englishMessageForError`/`createDeferredErrorMessage` pair is a third.

   It is finding 4's shape at a larger size: the policy belongs to ADR-0034 and to neither app, and there is nowhere to put it — `@repo/api-client` owns the transport and not the cache, and a package created for this would be a decision rather than a tidy-up. **What is _not_ a finding here is `shared/api/query-meta.ts`**, and the distinction is worth keeping: `D9.6` looked at that file, decided a second app should write its four lines, and priced the alternative (a door with nothing to export, plus a slice-wide lint exemption). That prediction came true exactly as written. The three above were predicted by nobody, and the one that would hurt most to have diverge is the retry rule.

9. **`SettingsOptions` is ADR-0054 geometry with a second consumer and no composition** (`D12.7`). It is finding 7's shape a third time and the cleanest instance of it yet, because unlike the account control there is no content half to argue about: `apps/customer/src/shared/ui/settings-options.tsx` is `apps/admin`'s file with the words changed in its comments and nothing changed in its output — the 44px option rung, the two layouts over one height, the inset `2px` bar over `--primary-tint`, the `min-w-0` that stops a `<fieldset>`'s UA `min-width: min-content` widening its card, and the `SELECTED` block that spells its own `hover:` twins because `cn` merges per modifier chain. Every line is §3 and §7 assignment; none of it knows what a theme or a language is.

   It is a `@repo/ui/compositions` candidate by ADR-0047's own test — presentation-only, no `@repo/contracts`, no routing, no forms — and it is copied rather than moved for the reason every duplication here was: a `packages/*` diff is named before it is made. What the move would have to settle is the generic parameter (`SettingsOptions<TValue extends string>` is typed by the caller's enum, which a package cannot narrow for it) and whether `layout` stays two words or becomes the composition's own vocabulary. Both are API decisions; neither is urgent while the two copies are byte-equivalent, and both become urgent the moment a §7 change has to land twice.

10. **The settings entity is `apps/admin`'s, minus the two thirds this app has no grid for** (`D12.7`). `settings.api.ts`, `settings.keys.ts` and `settings.queries.ts` differ from the admin's in the resource type's _name_ and nothing else — `StaffSettingsResource` and `UserSettingsResource` are the same shape, deliberately, and `@repo/contracts` says so in a comment naming this app. `settings.storage.ts` is the more interesting half: what was copied is ADR-0045's coalescing decision — the queued scalars, the one debounced `PATCH`, the subscriber installed rather than captured — and what was _not_ is everything ADR-0041's preference seam forced, because there is no grid, no store, no key to parse and no mirror to seed.

    That asymmetry is the finding rather than the line count. Finding 8 said ADR-0034's policy "belongs to neither app and there is nowhere to put it"; this one is narrower and more tractable, because the thing that belongs to neither app is exactly the part that survived the subtraction — a debounced writer over a per-key-merge endpoint — and the part that did not survive is precisely the part that would have made a shared version hard. A package boundary drawn here would be small and would have two honest consumers. It is still not drawn in this deliverable, because the seam runs through `@repo/api-client` (which owns the transport and not the cache) and through whatever owns `entities/*` conventions, which is nothing today.

11. **`@repo/form`'s shells have one submit appearance, so the most destructive form in the app draws in the primary style** (`D12.8`). `AppFormActions` renders `<Button type="submit">` with no variant and no way for a caller to ask for one, which was invisible while every config-driven form was a create, an edit or a password change. Account deletion is the first form whose _submit_ is the destructive act, and ADR-0054 §4 has a `destructive` token precisely so an irreversible action can say so where the click happens. The confirm path has this already — `apps/admin`'s `ConfirmDialog` takes a `destructive` prop — and the form path does not, which means the design language is available to the ceremony _without_ a field and unavailable to the one _with_ one.

    Copied nothing and changed nothing: the dialog ships with the default submit, and the warning is carried by the card's `variant="destructive"` trigger, the dialog's title and the four-sentence consequences list. The fix is a `@repo/form` diff — a `submitVariant` (or `destructive`) prop threaded from the three shells into `AppFormActions` — and it is small, which is exactly why it is written down rather than taken: this deliverable's rule is that a package diff is named before it is made, and the API question (one boolean, or the button's whole variant vocabulary) is a decision rather than a tidy-up. The next destructive form is what makes it urgent.

Findings 1, 2, 4, 7, 8, 9 and 10 are duplications the deliverable expected; finding 5 is a larger one it did not; findings 3 and 6 are defects, and 6 needed an ADR rather than a fix; finding 11 is the first **gap** — not a duplication and not a defect, but a package that serves this app almost completely and stops one prop short of the screen it was asked for. **None is a `packages/*` diff**, so §Definition-of-done item 3's list of _diffs_ is still empty. All are recorded because the alternative is that the second consumer arrives, notices, and says nothing — which is the failure this deliverable was split out to prevent.

**Amended 2026-09-01 (`D12.12`): the list of diffs is no longer empty, and both entries are named above.** Finding 6 became this deliverable's twelfth step, and building it corrected three comments in `packages/contracts` that named the retired cookie — on the same footing as `D12.4`'s `deleteProfileBody`, because a wire fact belongs to the contract and `@repo/contracts` is not one of the six packages the deliverable is a second consumer _of_. The one platform-package diff the step could have made, a stale cookie name in `packages/api-client`'s CSRF-retry comment, was **not** made and is named in `D12.12`'s own notes instead: the mechanism the comment describes is unchanged, so the correction is a word rather than a fix, and this deliverable's rule is that such a diff is named before it is made.

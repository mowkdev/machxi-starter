# D17 — Impersonation in a new tab: build notes

The per-step build record of [D17](0017-impersonation-new-tab.md) — what was built, the amendments, the review findings and their fates, the gate's output, and what is pending the operator — kept apart from the executable plan so a builder opens the plan and not the journal ([ADR-0068](../adr/0068-behaviour-specs-and-plan-notes.md) §2, the plan apart from its notes). `/step` appends here; `/ship` and the close-out read it.

## D17.1 — Accept ADR-0070; the exchange ends the impersonated session it replaces

**The head.** [ADR-0070](../adr/0070-impersonation-in-a-new-tab.md) moved `proposed` → `accepted` and its one parent [ADR-0057](../adr/0057-impersonation-sessions.md) moved to `superseded by` with the delta stated in both directions — §7's same-tab bullet replaced, §3's "its session row is not touched" narrowed to a **real** customer session. The index's topic row for sessions now names 0070 beside 0067 and 0064, 0057's records-table row names 0070 in its Status cell and this step in its Implemented cell, and the ledger's window section — the one place window state is stated — records the acceptance. The derived digests (`docs/rules/api-and-data.md`, `docs/rules/process.md`) picked 0070 up mechanically from `pnpm rules:digest`.

**The code (ADR-0070 §4).** The exchange's controller reads the user population's refresh cookie through `cookies.readRefreshCookie`, the way `refresh` reads it, and hands the raw token to the service — the service still knows nothing about HTTP (ADR-0009). Inside the exchange's own transaction, after the handoff is consumed and before the new session is minted, `AuthService.endReplacedImpersonation` resolves the token to a session and, when it is this population's, live and carries an actor, revokes it with `impersonation_ended` and writes its `impersonation.ended` row. A real customer session, and a cookie that resolves to nothing, change nothing; the exchange's refusals are untouched and still one indistinguishable `401`. `docs/specs/impersonation.md`'s exchange requirement gained the behaviour, two scenarios and ADR-0070 in its `Records:` line.

**Amendments.** None to the plan or the records. The done-when's "`data` names the replacement" is satisfied literally rather than by reading it down: the row carries `reason: "replaced"` plus `replacedByStaffId` and `replacedByHandoffId` off the consumed handoff, which is also what the security review asked for (below). The record's "`data` says it was replaced" is unchanged and still true.

**Review — `security-reviewer` and `adr-reviewer`, one pass each, no re-review.**

- **Fixed — the log line outlived its transaction** (security, medium). `endReplacedImpersonation` logged inside the transaction, which a later refusal rolls back; the log survived to describe an ending that never happened, while the audit row did not. The function now returns the boolean its doc comment always promised and the exchange logs after the commit.
- **Fixed — the row named only the previous operator** (security, medium). The `actor` is the staff member whose impersonation is ending, which is right, but on a shared support workstation the human who ended it is somebody else. `data` now names the replacing staff member and handoff.
- **Fixed — the grace-window claim was wrong** (security, low). The comment said a rotated-out token is one `refresh` itself would refuse; inside `REFRESH_ROTATION_GRACE_SEC` it is not. Reworded to state the gap deliberately and say why it is bounded — the exchange overwrites the jar, so the session it fails to end is one no tab can reach.
- **Fixed — the index and the gate** (ADR, blocker + major + minors). `pnpm format:check` was red on the new test (formatted); 0057's Implemented cell had no `D17.1` note (added); the index's D17 narrative bullet still read as pending (dated); the new spec scenario carried two outcomes in one THEN (split in two); `<=` on two `Date`s where the file compares `getTime()` twelve hundred lines up (aligned), and `AuthServiceDeps.audit`'s docstring still claimed one writer of `impersonation.ended` where there are now three (corrected).
- **Logged, not fixed — two exchanges racing on one jar** (security, low, plus the same reviewer's residual note). `sessions.revoke` is `update … where revoked_at is null` and returns `void`, so two exchanges reading the same live session both write an `impersonation.ended` row, and both mint — leaving a live impersonated session no tab can reach. Closing it means either a returning `revoke` (a shared repository signature, used by every revocation path) or a partial unique index on the sessions table. Both are bigger than this step and neither is what ADR-0070 §4 decided; it belongs to a record of its own. The exchange also now does cookie-dependent work, so it has a latency oracle behind a valid handoff — reachable only by staff who can mint, and the mint is budgeted per actor.

**Gate.** `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check` — **green**, exit `0`, every task cold on the test link (api 611 + 628, admin 499, customer 188, the packages green, prettier "All matched files use Prettier code style!"). `pnpm test:postman` — 165 requests, 504 assertions, 0 failed. `node scripts/docs-hygiene.mjs` — inherited documents clean, behaviour specs clean (11 files). `apps/api/test/impersonation.int.test.ts` is 26 cases, three of them new: the replaced session's refresh token answers `401 AUTH_SESSION_REVOKED` with an `impersonation.ended` row naming the replacement, a real customer session's cookie leaves that session refreshing, and an unknown cookie mints as before.

**Pending the operator.** Nothing from this step — it is API-side and machine-proved. The browser half of the definition of done arrives with `D17.2` and `D17.3`.

## D17.2 — The admin half: the tab opened on the click

**The code (ADR-0070 §1–§3).** `impersonate-user-dialog.tsx`'s `onConfirm` now opens a blank tab **synchronously inside the click** — `window.open("", "_blank")`, no URL because the address does not exist yet — keeps the handle, and only then mints. On success it builds the handoff URL once, sets `tab.opener = null`, assigns `tab.location.href`, resets the mutation and closes the dialog; `D13.8`'s "no `onClose()` first" was about a document that was leaving, and this one stays. A refused mint closes the tab it opened, lifts the latch and leaves the confirm open with its toast. A refused open — `null`, or a handle whose context is already `closed` — falls back to `window.open(url, "_self")` after the mint, exactly as `D13.8` built it, and does **not** close the dialog. `handoffUrl` and its test are untouched.

**The latch.** `leaving` is set at the open rather than on the answer, so it covers the whole open-to-navigation interval the plan names, and **a refusal lifts it** — the one departure from the comment `D13.8` left behind ("`leaving` is never cleared"). Set at click time and never cleared, a refused mint would leave the operator in a modal with a dead confirm and no exit but Cancel; a case asserts the confirm is enabled again after a refusal.

**The copy.** `users.impersonate.description` opened "This tab moves to the customer app", which the pre-opened tab made false in both locales. Rewritten in `en` and `lv` to say the customer app opens in a new tab and this panel stays. The three facts the confirm exists to carry — untouched session, refused operations, recorded against both — are unchanged, and the copy case grew a fourth fragment (`/new tab/`) so the promise is under test rather than under review.

**No spec change, deliberately.** [`docs/specs/impersonation.md`](../specs/impersonation.md) is the wire as a client observes it ([`docs/specs/README.md`](../specs/README.md); `.claude/rules/frontend.md` says an SPA spec arrives only when a step names one). This step moves no request, response, status, header or side effect — only which browsing context the panel hands the fragment to, which the record decides and the admin suite proves. The `Proved by:` lines were checked: none names a case this step renamed.

**Amendments.** None to the plan or the records.

**Review — `security-reviewer` and `code-reviewer`, one pass each, no re-review.**

- **Fixed — a closed handle is not a `null` one** (security, medium). `tab === null` was the only refusal the success path recognised, so a tab the operator shut during the round trip — or one an extension opened and closed again — took the writes as no-ops and ended in the outcome ADR-0070 §3 exists to prevent: a spent budget entry, an `impersonation.minted` row, a live sixty-second credential, a closed dialog, and no tab and nothing said. The test is now `tab === null || tab.closed`, the stub carries `closed` with a value rather than answering `undefined`, and a case drives it.
- **Fixed — a throw on the foreign handle would have skipped the reset** (security, low). The two lines that touch the other window can throw a dead-object `TypeError`; the handover is in a `try` whose `finally` resets, so the live handoff cannot outlive it in `getMutationCache()`.
- **Fixed — an unmount mid-flight orphaned the blank tab** (code, medium). TanStack Query runs no `mutate`-scoped callback for an observer that has gone, so a dialog left by Back while the mint was in flight got neither `onSuccess` nor `onError` and the tab outlived the panel. A ref holds the un-handed tab and an unmount cleanup closes it; the ref is cleared the moment the handle is handed over or closed, so the cleanup can only find a tab nothing was done with. Genuinely introduced by this step — before it there was no tab to orphan.
- **Fixed — "inside the click" was asserted by name, not by observation** (code, medium). The first case awaited `userEvent.click`, which resolves after microtasks, so an open moved into a microtask or into `onSuccess` would have passed. It now dispatches with `fireEvent.click` and asserts before the first `await`: one open carrying no URL, and the mint not yet even sent. That is the property a popup blocker checks.
- **Fixed — the fallback lost the assertion that was the point of the original case** (code, medium). The mutation-cache check had moved to the new-tab path, where the harness's spy `onClose` never unmounts anything; on the fallback path the dialog stays mounted in production too, so `reset()` is load-bearing there. Both paths now assert it, each with the reason that applies to it.
- **Fixed — two comments that argued from facts this delta removed** (both reviewers, low). `useImpersonateUser`'s "no `success` outcome" was justified by the document being torn down, true now only of the fallback — restated: the tab is the outcome. And the stub's "a read would throw" was wrong twice over (a set-only accessor and an absent property both read as `undefined`), so the comment now says what the stub cannot catch instead of claiming it cannot happen.
- **Fixed — the success path never asserted the tab is left open** (code, low). `expect(tab.close).not.toHaveBeenCalled()` on the handover case; a stray `close()` after the navigation would otherwise have gone unnoticed.
- **Logged, not fixed — one impersonation per browser is enforced at the exchange, not at the mint** (security, residual). Between a second mint and its redemption two live impersonated sessions exist in one jar; ADR-0070 §4 closes the window at the exchange by design. Worth naming if the handoff TTL ever grows.
- **Logged, not fixed — the token URL stays out of the customer tab's history by accident of the handle being on its initial `about:blank`** (security, residual). A second navigation of the same handle would push rather than replace. Nothing does that today and no test pins it.

**Refuted, not just asserted.** With `tab.closed` dropped from the guard and the unmount cleanup emptied, exactly the two new cases go red (`36 tests, 2 failed`) and the other thirty-four stay green — so both fixes are held down by something that fails without them.

**Gate.** `pnpm lint && pnpm check-types && pnpm test && pnpm size && pnpm format:check` — **green**, exit `0`. `lint` 17/17, `check-types` 16/16, `test` 15/15 tasks with **0 cached** (api 611 unit + 628 integration, admin 504 across 56 files — the impersonation block is 12 of them — customer 188, the packages green), `size` inside every budget (admin js 345.4/353.5 kB, entry 161.3/171.9 kB), `format:check` "All matched files use Prettier code style!". `node scripts/docs-hygiene.mjs` — inherited documents clean, behaviour specs clean (11 files).

**Pending the operator.** Two things, both browser-only and both already on the definition of done. **`pnpm test:e2e` is red until `D17.3` and expected to be**: `apps/customer/e2e/impersonation.spec.ts` drives the admin tab through the confirm and then waits for _that_ page to become the customer app, which is precisely the behaviour this step replaced. Rewriting it to drive a second page is `D17.3`, by the plan's own build order. And the browser half of the record — that the tab really opens beside the panel, that `window.opener` is `null` in it, that Back does not reach the panel, and that a pop-up blocker lands the operator in the same tab as before — cannot be seen from jsdom: the suite proves what this document _says_ to the handle, not what a browser does with it.

## D17.3 — The browser tier, and close-out

**The code (ADR-0070, ADR-0052 §The browser tier).** `apps/customer/e2e/impersonation.spec.ts` drives three browsing contexts in one jar: the admin panel and two customer tabs. `impersonateFrom(panel, row)` subscribes the context's `page` event **before** the confirm click — the tab is opened synchronously inside it, so a listener registered afterwards races the thing it listens for — and hands back the tab with the confirm locator. The walk then asserts what only a browser can answer: the confirm closes and the **grid is still on screen** behind it; in the opened tab `window.opener === null`, which is the effect of `D17.2`'s assignment rather than the assignment itself; the address is the customer origin's `/` with the fragment struck. The banner, the excluded operation and the allowed write run as before, in that tab.

**The second mint is the stage that needed both tabs alive** (ADR-0070 §4). It is driven from the grid the first mint left standing, which is the hazard that section answers; the first tab's next authenticated request is then refused, and the refusal is asserted **by code** — `AUTH_SESSION_REVOKED`, the discipline this file already applied to the exit's replay — because both mints target the same fixture customer, so the banner reads identically either way and a sign-out alone would prove nothing. The exit runs in the tab that still has a session (the second), for the reason the plan amendment gives: run first, it makes the second-mint stage vacuous.

**Amendments — one record, one plan step, and they are the same finding.** [ADR-0070](../adr/0070-impersonation-in-a-new-tab.md) §4 said the stale tab meets `401 AUTH_SESSION_REVOKED` "on its next **refresh** … a signed-out screen, not a silently swapped banner", and the second half of that is false for the path it names: a refresh carries the **jar's** cookie, which the exchange has just overwritten, so it succeeds and returns the replacement principal — and the customer app boots off a refresh, so any document boot of the stale tab lands in the second impersonation with the banner naming whoever was minted second. What the revocation really ends is the tab's **in-memory access token**. §4 is amended in place, labelled, to say "authenticated request"; §Consequences gained the bullet that states the identity swap as **bounded rather than prevented** and names what closing it would take — a client-side per-browsing-context identity check, a record of its own — and the plan's step 3 carries the same correction. The ledger's window section records the amendment, as it records every other. Found by `security-reviewer`; the browser tier is where the record's own sentence stopped being writable.

**Review — `security-reviewer` and `code-reviewer`, one pass each, no re-review.**

- **Fixed — the record's §4 claim was false for the path it named** (security, high). Above. The honest statement existed only inside a test comment; it is now in the record, the plan and the comment, in that order of authority.
- **Fixed — the stale tab's stage asserted only a heading** (security, medium). Both mints target the same customer — the dev fixtures hold one _active_ one — so "signed out rather than swapped" is unobservable from the screen. A `waitForResponse` registered before the focus asserts the code is `AUTH_SESSION_REVOKED`.
- **Fixed — the replay could pass on the _first_ session's token** (code, medium). With two exchanges behind it, `AUTH_SESSION_REVOKED` on the replay is only about the **exit** if the jar was really overwritten; an exchange that landed its session but wrote no cookie would leave `spent` naming the session the second mint had already revoked. The first session's token is read before the second mint and `spent` is asserted not to be it.
- **Fixed — the per-actor mint budget was unprobed and unstated** (security, medium). The walk now spends two entries of `RATE_LIMIT_IMPERSONATION_MAX`, which keys on the operator's id and is invisible to `assertApiWindowClear`'s global headers, so five runs in a quarter hour would fail as a thirty-second wait for a page event that names nothing. `impersonateFrom`'s `waitForEvent` takes a five-second timeout and rethrows naming the budget; the floor comment names it too.
- **Fixed — the swallowed click hid more than a race** (code, medium). The nudge is best-effort because a focus refetch usually gets there first, but `.catch(() => undefined)` swallowed a renamed or duplicated locator forever. Narrowed to `TimeoutError`; anything else is a defect in the file and is rethrown. The comment no longer claims the click is "guaranteed to reach the wire".
- **Fixed — the two re-measured figures did not reconcile** (code, medium). The spec grew +22 and the suite +18, stated as measurements of one change. Both were re-measured from a clear window (spec **50**, suite **156**), and the file now says plainly that this walk is the first figure in the tier that is not exactly repeatable — two stages turn on a tab regaining focus, and what a refocused tab refetches depends on which queries have passed a 30-second `staleTime`. Three runs measured 50, 50 and 54; the floor takes the low one plus the standing margin of 13, which is what the margin is for.
- **Measured and declined — `panel.bringToFront()` before the second mint** (code, uncertain). The panel is a background tab from the first `window.open` onwards and the second mint drives a focus-scoped Radix menu, so activating it first is the obvious defensive move. It costs **twelve requests** — a refocused tab refetches what is stale behind it, and behind this one is a grid — taking the spec from 50 to 62, the suite past 165 and ADR-0069 §2's own sizing premise (a tier run _and its retry_ beside Postman) past the 1000 it chose. Playwright dispatches input through CDP rather than through the window manager, so a background tab receives it; the line is one line away if a `--headed` run ever shows otherwise, and the comment says so with the number.
- **Documented, not built — no `afterEach` on the impersonation walk** (security, low). A failure between a mint and the exit leaves one live impersonated session for `IMPERSONATION_SESSION_TTL` and, on `retain-on-failure`, its refresh cookie in the trace. `playwright.config.ts`' trace paragraph — which had never named this cookie — now does, with its bound; the closing comment says "on the green path"; the `organizations.spec.ts` `afterEach` shape is named as the fix for a step that can measure it.
- **Fixed — ADR-0069's sizing premise was restated only as singles** (security, low). 330 + 165 doubled is **990** against the 946 the record chose 1000 on: ten requests of headroom, so the next growth of either suite crosses that record's premise rather than the raw sum. One clause carries the doubled figure.
- **Logged, not fixed — the reload path wants a record** (security, residual). Closing the identity swap is not an API decision: once the second exchange has written the jar there is nothing on the wire distinguishing the stale tab's boot from the new tab's. The candidate is the customer app recording the subject and actor it adopted per browsing context (`sessionStorage` survives a reload and is per tab) and refusing to adopt a different one silently. ADR-0070 §Consequences names it; it is not D17's.

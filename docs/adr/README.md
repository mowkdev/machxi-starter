# Architecture Decision Records

This directory holds the Architecture Decision Records (ADRs) for the `machxi-starter` blueprint repository.

The repository is a Turborepo/pnpm monorepo intended as a bootstrap for projects that need an API, an admin panel, a web app and (later) a mobile app. ADRs capture the _why_ behind the structure so that every project bootstrapped from this blueprint inherits the same conventions and can diverge deliberately rather than accidentally.

## What is in force

One row per topic, naming the record that governs it today. Where a record was superseded by a **delta**, the parent still stands for everything the successor does not touch and both are named. The window — which deliverable may amend its records in place — is stated once, in [the ledger](../plan/README.md#the-window); the condensed rules a session loads are the generated digests in [`docs/rules/`](../rules/).

## Conventions

- One decision per file, numbered sequentially: `NNNN-short-kebab-title.md`.
- Format follows [ADR-0050](0050-adr-lifecycle-and-verification.md) (MADR-lite: Context, Decision, Consequences, Alternatives — unchanged from the superseded ADR-0024 and ADR-0001).
- **The lifecycle is [ADR-0050](0050-adr-lifecycle-and-verification.md)**, superseding [ADR-0024](0024-adr-lifecycle.md) since D8 — statuses, altitude, when an ADR may be amended in place and when it must be superseded. In short: status is one of `proposed`, `accepted`, `deprecated`, `superseded by ADR-XXXX`; an accepted ADR with code standing on it is immutable, and change is expressed by a superseding ADR that **states the delta** and carries the parent's untouched sections by reference (whole restatement is permitted, never required — the rule ADR-0024 imposed and 0050 relaxed, which is why [0047](0047-ui-package-scope.md) and [0049](0049-admin-app-architecture.md) restate their parents whole and stand as they are). An ADR records decisions, not machine-checkable minutiae: counts and exhaustive enumerations belong in tests and lint rules.
- **The amendment window is scoped to a deliverable** ([ADR-0025](0025-deliverables.md) rule 2), not to a date. An ADR may be amended in place only while the deliverable it was written for is `in progress` in [`docs/plan/README.md`](../plan/README.md); once that deliverable ships, the ADR changes only through a superseding ADR.

### Planned (not yet written)

These will get their own ADRs when the corresponding features are implemented:

- Fine-grained permissions (permission table / policies) — see ADR-0017. [ADR-0042](0042-client-side-authorization.md) is not this: it mirrors the _existing_ role mounts on the client and says so.
- **A per-principal budget for expensive routes.** ADR-0020 §Residual risks names it as a missing category and ADR-0027 §Consequences adds the four credential endpoints to what it would cover. D2.3's security review sharpened it: on `POST /admin/{staff,users}/:id/password` the caller presents a password they may not know, so the `403` is a guessing oracle against the one credential that stops a stolen admin token, bounded only by the global `300 / 15 min / IP` and by argon2's own cost. It is a brute-force gap and not only a cost one, which is what the ADR that builds it has to close. Adding a fifth limiter would diverge from ADR-0020, which is frozen, so it is a new decision rather than a patch. **D13 takes one instance of the category rather than the category**: [ADR-0057](0057-impersonation-sessions.md) §1 gives the impersonation mint its own limiter keyed on the staff principal's id — decided in a record, as this bullet asks — and the general per-principal budget for the credential endpoints remains open.
- **Per-request principal freshness.** `authenticate` verifies the session and never the principal (ADR-0018), and `authorize` reads roles from the access token's claims, so an account that is disabled or hard-deleted keeps whatever its token says for up to `JWT_ACCESS_TTL`. D2.4 narrowed the window to a single statement by sweeping sessions again after the delete commits (ADR-0028 §Consequences, amended), and it cannot close it: a login already in flight inserts its session afterwards. Closing it means a principal check on the hottest path in the API, which is a cost decision and a supersession of ADR-0018 §Authenticated request.
- **Step-up authentication / re-authentication as a category.** ADR-0027 requires the actor's own password on an administrative reset because it is the only such mechanism available. A real one would replace that, and would be the right fence for ADR-0028's delete endpoints too.
- **Forced password change at next sign-in** (`must_change_password`) — needs a column, a migration and a branch in `authenticate`; ADR-0027 §Decision rule 4 states why it was not bolted on.
- **Email-based password reset** — needs email delivery, a single-use reset-token table, and the `3 / hour` limiter ADR-0020 §Rate limiting already reserves. See ADR-0027 §Out of scope. **The delivery half shipped at `D14.6`**: [ADR-0066](0066-infrastructure-seams.md) §1 — the `MailSender` port, a log adapter and an SMTP adapter, and Mailpit in the local compose file. The flows — reset, verification, email change, invitations — are their own deliverable after D15, and they compose against the port rather than deciding it.
- **Retention for soft-deleted accounts.** ADR-0028 keeps deleted user rows forever by design; how long personal data is kept is a compliance decision nothing has made. **D3.8 sharpened it from a storage question into an access one**: the users grid's scope switch (`filter[deletedAt][null]=false`) makes deleted accounts — email and both names — browsable in one click by anybody with `manager` or above. There is no retention window, no redaction and no restore path, and the ADR that closes this has to decide all three. It was considered for D3.10 and deliberately left unwritten: ADR-0028 is frozen so this is a supersession rather than an amendment, and the policy needs input the repository does not have.
- **Secret management and key rotation** — a `kid` scheme for `JWT_ACCESS_SECRET` when moving to asymmetric signing, and an argon2 **pepper** (`argon2`'s `secret` option). Both need the same key-id/overlap machinery, and rotating a pepper forces rehash-on-next-login, so they are one decision — see ADR-0018 §Consequences.
- **Scheduling the session prune.** `pnpm db:sessions:prune` exists (ADR-0008, D1.8) and expired rows accumulate until something runs it. What is undecided is _what_ runs it — cron, the platform's scheduler, or an in-process timer — which is the same decision as background jobs below.
- **OpenAPI generation** from `@repo/contracts`, and the contract-conformance test tier ADR-0021 leaves as "later". Until then the Postman collection is the API's documentation.
- **Shared rate-limit state.** The ADR-0020 limiters use an in-memory store, which counts per process; more than one API instance multiplies every limit by the instance count. A shared store is a deployment decision and belongs with the CI/deployment ADR. **Shipped `D14.6`**: [ADR-0066](0066-infrastructure-seams.md) §4 — `rate-limit-redis` behind `REDIS_URL`, the in-memory store by default, one store built in the container and handed to all four limiters, failing closed when a configured Redis is unreachable.
- **`apps/web` architecture.** ADR-0049 deliberately scopes itself to `apps/admin`, carrying that carve-out from the ADR-0032 it supersedes; Next.js App Router, server components and the user segment's session shape make `web` its own decision, owned by the marketing deliverable at the end of the ledger (**D14** since the 2026-08-29 insertion — `docs/plan/README.md` §How D11 was inserted).
- **Bulk mutation endpoints.** ADR-0038 executes bulk delete as a client-side fan-out over the per-row endpoints, on purpose — the ADR-0028 refusals are per-item semantics. A transactional `POST /admin/{staff,users}/bulk-*` becomes worth deciding if scale ever makes N requests the problem; it is an API deliverable's decision, with ADR-0028's rules to answer for.
- **A bounded URL-side filter schema.** `listQuerySearchSchema`'s `filterSchema` checks shape only — `field: z.string()`, scalar `value: z.unknown()` — which was safe while nothing rendered a filter no column owned. ADR-0039's chips bar makes an arbitrary deep-linked filter a _rendering_ surface (D4.4 clamps the label; the schema is where the length belongs). Bounding the field-name charset and the value length in `@repo/contracts` would close a class of "what does a hostile link do to this grid" questions at the source.
- **Negated filter operators.** ADR-0014's `FILTER_OPS` has no `ne` / `notLike` / `notIn`, so no ADR-0039 filter dialog may offer "not contains". Adding negation is a supersession of ADR-0014 (D1, frozen) and a repository change, not a UI change.
- **End-to-end browser tests (Playwright) for the frontend apps.** ADR-0036 deferred them; **they shipped at `D10.4`** (both apps carry `test:e2e`, beside the gate and never in it) and this entry was stale until 2026-09-02. What remains planned is running them automatically: [ADR-0059](0059-ci-containers-and-deployment.md) §1 (D14) schedules them nightly in CI.
- **The blueprint's rebranding seam.** [`docs/rebranding.md`](../rebranding.md) is the fork-time checklist: the catalogue `brand` blocks and the two document titles are the rendered identity (ADR-0046's design working as intended), and the runtime identifiers — the cookie names of [0056](0056-per-population-csrf-cookie.md)/[0029](0029-browser-token-transport.md), the JWT audience/issuer, the device storage keys whose parameters D12's finding 1 reserved — change once at fork or keep the name forever. Whether any seam becomes a real parameter (a storage-key prefix, an API-side cookie-prefix constant) is decided by the first fork that asks, owned by **D14** as the blueprint's outward face. **Shipped `D14.7`**: [ADR-0064](0064-brand-seams.md) — `APP_ID` on the API side deriving every cookie name and the JWT audience, `VITE_APP_ID` on each SPA deriving every device-storage key as `${appId}.${segment}.${fact}` through parameters the apps' `shared/` doors bind, `scripts/rename.mjs` for the mechanical half, and [`docs/rebranding.md`](../rebranding.md) reduced from seven sections to a three-line recipe. D12's finding 1 — two SPAs sharing `machxi.admin.*` — closes as a by-product.
- Background jobs, file storage. (Email delivery: the port shipped at `D14.6`, [ADR-0066](0066-infrastructure-seams.md) §1 — the flows have not.)
- Mobile app.
- **Multi-tenancy** — [ADR-0067](0067-organizations.md), written `proposed` 2026-09-02 and **accepted 2026-09-04 at the head of `D15.1`** ([`docs/plan/0015-organizations.md`](../plan/0015-organizations.md)): shared schema, organizations and memberships, a personal organization on every path that creates a user, resolution by URL, row-level security designed in and deferred. What remains open is that last clause — **enabling RLS** is a migration and a middleware once these tables exist, and its precondition, the application role, shipped at `D14.4`.

## Deliverables

**D1 — API foundation, shipped 2026-08-18.** A running, testable API against a local Docker Postgres, with database setup, a seeded super admin, both authentication flows, the staff/users admin resources and the user profile — verifiable end-to-end via Postman and covered by automated tests.

**D2 — API hardening and D3 prerequisites, shipped 2026-08-19.** Closed the gaps D1's review found — a cacheable integration-test gate, a CORS wildcard that blocked instead of allowing, no way for staff to change a password, a soft-delete read path with no write path — and made the transport decision the frontend apps could not start without.

- **Build order**: [`docs/plan/0002-api-hardening.md`](../plan/0002-api-hardening.md), D2.1–D2.6, all closed.

- **What it left decided but unbuilt**: three gaps written down before this window shut.

# ADR-0032: Admin app architecture — Feature-Sliced Design and TanStack Router

- Status: proposed
- Date: 2026-08-19

## Context

[ADR-0022](0022-frontend-apps.md) fixed what `apps/admin` *is* — a Vite + React SPA on the `admin` API segment — and explicitly deferred what it looks like inside: "frontend architecture (state, data fetching, routing, design system, i18n) will be covered by dedicated ADRs when those apps are built out." D3 is building it out, and this is the dedicated ADR for `apps/admin`'s structure and routing. Its siblings decide the API client and session store (ADR-0033), server state (ADR-0034) and the per-resource UI configuration (ADR-0035); each of those needs this one to say *where its code lives*.

Today `apps/admin` is the bare template: a `main.tsx`, one component under `src/app/`, no router, no data layer. Everything is still to be placed, which is exactly the window in which a placement rule is cheap.

The API side already has its answer to this question. [ADR-0009](0009-api-modular-layering.md) organises by feature first and layer second, gives each layer a single responsibility, and — the part that made it stick — states an import *direction* and confines every exception it grants. Frontends have the same failure mode ADR-0009 was written against, in a worse form: a React codebase left to grow by convenience becomes `components/`, `hooks/` and `utils/` folders where everything imports everything, a page cannot be deleted without grepping, and "where does this go?" is answered differently by every contributor. The API's cure does not transplant directly — a frontend's layers are not route/controller/service/repository — but its spirit does: named layers, a downward-only dependency rule, and enforcement that does not depend on review vigilance.

Two more forces shape the choice of router. First, the admin panel is grid-heavy by design: its screens are lists of staff and users whose pagination, sorting and filtering state ADR-0034 and ADR-0035 put **in the URL**, so that grid state survives reloads and is shareable. That makes typed search params a load-bearing feature of the router, not a nicety. Second, the app authenticates every screen except login ([ADR-0015](0015-route-segments-and-versioning.md): the whole `admin` segment requires a staff principal), so the guard question — where does "redirect to login" live? — has to be answered once, structurally, the way `authenticate()` at router level answered it for the API.

## Decision

### Feature-Sliced Design, importing strictly downward

`apps/admin` adopts [Feature-Sliced Design](https://feature-sliced.design) with the standard layers. The dependency rule is the whole point and is stated first:

```
app  →  pages  →  widgets  →  features  →  entities  →  shared
```

- A layer may import only from layers **below** it. Never upward, never sideways.
- Within a layer, code is grouped into **slices** (a slice ≈ a domain concept or a user interaction). Slices in the same layer do not import each other.
- A slice is consumed only through its **public API** — an `index.ts` at the slice root. Deep imports into a slice's internals are forbidden; what a slice does not export does not exist to the rest of the app.

The layers mean, in this codebase:

| Layer        | Holds                                                                       | May import        |
| ------------ | --------------------------------------------------------------------------- | ----------------- |
| **app**      | providers, the router, global styles, generated route tree — wiring only    | everything below  |
| **pages**    | one slice per screen; thin composition of widgets and features              | widgets and below |
| **widgets**  | large self-contained UI blocks reused across pages (shells, sidebar)        | features and below|
| **features** | user interactions that change something (a form, a dialog, a mutation)      | entities, shared  |
| **entities** | domain resources: query hooks, query-key factories, per-resource UI config  | shared            |
| **shared**   | the API client, `@repo/ui` re-exports, validated env, generic lib code      | nothing above it  |

### The D3 shape

The concrete tree D3 builds, so the sibling ADRs and the plan have coordinates to point at:

```
apps/admin/src/
├── app/
│   ├── providers/               # QueryClientProvider, RouterProvider, theme, Toaster
│   ├── routes/                  # file-based route definitions (wiring — see §Reconciliation)
│   ├── routeTree.gen.ts         # generated by the router plugin; never hand-edited
│   ├── index.tsx                # createApp composition, mounted by main.tsx
│   └── styles.css
├── pages/
│   ├── login/                   # composes widgets/auth-layout + features/auth/login
│   ├── staff/                   # composes widgets/dashboard-layout + the staff grid
│   ├── users/
│   └── profile/
├── widgets/
│   ├── dashboard-layout/        # the sidebar-07 shell: sidebar + header + outlet
│   ├── auth-layout/             # the login-01 shell: centered card, unauthenticated chrome
│   └── app-sidebar/             # navigation, current-principal block, logout
├── features/
│   ├── auth/login/              # the login form and its mutation
│   ├── staff-manage/            # create/edit/disable/reset-password dialogs + mutations
│   ├── users-manage/
│   └── profile-edit/            # name form, change-password form
├── entities/
│   ├── staff/                   # TanStack Query hooks, query-key factory, staff resource UI config (ADR-0035)
│   └── user/
└── shared/
    ├── api/                     # the API client (ADR-0033): axios instance, envelope/error handling, session store
    ├── grid/                    # AppGrid + the grid registry (ADR-0035) — resource-agnostic, no domain knowledge
    ├── form/                    # AppFormProvider, AppFormInput + the field registry (ADR-0035)
    ├── ui/                      # re-exports of @repo/ui — the one door components come through
    ├── config/                  # import.meta.env parsed by a zod schema, the ADR-0004 posture applied to Vite
    └── lib/                     # generic helpers with no domain knowledge
```

The split between `features` and `entities` follows the read/write seam ADR-0034 leans on: **entities own reads** (list and detail queries, the keys that cache them, the resource's column and field configuration), **features own writes** (the mutating interactions and the dialogs that host them). A feature composes entity hooks; an entity never knows a feature exists.

Everything here is functional per the house style: slices export plain functions, hooks and `as const` config objects — no classes, no decorators.

### Enforcement is part of the decision

FSD without an import linter decays into folders with aspirational names — the dependency rule only exists if something fails when it is broken, which is the lesson ADR-0009 encoded as "the direction this ADR exists to fix" and the API enforces by structure. Here structure cannot enforce it (any ES import resolves), so lint does:

- `eslint-plugin-boundaries` is added to `apps/admin`'s flat config (extending `@repo/eslint-config` as today). `boundaries/elements` names the six layers by folder pattern; `boundaries/element-types` encodes the table above; entry-point rules pin consumption to each slice's `index.ts`.
- An upward import, a cross-slice import within a layer, or a deep import past a public API **fails `pnpm lint`**, which fails the gate. The rule is taught by the error message, not by the onboarding doc.

```js
// eslint.config.js (shape, not the full matrix)
settings: {
  "boundaries/elements": [
    { type: "app",      pattern: "src/app/**" },
    { type: "pages",    pattern: "src/pages/*",    capture: ["slice"] },
    { type: "widgets",  pattern: "src/widgets/*",  capture: ["slice"] },
    { type: "features", pattern: "src/features/*", capture: ["slice"] },
    { type: "entities", pattern: "src/entities/*", capture: ["slice"] },
    { type: "shared",   pattern: "src/shared/*" },
  ],
},
rules: {
  "boundaries/element-types": ["error", { default: "disallow", rules: [
    { from: "app",      allow: ["pages", "widgets", "features", "entities", "shared"] },
    { from: "pages",    allow: ["widgets", "features", "entities", "shared"] },
    { from: "widgets",  allow: ["features", "entities", "shared"] },
    { from: "features", allow: ["entities", "shared"] },
    { from: "entities", allow: ["shared"] },
    { from: "shared",   allow: ["shared"] },
  ]}],
}
```

The FSD ecosystem ships its own linter, `steiger`, which understands the methodology natively. It is rejected here for a toolchain reason, not a quality one: this repository has one lint gate (`pnpm lint`, ESLint everywhere, ADR-0002), and a second linter is a second config format, a second set of versions to track, and a second thing CI must run. `eslint-plugin-boundaries` expresses the layer graph inside the toolchain that already exists.

### Routing: TanStack Router v1, file-based

`apps/admin` uses **TanStack Router v1** with **file-based route definitions** and the generated route tree, via the official Vite plugin.

The rationale, recorded because "file-based" is the part most likely to be second-guessed:

- **The generated route tree gives full type safety** on paths, params and search params. `Link to="/staf"` is a compile error; a search param the route did not declare is a compile error. With code-based routing the same safety exists only if the hand-maintained tree is kept precisely in sync — the codegen makes it unconditional.
- **Route-by-route code splitting is automatic** (`autoCodeSplitting: true` in the plugin). Every page becomes its own chunk with no `React.lazy` bookkeeping, which for an authenticated panel means the login screen does not download the data grid.
- **First-class typed search params** — `validateSearch` with a zod schema per route — are exactly the mechanism ADR-0034 and ADR-0035 lean on for grid list state in the URL. The router validates, defaults and types `?page=2&sort=email:asc` the way `validate()` middleware types `req.valid.query` on the API; the grid reads and writes route search, not component state.

The alternative within TanStack Router — code-based routing, a single `routeTree` built in TypeScript — avoids the codegen step at the cost of hand-maintained splitting and materially more boilerplate per route. It is the non-default path through the library and buys nothing this app needs; rejected.

### Reconciling file-based routes with FSD

A `routes/` directory looks like a seventh layer and is not one: route files are **wiring**, the SPA's equivalent of `apps/api/src/routes/` — path, guard, validation, mount — which is why they live under `app/`, the layer whose job is wiring. Configure the plugin accordingly:

```ts
// vite.config.ts
tanstackRouter({
  routesDirectory: "src/app/routes",
  generatedRouteTree: "src/app/routeTree.gen.ts",
  autoCodeSplitting: true,
})
```

Route files stay thin by rule: a path, `validateSearch`, a `beforeLoad` guard, and a lazy import of the page component from `pages/`. A route file that grows JSX beyond composition is a page in the wrong folder. `routeTree.gen.ts` is a build artifact that lives in the tree (the types depend on it), is excluded from lint, and is never hand-edited — a conflict in it is resolved by regenerating, not by merging.

### Layout topology and guards

Two **pathless layout routes** partition the app:

- **`_auth`** renders `widgets/auth-layout` — the login screen and anything else unauthenticated.
- **`_dashboard`** renders `widgets/dashboard-layout` — the sidebar shell around every protected page.

The router is created with a context carrying what guards and loaders need:

```ts
// app/providers/router.ts
const router = createRouter({
  routeTree,
  context: { queryClient, session },   // session: the token store from ADR-0033
});
```

Guards belong to the route tree, not to components — a `<RequireAuth>` wrapper is a guard that every new page has to remember, which is the per-route-auth mistake ADR-0015 rejected on the API. Instead:

```ts
// app/routes/_dashboard.tsx
export const Route = createFileRoute("/_dashboard")({
  beforeLoad: ({ context, location }) => {
    if (!context.session.isAuthenticated())
      throw redirect({ to: "/login", search: { redirect: location.href } });
  },
});

// app/routes/_auth.tsx — the mirror: an authenticated visitor is sent to the dashboard
```

The `redirect` search param is how a session that expires mid-task returns the operator to the screen they were on. Adding a protected page means adding it under `_dashboard/`; the guard is inherited, and there is no way to mount a protected page outside it by accident.

### Client state stays minimal

By decision, not by omission:

- **Server state** belongs to TanStack Query (**v5**) — caching, invalidation, background refetch, per ADR-0034.
- **Session state** belongs to the ADR-0033 token store, exposed to the router via context.
- **Everything else is local React state** (`useState`, `useReducer`, lifted no further than it must be). URL-worthy state lives in route search params, per §Routing.

No global state library — no Redux, Zustand, Jotai — until an ADR adds one with a problem it names. The categories above cover an admin panel; a fourth category appearing is the signal to write that ADR, not to reach for a store.

### Stack and scope

- Named versions: **React 19, Vite 7, TypeScript 5.9, TanStack Router v1, TanStack Query v5**. The implementation pins exact versions; this ADR pins the majors so a bump that changes one is a visible decision.
- This ADR governs **`apps/admin` only**. `apps/web` (Next.js) gets its own architecture ADR in its own deliverable: Next's file-system router and server components occupy the ground FSD's `app` and `pages` layers stand on, so mapping FSD onto it — or choosing not to — is a separate decision this one does not prejudge.

## Consequences

- "Where does this go?" has a mechanical answer, and a wrong answer fails lint rather than surviving review. The layer map also gives the future `ui-builder` agent and skills a deterministic scaffold target — "new resource screen" expands to a fixed set of paths (`entities/<x>`, `features/<x>-manage`, `pages/<x>`, one route file), the way `/new-api-module` already expands on the API side.
- Newcomers must learn the FSD vocabulary — six layer names and a direction — before the folder tree reads naturally. The boundaries lint teaches it mechanically: the first upward import produces an error naming both layers, which is a faster teacher than the methodology's documentation.
- A codegen artifact lives in the tree. `routeTree.gen.ts` is regenerated by `dev` and `build`, excluded from lint, and trivially conflict-resolved; the price of the generated file is the price of typed paths, and it is paid once in tooling config.
- Page-level lazy loading comes for free and stays free — no route added under this scheme can forget to code-split, because splitting is the plugin's job, not the author's.
- Guards are structural. A protected page outside `_dashboard` is not a review catch, it is impossible to write without visibly creating a new layout route — the same property `authenticate()` at router level gives the API.
- The dependency rule has a cost the API's does not: shared UI patterns discovered in two features cannot be imported sideways and must be *demoted* into `entities/` or `shared/` (or promoted into a widget). That refactor pressure is the mechanism by which the layers stay honest, and it is sometimes work.
- Two grids and two dialogs into D3, the `staff` and `user` slices will look near-identical. That symmetry is ADR-0035's problem and the reason the per-resource UI config lives in `entities/` — the layer both a page and a feature may reach.

## Alternatives considered

- **Plain type-based folders** (`components/`, `hooks/`, `utils/`, `api/`). The default shape of every Vite template and fine at ten files; at a hundred, everything imports everything, deleting a screen is archaeology, and no rule says where new code goes. It is the layer-first layout ADR-0009 rejected for the API, with weaker cohesion.
- **React Router 7.** The incumbent, well-documented, and framework-mode brings loaders and code splitting. Rejected on the two properties this app leans on hardest: its path/param typing is a typegen afterthought rather than the library's core design, and it has no first-class validated search params — the URL-held grid state of ADR-0034/0035 would be hand-rolled `URLSearchParams` parsing next to a data layer (TanStack Query) that TanStack Router integrates with natively.
- **Next.js for the admin panel.** Already rejected by ADR-0022 — a pure SPA is simpler for an authenticated internal tool and keeps the two stacks illustrated. Nothing in D3 has weakened that; an admin panel behind a login gets nothing from SSR.
- **`steiger` as the FSD linter.** Purpose-built for the methodology and would validate more of it (slice purity, public-API completeness) out of the box. Rejected to keep one lint toolchain: the boundary rule is the load-bearing part, `eslint-plugin-boundaries` expresses it inside the existing gate, and a second linter is a standing tax on every contributor and CI run.
- **Code-based TanStack Router routing.** Covered in §Routing: no codegen step, at the price of hand-maintained code splitting and per-route boilerplate, with the same library. The non-default that buys nothing here.

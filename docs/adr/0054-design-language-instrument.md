## Context

The panel shipped on stock shadcn neutral — competent and characterless. The operator commissioned a structural redesign through Claude Design against a canvas seeded from the shipped code; the result — one cool hue family, IBM Plex, band-structured chrome — came back as per-value tables and was accepted 2026-08-30 with six exclusions (plan §The reference settled). This record transcribes the decisions; the reference stays the illustration. Everything lands through the sanctioned surfaces: the token sheet, the `@repo/ui` compositions, `@repo/grid` chrome — plus `apps/admin`'s `auth-layout` for the login's arrangement only. **Amended 2026-08-30 (`D11.3`): "for the login's arrangement only" is too narrow, and §5 says so itself.** The active nav item and the sidebar's version footer are decided in §5 and live in `apps/admin`'s `widgets/app-sidebar`, because the drawer's *contents* are the app's by [ADR-0049](0049-admin-app-architecture.md) §The-shell-adapter while its geometry is the composition's. So the fourth surface is **the app's own shell widgets and `auth-layout`**, for what those layers already own — still never a generated primitive, and still every colour from a token. **Amended 2026-08-30 (`D11.5`): and `@repo/form`'s three record shells, on the same terms**, because two of §7's values are theirs to spell — the 20px field stack is `FieldGroup`'s gap and the footer row is each shell's own, both rendered one file above `RecordSurface` since `D8.9` precisely because the container is content-agnostic (ADR-0048 §4). A design value has to be reachable from the layer that renders the element it describes; the alternative is a container that reads the field map, which ADR-0035 forbids. Generated primitives stay byte-identical (ADR-0047); the popover's design is expressible through tokens alone by construction.

## Decision

### 1. Fonts

**IBM Plex Sans** (400/500/600) for UI; **IBM Plex Mono** (400/500) for identifiers, emails, timestamps and counts. **Self-hosted via `@fontsource` packages, imported by each app beside the stylesheet** — not Google's CDN: an EU-facing product does not send visitor IPs to a third party to render text, dev and e2e run offline, and the bundle budget prices the bytes honestly. Fallback stacks: the current system-ui stack for sans; `ui-monospace, SFMono-Regular, Menlo, monospace` for mono. `@theme` maps `--font-sans`/`--font-mono`. **Amended 2026-08-30 (`D11.1`): the sheet names the faces, each app loads its own bytes.** `--font-sans`/`--font-mono` live in `@repo/ui`'s token sheet, because the design system owns what the design *is*; the `@fontsource` imports are per-app, beside that app's stylesheet. `apps/admin` loads them here. **`apps/web` imports the same sheet and does not load them**, so the marketing site names IBM Plex and renders the fallback stack until D14 gives it its own imports — deliberate, not an oversight: it is a Next.js app of its own build shape, and D14 is where its bytes are priced.

### 2. Tokens (`globals.css`, both themes)

Every neutral and the primary sit on hue 258–264; neutral chroma ≤ 0.014. `--radius: 6px` (sm 4 · md 5 · lg 6 · xl 8 — checkbox / badge·chip / controls / card·dialog·popover; nothing rounder than 8). **Amended 2026-08-30 (`D11.1`): the base and the scale ship here; the per-component assignment is each surface's own step.** The four numbers are the token sheet's and land whole, but *which* number a component takes is spelled in the component, and for the generated primitives that spelling is the CLI's and byte-identical under ADR-0047 — buttons, inputs and selects are `rounded-md` (5, not the assignment's 6), the dialog `rounded-lg` (6, not 8), the popover `rounded-md` (5, not 8) and the badge `rounded-full`, which this sentence's own "nothing rounder than 8" forbids. Only `Card` (`rounded-xl` = 8) and `Checkbox` (a literal `rounded-[4px]`) already agree. **The assignment is reached from the sanctioned surfaces that own each shape, in the step that owns it** — §4's badges and chips in `@repo/grid` at `D11.2`/`D11.4`, §7's dialog, drawer, page card and popover through `RecordSurface` and the account control at `D11.5`. Where *only* a generated primitive spells the radius, the primitive's value ships, on the same terms as the focus ring below. Focus ring 3px at 20% light / 28% dark of `--ring` (= primary). **Amended 2026-08-30 (`D11.1`): the width ships, the opacity does not.** Seven generated primitives spell the ring `ring-ring/50 ring-[3px]`, and ADR-0047 keeps `packages/ui/src/components/` byte-identical to the CLI output, so the only way to 20%/28% is either an owned edit to seven files that every regenerate would re-fight, or putting the alpha into `--ring` itself — which contradicts the table row above and would dim every other consumer of the token. Neither is worth a focus ring's opacity. **What ships is 3px at 50% of `--ring`**, and this record says so rather than leaving the code quietly disagreeing with it; the reference's value is recoverable the day a supersession has a better reason to reach those files.

### 3. Type, controls, spacing

Type: 11/16·600·0.07em caps (column heads, group labels) · 12/16 (chips, badges, meta) · 13/18 (controls, cells, mono data) · 14/20 (body) · 16/22·600 (card/dialog titles) · 20/26·600 (page title) · 28/34·600 (login). Control heights (border-box): 26 chip/badge · 30 pager, quick-filter segment · 32 toolbar search · 34 buttons and icon buttons · 36 form inputs · 38 login controls · 44 settings option row. Spacing base 2px: 6 label→control · 8 controls-in-row · 10 cell padding, nav gap · 16 card stack · 20 page gutter, card padding · 24 dialog padding.

### 4. Grid chrome (`@repo/grid`) — the ADR-0037 delta

**The card frame retires: the table is edge-to-edge inside the inset**, bounded by band rules (`--border-strong` closes the chrome above it) instead of a border box — the scroll container, sticky header and static pager are untouched. Header row 34px, caps labels, header bg `0.985`/`0.215`, bottom rule `--border-strong`. Rows 44px (Comfortable) / 34px (Compact — see §6), rule `0.93`/`0.24`. Stripe (opt-in) `0.978`/`0.203`. Selected row: `--primary-tint` + `inset 2px 0 0 --primary`. Resize tick at rest 1×16px `0.9`/`0.36`. Statuses render as a 6px dot (`--success` active, `--warning` invited, neutral disabled) beside the label — the same resource-agnostic renderer, re-drawn. Emails, timestamps, counts and role badges take the mono face.

**Amended 2026-08-30 (`D11.2`): the four chrome lightnesses above ship as named tokens, and "which column is data" is the config's answer.** Two things the applying step found, neither smuggled.

_The values need tokens._ The header ground, the row rule, the stripe and the tick are the only values in this record that **no palette token carries** — `0.985` sits between `--background` and `--muted`, `0.93` is lighter than `--border` in light and `0.24` darker than it in dark, and the tick wants to be *lighter* than the rule in dark so a 1px grip stays findable. §2's own rule is that a colour in a component is the defect, so they land in the token sheet as `--grid-header`, `--grid-rule`, `--grid-stripe` and `--grid-tick`, each taking the chroma of the token it sits beside so the hue family and the ≤ 0.014 neutral ceiling still hold. The sheet is one of the three sanctioned surfaces; this is it being used rather than worked around.

_"Emails take the mono face" is not derivable in the grid._ A timestamp is — the formatter says so — but `@repo/grid` may hold no domain knowledge (ADR-0049), and *this column holds an address* is domain knowledge. So `ColumnConfig` grows one optional serializable flag, `mono`, resolved into the column meta once by `buildColumns` the way `align` and `structural` already are; the resources set it on their email and timestamp columns. It is config vocabulary growing, not a decision changing, and it keeps a per-usage override able to turn it off.

One consequence stated because it is a visible change of behaviour rather than of value: **the status renderer's negative list retires with the badge.** `disabled` rendered `destructive` — the palette's one alarm colour spent on a row's ordinary resting state — and "neutral disabled" above is what ships. Destructive stays for actions that destroy something.

### 5. Band chrome and the shell — the ADR-0048 delta

The inset is a stack of full-width bands: **header 56px** (breadcrumb left, account control right — a 40px bordered control with a 26px tinted monogram) · **page-header band** (20/26 title + mono count badge + 13px description left; actions right — icon buttons 34×34 and the primary; `AppShell` gains the width for this: a `description` and a `pageActions` slot, the need ADR-0048 said would name them) · **toolbar band 48px** and **"Filtered by" band 40px** (the grid page's, see below) · **pager band 48px**. The page container gains a **full-bleed variant** for band layouts; document pages keep the `p-4` gutter. Sidebar 240px; the active nav item is a 2px inset `--primary` bar over `--primary-tint`, not a grey pill; **the sidebar gains a 48px footer holding the version string alone** (mono, right-aligned) — a **build-time constant from a deliberately-bumped tracked source via Vite `define`**, never a runtime env var and never an uncached git SHA (a cached build must not lie about its version). Hot filters render as a 30px **segmented control**; the applied-filters bar becomes the **"Filtered by" band** — caps label, 26px `--primary-tint` chips, underlined Clear all — presentation only: one chip per filter, hot filters chipped, removal and the live region exactly as ADR-0052 decided (**that is this record's 0052 delta — nothing behavioural moves**).

**Amended 2026-08-30 (`D11.3`): the four switches this section left implicit are named, and one number yields to another this section already wrote.** The step that built the bands found each of them, and none is a change of value.

_The full-bleed variant has no flag of its own; `fullHeight` selects it._ A second boolean would be `true` on exactly the routes that already declare ADR-0037's opt-in and `false` on the rest, in both apps — a band layout and a height budget are the same category of page — and an always-equal prop is the slot-with-no-consumer defect ADR-0048 §2 spends a paragraph on. The day a screen wants one without the other is the day it splits, with a consumer to name.

_The description travels on the route, not in the page._ The band's second line is per-screen copy, so it rides the channel the title rides: the shells' route-meta reader (`@repo/app-services`) grows a `description?: TranslationKey` in `staticData` and a `useRouteDescription` beside `useRouteTitle`. **Which match it reads is `fullHeight`'s answer, which is ADR-0048 §2's own discriminator rather than a new one.** Under the `page` surface (`fullHeight` false) the record replaced the list, so the description comes from the match whose *title* won — that route declares none, and a record's heading carries no line rather than the list's sentence under the record's name. Under an overlay, and on an ordinary list (`fullHeight` true), the list is still the screen and the grid is still mounted behind the modal, so the deepest *description* wins and the band does not move. The second half is the step's review finding: coupled to the title alone, opening a row on either shipped resource — both overlays — took nineteen pixels of band away and handed them to the grid behind the dialog, twice per edit. The alternative, leaving the description in each page, would put it below the `<h1>` in the page container instead of beside it in the band, which is not what this section draws. **The mono count badge stays undrawn**: nothing hands `AppShell` a count today, and a slot with no consumer is the defect above. It costs one prop when a screen names it.

_`pageActions` lands in the package and not yet in the app._ The shell has the slot, because this section names its consumer — `D11.6`'s 34×34 density control — but `apps/admin`'s adapter does not grow the prop until something passes it. The package's own suite proves both directions; the app's chain stays honest.

_The sidebar's 240px is the composition's, not the app's._ The width is one custom property that two sibling elements divide — the gap that reserves the column and the fixed container that fills it — and only `SidebarProvider`'s wrapper is an ancestor of both. A consumer setting it on its own `<Sidebar>` moves the drawer and leaves a 16rem hole behind it. `AppShell` sets it through the `style` the primitive already merges, so ADR-0047's byte-identical rule is untouched.

_And the gutter that ships is 16px, not §3's 20._ §5's own sentence — "document pages keep the `p-4` gutter" — is the one that governs, because the two must agree: the header and page-header bands, the grid's toolbar, filter and pager bands, and every document page's container now inset by the same 16px, so a title, a search box and a paragraph line up down the left edge whichever layout a screen is. Giving the bands 20 and the document pages 16 would have been the reference's number bought with a visible misalignment between screens.

**Amended 2026-08-30 (`D11.4`): the grid's three bands ship their heights as floors, and §3's 34px button belongs to the band above them.** The step that drew the toolbar, the segments and the "Filtered by" row found three things, none of them a change of value.

_A band's height is a `min-h`, not an `h`._ Every one of these bands wraps — the toolbar has search, the stances and the actions on one line, the filter band has as many chips as the URL carries, the pager has a range and five controls — and `flex-wrap` is what has kept a narrow viewport stacking them inside the frame since `D4.1` rather than overflowing it. A fixed height with `flex-wrap` still on it does not make the band shorter; it makes the second row spill out of it. So the record's 48 and 40 are what the bands measure wherever they are drawn unwrapped, which is every viewport the reference draws, and the floor is how they are spelled. The browser tier measures the number; the package tier asserts the floor.

_The toolbar's buttons keep the primitive's 32, and §3's 34 is this section's own._ §5 assigns 34 where it names it — "icon buttons 34×34 and the primary", in the page-header band — and the toolbar band's controls are the two §3 sizes this step's own sentence names, search at 32 and a segment at 30. The rest of that row is `Button size="sm"` at the CLI's 32, and one of them is the app's `createAction` passing through a slot, so a 34 reachable only by overriding some of the row's buttons would buy the reference's number with a row whose controls no longer agree with each other. The same terms as §2's focus ring: where the generated primitive's scale is what spells a control, its value ships.

_A presence stance is one segment, and takes the track's height rather than a track of its own._ "Segmented control" is a shape for a set of mutually-legible options; a lone toggle wrapped in a track is a bordered button with a second element around it, and the second element is what a screen reader walks past on the way to the only control inside. It takes the track's 30px, the segment's type and the same `--primary-tint` pressed state, so the two kinds read as one family at one height.

### 6. Density

Two numbers, not a scale: **Comfortable 44px (default) / Compact 34px**, differing in exactly row height, cell padding (10→8) and badge padding. A 34×34 icon control in the page-header band switches it; **the fact is an account setting** — the key, its schema and its Preferences card belong to [ADR-0053](0053-account-area.md), which owns the settings surface.

**Amended 2026-08-30 (`D11.6`): the three numbers, spelled.** "Badge padding" was the one term above with no value beside it, and a mode is not implementable until every value it moves has one; the other two are stated and are unchanged.

| What                | Comfortable | Compact | Where                                    |
| ------------------- | ----------- | ------- | ---------------------------------------- |
| Body row height     | 44          | 34      | the `td`, `h-[44px]` / `h-[34px]`         |
| Cell padding (x)    | 10          | 8       | `th` **and** `td`, `px-2.5` / `px-2`      |
| In-row badge        | 26 × 8      | 22 × 6  | `h-[26px] px-2` / `h-[22px] px-1.5`       |

Three things the applying step settled, none of them smuggled.

_The header's padding moves and its height does not._ §4 fixes the header row at 34, and a Compact body row is 34 too — the header is where the two densities meet rather than something density changes. But the padding is a **column** value, not a row one: a `td` at 8 under a `th` at 10 is every label two pixels off its own column, so the horizontal padding is the pair's and the height is the body's alone. That is what "cell padding" has to mean for the mode to be invisible where it should be.

_"Badge" is the in-row badge._ The role badge is the only badge left inside a row — §4 retired the status badge for a dot — so it is what the term names. The chips in the Filtered-by band and the segments in the toolbar are chrome **around** the table at their own fixed heights (§4, §5), and a row-density mode that resized the toolbar would be a mode that moved the height budget it lives inside. 22 keeps the badge's 6px breathing room inside a 34px row, which is what 26 does inside 44.

_The default is the contract's._ `DEFAULT_GRID_DENSITY` is `"comfortable"` in `@repo/contracts` (ADR-0053 §2, ADR-0023) and the grid's own fallback is that same constant, so a table rendered outside a provider — a package test, a future app that has not wired settings — is Comfortable for one declared reason rather than two agreeing ones.

### 7. The other surfaces

Record container, all three variants as siblings: 60px title bar (16/22 title + 12px meta line), 24px body padding with a 20px field stack, **64px footer band** (`--muted` bg, top rule) holding Cancel + primary; dialog 600px, drawer 512px full-height with the body scrolling between static bands, page card 672px with the record label as the page's one `h1`. Popover: 232px, 4px padding, radius 8, 32px items, hover `--accent` — tokens only. Login (in `apps/admin`'s `auth-layout`): a left-aligned 400px column — brand line, 28/34 heading, an 8px-radius card with 38px controls — on a 48px hairline-grid ground; same values both themes.

**Amended 2026-08-30 (`D11.5`): five things the applying step found, none smuggled.**

_Both bands are floors, and the title bar's floor is exercised._ `D11.4` wrote the rule for §5's grid bands — a band's height ships as a `min-h`, because a fixed height on a wrapping band does not make it shorter, it makes the second row spill out of it — and it holds here for a sharper reason. The footer holds two fixed-height controls and measures 64 in both shells; the title bar holds **copy**, and the users drawer's edit description ("Email is not editable — …") wraps to two lines at 512px, so that band measures 73. That is the floor doing its job rather than a defect: the alternative is truncating a sentence that explains why a control is disabled. So 60 is what the band measures wherever the meta line is one line, and the browser tier asserts it exactly on the dialog and as a floor on the drawer.

_The title bar takes a bottom rule._ The paragraph above gives the footer two properties — a `--muted` ground and a top rule — and gives the title bar only its height and its type, which leaves the body's upper boundary undrawn. A body that scrolls **between** two static bands needs the upper one closed, or content slides under a title with no edge to slide under, and the reference's own idiom everywhere else (§4's header band, §5's page-header band) is a band bounded by a rule. So the title bar is `border-b`, on the same `--border` hairline the frame is drawn with. This is the one value in §7 that the record adds rather than transcribes, and it is written here rather than left in a component.

_The `page` variant renders no title bar._ "Page card 672px with the record label as the page's one `h1`" is satisfied by the shell, not by the container: [ADR-0048](0048-app-shell-and-record-surfaces.md) §2 — untouched by this record, whose delta on 0048 is the shell's chrome geometry — puts the record's heading in the shell's `<h1>`, and §5's page-header band above the page container is where that heading now sits, at 20/26. A 60px band inside the card would be a second visible heading with one accessible name, which is the defect `D4.2` found by testing the shells against each other. So under `page` the anatomy is: §5's band above the card, the 24px body, the 64px footer band — three bands, one of them the shell's. The `description` follows the title: it is the shell's band's second line on a route that declares one (`D11.3`), and inside the card it renders as a lede at the top of the body, where the body's own gutter reaches it — **at §3's 14/20 body rung, not the 12px meta rung the other two use**. That is a real difference between the variants and it is the same difference the heading is: a meta line is the second half of a 60px title bar and is sized to sit under a title, while a lede is the first paragraph of a body and is read as copy. It is what shipped before this step, and it is stated here so the next reader does not "fix" it into 12px.

_The dialog is the only width that moves, and it is a bracket value._ 600px sits between Tailwind's `lg` (512) and `2xl` (672), so `dialog`/`md` is `sm:max-w-[600px]`. The drawer's 512 and the page card's 672 are what `sm:max-w-lg` and `max-w-2xl` already resolved to, which is why the round-2 note calls them unchanged. The radius assignment §2 deferred to this step lands with it: the dialog frame takes `rounded-xl` (8) and the account popover the same, over the generated primitives' `rounded-lg` (6) and `rounded-md` (5) — through the `cn` merge, so `packages/ui/src/components/` is untouched.

_Two of §7's values are reached from `@repo/form`, not from a composition._ The 20px field stack is `FieldGroup`'s gap and the footer row is the shells' own, and both are rendered in `@repo/form`'s three wrappers rather than inside `RecordSurface` — because the fields are the app's body content and the container is content-agnostic by [ADR-0048](0048-app-shell-and-record-surfaces.md) §4. §Context's surface list is widened accordingly, on the same terms and for the same reason as `D11.3`'s widening: still never a generated primitive, still every colour from a token. What moved with it: the `mt-12` the two shells carried as the fields-to-footer distance **retires**, because the footer band's height and its top rule are that distance now, and a 3rem margin inside a 64px band pushes the actions out of the band they live in. The dialog's `p-1 -m-1` paint room retires for the same class of reason — `D8.11` added it because a scrolling body clips ink overflow at its padding box and a `w-full` field sat on that edge, and 24px of body padding is eight times the room a 3px ring needs.

**Amended 2026-08-30 (`D11.7`): five things the login step had to read rather than transcribe, none smuggled.**

_"Left-aligned" is the column's placement, not only its copy._ The sentence above names a width and an alignment, and the alignment is the half that distinguishes it from what shipped — the `login-01` block centred a `max-w-sm` card *and* centred the text inside it. What ships is a column at the ground's left: the layout is a flex row with no `justify-*`, vertically centred, and its inset is **two 48px modules (`md:px-24`) at `md` and up**, so the column's left edge lands on a grid line rather than near one; below `md` the ground has no room for a module and the inset is the page's ordinary 24. Naming the inset here is what keeps "left-aligned" from being re-tuned by eye later.

_The card holds the controls, and the sentence about the screen moves out of it._ §7 lists the card's contents as the 38px controls, and the login's subtitle is not one — it is a **lede about the screen**, so it joins the brand line and the heading in the column above the card and travels on `D11.3`'s route channel (`staticData.description`, `useRouteDescription`) rather than as a `CardDescription` a page hard-codes. It takes the 14/20 body rung for exactly the reason the `page` variant's lede does, two paragraphs up. Above it the **brand line takes §3's 11/16·600·0.07em caps rung** — the record's one label size, and a label above a title is what it is.

_The card takes §3's own card rungs, now that nothing else is inside it._ 20px padding and a 16px stack, over the primitive's 24 and `FieldGroup`'s 28 — the plain-card rungs, not the 24/20 the record surfaces take, which §7 gives to the dialog and the drawer. Its radius needs no assignment: `Card` is the one generated primitive whose `rounded-xl` already agrees with §2's 8.

_The 38px rung and the 13/18 control type are spelled on the call site, and §3's type rung is otherwise still open._ The generated `Input` and `Button` ship 36px, and their own sizes are `text-base md:text-sm` and `text-sm` respectively; ADR-0047 keeps `packages/ui/src/components/` byte-identical, so the login spells both values through `cn`, the route §7's dialog width already took at `D11.5`. **All three of its controls take the type, not only the two fields** — a card holding a 13px field above a 14px button is the reference disagreeing with itself. What this does not do is close the rung app-wide: `D11.5` gave the record surfaces their heights and paddings and left their fields on the primitive's size, so the login is for now the only form on §3's control type. That is a **gap, not a divergence** — named here so the sweep that closes it is a decision someone takes rather than a difference someone finds.

_The hairline ground is a paint, and its colour is the token._ A 48px grid of 1px lines is two `linear-gradient`s tiled at `48px 48px`, which has nothing to say to Tailwind's scale, so it ships as an inline `style` on the layout rather than as a utility. §2's rule survives that intact because the lines are drawn in `var(--border)` — the same hairline the rest of the chrome is ruled with, which is also what makes "same values both themes" true by construction rather than by a second declaration.

**Amended 2026-08-30 (`D11.8`): the settings layout's geometry, which this section named as a surface and never gave numbers.** §7's list ends at the login, and [ADR-0053](0053-account-area.md) §4 names `SettingsLayout` without measuring it — so the values below come from the reference's own `/account` artboard, transcribed rather than invented, and are written here because this record is where a surface's geometry lives.

_The arrangement._ A **220px nav column**, a **32px gap** and a **content column capped at 720px**, the cards inside it on §3's 16px stack and the nav's own items **2px** apart. The cap holds at every width rather than only above the breakpoint — the same measure is wanted in the stacked layout, and a prefixed class is one more thing a later re-tune of the collapse could drop without the layout looking different at the width it was tested at. **§3's `10 nav gap` is not this nav's**, and the collision is named rather than left for a later reader to resolve by picking one: the section links are 2px apart in the reference and 2 is what ships, so §3's rung is not read onto them. Which nav that rung *is* — the drawer's, at a distance the generated `SidebarMenuButton` currently spells itself — is a question this step does not answer and does not need to; it is named here so the next reader finds a stated gap rather than a silent disagreement.

_The layout supplies no gutter, and that is `D11.3`'s division read from the other end._ `/account` is a document page, so §5's page container is already spending the 16px gutter on it. A composition that carried padding of its own would inset the area twice, and the second inset is invisible in every jsdom query — which is why the package tier asserts the *absence* of a padding class rather than a measurement.

_The collapse is one breakpoint, and the nav wraps rather than scrolls._ Below `md` the panes stack and the nav becomes a row above the content; above it the nav is the fixed left column. The items are the **app's** nodes, so an overflow rule would be this composition imposing a class on children it does not own — a wrap needs nothing from them. The mirror of that in the other direction ships too: a wrapping *column* with a definite height splits into a second column rather than overflowing, so the wrap is turned off where the direction turns.

_The landmark's name is a prop, not a `UiStrings` key._ That is a refinement of [ADR-0053](0053-account-area.md) §4's division rather than of this section's geometry, and it is decided there, amended at this step; it is noted here only so a reader of §7 is not left thinking the composition names itself.

**Amended 2026-08-30 (`D11.9`): the section link's own height and type, which the amendment above deliberately left open, and which nav §3's `44 settings option row` belongs to.** The paragraph above gives this nav its column width and its 2px item gap and stops there, so the step that built the links had no value to transcribe and did not invent one: the links ship at **36 high with 14px labels** — the height the app's generated controls are on today, and §3's body rung for the text. Neither is a reading of §3's control rungs, and saying so is the point of this paragraph: 34 is the button rung the app has not swept to (`D11.7` named that gap and it is still open), and 13/18 is the control rung the login is so far the only screen on. A nav label is read as copy rather than typed into, which is why the body rung is the honest one of the two for it. **§3's 44 is not this rung either**: a settings option row is a theme or language row *inside* a Preferences card, which is `D11.10`'s to build, and reading it onto a section link would make the account nav the tallest in the app — the app's other nav, `SidebarMenuButton`, measures 32. What the links do take from a record is the **active treatment**, which is §5's sidebar item — an inset 2px bar in `--primary` over `--primary-tint` — because "the nav item you are on" already has one visual form here and the account page is the one screen that shows both navs at once.

### 8. Not adopted

The reference's inventions stay out, as the plan records: no login "Forgot?" link, no health dot, no nav count badges, no destructive actions in surface footers, no session-TTL copy, and mock content (sample filters, numeric ids, the `Navigation /` crumb root) yields to what the contracts and D8.6's trail actually provide.

## Consequences

- Practically every screen's diff is a token diff; the structural steps are the ones that touch layout code, and each updates its e2e specs in the same diff.
- The bundle budget prices the fonts and the redesign in bytes; raising `size-budget.json` is a reviewed diff.
- The version footer creates the bump obligation: a release habit of one line, or the footer lies.
- The customer app (D12) inherits all of it through the packages.

## Alternatives considered

- **Stay on shadcn neutral.** Zero cost, zero identity; rejected by the operator with the redesign commission itself.
- **Google Fonts CDN.** Simpler; rejected — third-party requests from an EU-facing product, an external runtime dependency, and offline dev/e2e breakage.
- **Git SHA as the footer version.** Always truthful at build time, wrong from a warm cache, and cache-busting if made an input; rejected as primary.
- **A density scale (3+ steps or free value).** More knobs than the two jobs found in use; rejected for two named numbers.

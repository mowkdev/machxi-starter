# ADR-0069: The development rate-limit profile (supersedes ADR-0020 in part — a delta)

- Status: accepted
- Date: 2026-09-05
- Supersedes: [ADR-0020](0020-security-baseline.md) (delta: the **committed development** profile carries a larger `RATE_LIMIT_GLOBAL_MAX`, because this repository's own browser tier is a legitimate consumer of more than 300 requests in a window; the schema default, the window, the three other limiters, their keys and every other decision 0020 makes stand — its third partial successor)

> Written and **accepted 2026-09-05 at the head of `D15.8`**, joining the open D15 window at the step that needs it (the `D12.12`/0056 precedent, and `D15.7`/0068's). ADR-0020 moves to `superseded by` at the same head — this record is the one place its rate-limit row is qualified, and 0020 stands for everything neither this record nor [ADR-0059](0059-ci-containers-and-deployment.md) nor [ADR-0066](0066-infrastructure-seams.md) touches. Amendable in place, labelled, while D15 is `in progress` ([the ledger](../plan/README.md#the-window)).

## Context

[ADR-0020](0020-security-baseline.md) sets a global budget of 300 requests per fifteen minutes per address over `/api`, in an in-memory store ([ADR-0066](0066-infrastructure-seams.md) §4 makes the store configurable; the number is 0020's). It was written when the API was the only thing in the repository that made requests.

**The repository has since grown a consumer of its own, and at `D15.8` it crossed the line.** The browser tier is two Playwright suites over one long-lived dev stack, and `pnpm test:e2e` runs them back to back through one limiter. Measured that day, each suite alone in a clear window: the admin's is 174 requests, the customer's 134 — **308 against 300**. Neither suite is padded and no floor was trimmed to make the sum work; what grew is the applications under them. So the repository's own definition of done contains a command a stock clone cannot run green, and the failure it produces is a `429` in the middle of a healthy suite. It is not only a clone's problem: the nightly browser-tier workflow copies this same `.env.example` and runs `pnpm test:e2e` as one command, so it is on the same wall.

**A build step could not answer it**, which is why three of them did not: `D11.6` recorded a larger development maximum as one of two candidate fixes, `D11.11` took the other (the tier's own window probe) and left this one, and `D15.8` measured the wall and stopped. The number is a decision of a frozen record, and it is load-bearing in that record's own §Residual risks, where the global budget is what bounds an argon2 burst — so moving it moves the premise of a recorded risk acceptance rather than an operational preference. That is a supersession, and this is it.

**The shape is not new; only the file is.** `apps/api/.env.test` already carries a maximum of its own, because the integration tier drives thousands of requests through the same app in seconds and a shared budget would make the suite a coin toss. A profile whose traffic is generated by this repository's own tests already sizes this variable to itself.

## Decision

### 1. The committed development profile carries a larger global maximum

The root [`.env.example`](../../.env.example) — the **development** template, which sets `NODE_ENV=development` and is copied to a git-ignored `.env` — sets `RATE_LIMIT_GLOBAL_MAX=1000`. Nothing else moves.

### 2. Why 1000, and what it buys

The number is sized to what one address legitimately spends in one window on this repository's own verification, twice: the browser tier (308) and the Postman collection (165) are 473 together, and a tier run that fails and is run again is 946. A window that cannot hold a failed run and its retry is a window that produces a second, false failure on the diagnosis attempt — which is the class of defect the tier's own probe was built for at `D11.11`, and the reason the answer is not "308 plus slack".

It stays a **limit** rather than an off switch, which is the other half of the choice. Sustained, 1000 in fifteen minutes is about 1.1 requests per second: a client stuck in a render loop against the dev API still spends it — in under a minute at twenty requests a second, and in a few at two — so a developer still meets the `429` envelope, the `Retry-After` header and the tier's own refusal message on a machine where they can be read. The test profile's maximum is deliberately not reused here; a development stack that never refuses anything is a stack on which ADR-0020's most visible behaviour is never once observed.

### 3. What does not move, and where a deployment's number comes from

- **The schema default stays 300.** A deployment that states nothing is exactly as ADR-0020 decided, and so is the sketch in [ADR-0004](0004-configuration-and-environment.md), which is therefore not a parent of this record.
- **The production template is a different file.** [`docker/prod/.env.example`](../../docker/prod/.env.example) is the deployment checklist ([ADR-0059](0059-ci-containers-and-deployment.md) §6) and does not carry this variable, so the development value is not on the path a deployment copies forward. This is the answer to the hazard that put `KNOWN_PUBLIC_SECRETS` in ADR-0020: a committed development value reaching production. Unlike a signing key, a request budget carries no secret and a larger one may be a perfectly correct production choice, so the answer is separation rather than a startup refusal — refusing a number in production would refuse a capacity decision only the deployment can make.
- **The window, the login, refresh and impersonation limiters, their keys and `skipSuccessfulRequests` are untouched**, and so is every non-limiter row of ADR-0020. What the global maximum does bound on its own is in §4, which is where this record's own consequence is stated rather than waved past.

### 4. ADR-0020's residual risk, restated honestly for the new number

0020 §Residual risks accepts two things about the global budget, and this record moves the premise of both. Neither is left for a reader to reconstruct.

**Cost.** The budget is a counter over a window rather than a rate, so all of it may arrive at once: hash-bearing requests fill the bounded queue behind `AUTH_MAX_CONCURRENT_HASHES` and what follows is indiscriminate shedding with `503`. At 1000 the **burst** is three times larger, and an attacker pacing it to hold the pool saturated keeps it saturated three times longer — of the order of thirty seconds rather than ten, at the argon2 capacity that record measures. The **sustained** rate stays more than an order of magnitude below that capacity, so it remains a burst-recovery problem and not a denial of service.

**Guessing.** This is the half a smaller record would have skipped. The login limiter keys on address **and** email, so varying the email buys a fresh budget per key, and 0020 says plainly that the only aggregate bound on one address is the global maximum. It therefore bounds guessing and not only volume: at 1000 one address can spray 1000 credential pairs in a window rather than 300.

Both are accepted here for the same reason, and only for it: this record moves a **development** file, where the traffic is the developer's own and the adversary is absent. A deployment inherits 300 unless it decides otherwise, and 0020's §Residual risks — including the per-address hash limiter it names as the real fix — is the paragraph to read before it does.

## Consequences

- `pnpm test:e2e` is green as one command on a stock clone and in the nightly workflow, which runs it the same way off the same file, and it stays green while the tier grows — which is what item 4 of a deliverable's definition of done has to mean.
- The two suites' floors keep their meaning: each states its own measured cost, the combined run has headroom above both, and the probe still reports a real budget rather than an unreachable one.
- A developer whose `.env` predates this record keeps 300 and keeps the wall. Refreshing the one line is the fix, and the tier's refusal message names it.
- Anyone reading ADR-0020's rate-limit row must now read this record beside it for the development profile. That is the cost of a delta, and it is smaller than the alternative — a number in a frozen record that the repository's own tooling quietly disagrees with.

## Alternatives considered

- **Trim the tier to fit 300** — about a dozen requests of coverage, the four cold-URL account boots or the registration reload. Cheap today and wrong in a month: the next screen puts it back over the line, and the thing being cut is coverage, to protect a number that protects nothing in development.
- **Document the tier as two commands**, one suite per window with the API restarted between them. Costs nothing and concedes that a starter ships a definition-of-done item its own clone cannot run.
- **Leave it to each machine's git-ignored `.env`.** This is the status quo, and it makes the repository's own instructions depend on a file nobody can review — every clone rediscovers the wall, and the fix is uncommitted folklore.
- **Skip the global limiter entirely when `NODE_ENV=development`.** Simplest, and it deletes the one place a developer ever sees the `429` path work. A limiter whose behaviour is exercised only in production is a limiter nobody has watched.

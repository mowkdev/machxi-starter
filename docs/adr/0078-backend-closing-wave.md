## Context

Four rows were left for the backend, and the starter is wanted for a project. Scoping read each against one question: what does it cost to build after a fork exists?

The answer turned on a fact nobody had written down. Drizzle's `migrate()` reads the newest row of its table and applies a journal entry only when the entry's timestamp is later; the hash it stores is never compared. A fork that has applied a migration of its own and then merges an older one from the starter skips it, silently, and the schema and the code disagree from that release on. Every migration the starter ships after a fork exists would meet this, so the runner is decided first and the rest of the wave lands on it.

The other findings are as the reviews left them: one signing secret with no rotation path, shared with the OIDC codec (`SEC-01`); index builds that cannot be concurrent (`DB-01`); tenant isolation enforced by code alone (`SEC-07`); SPA images running as root with no health check, an install layer every source edit invalidates, and a compose file with no limits (`CI-05`, `CI-10`, `CI-11`); and a composite package's restored buildinfo masking its own type error (ADR-0073 §6).

## Decision

### 1. A migration is applied when its hash is recorded

`@repo/db`'s runner replaces `migrate()` with its own loop over the journal: an entry whose hash is absent from the applied-state table is applied, in journal order, and recorded. The table, its columns and the hashes already in it are Drizzle's and are read as they stand, so a deployed database needs no change. The advisory lock, the owner role and the single transaction for the ordinary lane stand.

**A second lane runs outside the transaction.** A migration file marked for it has each statement executed on its own and is recorded when the last one succeeds. Its statements are written to be repeatable, because a failure part-way leaves the file unrecorded and the next run starts it again. It exists for `CREATE INDEX CONCURRENTLY` and for `VALIDATE CONSTRAINT`.

A hash is taken over the file's bytes as committed; the migrations directory is pinned to one line ending so that a checkout cannot change it. [`docs/forking.md`](../forking.md) says how a fork merges the journal.

> **Amended 2026-09-30 (D29.1) — an entry is recorded by its hash or by its journal timestamp.** The dev database, migrated by Drizzle since D1, holds four hashes that are no committed file's — `0007`, `0008`, `0010` and `0013`, files hashed under a CRLF checkout or edited before they were committed — so a hash-only rule would have replayed four migrations onto it, and would do the same to any deployment with such a row. Drizzle writes the entry's journal `when` into `created_at` beside the hash, and so does this runner; an entry is applied when a row carries either. The hash stays the content's record, and the timestamp is the entry's identity for every row Drizzle wrote. A fork's own entries carry timestamps of their own, so nothing merged is mistaken for applied. The runner also normalises a file to LF before hashing it, so the hash is the committed bytes' on a machine where the pin is not yet in force.
>
> **Amended 2026-09-30 (D29.1) — how a file is marked for the second lane.** Its first line is `-- migrate:concurrently`. The mark sits in the SQL, not in the journal, because `drizzle-kit generate` rewrites `_journal.json` and would drop a field it does not know. Each statement of such a file is one statement — Postgres runs a multi-statement string as one implicit transaction, which refuses `CONCURRENTLY` — and an index build is written drop-then-create (`DROP INDEX CONCURRENTLY IF EXISTS` first), because a failed concurrent build leaves an invalid index that `IF NOT EXISTS` would keep. A run of ordinary files still shares one transaction; a marked file commits what precedes it and runs alone. Two things about the lock follow from the lane, both found by the step's review. A run waiting for it polls `pg_try_advisory_lock` rather than blocking in `pg_advisory_lock`, because a backend blocked in a statement holds a snapshot and `CREATE INDEX CONCURRENTLY` waits for every older snapshot, so two overlapping release jobs would deadlock on a marked file (the case "two runs over a concurrent-lane file serialise without a deadlock" is red against the blocking call). And the runner's connection is never retired by the driver (`maxLifetime: 0`), since postgres.js otherwise replaces a connection after 30–60 minutes and the session-level lock would not survive into the next statement.

### 2. A key ring for the access token, and a key of its own for the OIDC codec

`JWT_ACCESS_SECRET` is the current secret and `JWT_ACCESS_SECRET_PREVIOUS` is optional. A token is signed with the current secret and carries a `kid` derived from it; verification picks the secret the `kid` names and refuses any other. A token with no `kid` is verified against the current secret, so a deployment takes this release without a sign-out. Rotation is: move current to previous, set a new current, remove previous after one access-token lifetime.

The OIDC transaction codec stops sharing the key. `OIDC_TRANSACTION_SECRET` is optional; unset, the codec's key is derived from the access secret under a label of its own, so the separation is structural in a default clone and the two rotate independently where a deployment states both. A committed value is refused in production for every secret here, as it is today for one.

> **Amended 2026-09-30 (D29.2) — how the key id and the derived key are made, and what the schema refuses.** The `kid` is an HMAC-SHA256 of a fixed label under the secret, truncated to sixteen base64url characters: a plain digest of the secret in a public header would be an offline oracle for it, and the HMAC names the key without saying anything about it. The codec's derived key is HKDF-SHA256 over the access secret with a versioned label; changing the label is a rotation of that key, which fails the sign-ins in flight and nothing else. Beyond the production refusal of a committed value, the schema refuses `JWT_ACCESS_SECRET_PREVIOUS` equal to `JWT_ACCESS_SECRET` (a rotation whose second half never happened) and `OIDC_TRANSACTION_SECRET` equal to either (the sharing this section removes), in every environment.

### 3. Lock order, and a deadlock retried once

The federated exchange takes its locks in an order that cannot deadlock against a credential event's sweeps, and a concurrent integration case proves it. The transaction helper at the composition root retries a transaction the database aborted as a deadlock victim (`40P01`), a bounded number of times; nothing inside a transaction has an effect outside the database, which is what makes the retry safe and is already the rule for mail.

> **Amended 2026-09-30 (D29.3) — what the order is, and the bound.** A credential event reaches an account's `federated_login` handoff twice: in its sweep, before the account row, and again behind the row, because the callback mints behind that row. An exchange that claimed its handoff and then wrote the account met the second sweep head-on, and one that locked the account first would meet the first. So a **per-principal credential lock** — a transaction-scoped advisory lock apart from the mint's — sits ahead of both: `supersedeAll` takes it after the `reset_password` rows (the reset by mail arrives holding one, and a second sweep must still queue on that row first) and before every other purpose, the exchange reads whom its handoff names without claiming it, takes the same lock, then the account row, then claims; and the callback, which locks the account and then mints — superseding an older live handoff the event's sweep may already hold — takes the same lock before the row (found by the step's `security-reviewer`; the edge predated the step). Whichever arrives second waits holding nothing the first needs. Three integration cases prove it — each red against the order without the part it tests — by running the event's remaining statements under a lock timeout shorter than the deadlock detector's, so a retry cannot hide an inversion. The helper runs a victim **three times in all**, logs each retry on the request's logger, and passes every other failure through at once. Residual, named rather than closed: a password login takes no credential lock, so where its session cap and a reset's session sweep reach the same rows in opposite orders, the retry is what answers it.

### 4. Row-level security is a timeboxed spike

[ADR-0067](0067-organizations.md) §5's shape is unchanged. What is unproven is the mechanism under it: a transaction scoped to the request, the setting placed by the membership guard, policies that admit the principal-scoped reads and the staff segment by an explicit setting and nothing by omission, and the harness running as the application role. A one-day spike proves or refutes it. Green lands in D29 and this section is amended in place with what was built; red becomes a planned row with the blocker named.

> **Amended 2026-09-30 (D29.4) — the spike landed; what was built.** Green, inside its timebox, in a worktree with its own install and its own database. The mechanism, as it stands:
>
> - **The policies.** Migration `0019` turns row-level security on for both tables in `TENANT_OWNED_TABLES` — declared as `pgPolicy` entries beside the tables, so `drizzle-kit` generates them and the enumeration test reads them — with one permissive policy per setting that may admit a row: `app.organization_id` (the tenant; read and write), `app.user_id` (a user's own memberships and the invitations addressed to their account's current address; **read, and an invitation stamped — never a membership written**), `app.invitation_token_hash` (the one invitation the transaction holds the hash of; read and stamped), and `app.tenant_unscoped` set to `staff` or `system` (read and write). A setting is read through `nullif(current_setting(…, true), '')`, so unset and reset both mean nothing. No `FORCE`: the owner, which migrates and truncates, is not bound; the application role always is.
> - **Where the setting is placed — per transaction, from the request, not one transaction per request.** The composition root's transaction helper opens every transaction with the scope of the request it runs in (`openInRequestScope`: the principal `authenticate` placed and the organization `requireMembership` placed, read from the request context when the transaction opens, one `set_config(…, true)` round trip). A repository over a tenant-owned table runs on its caller's transaction or opens one of its own the same way (`withinTransaction`), never on the bare pool. A **request-wide** transaction was not built, because three rules already in force refuse it: §3's retry reruns a transaction from the start, which a savepoint inside a longer transaction cannot honestly do; mail is sent after commit, which a transaction that outlives the service's cannot promise; and the response would have to wait for a commit the handler does not own. What the spike needed from "a transaction scoped to the request" was the request's scope on every transaction, and that is what exists.
> - **The explicit placements.** The staff segment is `staff` by its principal (ADR-0067 §3, staff are above tenants). The seeders place `system` on each seeder's transaction. A membership is written inside its organization's scope: a path that creates an organization (the personal one on registration and the federated callback, a team on the user segment) or joins one by a spent invitation places it by name (`memberships.enterOrganization`) before the write. The public token lookup places the hash it reads by.
> - **The harness as the application role** was already true (ADR-0061 §1). A test's own reads of the two tables go through `asTooling` (the API tier) or a pool created `tenantUnscoped: "system"` (the `@repo/db` tier, which asserts on tooling), named rather than implied.
>
> What it cost: nothing measurable — the API's integration tier ran in 75.9 s before and in 74.4, 73.3 and 76.0 s over three runs after (826 → 830 cases). What it proves: "every tenant-owned table carries a policy" (red with one table's removed), "a query that forgets its organization returns nothing", a member's transaction reading one organization and the caller's own rows, a write into another organization refused `42501`, and the staff segment reading every tenant. Residual, named: the principal branch admits a user's own memberships in every organization, so a forgotten scope inside a user's request can still read *their own* rows elsewhere — never another account's. Pooler configuration is unchanged, because a transaction-local setting is what a transaction-mode pooler already keeps.
>
> **Amended 2026-09-30 (D29.7) — hardened, from the independent review of `D29.4`.** Four changes, each closing a Low that review logged; none changes the wire.
>
> - **Every setting on every transaction.** The request's opener no longer adds the settings its scope names — it writes all four, `''` for each it does not name (`replaceTenantScope`), so a value already on the session (the tooling's `tenantUnscoped` startup parameter, a session-level `set_config`) is shadowed for the transaction and never reaches a request. `setTenantScope`, which adds, stays for the placements inside a transaction (`enterOrganization`, the token lookup) and for the seeders.
> - **A boot refusal.** In production the API asks the database who it is before binding the port, and refuses to start when its role is a superuser, holds `BYPASSRLS`, or holds the owner's privileges on a table under row-level security — the three kinds of role the policies do not bind, since there is no `FORCE`. Read by the row-level-security flag rather than the tenant-owned list, which is the test tier's; every listed table has the flag. Development and test are exempt. `docs/deploy.md` names the requirement and the deploy order across `0019`: code first, then the migration.
> - **The invitation's column grant.** Migration `0020` revokes table-level `UPDATE` on `organization_invitations` from the application role and grants it on `accepted_at`, `declined_at`, `revoked_at` and `updated_at` alone: the consume policies choose the rows, and the grant keeps an admitted `UPDATE` to the stamps, so a transaction that sees an invitation by its address or its hash cannot move it to another organization or raise its role. A migration that recreates the table must re-issue the pair, for [ADR-0061](0061-database-roles-and-append-only-enforcement.md) §2's reason — the default privileges would grant every column back.
> - **The principal is left out of an organization-scoped transaction** — tried, and kept, the integration tier green. Once `requireMembership` has placed an organization, the opener places that organization alone, so a query that forgets its organization inside a member's request reads that organization's rows and not the caller's own memberships and invitations elsewhere. The residual named above narrows to what it always was by design: a request outside an organization — the switcher, the caller's invitations — reads the caller's own rows across organizations, and never another account's.
>
> **Amended 2026-09-30 (D29.7, follow-up) — the boot refusal counts membership and every owned table**, closing two Lows of the step's independent `security-reviewer` pass. The refusal also names a role that is a **member** of a superuser or `BYPASSRLS` role (the attributes are not inherited, and such a role is one `SET ROLE` from both), and it counts ownership — or membership in the owner — of **any** ordinary or partitioned table outside the system schemas, **whatever its row-level-security flag**: before `0019` is applied no table has the flag, and an API connected as the owner on the code-first release would otherwise boot and keep serving once the migration landed. The application role owns nothing (ADR-0061 §1, the migrations table included), so nothing about a correct deployment changes. `main.ts` now logs a failed query while asking under its own message rather than the refusal's; both still stop the process. The integration cases build the two roles as the test cluster's superuser inside a rolled-back transaction (`DATABASE_URL_TEST_SUPERUSER`, read by that one file from `apps/api/.env.test`).
>
> Still residual, and carried by a `planned` ledger row rather than here: a settable `staff` or `system` value is a widening any SQL-injected statement could also place (a separate role or a `SECURITY DEFINER` setter would not be); the staff segment sees every tenant at the database level; the scope is read from request storage rather than handed down from `ctx`; and the repository-level tests run under `system`.

### 5. The reference images and compose

The SPA images run an unprivileged nginx with a `HEALTHCHECK`. All three Dockerfiles fetch dependencies from the lockfile alone before the source is copied. The production compose states resource limits and a bounded log driver per service.

> **Amended 2026-09-30 (D29.5) — what was built.**
>
> - **The SPA images** run `nginxinc/nginx-unprivileged` (Alpine, the stock image's minor), which runs nginx as uid 101 from the first instruction; the runtime stage states `USER 101` so that a later `USER root` cannot leak into the container unnoticed. A port below 1024 is root's, so `nginx.conf` listens on **8080**, the Dockerfile exposes it and the compose file maps the loopback port to it. The `HEALTHCHECK` is BusyBox `wget` against `/healthz`, an exact-match location nginx answers itself, unlogged, with no file read — liveness of the server, which is all a static image can lose. The substitution of the API origin into the policy is unchanged and runs as the unprivileged user. Renovate's base-image rule names the new image.
> - **The fetch layer.** Each build stage copies `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` and runs `pnpm fetch` before `COPY . .`, and installs `--frozen-lockfile --offline` after it — the offline install is also what proves the fetch left nothing to download. The manifest comes for its `packageManager` field (Corepack's pnpm pin), and the workspace file for the settings pnpm 12 reads there alone (`overrides`, `allowBuilds`, the cooldown and `trustLockfile`). In the SPA images the fetch sits above the build arguments, because an `ARG` promoted to `ENV` keys every later layer and the SPA images take one per environment. Measured on a warm builder: a source edit reuses the fetch layer, and the offline install takes under a second where the fetch took five.
> - **The compose file** gives every service `deploy.resources.limits` — the API 1 CPU and 1 GiB, sized by argon2's memory per hash times the concurrent hashes; `migrate` 1 CPU and 512 MiB; `prune` half a CPU and 256 MiB; each SPA half a CPU and 128 MiB — and one `x-logging` anchor, the `json-file` driver capped at three files of 10 MB. The numbers are starting points written in the file, not variables: a deployment that sizes them edits the file it deploys, and `docs/deploy.md` says what each follows.
>
> What `docker compose -f docker/prod/compose.yaml config` renders carries both on all five services; hygiene cases hold the four places the SPA port is written to one number, the fetch ahead of the source in all three Dockerfiles, and the limits and the log anchor on every service.

### 6. What `check-types` caches for a referenced project

Decided by measurement at the step that builds it, between the emit cached without its buildinfo and the task uncached where a package is its own consumer. The step amends this section with the choice and its numbers; the hygiene case that reproduces the masked error is what proves it.

> **Amended 2026-09-30 (D29.5) — the task is uncached for a package; the emit without its buildinfo is refused.** The root task table's `check-types` says `cache: false`, and each app's `turbo.json` opts back in with `cache: true` and no output, as `D20.12` left them. So a composite package's `tsc -b` runs on every `check-types`, incremental on its own buildinfo, and nothing a cache hit writes back can tell it there is nothing to do; an app's hit replays a green for inputs that were checked and restores nothing the compiler reads.
>
> The other candidate was built and measured first. Caching `dist-types/**` without `*.tsbuildinfo` passes the masking case — and a consumer whose own hash moved then finds each referenced package with declarations and no buildinfo, which `tsc -b` reads as out of date: with the local cache warm, a fresh tree and one file added to `apps/api`, the API's task rebuilt `config-vitest`, `contracts`, `crypto`, `db` and `logger` into their own directories. That is ADR-0062 §3's refusal — one package's task writing into another's — and with the three apps scheduled at once it is three writers on the same files. So it is refused, whatever it saves.
>
> The numbers, `pnpm check-types` on this repository's seventeen tasks, four cores: `--force` cold (no `dist-types/`, no app buildinfo) **10.8 s and 10.4 s before, 11.9 s and 10.8 s after**; `--force` warm **1.65 s and 1.61 s before, 1.58 s and 1.71 s after** — the same compile either way, since `--force` bypasses the cache. What the choice costs shows without `--force`: an unchanged tree was a full cache hit in **0.22 s** and is **1.43 s** after, fourteen incremental `tsc -b` runs that each find their state current; and CI's shape — the local cache restored over a fresh checkout, one app changed — took **1.9 s** before and **7.1 s** after, every package compiled once from nothing. The emit-without-buildinfo shape took 2.8 s there, with the cross-package writes above. A second on the inner loop and five in CI buy a `check-types` whose green a restored file cannot decide.
>
> The proof is `scripts/docs-hygiene.test.mjs`'s "a package's restored buildinfo cannot mask its own error": it resolves each composite package's effective `check-types` entry, runs `D20.12`'s experiment for every shape found on a scratch copy of the package with no references — warm, keep what a hit restores, break a source file, write the kept files back after it, compile — and refuses an exit `0`. It is red on the tree before this amendment and green after, and it asserts that restoring `dist-types/**` still masks, so a compiler that stopped masking would be noticed rather than silently pass the case. ADR-0073 §6's invariant stands with no exception left open.

### 7. What this record declines

- **An argon2 pepper.** Adding one later costs what adding one now costs, a rehash on next login, and it would put a secret in the database tooling today.
- **A credential epoch.** §3's retry and lock order bound the race it would close; it stays a named residual.
- **The scheduler seam and the mail outbox.** They stay on the ledger's operations row, planned. The `prune` service already runs in the reference deployment, and §1 is what lets their migration merge into a fork later.
- **Audit retention** stands as [ADR-0058](0058-append-only-audit-log.md) and ADR-0061 decided it: a reviewed migration, never a job.

## Consequences

- A fork merges the starter's migrations and they are applied. The journal is still one file both sides edit; the conflict is a git conflict, resolved by hand.
- The runner is this repository's code. A Drizzle release that changes the journal or the table is read before it is taken.
- A leaked signing secret can be retired without signing everyone out.
- A request that loses a deadlock is answered as if it had not; one that loses repeatedly is still a `500`.
- Three new optional variables, each a three-place change (ADR-0004 as carried), none required in a default clone.

## Alternatives considered

- **Refusing a skipped migration and fixing timestamps by hand.** It makes the skip loud and leaves every merge a manual edit.
- **`JWT_ACCESS_SECRETS` as a list**, the row's wording. A rename breaks every deployment's environment for the same behaviour.
- **EdDSA.** A key pair buys verification without the signing key, which nothing here needs; it remains ADR-0018's named later step.
- **Building row-level security outright.** The mechanism is the unknown, and a stalled step would hold the wave.

## Context

[ADR-0017](0017-identity-model-populations-and-roles.md) made `users.password_hash` nullable for "the social / passwordless paths in ADR-0018's future scope", login has always read a null hash as "no password login for this account", and [ADR-0057](0057-impersonation-sessions.md) §2 built the shape a redirect callback needs — a single-use handoff delivered in a fragment and exchanged for a session on cookie transport — which [ADR-0071](0071-mail-flows.md) §1 generalised into `account_tokens` and §3 used to sign a device in from a link. The one rule that makes a federated login safe, that an external identity may attach to a local account only when that account's address is proven, became true at `D18.3`: every `active` user has a verified or asserted address, and nothing downstream re-checks a flag (0071 §3). The operator's decisions of 2026-09-09 and 2026-09-10 fixed the rest: users only, plain OpenID Connect with PKCE verified with `jose` and no new auth library, the issuer stubbed in unit tests only, the callback handed off the impersonation way. The decisions of 2026-09-11, recorded below, answer what those left open.

## Decision

### 1. The identity table and the linking rule

`federated_identities`: `id`, `user_id` (references `users.id`; a user is soft-deleted, so the row outlives nothing it should not), `provider` (`FEDERATED_PROVIDERS` in `@repo/contracts`, one value today: `google`), `subject` (the provider's stable `sub`), `email` (the address the provider reported when the row was written — informational, never a lookup key after the link), `linked_at`, `last_login_at`, timestamps. Unique on (`provider`, `subject`) and on (`user_id`, `provider`): one Google account resolves to one user, and one user holds at most one identity per provider.

Resolution at a sign-in, in this order and no other. **By subject first**: a row for (`google`, `sub`) names the user, whatever address either side carries today — a person who changed their address under 0071 §6, or at Google, still signs in. **By address second, and only under three conditions together**: the ID token says `email_verified: true`, a live user holds that address, and that user is `active`. The identity is linked to that user then, and `email_verified_at` is left as it was — the address was already proven. A `pending_verification` holder is refused with 0071 §3's own `403 AUTH_EMAIL_UNVERIFIED` and nothing is linked, because the password on that row belongs to whoever registered it, and a pre-registered address is the account-takeover primitive 0071 §Alternatives names; a `disabled` holder is refused `AUTH_ACCOUNT_DISABLED`, login's own answer. **By creation last**: no row and no holder creates a user — `active`, `email_verified_at = now()` on the provider's claim, `password_hash` null, names from the token's `given_name` and `family_name`, the personal organization in the same transaction ([ADR-0067](0067-organizations.md) §2's rule for every path that brings a user into existence) — **only when `FEATURE_USER_REGISTRATION` is on**. That flag means "may new accounts be made here" and a second door does not change the meaning: with it off the answer is `403 AUTH_FEDERATED_SIGNUP_CLOSED` and no row is written. An unverified `email` claim never matches and never creates.

**Amended 2026-09-11 (D19.1), on that step's `security-reviewer`: linking by address reads whether the provider is _authoritative_ for the address, not only whether it says `verified`.** The rule above took `email_verified: true` as proof that the person controls the address now. Google documents that it is that only where Google hosts the mailbox — a `gmail.com` or `googlemail.com` address, or a Workspace address whose `hd` claim is the address's own domain. For any other address Google checked the mailbox once, when the Google account was created, and the mailbox may have changed hands since: a former employee's work address, a domain that lapsed and was bought. Linking such an identity to whoever holds the address here would hand the account to the mailbox's previous owner — the account-takeover case this section exists to close, arriving through the provider's claim rather than through a pre-registered password. So **the second condition becomes four**: `email_verified: true`, **the provider authoritative for the address**, a live holder, and that holder `active`. A verified address the provider is not authoritative for, held by a live user of any status, is refused `403 AUTH_FEDERATED_LINK_REQUIRED` and nothing is linked — the person signs in with their password and links Google from the security section (§3), which proves both sides at once. **Creation is unchanged**: with no holder there is no account to take over, and a verified claim is what creating one has always read; an address that later proves to belong to somebody else is recovered by its mailbox, through §3's reset link, which is the model this repository already runs on. The port says which is which: the adapter reports `emailAuthoritative` beside `emailVerified`, and nothing but the adapter knows the provider's hosting rule.

**Amended 2026-09-11 (D19.1), on that step's `code-reviewer`: deleting an account deletes its identities.** "A user is soft-deleted, so the row outlives nothing it should not" was true of the foreign key and missed the constraint: (`provider`, `subject`) is unique with no predicate, so an identity left on a deleted account would hold that Google account for ever, and the person could come back with a password (ADR-0028 releases the address) but never through Google. The account's `federated_identities` rows are therefore **hard-deleted in the transaction that soft-deletes the account**, on both deletion paths — the identity table's version of releasing the address. Nothing is lost: an identity is a way in, a deleted account has none, and the trail keeps the account's own deletion.

**Amended 2026-09-11 (D19.2), on that step's `security-reviewer`: creation reads authority too.** The amendment above left creation on a verified claim alone, and gave its reason — an address that later proves to belong to somebody else "is recovered by its mailbox, through §3's reset link". Building the flow showed the reason does not hold: the reset changes the password and ends the sessions, and the **identity stays**, so the mailbox's previous holder — the former employee, the buyer of a lapsed domain — who made the account through Google keeps signing in by subject after the rightful owner has reset it. That is the federated pre-hijack, reopened by the one path the amendment left alone. So **a verified address the provider is not authoritative for neither links nor creates**: it is refused `403 AUTH_FEDERATED_LINK_REQUIRED` **whether or not an account holds it**, and the check runs before the address is looked up, so the answer also stops telling a claim that proves nothing whether an account exists. The person registers or signs in with a password and links Google from the security section (§3), exactly as the holder of such an address already had to. Creation on an address the provider hosts — `gmail.com`, or a Workspace domain naming itself in `hd` — is unchanged. The cost is stated for the operator: a person whose Google account uses a non-Google, non-Workspace address cannot make an account here through Google at all, only link one.

**Amended 2026-09-11 (the operator, between `D19.2` and `D19.3`; built at `D19.4`): the `D19.2` narrowing of creation is withdrawn — creation returns to a verified claim wherever registration is open, because the reset now recovers everything.** The finding behind the narrowing is real and the record keeps its name for it: an identity that survives a password reset lets a mailbox's previous holder keep signing in by subject after the rightful owner has recovered the account. What the narrowing missed is that the same identity survives the same reset through a second door — §3's explicit link, where any Google account may attach to a password account whose mailbox later changes hands — so refusing creation on a non-hosted address closed one instance of a class and left the class open for `D19.4` to meet again. The class is closed where [ADR-0071](0071-mail-flows.md) §4 already reasons about recovery: a reset by the mailbox ends every session and spends pending links because "the account may be being recovered from somebody", and a federated identity is a credential of exactly that kind, so **a reset removes every federated identity of the account** (§3, amended). With that in force, an account made through Google on an address the provider does not host is recovered by its mailbox the way a pre-registered password account already is, and the cost the `D19.2` amendment stated for the operator — no account through Google on an Outlook or custom-domain address — buys nothing. So: **by creation, a verified `email` claim creates wherever `FEATURE_USER_REGISTRATION` is on, authoritative or not**; the authority check leaves the head of the resolution and returns to where `D19.1` put it, on the address match alone, which is the provider's own guidance for attaching an identity to an account that already exists. `AUTH_FEDERATED_LINK_REQUIRED` keeps that one meaning — a verified, non-authoritative address that a live account holds — and its sentence returns to offering sign-in and linking. Until `D19.4` builds the reset's half, the `D19.2` behaviour stays in the code, and `D19.3` is untouched by either reading: the landing route renders a code's sentence and does not know the rule.

**Amended 2026-09-11 (the operator, after `D19.4`), spelling out what the withdrawal implies.** With creation open again, a verified claim on an address the provider does not host is answered `AUTH_FEDERATED_LINK_REQUIRED` when a live account holds the address and creates one when none does — which tells the holder of such a claim whether an account exists. That is the signal registration's `409 USER_EMAIL_TAKEN` already gives to anyone with an address, accepted at [ADR-0071](0071-mail-flows.md) §6, and it is accepted here on the same terms: the claim is Google's word that the person controls the mailbox, which is more than registration asks. The `D19.2` amendment's "no existence signal either way" described the narrowed rule and does not describe this one.

### 2. The flow — start, callback, exchange

Three endpoints on the public segment, mounted **only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both set** (both or neither, refused otherwise at startup); absent, the paths answer `404 ROUTE_NOT_FOUND` exactly as registration does with its flag off ([ADR-0004](0004-configuration-and-environment.md)).

- **`POST /public/auth/google/start`** is an XHR, not a navigation, and answers `{ authorizationUrl }` while setting the transaction cookie. A `GET` that redirected would be a link anyone could plant to start a flow in a victim's browser; a `POST` from the SPA's own client is a request the transport opt-in header already forces through a preflight. The cookie is **`__Host-<APP_ID>.oidc`**: `HttpOnly`, `Secure`, `SameSite=Lax`, path `/`, ten minutes, on the API's own origin — and its value is a compact HS256 JWT minted with `jose` under `JWT_ACCESS_SECRET` with audience `<APP_ID>-oidc`, carrying `state`, `nonce`, the PKCE `code_verifier`, the `intent` (`signin` or `link`), the user id when linking, and the SPA's current locale. Signed, not encrypted, on purpose: nothing in it is a secret to the browser that owns it, and `__Host-` keeps every other origin out. `Lax` is what lets a top-level navigation back from Google carry it. This is the only cookie the flow adds, and it is a delta on ADR-0029 rather than a change to it: the transport of *sessions* is untouched. It is behind a limiter of its own on `RATE_LIMIT_LOGIN_MAX`'s number, keyed on the source address alone (the `D18.2` precedent for a second counter on one number): a start costs the API a signature and Google a redirect, and no email exists yet to key on.
- **`GET /public/auth/google/callback?code&state`** is the one navigation, from Google. It reads the cookie, matches `state`, clears the cookie, exchanges `code` with the verifier and the client secret at the token endpoint, verifies the ID token with `jose` against the issuer's published keys (`iss`, `aud`, `nonce`, `exp`), and resolves per §1. For a sign-in it mints an `account_tokens` row — purpose **`federated_login`**, the user as principal, `FEDERATED_HANDOFF_TTL` sixty seconds, the impersonation handoff's number for the impersonation handoff's reason — and answers `302` to `${CUSTOMER_APP_URL}/auth/google#token=…`. For a link it writes the identity and answers `302` to `${CUSTOMER_APP_URL}/auth/google#linked=google`. **Every refusal is a `302` to the same route with `#error=<code>` and nothing else in the fragment**: the SPA renders the catalogue's sentence for the code, and the API's error body — which a navigation could only show as JSON on a bare page — is never the thing a person sees. The callback carries no CSRF guard and no limiter beyond the global one, on 0071 §3's `D18.5` reasoning: the state in the cookie is the binding, the code is single-use at Google, and the budget sits at the start.
- **`POST /public/auth/google/exchange { token }`** consumes the `federated_login` token and answers **login's body on cookie transport** — 0071 §3's `verify-email` shape, inherited whole, including its `D18.4` amendment: the route that lands must not spend the fragment on mount in a browser that already holds a session, because a live link handed to a signed-in person is a forced-login primitive whatever minted it. A second exchange answers `401 UNAUTHENTICATED`; a token of another purpose or population is the same `401`.

**Amended 2026-09-11 (D19.2): which code a refusal the section does not name carries.** §1 names four — `AUTH_EMAIL_UNVERIFIED`, `AUTH_ACCOUNT_DISABLED`, `AUTH_FEDERATED_SIGNUP_CLOSED`, `AUTH_FEDERATED_LINK_REQUIRED` — and building the callback met the rest. A callback this browser did not start (no transaction cookie, a `state` that does not match it, a person who declined at Google), a code or ID token the provider or the adapter refuses, and an `email` claim that is unverified, absent or not an address all answer the generic **`UNAUTHENTICATED`**, one sentence for "that sign-in did not work, try again" — and the unverified claim answers it **whether or not an account holds the address**, because a claim that proves nothing may not learn anything either. The provider not answering is **`SERVICE_UNAVAILABLE`**, the one refusal a person should retry later rather than differently. A race the resolution loses — the address or the subject taken by a concurrent commit, or an address whose account already holds a *different* identity of this provider — is the generic **`CONFLICT`**, and nothing is written: the owner unlinks the old identity before another can take its place. No new code, so the catalogue grows by §1's two alone. And the transaction is **spent on every outcome**, since it is good for one callback.

**Amended 2026-09-11 (D19.2), on that step's `security-reviewer`: the handoff is bound to the browser, and the callback and the start are held to what this section claimed of them.** Three changes, each closing a gap between what the section said and what its first build did.

- **The exchange requires the browser the callback answered.** The transaction cookie binds the *callback* to the browser that started; nothing bound the *exchange*, so the sixty-second token was a bearer credential anybody could relay — run the flow in one's own browser, lift `#token=` from the redirect, and send somebody to the landing route, which signs a browser that holds no session into the relayer's account. §2's ask-first rule covers only a browser that already has one. So on a sign-in the callback **replaces** the transaction cookie with a **handoff binding** — the SHA-256 of the token it put in the fragment, sealed with the same key and audience and a `k` claim that keeps the two kinds apart, living `FEDERATED_HANDOFF_TTL` — and `exchange` refuses, with its one `401`, any token the cookie does not bind, **before** it spends anything; the cookie is cleared either way. The exchange is a same-site request from the customer app, which the refresh cookie's own `Strict` already assumes, so the `Lax` cookie travels with it.
- **The callback carries a limiter of its own** — `RATE_LIMIT_LOGIN_MAX`'s number keyed on the source, the start's shape in a separate counter — where the bullet above said "no limiter beyond the global one". The sealed transaction is single-use only in an honest browser, so its holder can replay it for ten minutes with invented codes, and each replay is a request from this API to Google's token endpoint: harmless to authentication, which PKCE and Google's one-time codes protect, and not to the client's quota. A person makes one callback per start, so the honest path never meets it; its `429` is the one answer on the route that is not a redirect.
- **The start takes a JSON body or nothing.** The bullet's reason for a `POST` was that the customer app's request is forced through a preflight; nothing enforced it, and a cross-site form posting `text/plain` reached the start with a body no parser read and the schema accepted as `{}` — overwriting a victim's in-flight transaction and spending their start budget. A request that is not `application/json` is refused `400 VALIDATION_ERROR` and sets no cookie.

The provider is a **port** in the API's core, [ADR-0066](0066-infrastructure-seams.md)'s shape: `createGoogleOidcProvider(config)` does discovery, PKCE and `jose` verification, and `createFakeOidcProvider()` answers a scripted ID token. The integration tier drives the callback against the fake, so the whole flow but Google itself is proved against Postgres; the browser tier does not drive it (the operator's decision at planning). The API learns its own public origin for the redirect URI — **`API_PUBLIC_URL`**, an origin, defaulting to `http://localhost:4000` and refused at that value in production the way `CUSTOMER_APP_URL` is — and the redirect URI is `${API_PUBLIC_URL}/api/v1/public/auth/google/callback`, stated once in [`docs/deploy.md`](../deploy.md) for the console.

### 3. The credentials an account keeps

`me` and `/user/profile` gain **`hasPassword`** and **`identities`** (`provider`, `email`, `linkedAt`), so a client can say which ways in exist without a second request; the admin's user resource gains the same `identities` read-only, and no admin screen draws it in D19 (the operator's decision; the panel's bundle has no room and the lever is its own row).

- **Link**: `POST /user/profile/identities/google/start`, authenticated, CSRF-guarded, answering `{ authorizationUrl }` with the cookie's `intent = link` and the caller's id. The callback links when the subject is free and refuses `409 AUTH_IDENTITY_TAKEN` when another user holds it. The Google address need not match the account's: the person has proven control of both sides, and the account's address does not change.
- **Unlink**: `DELETE /user/profile/identities/:provider { currentPassword }`. Refused `409 AUTH_LAST_CREDENTIAL` when `password_hash` is null — the account would have no way in — and otherwise held to [ADR-0027](0027-credential-self-service-and-reset.md)'s current-password rule, because severing the owner's own way back in is takeover-adjacent. Every session but the caller's is left alone; nothing about the account's sessions changes.
- **Set a password**, for an account that has none: the security section offers it and it **sends 0071 §4's reset link** to the proven address — no new endpoint, and a stolen session cannot mint itself a permanent credential. The change-password dialog is hidden while `hasPassword` is false, since it would ask for a password that does not exist.
- **Login with a password on a passwordless account** stays `401 AUTH_INVALID_CREDENTIALS` through the dummy hash, as it has since D1: the answer must not say which way in exists.
- **Impersonation**: link and unlink join ADR-0057 §5's list under `refuseImpersonated` and its one code. Support may see the identities; it may not reshape them.

Audit ([ADR-0058](0058-append-only-audit-log.md)): `account.identity_linked` and `account.identity_unlinked` with the user as actor; an account created through §1 writes what registration writes, with the provider named in the details; a sign-in through §2 is a session mint like any other.

**Amended 2026-09-11 (D19.2): what "what registration writes" is.** Registration itself writes no row; its trail is `account.verified`, written when the link proves the address. So an account created through §1 writes **`account.verified` with `{ provider }`** — its address is proven by the provider's claim in the same instant — and **`account.identity_linked` with `{ provider, via: "signup" }`** beside it, so "when did this Google account attach to this user" has a row whichever path attached it. A link by address at sign-in (§1's second rule) writes `account.identity_linked` with `via: "address"`; §3's explicit link will write it with its own `via`. The subject is never in the details — it is the key a sign-in resolves by, not a fact about the account.

**Amended 2026-09-11 (the operator, between `D19.2` and `D19.3`; built at `D19.4` and `D19.5`): what a reset does to the identities, how a password is set from a session, and what a passwordless account may not do yet.** Three rules, the first of which is the delta on [ADR-0071](0071-mail-flows.md) §4 and [ADR-0027](0027-credential-self-service-and-reset.md) that §1's last amendment leans on.

- **A password written without the account's own authority removes every federated identity**, in the transaction that writes it: the reset by mail (0071 §4, `POST /{user,admin}/auth/password/reset` — staff hold no identities, so the user segment is where it bites) and the administrative reset (0027, `POST /admin/users/:id/password`), each writing one `account.identity_unlinked { provider, via: "reset" }` row per identity beside the row it already writes. The mailbox, or the operator, recovers the account from everyone — the person who reset it is signed in by the password they just chose and links Google again from the security section in one click. A password change with the current password (0027) removes nothing: the account's own authority asked for it.
- **"Set a password" is `POST /user/profile/password/set-link`** — authenticated, CSRF-guarded, `refuseImpersonated`, answering `202 { accepted: true }` behind the password-reset limiter's own counter — which mints the caller's own `reset_password` token with `payload: { requestedBy: "session" }` and mails 0071 §4's template to the account's address; the same `/reset-password` screen and the same `reset` endpoint consume it, and **a consume whose payload says the session asked keeps the identities**: the session asked and the mailbox confirmed, which is the account's own authority twice over. No new purpose and no new screen. An account that has a password may use it too, and gets the same keep. The anonymous `forgot` stays open to a passwordless account — an address is recoverable whatever a person remembers — and a person who takes that door instead of this one re-links Google afterwards; the security section offers this one.
- **A passwordless account may not change its password, change its address or delete itself until it has set one.** The API is unchanged: each of the three asks the current password, a null hash never verifies, and the answer is the `403 AUTH_CURRENT_PASSWORD_INVALID` it has always been. The customer app says so instead of asking: while `hasPassword` is false the three dialogs are replaced by one sentence, "set a password first", and the control that does it (§4). The alternative — accepting the reset link as the proof for those three — would make the mailbox a second current password for every account, which 0027 decided against once and this record does not reopen.

**Amended 2026-09-11 (the operator, after `D19.4`, on the independent `security-reviewer` pass over that step; built at `D19.5`): what a session-minted link may keep.** The finding, wider than `D19.4`'s notes logged it: a session in the wrong hands links its own Google account (allowed — a link needs only the session) and calls `set-link`; the owner receives what is byte-for-byte the recovery template, follows it to secure the account, and the consume — session-minted — keeps the intruder's identity while revoking every session, so the recovery looks complete and is not. That is a stolen session minting itself a permanent credential through the owner's click, the case §Alternatives rejected a set-password endpoint for. Two rules close it. **`set-link` is for an account without a password**: with a hash on the row it answers `409 CONFLICT`, because change-password with the current password is that account's way and the second door is what the laundering needs. And **a session-minted consume keeps only the identities linked before the session that asked was created**: the mint seals the session's id in the payload beside `requestedBy`, the consume reads that row's `created_at` (a revoked row still says when it began; a pruned one means keep nothing) and removes every identity whose `linked_at` is later. A stolen cookie is the owner's own session, opened before anything the intruder did, so whatever the intruder linked is younger than it and goes, and what the owner signed up or linked with before is older and stays. On today's one provider the first rule alone suffices — a passwordless account can neither gain a second Google identity nor lose its only one from a session — and the second is what keeps it sufficient when a second provider arrives. The draft of this paragraph written earlier the same day refused `set-link` while a mailbox-minted link was live; that closed the narrower case the build notes described and not this one, and it is withdrawn unbuilt. The trail says which kind of reset it was: `account.password_reset` gains `data: { requestedBy: "session" | "mailbox", unlinked }`. And both the link callback and the reset **lock the account row** before they act, so a link that commits beside a reset cannot leave an identity the reset did not see.

**Amended 2026-09-12 (the operator, after `D19.5`, on that step's `security-reviewer`): the sentence above about a second provider does not hold, and is withdrawn.** The reviewer's case: with two providers, an intruder on a passwordless account links provider B, signs in _through B_ to obtain a session younger than that link, and asks for the set-password link from that session — B is older than the asking session and is kept. And `set-link`'s mint still supersedes a live `forgot` link with a byte-identical mail, so the intruder can turn the owner's mailbox recovery into a session-minted one. Both are unreachable today: the first rule (`set-link` for a passwordless account alone) and one identity per provider leave nothing for a session to keep that the owner did not put there. What the second rule buys today is defence in depth, not sufficiency. **Before a second provider is added, the keep must trace which identity a session was minted through** — a session opened by a federated sign-in records its identity, and a session-minted consume removes that identity's siblings, or keeps nothing a federated session could have added — and that is the decision the second provider's record makes, not this one.

**Amended 2026-09-11 (D19.4): what building §3's API settled.** Five precisions, the first of them a rule.

- **A link completes only while the session that asked for it is live.** The link start seals the caller's account **and session** into the transaction beside `intent = link`, and the callback refuses — `#error=UNAUTHENTICATED`, nothing written — when that session has been revoked, has expired, belongs to another account or was minted by impersonation. Without it the ten-minute transaction was a way round the reset rule above: a session in somebody else's hands starts a link, the owner resets the password — which ends every session and removes every identity — and the callback then attaches the other person's Google account to the recovered account anyway. A subject the caller already holds is linked again as a no-op; a second Google account on an account that has one is the generic `CONFLICT`, the sign-in's rule; `account.identity_linked` says `via: "link"`.
- **"CSRF-guarded" on the link start is the bearer token.** [ADR-0029](0029-browser-token-transport.md) keeps the access token in a header precisely so that no bearer route needs the double-submit check; that check fires only on a request leaning on the refresh cookie, which is scoped to `/user/auth` and never reaches `/user/profile`. Mounted there it would be inert, so it is not mounted. The start takes a JSON body or nothing, as §2's start does, and carries no limiter of its own: it costs a signature, and the callback — the half that costs Google a request — keeps the budget §2 gave it.
- **Unlink answers in this order**: `409 AUTH_LAST_CREDENTIAL` for an account with no password, before any password is asked for; `403 AUTH_CURRENT_PASSWORD_INVALID` when the password does not verify; `404 NOT_FOUND` when nothing of that provider is linked, which by then tells the caller only about themselves; otherwise `204` with `account.identity_unlinked { provider, via: "unlink" }`. Unlink is mounted whether or not the Google client is configured — removing a way in needs nothing from Google — while the link start, like §2's routes, exists only where it is.
- **The administrative reset's rows are `setEmail`'s shape**, not "beside the row it already writes": that reset writes no row of its own, so each `account.identity_unlinked` it writes names the operator as actor, from the context, and carries the account as `subjectId` beside `provider` and `via: "reset"` ([ADR-0058](0058-append-only-audit-log.md)). The reset by mail's rows name the account as actor, off the claimed token, as its `account.password_reset` does.
- **The set-password link's budget is `RATE_LIMIT_PASSWORD_RESET_MAX` an hour keyed on the account**, in a counter of its own: the link goes to the account's own address and nowhere else, so the caller and the mailbox are one budget, and a counter apart from `forgot`'s keeps either from spending the other.

### 4. The customer app

`VITE_FEATURE_GOOGLE_SIGN_IN` (default `false`) decides whether the button exists in the bundle, and **the API's mount is the control** — the registration flag's own wording (0067 §6): a build with the button against an API without the client reaches `404` and renders the catalogue's sentence. "Continue with Google" sits under the sign-in card and, gated by both flags, under the register card; it posts `start` and assigns `authorizationUrl` to the window. No Google script and no external asset: the SPA's content policy allows neither, and the plain redirect needs neither. The `/auth/google` route is guard-free and composes `AuthLayout` itself, `/impersonate`'s shape for `/impersonate`'s reason; it strikes the fragment, applies §2's ask-first rule, exchanges, and lands home; `#linked` lands on `/account/security` with a notice; `#error` renders the sentence with a link to sign in. The security section gains **Sign-in methods** — the password's row with "Set a password" or "Change password", Google's row with link or unlink, the unlink dialog asking the current password — beside the existing cards. Copy in both locales.

**Amended 2026-09-11 (the operator, after `D19.3` and `D19.4`; built at `D19.5`): three things the first build of the landing route left open.** The sign-in screen's **`redirect` survives the round trip**, carried by the SPA and never by the API: the button stores it under the app's device key before leaving, the landing route reads it once and lands there when it is an app-relative path, on `/` otherwise — a location in the fragment would be a value an attacker's link could set. **A link refusal lands on Security**: when the browser holds a session and the fragment carries `#error=`, the landing route goes to `/account/security` and shows the code's sentence as a notice, because the only flow a signed-in browser reaches the callback from is a link, and "sign in again" is the wrong sentence for it; the `#linked` notice is drawn only when the server's `identities` list the provider, since the history state that requests it can be planted and the list cannot. And **the mark is Google's**, in its four colours — the provider's guidelines ask for it, and a brand mark is the exception to [ADR-0054](0054-design-language-instrument.md)'s one palette, stated once so nobody tidies it.

### 5. What stands

Sessions, rotation, reuse detection, the cookie transport and both CSRF cookies; the mint, the handoff and every other rule of impersonation; `account_tokens` and its mechanism; the invariant that every `active` user has a proven address; the registration flag's meaning; the current-password rule wherever a credential is removed; every rule about staff, who get no federated login here.

## Consequences

- A second provider is an enum value, an adapter behind the port and a button: nothing in §1–§3 names Google but the discovery URL and the claim names.
- Staff sign-in, when its row comes, has a table and a resolution rule to reuse and one question of its own — how a staff row is matched — which this record leaves exactly where the planning left it.
- The customer bundle's `entry` has about 3 kB of headroom and the sign-in screen is in it; the button and its copy in two locales may be the sixth raise, and the step that adds them measures rather than assumes.
- A third cookie name enters the roster [ADR-0064](0064-brand-seams.md) derives from `APP_ID`; a fork renaming its brand renames it with the others.
- The browser tier gains no request, so [ADR-0069](0069-development-rate-limit-profile.md)'s spent headroom is not spent further; the operator's browser walk with real credentials is the only place Google itself is exercised, and the definition of done says so.
- A person who holds both credentials and recovers the password by mail finds Google disconnected afterwards and re-links it in one click; the reset screen says so. That is the price of the mailbox recovering the account from everyone, and it is paid by the rare path rather than by every sign-up on a non-Google address.
- A person who links Google and sets a password in the same session finds that identity removed when the link is consumed — it is younger than the session that asked — and re-links it in one click. The rule cannot tell that person from an intruder, and it is the intruder it is for.

## Alternatives considered

- **Google Identity Services (the popup, One Tap, the ID token posted to the API).** Needs Google's script on the SPA's origin, which the content policy refuses, and puts the token in a request body the SPA composes; the redirect flow needs no script and lets the API hold the whole transaction.
- **`openid-client` or Passport.** The operator's decision was no new auth library; discovery, PKCE and JWKS verification are a few hundred lines over `jose`, which the API already depends on for its own tokens.
- **The OIDC transaction in a database row keyed by `state`.** No new cookie, but nothing binds the callback to the browser that started it, which is the login-CSRF case the cookie exists to close; and a row per click needs a sweep.
- **Activating a `pending_verification` account on Google's claim.** One fewer dead end, and the pre-registered password stays valid on an account the victim just walked into; refusing costs the person one verification mail.
- **A set-password endpoint on the session.** One form and no mail, but a hijacked session becomes a permanent password; the reset link already exists and proves the mailbox.
- **The handoff token in the query string, or the session's refresh token in the redirect.** Both rejected by ADR-0057 §2 and inherited whole.
- **Refusing creation on an address the provider does not host** (built at `D19.2`, withdrawn between `D19.2` and `D19.3`). Google's own guidance, and it does close the pre-hijack through creation — but not through the explicit link, which admits any Google account, so the class it aimed at stayed open; and it turned every Outlook, Yahoo or custom-domain Google user away from the sign-up button. Removing the identities at a reset closes the class at its root and keeps creation where the operator put it.

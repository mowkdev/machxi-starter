# ADR-0072: Federated identity — sign in with Google (supersedes ADR-0017, 0029 and 0057 in part — deltas)

- Status: accepted
- Date: 2026-09-11
- Supersedes: [ADR-0017](0017-identity-model-populations-and-roles.md) (delta: a `federated_identities` table beside `users`, and a user may hold no password and one or more federated identities — the population the record reserved a nullable hash for; both populations, their tables, their roles and every invariant stand); [ADR-0029](0029-browser-token-transport.md) as carried by [ADR-0056](0056-per-population-csrf-cookie.md) and [ADR-0064](0064-brand-seams.md) (delta: a third cookie name, `__Host-<APP_ID>.oidc`, set and read by the API alone for the minutes an authorization round trip lasts; the refresh cookie, both CSRF cookies and every transport decision stand); [ADR-0057](0057-impersonation-sessions.md) (delta: §5's exclusion list grows linking and unlinking a federated identity; everything else stands)

> Written 2026-09-11 by `/scope` for D19 ([`docs/plan/0019-google-sign-in.md`](../plan/0019-google-sign-in.md)) — writing is not opening, opening is not accepting. `proposed` at writing; **accepted 2026-09-11 at the head of `D19.1`**, where [ADR-0017](0017-identity-model-populations-and-roles.md) moved to `superseded by` and §1's table and §2's configuration and provider port were built, with the enumerations that name every table grown; the other two parents move at the step that makes each delta true (the `D10.5` precedent; the plan names which). Amendable in place, labelled, while D19 is `in progress` ([the ledger](../plan/README.md#the-window)).

## Context

[ADR-0017](0017-identity-model-populations-and-roles.md) made `users.password_hash` nullable for "the social / passwordless paths in ADR-0018's future scope", login has always read a null hash as "no password login for this account", and [ADR-0057](0057-impersonation-sessions.md) §2 built the shape a redirect callback needs — a single-use handoff delivered in a fragment and exchanged for a session on cookie transport — which [ADR-0071](0071-mail-flows.md) §1 generalised into `account_tokens` and §3 used to sign a device in from a link. The one rule that makes a federated login safe, that an external identity may attach to a local account only when that account's address is proven, became true at `D18.3`: every `active` user has a verified or asserted address, and nothing downstream re-checks a flag (0071 §3). The operator's decisions of 2026-09-09 and 2026-09-10 fixed the rest: users only, plain OpenID Connect with PKCE verified with `jose` and no new auth library, the issuer stubbed in unit tests only, the callback handed off the impersonation way. The decisions of 2026-09-11, recorded below, answer what those left open.

## Decision

### 1. The identity table and the linking rule

`federated_identities`: `id`, `user_id` (references `users.id`; a user is soft-deleted, so the row outlives nothing it should not), `provider` (`FEDERATED_PROVIDERS` in `@repo/contracts`, one value today: `google`), `subject` (the provider's stable `sub`), `email` (the address the provider reported when the row was written — informational, never a lookup key after the link), `linked_at`, `last_login_at`, timestamps. Unique on (`provider`, `subject`) and on (`user_id`, `provider`): one Google account resolves to one user, and one user holds at most one identity per provider.

Resolution at a sign-in, in this order and no other. **By subject first**: a row for (`google`, `sub`) names the user, whatever address either side carries today — a person who changed their address under 0071 §6, or at Google, still signs in. **By address second, and only under three conditions together**: the ID token says `email_verified: true`, a live user holds that address, and that user is `active`. The identity is linked to that user then, and `email_verified_at` is left as it was — the address was already proven. A `pending_verification` holder is refused with 0071 §3's own `403 AUTH_EMAIL_UNVERIFIED` and nothing is linked, because the password on that row belongs to whoever registered it, and a pre-registered address is the account-takeover primitive 0071 §Alternatives names; a `disabled` holder is refused `AUTH_ACCOUNT_DISABLED`, login's own answer. **By creation last**: no row and no holder creates a user — `active`, `email_verified_at = now()` on the provider's claim, `password_hash` null, names from the token's `given_name` and `family_name`, the personal organization in the same transaction ([ADR-0067](0067-organizations.md) §2's rule for every path that brings a user into existence) — **only when `FEATURE_USER_REGISTRATION` is on**. That flag means "may new accounts be made here" and a second door does not change the meaning: with it off the answer is `403 AUTH_FEDERATED_SIGNUP_CLOSED` and no row is written. An unverified `email` claim never matches and never creates.

**Amended 2026-09-11 (D19.1), on that step's `security-reviewer`: linking by address reads whether the provider is _authoritative_ for the address, not only whether it says `verified`.** The rule above took `email_verified: true` as proof that the person controls the address now. Google documents that it is that only where Google hosts the mailbox — a `gmail.com` or `googlemail.com` address, or a Workspace address whose `hd` claim is the address's own domain. For any other address Google checked the mailbox once, when the Google account was created, and the mailbox may have changed hands since: a former employee's work address, a domain that lapsed and was bought. Linking such an identity to whoever holds the address here would hand the account to the mailbox's previous owner — the account-takeover case this section exists to close, arriving through the provider's claim rather than through a pre-registered password. So **the second condition becomes four**: `email_verified: true`, **the provider authoritative for the address**, a live holder, and that holder `active`. A verified address the provider is not authoritative for, held by a live user of any status, is refused `403 AUTH_FEDERATED_LINK_REQUIRED` and nothing is linked — the person signs in with their password and links Google from the security section (§3), which proves both sides at once. **Creation is unchanged**: with no holder there is no account to take over, and a verified claim is what creating one has always read; an address that later proves to belong to somebody else is recovered by its mailbox, through §3's reset link, which is the model this repository already runs on. The port says which is which: the adapter reports `emailAuthoritative` beside `emailVerified`, and nothing but the adapter knows the provider's hosting rule.

**Amended 2026-09-11 (D19.1), on that step's `code-reviewer`: deleting an account deletes its identities.** "A user is soft-deleted, so the row outlives nothing it should not" was true of the foreign key and missed the constraint: (`provider`, `subject`) is unique with no predicate, so an identity left on a deleted account would hold that Google account for ever, and the person could come back with a password (ADR-0028 releases the address) but never through Google. The account's `federated_identities` rows are therefore **hard-deleted in the transaction that soft-deletes the account**, on both deletion paths — the identity table's version of releasing the address. Nothing is lost: an identity is a way in, a deleted account has none, and the trail keeps the account's own deletion.

### 2. The flow — start, callback, exchange

Three endpoints on the public segment, mounted **only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both set** (both or neither, refused otherwise at startup); absent, the paths answer `404 ROUTE_NOT_FOUND` exactly as registration does with its flag off ([ADR-0004](0004-configuration-and-environment.md)).

- **`POST /public/auth/google/start`** is an XHR, not a navigation, and answers `{ authorizationUrl }` while setting the transaction cookie. A `GET` that redirected would be a link anyone could plant to start a flow in a victim's browser; a `POST` from the SPA's own client is a request the transport opt-in header already forces through a preflight. The cookie is **`__Host-<APP_ID>.oidc`**: `HttpOnly`, `Secure`, `SameSite=Lax`, path `/`, ten minutes, on the API's own origin — and its value is a compact HS256 JWT minted with `jose` under `JWT_ACCESS_SECRET` with audience `<APP_ID>-oidc`, carrying `state`, `nonce`, the PKCE `code_verifier`, the `intent` (`signin` or `link`), the user id when linking, and the SPA's current locale. Signed, not encrypted, on purpose: nothing in it is a secret to the browser that owns it, and `__Host-` keeps every other origin out. `Lax` is what lets a top-level navigation back from Google carry it. This is the only cookie the flow adds, and it is a delta on ADR-0029 rather than a change to it: the transport of *sessions* is untouched. It is behind a limiter of its own on `RATE_LIMIT_LOGIN_MAX`'s number, keyed on the source address alone (the `D18.2` precedent for a second counter on one number): a start costs the API a signature and Google a redirect, and no email exists yet to key on.
- **`GET /public/auth/google/callback?code&state`** is the one navigation, from Google. It reads the cookie, matches `state`, clears the cookie, exchanges `code` with the verifier and the client secret at the token endpoint, verifies the ID token with `jose` against the issuer's published keys (`iss`, `aud`, `nonce`, `exp`), and resolves per §1. For a sign-in it mints an `account_tokens` row — purpose **`federated_login`**, the user as principal, `FEDERATED_HANDOFF_TTL` sixty seconds, the impersonation handoff's number for the impersonation handoff's reason — and answers `302` to `${CUSTOMER_APP_URL}/auth/google#token=…`. For a link it writes the identity and answers `302` to `${CUSTOMER_APP_URL}/auth/google#linked=google`. **Every refusal is a `302` to the same route with `#error=<code>` and nothing else in the fragment**: the SPA renders the catalogue's sentence for the code, and the API's error body — which a navigation could only show as JSON on a bare page — is never the thing a person sees. The callback carries no CSRF guard and no limiter beyond the global one, on 0071 §3's `D18.5` reasoning: the state in the cookie is the binding, the code is single-use at Google, and the budget sits at the start.
- **`POST /public/auth/google/exchange { token }`** consumes the `federated_login` token and answers **login's body on cookie transport** — 0071 §3's `verify-email` shape, inherited whole, including its `D18.4` amendment: the route that lands must not spend the fragment on mount in a browser that already holds a session, because a live link handed to a signed-in person is a forced-login primitive whatever minted it. A second exchange answers `401 UNAUTHENTICATED`; a token of another purpose or population is the same `401`.

The provider is a **port** in the API's core, [ADR-0066](0066-infrastructure-seams.md)'s shape: `createGoogleOidcProvider(config)` does discovery, PKCE and `jose` verification, and `createFakeOidcProvider()` answers a scripted ID token. The integration tier drives the callback against the fake, so the whole flow but Google itself is proved against Postgres; the browser tier does not drive it (the operator's decision at planning). The API learns its own public origin for the redirect URI — **`API_PUBLIC_URL`**, an origin, defaulting to `http://localhost:4000` and refused at that value in production the way `CUSTOMER_APP_URL` is — and the redirect URI is `${API_PUBLIC_URL}/api/v1/public/auth/google/callback`, stated once in [`docs/deploy.md`](../deploy.md) for the console.

### 3. The credentials an account keeps

`me` and `/user/profile` gain **`hasPassword`** and **`identities`** (`provider`, `email`, `linkedAt`), so a client can say which ways in exist without a second request; the admin's user resource gains the same `identities` read-only, and no admin screen draws it in D19 (the operator's decision; the panel's bundle has no room and the lever is its own row).

- **Link**: `POST /user/profile/identities/google/start`, authenticated, CSRF-guarded, answering `{ authorizationUrl }` with the cookie's `intent = link` and the caller's id. The callback links when the subject is free and refuses `409 AUTH_IDENTITY_TAKEN` when another user holds it. The Google address need not match the account's: the person has proven control of both sides, and the account's address does not change.
- **Unlink**: `DELETE /user/profile/identities/:provider { currentPassword }`. Refused `409 AUTH_LAST_CREDENTIAL` when `password_hash` is null — the account would have no way in — and otherwise held to [ADR-0027](0027-credential-self-service-and-reset.md)'s current-password rule, because severing the owner's own way back in is takeover-adjacent. Every session but the caller's is left alone; nothing about the account's sessions changes.
- **Set a password**, for an account that has none: the security section offers it and it **sends 0071 §4's reset link** to the proven address — no new endpoint, and a stolen session cannot mint itself a permanent credential. The change-password dialog is hidden while `hasPassword` is false, since it would ask for a password that does not exist.
- **Login with a password on a passwordless account** stays `401 AUTH_INVALID_CREDENTIALS` through the dummy hash, as it has since D1: the answer must not say which way in exists.
- **Impersonation**: link and unlink join ADR-0057 §5's list under `refuseImpersonated` and its one code. Support may see the identities; it may not reshape them.

Audit ([ADR-0058](0058-append-only-audit-log.md)): `account.identity_linked` and `account.identity_unlinked` with the user as actor; an account created through §1 writes what registration writes, with the provider named in the details; a sign-in through §2 is a session mint like any other.

### 4. The customer app

`VITE_FEATURE_GOOGLE_SIGN_IN` (default `false`) decides whether the button exists in the bundle, and **the API's mount is the control** — the registration flag's own wording (0067 §6): a build with the button against an API without the client reaches `404` and renders the catalogue's sentence. "Continue with Google" sits under the sign-in card and, gated by both flags, under the register card; it posts `start` and assigns `authorizationUrl` to the window. No Google script and no external asset: the SPA's content policy allows neither, and the plain redirect needs neither. The `/auth/google` route is guard-free and composes `AuthLayout` itself, `/impersonate`'s shape for `/impersonate`'s reason; it strikes the fragment, applies §2's ask-first rule, exchanges, and lands home; `#linked` lands on `/account/security` with a notice; `#error` renders the sentence with a link to sign in. The security section gains **Sign-in methods** — the password's row with "Set a password" or "Change password", Google's row with link or unlink, the unlink dialog asking the current password — beside the existing cards. Copy in both locales.

### 5. What stands

Sessions, rotation, reuse detection, the cookie transport and both CSRF cookies; the mint, the handoff and every other rule of impersonation; `account_tokens` and its mechanism; the invariant that every `active` user has a proven address; the registration flag's meaning; the current-password rule wherever a credential is removed; every rule about staff, who get no federated login here.

## Consequences

- A second provider is an enum value, an adapter behind the port and a button: nothing in §1–§3 names Google but the discovery URL and the claim names.
- Staff sign-in, when its row comes, has a table and a resolution rule to reuse and one question of its own — how a staff row is matched — which this record leaves exactly where the planning left it.
- The customer bundle's `entry` has about 3 kB of headroom and the sign-in screen is in it; the button and its copy in two locales may be the sixth raise, and the step that adds them measures rather than assumes.
- A third cookie name enters the roster [ADR-0064](0064-brand-seams.md) derives from `APP_ID`; a fork renaming its brand renames it with the others.
- The browser tier gains no request, so [ADR-0069](0069-development-rate-limit-profile.md)'s spent headroom is not spent further; the operator's browser walk with real credentials is the only place Google itself is exercised, and the definition of done says so.

## Alternatives considered

- **Google Identity Services (the popup, One Tap, the ID token posted to the API).** Needs Google's script on the SPA's origin, which the content policy refuses, and puts the token in a request body the SPA composes; the redirect flow needs no script and lets the API hold the whole transaction.
- **`openid-client` or Passport.** The operator's decision was no new auth library; discovery, PKCE and JWKS verification are a few hundred lines over `jose`, which the API already depends on for its own tokens.
- **The OIDC transaction in a database row keyed by `state`.** No new cookie, but nothing binds the callback to the browser that started it, which is the login-CSRF case the cookie exists to close; and a row per click needs a sweep.
- **Activating a `pending_verification` account on Google's claim.** One fewer dead end, and the pre-registered password stays valid on an account the victim just walked into; refusing costs the person one verification mail.
- **A set-password endpoint on the session.** One form and no mail, but a hijacked session becomes a permanent password; the reset link already exists and proves the mailbox.
- **The handoff token in the query string, or the session's refresh token in the redirect.** Both rejected by ADR-0057 §2 and inherited whole.

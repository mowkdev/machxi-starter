This record depends on 0047: 0031 as it stands says *"the layout composition an app owns lives in the app, the primitives it is built from live here"*, and everything below that puts a composition in `@repo/ui` is licensed by ADR-0047's changed what-code-the-package-may-hold section, not by this record.

## Context

Every screen in `apps/admin` is built from two layouts nobody designed, and the planned customer SPA ([D11](../plan/0011-customer-app.md)) will need both. D8 is design work, not a move: the shell and the record surface become generic, slotted compositions in `@repo/ui`, generalised **against the working consumer, in place** — `apps/admin` with its full test tier is the cheapest verification available — while every piece of behavioural machinery (grid, API client, resource config, form machinery) stays exactly where it is, so that [D9](../plan/0009-platform-extraction.md)'s extraction afterwards is mechanical and checkable by test totals.

**The record surface scrolls the wrong thing.** `apps/admin/src/shared/form/app-form-surface.tsx` puts `overflow-y-auto` on the drawer's entire `SheetContent` with `SheetHeader` inside it, so the title scrolls away with the fields; on the **drawer and page paths** the footer is a class string (`FOOTER = "mt-6 flex justify-end gap-2"`) rendered *inside* the scrolling body, so Save scrolls away too. The dialog path is a separate file with a different shape of the same defect: `app-form-dialog.tsx` wraps its actions in `DialogFooter className="mt-6"`, passes no `className` — so the modal has exactly `DialogContent`'s one `sm:max-w-lg` width — and its failure mode is an **unbounded `DialogContent`** that grows past the viewport rather than a footer that scrolls inside it. The footer's contents are `AppFormActions` and nothing else in all three. A form long enough to scroll loses its title and its Save button — the case in which the operator most needs them.

**The shell has no slots.** `apps/admin/src/widgets/dashboard-layout/index.tsx` hardcodes its header as `SidebarTrigger + Separator + <h1>{title}</h1>`. There is nowhere to put an action, a breadcrumb or a status control. Two corrections to the plan's framing belong here rather than in a later step's surprise:

- **The stranded chrome was placed deliberately, not accidentally.** The plan says theme, locale and logout landed in the sidebar footer "because it was the only region that took children"; the code records the opposite reasoning — [ADR-0032](0032-admin-app-architecture.md) assigns "navigation, current-principal block, logout" to `widgets/app-sidebar`, and D6.3/D7.5 put the preferences in the account menu on purpose ("a preference about the operator, in the menu named after them"). Moving them to the header is therefore a **reversal this record argues** (§Decision 2), not an accident it fixes — and a divergence from frozen ADR-0032's widget assignment, carried by **[ADR-0049](0049-admin-app-architecture.md)**, the supersession written for it, rather than argued away.
- **The breadcrumb is not unrendered in the sense claimed.** `shared/ui/index.ts` has exported six breadcrumb symbols since D3.3, `packages/ui`'s own suite renders `Breadcrumb`/`BreadcrumbEllipsis`, and the `breadcrumb`/`more` `UiStrings` keys already have a `t()` call site and an `lv` entry. What is true is narrower: **no admin screen composes one**. No door widening is needed for the non-collapsing trails the record routes render — `BreadcrumbEllipsis`, the `more` key's carrier, is deliberately not among the six exported symbols, and the seventh export is owed by the first trail that collapses. The stale "never reached the `shared/ui` door" comment in `apps/admin/src/app/providers/ui-strings.tsx` is corrected by whichever step first renders one.

Against speculative generality the plan carries a governing rule this record adopts as its own: **every slot and every variant must answer a need the repository can name today** — an `apps/admin` screen, a customer-app requirement written into [D11's plan](../plan/0011-customer-app.md), or an invariant a frozen ADR already imposes. Today D11's file states its needs only generically ("whichever shell slots this app fills differently from the admin panel"), so any slot below that cites D11 must have its requirement **written into `docs/plan/0011-customer-app.md` in the same change** — the citation is not allowed to point at a sentence that does not exist.

Two packaging facts frame everything below. `@repo/ui` declares only design-system runtime dependencies (`class-variance-authority`, `clsx`, `lucide-react`, `radix-ui`, `sonner`, `tailwind-merge`, `tailwindcss`, `tw-animate-css`) plus react/react-dom peers — **no `react-hook-form` and no `@tanstack/react-router`** — and two of the plan's own record-surface promises (a footer reading `isPending`/`isDirty`/`isValid` through `useFormContext`; the page variant's `useBlocker` navigation blocker) each require one of those. And [ADR-0046](0046-interface-localization.md) §12 forbids the package an i18n dependency while §13 gives *shared packages* a `register(i18n)` route — two incompatible mechanisms, and D8 is the first work that must choose between them for `@repo/ui` specifically.

## Decision

### 1. Both compositions live in `@repo/ui`, on a new hand-written path, and the package gains no dependency

**The shell and the record-surface container are compositions in `@repo/ui`**, under a path outside `components/` and `hooks/` — the `ui-strings.tsx` precedent, which is what keeps them formatted (the `.prettierignore` carve-out covers only those two directories) and outside [ADR-0031](0031-ui-design-system.md)'s regenerate-and-diff surface:

```
packages/ui/src/
├── components/           # generated primitives — byte-identical to CLI output, unchanged
├── compositions/         # hand-written; prettier applies; not under regenerate-and-diff
│   ├── app-shell.tsx     # "use client"
│   ├── banner.tsx        # "use client" — it reads UiStrings, so it is stateful by §1's own rule
│   └── record-surface.tsx  # "use client"
└── ui-strings.tsx        # the precedent (D7.3)
```

- **Every new path costs three coordinated edits, made together**: the `exports` entry [ADR-0047](0047-ui-package-scope.md)'s map pins (`"./compositions/*": "./src/compositions/*.tsx"`), a pattern in `apps/admin`'s `no-restricted-imports` group beside `components/*`, `hooks/*`, `lib/*` and `@repo/ui/ui-strings`, and a named re-export through `shared/ui/index.ts`. A path added without the lint pattern is a hole the one-door rule cannot see; D7.3 established the triple and this repeats it.
- **Neither `react-hook-form` nor `@tanstack/react-router` enters `@repo/ui`.** The container is **geometry-only**. `AppFormFrame` (react-hook-form) and the page variant's `useBlocker` stay in `apps/admin` as thin wrappers around the container (§4). This keeps the shell's own rule — it knows nothing about routing — true of the package, keeps ADR-0047's dependency-location rule minimal, and charges one honest price: D9's file-count table, which assumes "the surfaces D8 moved to `@repo/ui`", takes a **one-line correction** when D8's build order is written — the geometry moved, the two behavioural wrappers stayed.
- **Stateful compositions carry `"use client"`.** `apps/web` compiles the package through `transpilePackages`, and a composition without the directive is unimportable from a Next server component. ADR-0031's stated coupling cost — a change to a shared primitive is a change to both apps — now applies to compositions too.
- **Composition micro-copy is `UiStrings` keys** — new keys with English defaults, fed from `apps/admin`'s `common:ui.*` exactly as the existing thirteen are; anything content-like stays a slot the app fills with its own JSX. The Banner's dismiss-control label is the first concrete key, and **it is the fourteenth**. Its price is five coordinated edits, not one, and they are named here because four of them are silent when missed: the `UiStrings` interface field, the `DEFAULT_UI_STRINGS` entry, **both** hand-maintained lists in `UiStringsProvider` (the destructure and the `useMemo` dependency array — omitting the second freezes the string at its first value with nothing failing), the app's `AppUiStrings` provider line (omitting it makes the key an `i18n:check` orphan and exits 1), and both `en` and `lv` catalogues. A composition that reads `UiStrings` is a client component by construction — `banner.tsx` included, which is why the tree above marks it. ADR-0046 §13's `register(i18n)` route is **not** used for `@repo/ui`, and the reason is not the one it is easy to reach for: §13 is dependency *injection* — the instance arrives as a parameter — so it would add no i18next import. What rules it out is that its `I18n` type is `apps/admin`-owned until [D9](../plan/0009-platform-extraction.md) extracts it, and `UiStrings` already reaches every primitive at one key per string. The surface's own close needs **no new string**: `DialogContent` and `SheetContent` already render a localized close button behind `showCloseButton`.

### 2. The shell: one slotted composition over the sidebar-07 primitives

A composition that **knows nothing about routing or authorization** — navigation arrives as JSX, so the `can()` join ([ADR-0042](0042-client-side-authorization.md)) and the typed route links stay in the app that owns them:

```tsx
// packages/ui/src/compositions/app-shell.tsx — illustrative of shape and naming
export const AppShell = ({
  sidebar,                     // the whole drawer as one node — the app's <Sidebar>, not three fragments
  headerEnd,                   // beside the trigger, which stays the shell's
  breadcrumbs,                 // the header row's trail — JSX the app composes, not data
  banner,                      // full-width region above the header — §3
  title,                       // the page header: the row the single <h1> lives in
  fullHeight = false,          // ADR-0037's per-page opt-in, unchanged in meaning
  children,                    // the page, inside the page container
}: AppShellProps) => …
```

**The drawer arrives as one node, not as three regions**, and this is the record's own correction: an earlier draft gave the shell `brand`/`nav`/`sidebarFooter`. That shape cannot be filled. `apps/admin`'s `AppSidebar` **is** the `<Sidebar>` with its `SidebarHeader`, `SidebarContent`, `SidebarFooter` and `SidebarRail` (`apps/admin/src/widgets/app-sidebar/index.tsx:257-309`), [ADR-0049](0049-admin-app-architecture.md) keeps it whole in the `widgets` layer and has the `_dashboard` route file hand it in, and after the account menu leaves (below) `sidebarFooter` would have had no filler at all — the unexercised-slot defect this record's own rule forbids. `collapsible="icon"` and the mobile `Sheet` swap stay the primitive's, inside the app's node.

Every remaining slot answers a need nameable **today**, which is the slot-honesty rule applied to this record rather than asserted by it: `sidebar` is the admin drawer; `headerEnd` is the account menu (below); `breadcrumbs` gives the long-exported primitives their first composed screen (D8.4); `banner` has the pseudo-locale notice now and D12's impersonation banner next (§3); `title` is the `<h1>` the shell already renders. **`headerStart` and `pageActions` are deliberately not in the v1 API** — nothing in `apps/admin` fills either (the trigger stays the shell's; the one `CardAction` in the app is a section action inside `pages/profile`, not a page action, and the grid toolbar keeps Create where [ADR-0038](0038-grid-selection-and-capabilities.md) put it at D4.3) — and a slot with no consumer is the defect this repository has recorded twice. Either is one prop wide when a screen names it.

- **The page container carries [ADR-0037](0037-grid-viewport-layout.md)'s height contract unchanged, as this component's responsibility** — and it is a **two-element chain the shell must own both ends of**: `min-w-0` always on the container; in full-height mode `h-svh` on the **`SidebarInset`** and `min-h-0` on the **page container**, which is where the code puts them today (`apps/admin/src/widgets/dashboard-layout/index.tsx:62,71-78`). Collapsing them onto one element drops `h-svh` from the inset and breaks the chain everything below divides; jsdom lays nothing out, so no test would say so. The machine-checkable surface is preserved literally: **`data-slot="page-container"` and `data-full-height` stay on the same element**, `data-full-height` **present as an empty string when on and absent when off** — the producing form today, and the form the three routing tests' valueless `toHaveAttribute` silently accepts a `"false"` for. The `fullHeight` join point is untouched in meaning: the record routes' `staticData` expressions (`fullHeight: editSurfaceOf(config) !== "page"`) keep meaning what they mean, because §4 does not change what the `page` variant does to the grid underneath.
- **The page-header row is a `shrink-0` in-flow sibling above the page container**, not a child of it — the same reasoning the banner region gets one bullet down, and for the same reason: a row inside `data-slot="page-container"` becomes a new in-flow sibling of `children` inside the `min-h-0` box every grid divides, and silently takes height from all of them. Outside and `shrink-0`, it costs the budget exactly what today's `h-16 shrink-0` header costs it, which is the property that lets ADR-0037's chain stay one reviewable path.
- **The shell keeps the screen's single `<h1>`, and the page header is the row it lives in.** Today the shell renders `staticData.title` as the only `<h1>` and three pages repeat the same string as a `CardTitle` — a styled `div`, not a heading, which is the reason the staff, users and dashboard heading queries match one element. The title the app hands the shell renders as the one `<h1>`; **every page that repeats its route title in a `CardTitle` drops it — `pages/staff`, `pages/users` and `pages/dashboard`.** The last of those is not a grid page and is easy to miss: no test can see the leftover, because `CardTitle` is a `div`. `pages/profile`'s `CardTitle`s are `account.title` and `password.title` — section names, not the route title — and they stay.
- **Under the `page` variant the surface renders no heading of its own; the shell's `<h1>` is the record's title.** This is a rule, not a nicety: `staff:create.routeTitle` and `staff:create.title` are the *same string* ("New staff member", and the users mirror), so the shell's `<h1>` and the surface's own `<h2>` (`apps/admin/src/shared/form/app-form-surface.tsx:239`) would be two visible headings with one accessible name the moment any resource declares `editSurface: "page"`. Today only Radix's `aria-hidden` over the rest of the document keeps `findByRole("heading", …)` single-match in the other two variants, and the `page` variant has no modal and no overlay to supply it. So `dialog` and `drawer` keep their own `DialogTitle`/`SheetTitle` — Radix requires them for the accessible name anyway — and `page` renders its `description` without a heading. The [ADR-0044](0044-record-routes-without-list-state.md) invariant survives exactly: the record's title is always a real heading, rendered by the surface in two variants and by the shell in the third, and there is always exactly one of it.
- **The whole `AccountMenu` dropdown moves to `headerEnd`** — the slot's proving consumer. This **reverses the placement half of D6.3/D7.5 deliberately**: those steps put theme and locale in the account menu because a preference about the operator belongs in the menu named after them, and that reasoning survives — the menu is intact, `ThemeMenuItems`/`LocaleMenuItems` keep their `DropdownMenuRadioGroup` shape and its screen-reader semantics, and nothing about the two feature components changes. What changes is where the menu mounts, and the argument is D11's: **header chrome is exactly what the second app places differently**, so the shell's header must be able to hold it — a requirement written into `docs/plan/0011-customer-app.md` in the same change, per the slot-honesty rule. Moving the bare menu-item fragments instead would force both features out of the radio-group pattern; the cheap move is the whole menu.
- **The `breadcrumbs` slot is JSX, not data** — the app composes `Breadcrumb*` from its `shared/ui` door with `asChild` over the router's typed `Link`, and hands the finished trail in. A shell that took crumb labels and hrefs would emit plain anchors, i.e. a full document reload under TanStack Router, and would be a shell that knows about routing — the thing §2 opens by ruling out. The trail's items come from the only source that exists: route `staticData` (which carries `title` today) plus the record loader's own label, and because they are operator-facing copy [ADR-0046](0046-interface-localization.md) §8 makes them `TranslationKey`s rather than strings. `BreadcrumbEllipsis` is deliberately not among the six symbols `shared/ui` exports, so a trail that never collapses needs no door widening and the seventh export is owed by the first trail that does.
- **`widgets/dashboard-layout` survives as a thin adapter over `AppShell`** — it supplies the slots from the app's routing, `can()` join and features, and stays the `_dashboard` layout component in the `widgets` layer. That placement is carried by **[ADR-0049](0049-admin-app-architecture.md)**, the supersession of frozen [ADR-0032](0032-admin-app-architecture.md) written for this deliverable and accepted at the head of `D8.3`: the layer still owns the composition's *contents*, the package owns its *geometry*, and the account block leaving `app-sidebar`'s footer is a divergence from 0032 that 0049 carries whole rather than a claim that 0032 is untouched.

**Deliberately out of scope, named so nobody wonders whether they were forgotten**: navigation as a typed data array (ADR-0042's containment carve-out keeps "which entries render" a per-app judgement); command palette; global search; tenant switcher; and everything D12 puts *in* the banner — the `impersonatedBy` field on the principal and the `ImpersonationBanner` itself are [D12](../plan/0012-impersonation.md)'s.

### 3. The banner: a dumb region and a hand-written component

- **The `banner` slot is a `shrink-0` in-flow sibling above the header, and it renders nothing at all — not an empty `div` — when handed nothing.** It sits inside the `h-svh` box in full-height mode, so ADR-0037's flex budgeting absorbs it without arithmetic: chrome takes what it declares and the scroll body takes the rest. That is the existing argument restated, not a new one; an empty element that reserved space would shift every grid page's budget.
- **`Banner` is a generic component in the compositions path, hand-written rather than built on shadcn's alert primitive** (which the package does not carry): variants, a `message`, an `action` slot, and a `dismissible` flag — included now because its first real consumer, D12's impersonation banner, needs `dismissible={false}`. **`dismissible` exposes an `onDismiss` callback and the component holds no dismissed state of its own**: who is allowed to dismiss what, and whether it stays dismissed across a navigation, is a session question, and a composition that answered it would be the opposite of the next sentence. It is **dumb by construction: no `@repo/contracts` import**, no principal, no session store — a checkable boundary, and the reason the shell never learns *why* a banner is showing.
- **The in-admin consumer is the dev-only pseudo-locale notice, and its condition is a prop with a named channel.** `VITE_I18N_PSEUDO` only sets the app's default. The channel is decided here rather than discovered at the step, because none exists: `renderApp`'s existing `pseudo` option means something else already (it selects the pseudo-locale *lens* and reaches only `createI18n`), and `createAppRouter`'s context is exactly `{session, queryClient, client}`, which no record here may widen. So the notice's visibility is **a prop on `widgets/dashboard-layout`, supplied by `app/routes/_dashboard.tsx` from a small `PseudoNoticeProvider` in `app/providers`** — the shape `ThemeProvider` already has in that directory — whose default is `config.VITE_I18N_PSEUDO` and which `renderApp` overrides through a **new option named `pseudoNotice`**, distinct from `pseudo`. Gating it on the config variable directly would render it in no test in the repository — the admin vitest config pins `VITE_I18N_PSEUDO` to `"false"` for the whole suite on purpose — which is the same unexercised-surface defect this repository has recorded twice about the `page` edit surface; and reusing `pseudo` would mount the notice on all nine routes of §14's pseudo-locale walk, whose copy would then have to survive `unaccented()`.

### 4. The record surface: one geometry-only container, three variants, both mounts

One content-agnostic container replaces the shells inside `app-form-surface.tsx` — fixed header, scrolling body, fixed footer:

```tsx
// packages/ui/src/compositions/record-surface.tsx — illustrative of shape and naming
type RecordSurfaceSize = "sm" | "md" | "lg" | "xl" | "full";

export const RecordSurface = ({
  variant,                  // "dialog" | "drawer" | "page"
  size = "md",              // token → a class string merged through cn onto
                            //   DialogContent / SheetContent; zero generated-file edits
  title, description,       // the fixed header; title is a real heading in all three variants
  footer,                   // the fixed footer — a slot, not a fixed set of actions
  open, onOpenChange,       // the controlled mount; omitted for the routed, always-open mount
  dismissible = true,       // false refuses dismissal — Escape, overlay, close — while a mutation is in flight
  column,                   // the inversion: a render prop the app fills with its <form> — see below
  children,                 // the scrolling body: overflow-y-auto min-h-0
}: RecordSurfaceProps) => …

// column?: (props: { className: string; children: ReactNode }) => ReactElement
//   Called with the container's geometry classes and its three rows.
//   Omitted → the container renders its own <div> as the column.
```

- **The `<form>` wraps header, body and footer, and only the body scrolls** — and the way it does so is an **inversion**, decided here because the obvious reading of "the container holds the frame" is unbuildable. This is what makes a `type="submit"` button work in a *fixed* footer and lets that footer read form state through context. It fights the primitives' own layout — `DialogContent` is `grid … gap-4 p-6`, `SheetContent` is `flex flex-col gap-4`, both laying out their direct children — so wrapping collapses them to a single child, and that child must be the element carrying the row template and the body's `min-h-0`.

  **`AppFormFrame` keeps the `<form>`** — `form.handleSubmit(onSubmit)` stays attached to it directly, as it is today — **and supplies it to the container as the container's inner column through the `column` render prop.** The container calls `column({ className, children })` with its geometry classes and its three rows, and the app returns `<AppFormFrame className={className} …>{children}</AppFormFrame>`. So the `<form>` really does wrap all three rows; the footer is inside it by construction and `type="submit"` keeps working.

  **The mechanism is a render prop, deliberately, and not `asChild`.** This repository's `asChild` is Radix `Slot.Root` throughout (`button.tsx:51`, `badge.tsx:36`, `breadcrumb.tsx:54`, `sidebar.tsx:424` and four more), and `Slot.Root` **clones its single child and merges props onto it — it does not render the parent's own children inside it**. The injection would need `Slot.Slottable`, which appears nowhere in this repository and would be a new package convention bought for one call site; and the element handed over is the `AppFormFrame` *component*, not a DOM node, so a clone would have to be trusted to forward `className` regardless. A render prop states both obligations in the type and needs no convention at all.

  `AppFormFrame`'s locked `FieldSet` — two of the three halves of [ADR-0035](0035-config-driven-resource-ui.md)'s submit lock — sits between the `<form>` and the rows and therefore must stop laying out (`display: contents`), so the rows remain the form's own grid children while every control, the footer's included, stays inside the lock. **ADR-0035's one-form-frame ownership is untouched**: there is still exactly one `<form>`, still owned by the frame, and the footer still lands inside the disabled `FieldSet` — the property `app-form-surface.test.tsx`'s in-flight lock assertion checks in all three shells.

  The rejected reading, named so no step re-derives it: the container as the outer element with the frame rendered into `children`. It puts the container's `footer` slot outside both the `<form>` and the `FieldSet`, which breaks `type="submit"` and leaks the submit lock in one move.
- **The `dialog` variant's viewport bound goes on `DialogContent`, not on the column.** `DialogContent` carries **no `max-h` at all** (`packages/ui/src/components/dialog.tsx:75-78`: centred by transform, `grid`, `p-6`, `sm:max-w-lg`), so a `max-h` on the inner form bounds nothing — the dialog grows past the viewport and the body scrolls inside the padding, which is the dialog path's own shape of the defect §Context names. The size token's per-variant class therefore carries the `max-h` onto `DialogContent` itself through the `cn` merge, and the column keeps only the row template and the body's `min-h-0`. The `drawer` variant needs no equivalent: `SheetContent` is already `inset-y-0 h-full` on both side variants.
- **The container is content-agnostic; the frame supplies the element, not the contents.** Container and form frame are fused today; split, the same surface serves a detail view, a confirmation with a long body, or a wizard — none of which hand it a `<form>` at all, and for those the container renders its own `div` as the inner column. Only the form case takes the `asChild` path. The behavioural halves stay in `apps/admin` as thin wrappers: the footer's `isPending`/`isDirty`/`isValid` reads through `useFormContext` in the app's wrapper, and the page variant's `useBlocker` (`enableBeforeUnload: false`) stays in the app's `AppFormPage` — a router hook has no business in a package whose shell "knows nothing about routing".
- **`AppFormFrame`'s signature changes, and that is the routed-mount step's work.** It gains a `className` it forwards to its `<form>`, its `FieldSet` gains the `contents` display, and it renders the container's rows as its `children` rather than laying out `FieldGroup`/`AppFormError`/`footer` itself — those move to the call site, as the container's body content and `footer` slot. Its prop doc's rule — the footer "has to be *inside* the `<form>` and inside the locked `FieldSet`" — is preserved by the inversion rather than waived by it.
- **The container serves both mounts.** The routed mount is always-open and closing is a navigation; but three shipped, deliberately non-routed ceremonies — profile change-password and both administrative password resets — consume `AppFormDialog` directly with `open`/`onOpenChange` state. A container that assumed the routed contract would break all three; `open`/`onOpenChange` are therefore part of its API, defaulted for the routed case.
- **Sizes are a token set, not free values**: `sm | md | lg | xl | full`, mapped per variant to a class string and merged through `cn` onto `DialogContent`/`SheetContent` — both already merge `className`, so sizes cost **zero generated-file edits**. Any further generated-file edit carries the ADR-0031 comment naming the rule that forced it, per ADR-0047's carried rule.
- **Every [ADR-0044](0044-record-routes-without-list-state.md)/[0035](0035-config-driven-resource-ui.md) invariant carries over as this container's job**: the URL is identical across all three variants; closing is a navigation for the routed mount; an in-flight mutation refuses dismissal in all three shells (the `dismissible` flag is how the wrapper says so); and the title is a real heading in all three — the defect `D4.2` found by testing the shells against each other.
- **The structural pins hold**: the `dialog` variant keeps rendering a Radix Dialog (`role="dialog"`), the `drawer` variant the primitive `SheetContent` with `data-slot="sheet-content"` and still modal, and the `page` variant neither. **Three** suites name shells by exactly those and must keep passing unchanged — `app/__tests__/record-routes.test.tsx:98`, `shared/form/__tests__/app-form-surface.test.tsx:232` and `pages/users/__tests__/users-page.test.tsx:285-287` — and the third is the one that also depends on the drawer staying modal, since its hidden-row assertion rests on Radix's `aria-hidden` over the rest of the document.
- **`ConfirmDialog` does not adopt the container in D8.** It stays on `AlertDialog` — its own Radix root, no `showCloseButton` — and is named here as the future candidate for the container's "confirmation with a long body" case, decided when one exists rather than left to a step to discover.

### 5. Testing: geometry asserted in the package, behaviour asserted in the app

- **`@repo/ui`'s extended suite asserts roles, accessible names, `data-slot`/`data-*` attributes and the composition's own geometry classes** — and nothing behavioural: its harness is a `matchMedia` stub and Testing Library cleanup, with no form, no router, no MSW and **no `@testing-library/user-event`** (it is not among the package's devDependencies). The geometry half of that list is not a widening but the point: `data-full-height` is an attribute rather than a slot, and the size tokens are class strings, so a rule of "slots only" would forbid the assertions this record's own decisions need. What the missing `user-event` costs is stated rather than discovered: the controlled mount is asserted here **declaratively** — content present under `open`, absent after a rerender with `open={false}` — while `onOpenChange` actually firing from a dismissal gesture is asserted in `apps/admin`, where `user-event` lives.
- **The three-shell parity suite stays in `apps/admin` and is the `page` variant's exerciser.** It depends on `react-hook-form`, a real memory router and `@/test/render`, so it cannot follow the container into the package; extended to the new container it covers `dialog | drawer | page` without any shipped resource changing — no resource declares the page edit surface, and the suite is what keeps that variant from being the third unexercised surface.

## Consequences

- **Both SPAs get their frame from one package**, and D9's extraction stays mechanical: nothing behavioural moved, so its "no behaviour change" claim remains checkable by comparing test totals — minus the one-line file-count correction §Decision 1 charges.
- **Long forms keep their title and their Save button in every size token** — the defect that motivated the surface, closed structurally rather than per-screen.
- **The D6.3/D7.5 placement of theme and locale is reversed, on the record.** The account-menu *grouping* survives intact; its *mount* moves to `headerEnd`. Anyone reading D6.3's reasoning finds the counter-argument here rather than a silent contradiction.
- **The three pages that repeat their route title lose the duplicated `CardTitle`** — `staff`, `users` and `dashboard` — and the existing heading queries keep matching exactly one element; a page that reintroduces a second heading with the route's title breaks them, which is now a feature of the queries rather than an accident. The `page` surface variant is held to the same rule by §2's heading bullet, which is the only place the duplicate is armed in the *catalogue* rather than in a component.
- **The slot-honesty rule is enforceable at review, and this record was cut down by it**: a slot justified by D11 must point at a sentence in `docs/plan/0011-customer-app.md`, added in the same change — and D11's file states its needs only generically today, so the sentence is written by the step that cites it. Every slot in the v1 API has a today-consumer (`sidebar`, `headerEnd`, `breadcrumbs`, `banner`, `title`), and the three that did not — `brand`/`nav`/`sidebarFooter` as separate drawer regions, plus `headerStart` and `pageActions` — were struck rather than shipped unexercised.
- **Three coordinated edits per new package path** (exports entry, lint pattern, `shared/ui` re-export) are now a stated pattern with two precedents; forgetting the lint pattern is the failure mode to check for.
- **The banner region is D12-ready and D12-free**: the slot, the component and `dismissible` ship now; the principal field, the session plumbing and the `ImpersonationBanner` content remain D12's, and the no-`@repo/contracts`-import rule is the boundary a review can check.
- **`widgets/dashboard-layout` thins rather than disappears**, and its `widgets`-layer placement is carried by [ADR-0049](0049-admin-app-architecture.md), which supersedes frozen [ADR-0032](0032-admin-app-architecture.md) whole at `D8.3` rather than leaving the account-block move as an unrecorded divergence; the same thinning holds for `shared/form`'s wrappers around the container.
- **What becomes harder**: the compositions are hand-maintained code in a package that was previously (almost) all generated — they are owned like `ui-strings.tsx`, with no upstream to diff against; and ADR-0031's upgrade-cadence coupling now covers layout, so a shell change is a both-apps change by construction, `"use client"` included.
- **Follow-ups owed to specific files**: the stale breadcrumb comment in `apps/admin/src/app/providers/ui-strings.tsx` (corrected by the first step that renders one); the four comments that still say the design system has *six* strings when it has thirteen and is about to have fourteen (`packages/ui/src/ui-strings.tsx:22,108,110`, `packages/ui/src/__tests__/ui-strings.test.tsx:45`, `apps/admin/src/app/index.tsx:93`, `apps/admin/src/test/render.tsx:217`, `apps/admin/src/app/__tests__/ui-strings.test.tsx:19`), corrected by the step that adds the fourteenth; the D9 file-count line at `docs/plan/0009-platform-extraction.md:18` **and** `:27` (a two-line correction, not one); the amendment owed to [ADR-0047](0047-ui-package-scope.md) §What-this-does-not-decide, whose ADR-0032 pointer must become an ADR-0049 pointer at `D8.3`; and the D11 requirement sentence, written with the slot that cites it.

## Alternatives considered

- **The compositions stay per-app and the customer app forks them.** The default under frozen ADR-0031, and the drift argument that created `@repo/ui` applies with more force to layout than to buttons: two shells diverge at the first app-local fix. Rejected because the second consumer's requirements are nameable now; the honest trade-off is that this is the divergence that forces ADR-0047 at all.
- **A separate compositions package (`@repo/layouts`).** Avoids superseding 0031 and was considered and rejected by the operator in favour of **one door per app** — a second package is a second exports map, a second lint pattern set and a second version to keep in step, bought only to keep a frozen record unedited, which is not what the supersession mechanism is for.
- **Two additive ADRs — one for the shell, one for the surface.** They share the packaging path, the strings mechanism, the testing split and the slot-honesty rule; splitting them would state each twice or cross-reference itself into one record anyway. One record, at the cost of length.
- **`react-hook-form` and `@tanstack/react-router` enter `@repo/ui` so the whole surface moves.** The reading D9's plan currently assumes. Rejected: it contradicts the shell's own no-routing rule, hands the design system a form engine ADR-0031 §Field-family deliberately kept it agnostic of, and couples both apps to two more heavy dependencies. The honest trade-off is that "one container, three variants" covers **geometry only**, the behavioural wrappers stay app-side, and D9's table takes its correction.
- **A submit button outside the form, carrying `form="<id>"`.** Avoids fighting the primitives' layout, and needs id plumbing through every surface while still leaving the footer outside the `useFormContext` it reads — the wrong half of the problem solved.
- **`Banner` on shadcn's alert primitive.** The package has no `alert` today; generating one only to compose over it puts the banner's base under the regenerate-and-diff rule for no upstream benefit, since the banner's shape (full-width, action slot, dismissible) is not the alert's. Hand-written, at the cost of owning its look outright.
- **The pseudo-locale notice gated on `config.VITE_I18N_PSEUDO` directly.** Renders in no test in the repository — the suite pins the variable to `"false"` on purpose — so the slot would be exercised only in a dev build. A prop with the env var as the app's default keeps the honest consumer honest.
- **ADR-0046 §13's `register(i18n)` for the compositions' strings.** The right mechanism for the packages D9 will extract, and the wrong one here — but not for the reason it is easy to give. §13 is dependency *injection*: the instance arrives as a parameter and the package calls `addResourceBundle` on it, so it adds no i18next import (`src/test/render.tsx` already runs that shape). What rules it out is that §13's `I18n` type is `apps/admin`-owned until D9 extracts it, so the package cannot import even the type. `UiStrings` already exists, already reaches every generated primitive, and grows by one key per string.
- **Prove `headerEnd` by moving only `ThemeMenuItems`/`LocaleMenuItems`.** They are bare `DropdownMenuRadioGroup` fragments, mountable only inside a `DropdownMenuContent`; moving them alone means restructuring both features away from the radio-group semantics D6.3 chose. The whole `AccountMenu` moves instead — cheaper, and it keeps the D6.3 reasoning intact while reversing only the mount point.
- **The page header renders its own heading beside the shell's `<h1>`.** The obvious composition and a shipped bug: the staff, users and dashboard heading queries would match two elements and throw. One owner of the `<h1>`, decided once; the three pages' pseudo-titles go, and §2's `page`-variant rule closes the same duplicate where it is armed in the catalogue rather than in a component.
- **`ConfirmDialog` adopts the container now.** Uniform, and premature: `AlertDialog` is its own Radix root with its own dismissal semantics, no shipped confirmation has a long body, and adopting the container would be the third change to a working surface in one deliverable. Named as the candidate instead, so the next long confirmation re-reads this bullet rather than re-deriving it.

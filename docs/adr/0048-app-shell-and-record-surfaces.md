## Context

Every screen in `apps/admin` is built from two layouts nobody designed, and the planned customer SPA ([D11](../plan/0011-customer-app.md)) will need both. D8 is design work, not a move: the shell and the record surface become generic, slotted compositions in `@repo/ui`, generalised **against the working consumer, in place** — `apps/admin` with its full test tier is the cheapest verification available — while every piece of behavioural machinery (grid, API client, resource config, form machinery) stays exactly where it is, so that [D9](../plan/0009-platform-extraction.md)'s extraction afterwards is mechanical and checkable by test totals.

**The record surface scrolls the wrong thing.** `apps/admin/src/shared/form/app-form-surface.tsx` puts `overflow-y-auto` on the drawer's entire `SheetContent` with `SheetHeader` inside it, so the title scrolls away with the fields; on the **drawer path** the footer is a class string (`FOOTER = "mt-6 flex justify-end gap-2"`) rendered *inside* that scrolling body, so Save scrolls away with it. The `page` path shares the class string but not the defect: `AppFormPage` is a `<Card className="max-w-2xl">` in document flow with no scroll container of its own, so its header and footer do not scroll away — the document scrolls, which is the correct behaviour for a page and is preserved unchanged below. The dialog path is a separate file with a different shape of the same defect: `app-form-dialog.tsx` wraps its actions in `DialogFooter className="mt-6"`, passes no `className` — so the modal has exactly `DialogContent`'s one `sm:max-w-lg` width — and its failure mode is an **unbounded `DialogContent`** that grows past the viewport rather than a footer that scrolls inside it. The footer's contents are `AppFormActions` and nothing else in all three. A form long enough to scroll loses its title and its Save button — the case in which the operator most needs them.

**The shell has no slots.** `apps/admin/src/widgets/dashboard-layout/index.tsx` hardcodes its header as `SidebarTrigger + Separator + <h1>{title}</h1>`. There is nowhere to put an action, a breadcrumb or a status control. Two corrections to the plan's framing belong here rather than in a later step's surprise:

- **The stranded chrome was placed deliberately, not accidentally.** The plan says theme, locale and logout landed in the sidebar footer "because it was the only region that took children"; the code records the opposite reasoning — [ADR-0032](0032-admin-app-architecture.md) assigns "navigation, current-principal block, logout" to `widgets/app-sidebar`, and D6.3/D7.5 put the preferences in the account menu on purpose ("a preference about the operator, in the menu named after them"). Moving them to the header is therefore a **reversal this record argues** (§Decision 2), not an accident it fixes — and a divergence from frozen ADR-0032's widget assignment, carried by **[ADR-0049](0049-admin-app-architecture.md)**, the supersession written for it, rather than argued away.
- **The breadcrumb is not unrendered in the sense claimed.** `shared/ui/index.ts` has exported six breadcrumb symbols since D3.3, `packages/ui`'s own suite renders `Breadcrumb`/`BreadcrumbEllipsis`, and the `breadcrumb`/`more` `UiStrings` keys already have a `t()` call site and an `lv` entry. What is true is narrower: **no admin screen composes one**. No door widening is needed for the non-collapsing trails the record routes render — `BreadcrumbEllipsis`, the `more` key's carrier, is deliberately not among the six exported symbols, and the seventh export is owed by the first trail that collapses. The stale "never reached the `shared/ui` door" comment in `apps/admin/src/app/providers/ui-strings.tsx` is corrected by whichever step first renders one.

Against speculative generality the plan carries a governing rule this record adopts as its own: **every slot and every variant must answer a need the repository can name today** — an `apps/admin` screen, a customer-app requirement written into [D11's plan](../plan/0011-customer-app.md), or an invariant a frozen ADR already imposes. Today D11's file states its needs only generically ("whichever shell slots this app fills differently from the admin panel"), so any slot below that cites D11 must have its requirement **written into `docs/plan/0011-customer-app.md` by the step that cites it** — the citation is not allowed to point at a sentence that does not exist.

Two packaging facts frame everything below. `@repo/ui` declares only design-system runtime dependencies (`class-variance-authority`, `clsx`, `lucide-react`, `radix-ui`, `sonner`, `tailwind-merge`, `tailwindcss`, `tw-animate-css`) plus react/react-dom peers — **no `react-hook-form` and no `@tanstack/react-router`** — and two of the plan's own record-surface promises (a footer reading `isPending`/`isDirty`/`isValid` through `useFormContext`; the page variant's `useBlocker` navigation blocker) each require one of those. And [ADR-0046](0046-interface-localization.md) §12 forbids the package an i18n dependency while §13 gives *shared packages* a `register(i18n)` route — two incompatible mechanisms, and D8 is the first work that must choose between them for `@repo/ui` specifically.

## Decision

### 1. The compositions live in `@repo/ui`, on a new hand-written path, and the package gains no dependency

**The shell and the record-surface container are compositions in `@repo/ui`**, under a path outside `components/` and `hooks/` — the `ui-strings.tsx` precedent, which is what keeps them formatted (the `.prettierignore` carve-out covers only those two directories) and outside [ADR-0031](0031-ui-design-system.md)'s regenerate-and-diff surface:

```
packages/ui/src/
├── components/           # generated primitives — byte-identical to CLI output, unchanged
├── compositions/         # hand-written; prettier applies; not under regenerate-and-diff
│   ├── app-shell.tsx     # "use client"
│   ├── banner.tsx        # "use client" — it reads UiStrings, so it is stateful by §1's own rule
│   └── record-surface.tsx  # "use client"
└── ui-strings.tsx        # the precedent (D7.3)
```

- **A new path costs two coordinated edits, and each symbol on it costs one more** — [ADR-0047](0047-ui-package-scope.md) §What-code states the split and this record follows it. Per path, made together: the `exports` entry 0047's map pins (`"./compositions/*": "./src/compositions/*.tsx"`) and a pattern in `apps/admin`'s `no-restricted-imports` group beside `components/*`, `hooks/*`, `lib/*` and `@repo/ui/ui-strings`. Per symbol: a named re-export through `shared/ui/index.ts`, landing with the symbol — `Banner`, then `AppShell`, then `RecordSurface` — because that file re-exports names, not modules, and a re-export from an empty directory does not compile. `ui-strings` looked like an atomic triple at D7.3 only because its path and its first symbol landed in one commit.
- **Neither `react-hook-form` nor `@tanstack/react-router` enters `@repo/ui`.** The container is **geometry-only**. `AppFormFrame` (react-hook-form) and the page variant's `useBlocker` stay in `apps/admin` as thin wrappers around the container (§4). This keeps the shell's own rule — it knows nothing about routing — true of the package, keeps ADR-0047's dependency-location rule minimal, and charges one honest price: D9's file-count table, which assumes "the surfaces D8 moved to `@repo/ui`", takes a **two-line correction** at `D8.10` (`docs/plan/0009-platform-extraction.md:18` and `:27`) — the geometry moved, the two behavioural wrappers stayed.
- **Stateful compositions carry `"use client"`.** `apps/web` compiles the package through `transpilePackages`, and a composition without the directive is unimportable from a Next server component. ADR-0031's stated coupling cost — a change to a shared primitive is a change to both apps — now applies to compositions too.
- **Composition micro-copy is `UiStrings` keys** — new keys with English defaults, fed from `apps/admin`'s `common:ui.*` exactly as the existing thirteen are; anything content-like stays a slot the app fills with its own JSX. The Banner's dismiss-control label is the first concrete key, and **it is the fourteenth**. Its price is six coordinated edits, not one, and they are named here because they fail in six different places — none of them silently, per ADR-0047 §Consequences: three are `check-types` errors, the `useMemo` dependency is `react-hooks/exhaustive-deps` under `--max-warnings 0`, and the last is an `i18n:check` orphan: the `UiStrings` interface field, the `DEFAULT_UI_STRINGS` entry, **all three** hand-maintained lists in `UiStringsProvider` (the destructure, the object literal returned from `useMemo`, and the dependency array — the literal is compiler-owned through `useMemo<UiStrings>`, which is what makes its omission a red gate rather than a silent bug), the app's `AppUiStrings` provider line (omitting it makes the key an `i18n:check` orphan and exits 1), and both `en` and `lv` catalogues. A composition that reads `UiStrings` is a client component by construction — `banner.tsx` included, which is why the tree above marks it. ADR-0046 §13's `register(i18n)` route is **not** used for `@repo/ui`, and the reason is not the one it is easy to reach for: §13 is dependency *injection* — the instance arrives as a parameter — so it would add no i18next import. What rules it out is [ADR-0047](0047-ui-package-scope.md) §Context's ordering, restated here so the two records give one ground rather than two: this package must render correct English with **no provider and no i18n mounted at all** — `apps/web` today — which `UiStrings` does by construction and §13 does not. That §13's `I18n` type is `apps/admin`-owned until [D9](../plan/0009-platform-extraction.md) extracts it is the **secondary, mechanical blocker, and it expires at D9 while the first reason does not** — so a D9 reader does not conclude that `register(i18n)` becomes available here. The surface's own close needs **no new string**: `DialogContent` and `SheetContent` already render a localized close button behind `showCloseButton`.

### 2. The shell: one slotted composition over the sidebar-07 primitives

A composition that **knows nothing about routing or authorization** — navigation arrives as JSX, so the `can()` join ([ADR-0042](0042-client-side-authorization.md)) and the typed route links stay in the app that owns them:

```tsx
// packages/ui/src/compositions/app-shell.tsx — illustrative of shape and naming
export const AppShell = ({
  sidebar,                     // the whole drawer as one node — the app's <Sidebar>, not three fragments
  headerEnd,                   // beside the trigger, which stays the shell's
  breadcrumbs,                 // the header row's trail — JSX the app composes, not data
  banner,                      // the content column's width, above the header, inside the inset — §3
  title,                       // the page header: the row the single <h1> lives in
  fullHeight = false,          // ADR-0037's per-page opt-in, unchanged in meaning
  children,                    // the page, inside the page container
}: AppShellProps) => …
```

**The drawer arrives as one node, not as three regions**, and this is the record's own correction: an earlier draft gave the shell `brand`/`nav`/`sidebarFooter`. That shape cannot be filled. `apps/admin`'s `AppSidebar` **is** the `<Sidebar>` with its `SidebarHeader`, `SidebarContent`, `SidebarFooter` and `SidebarRail` (`apps/admin/src/widgets/app-sidebar/index.tsx:257-309`), [ADR-0049](0049-admin-app-architecture.md) keeps it whole in the `widgets` layer and has the `_dashboard` route file hand it in, and after the account menu leaves (below) `sidebarFooter` would have had no filler at all — the unexercised-slot defect this record's own rule forbids. `collapsible="icon"` and the mobile `Sheet` swap stay the primitive's, inside the app's node.

Every remaining slot answers a need nameable **today**, which is the slot-honesty rule applied to this record rather than asserted by it: `sidebar` is the admin drawer; `headerEnd` is the account menu (below); `breadcrumbs` gives the long-exported primitives their first composed screen (`D8.6`); `banner` has the pseudo-locale notice now and D12's impersonation banner next (§3); `title` is the `<h1>` the shell already renders. **`headerStart` and `pageActions` are deliberately not in the v1 API** — nothing in `apps/admin` fills either (the trigger stays the shell's; the one `CardAction` in the app is a section action inside `pages/profile`, not a page action, and the grid toolbar keeps Create where [ADR-0038](0038-grid-selection-and-capabilities.md) put it at D4.3) — and a slot with no consumer is the defect this repository has recorded twice. Either is one prop wide when a screen names it.

- **The page container carries [ADR-0037](0037-grid-viewport-layout.md)'s height contract unchanged, as this component's responsibility** — and it is a **three-element chain the shell must own every link of**: `AppShell` renders **`SidebarProvider`** around the app's `sidebar` node and the inset — its `defaultOpen` and mobile behaviour unchanged, and its `min-h-svh` load-bearing as a floor rather than a ceiling — the container is `flex min-w-0 flex-1 flex-col gap-4 p-4` unconditionally and gains `min-h-0` in full-height mode, while the **`SidebarInset`** gains `h-svh` — the shipped list, quoted rather than paraphrased (`apps/admin/src/widgets/dashboard-layout/index.tsx:62,71-78`). Every one of them is load-bearing and all are named, for two reasons: `flex-1` is what gives `min-h-0` anything to mean (a `min-h-0` on a box that is not a flex child overrides nothing), and `gap-4 p-4` is **every screen's padding and gutter** — a composition built to a list that dropped them would strip the whole app's spacing, and neither jsdom nor a four-class assertion would see it. **`gap-4 p-4` are the shell's own defaults**, not app-supplied, because a page container that leaves its own padding to each consumer is not a page container. Collapsing them onto one element drops `h-svh` from the inset and breaks the chain everything below divides; jsdom lays nothing out, so no test would say so. The machine-checkable surface is preserved literally: **`data-slot="page-container"` and `data-full-height` stay on the same element**, `data-full-height` **present as an empty string when on and absent when off** — the producing form today, and one the routing tests cannot police: their on-case assertion is a valueless `toHaveAttribute`, which would accept a `"true"` just as silently, so the package test is what asserts the empty-string value on and the absence off. The `fullHeight` join point is untouched in meaning: the record routes' `staticData` expressions (`fullHeight: editSurfaceOf(config) !== "page"`) keep meaning what they mean, because §4 does not change what the `page` variant does to the grid underneath.
- **The chrome above the page container is two `shrink-0` rows, not one.** The existing `h-16 shrink-0` header keeps the trigger, the breadcrumbs and `headerEnd` — and loses the `Separator` that divided the trigger from the title, which leaves with the title; its door line stays, kept by three other consumers; the page-header row sits below it carrying the `<h1>`, its height content-driven rather than declared. Both are in-flow siblings above the page container, so ADR-0037's budgeting absorbs them the way it already absorbs the `h-16` header: chrome takes what it declares, the scroll body takes the rest. The cost is stated rather than discovered — a full-height grid loses the page-header row's height, roughly one line of text, from the viewport it had before.
- **The page-header row is a `shrink-0` in-flow sibling above the page container**, not a child of it — the same reasoning the banner region gets one bullet down, and for the same reason: a row inside `data-slot="page-container"` becomes a new in-flow sibling of `children` inside the `min-h-0` box every grid divides, and silently takes height from all of them. Outside and `shrink-0`, it costs the budget exactly what today's `h-16 shrink-0` header costs it, which is the property that lets ADR-0037's chain stay one reviewable path.
- **The shell keeps the screen's single `<h1>`, and the page header is the row it lives in.** Today the shell renders `staticData.title` as the only `<h1>` and three pages repeat the same string as a `CardTitle` — a styled `div`, not a heading, which is the reason the staff, users and dashboard heading queries match one element. The title the app hands the shell renders as the one `<h1>`; **every page that repeats its route title in a `CardTitle` drops it — `pages/staff`, `pages/users` and `pages/dashboard`.** The last of those is not a grid page and is easy to miss: no test can see the leftover, because `CardTitle` is a `div`. `pages/profile`'s `CardTitle`s are `account.title` and `password.title` — section names, not the route title — and they stay.
- **Under the `page` variant the surface renders no heading of its own; the shell's `<h1>` is the record's title — and the shell must be given the record's title to render.** The duplicate this closes is armed in the catalogue: `staff:create.routeTitle` and `staff:create.title` are the *same string* ("New staff member", and the users mirror), so the shell's `<h1>` and the surface's own `<h2>` (`apps/admin/src/shared/form/app-form-surface.tsx:239`) would be two visible headings with one accessible name the moment any resource declares `editSurface: "page"`. Only Radix's `aria-hidden` over the rest of the document keeps `findByRole("heading", …)` single-match in the other two variants, and `page` has no modal and no overlay to supply it.

  **Suppressing the surface's heading is therefore only half a rule, because the two strings are not always equal.** `staff:edit.routeTitle` is "Edit staff member" while `edit.title` is "Edit {{email}}", and the route declares the former — so a `page` edit route with a suppressed surface heading would name the record in no heading at all, which is the ADR-0044 invariant failing in the other direction. The other half of the rule closes it: **for a record route rendering the `page` variant the shell's title is the record's own label when the route supplies one, falling back to `staticData.title`.** It is scoped to `page` deliberately: under `dialog` and `drawer` the shell is behind a modal and keeps the route title, so no shipped screen changes its heading and the browser walk gains no item. The channel's shape is decided here rather than at the step, because a reader over untyped loader data is a cast waiting to happen: the record routes declare a **third optional `staticData` field, `recordLabel?: (loaderData: unknown) => string | undefined`**, and `apps/admin/src/shared/lib/route-meta.ts` calls it on the deepest match beside the `title`/`fullHeight` reads it already does. The field's *type* lands in the `StaticDataRouteOption` augmentation in `app/providers/router.tsx` — `app`-layer wiring, where the other two already live — while the callback is written by each `$id` route, which owns the type of its own loader data and is the one place that can narrow it honestly. The callback's parameter stays `unknown` and **each route narrows inside its own body**: under `strictFunctionTypes` a declared `(loaderData: unknown) => …` is checked contravariantly, so a callback written as `(staff: StaffResource) => staff.email` would not satisfy it. What the design buys is therefore not the absence of a narrowing but its *location* — one per route, written by the code that knows the type, with **no cast anywhere in `route-meta.ts` or the hook**. A match that carries no loader data yields `undefined`, and the shell falls back to `staticData.title`. It is read by **a third hook, `useRouteRecordLabel(): string | undefined`**, beside the untouched `useRouteTitle`: a label is loaded data, not a `TranslationKey`, so it must bypass the `t()` wrap `useRouteTitle` applies, and it scans for the deepest match that declares `recordLabel` independently of the deepest match that declares `title`. **The channel and its consumers are separate**: the breadcrumb's last crumb reads the label unconditionally, while the shell's `title` takes it only on the `page` branch, and the place that decides is the **`_dashboard` route file**, which resolves the route meta and passes `recordLabel ?? routeTitle` down as the shell's `title` when the route renders a `page` surface and `routeTitle` otherwise — the adapter's job is to place what it is handed, per [ADR-0049](0049-admin-app-architecture.md) §The-shell-adapter, and its props are unchanged apart from the new slots. **The discriminator already exists and no fourth `staticData` field is added**: the record routes declare `fullHeight: editSurfaceOf(config) !== "page"`, so on a record route `fullHeight === false` *is* the `page` surface. The adapter therefore passes `recordLabel ?? routeTitle` on the `fullHeight === false` branch for **every** route, not only record routes — which is a no-op wherever no route declares `recordLabel`, `/profile` included, and is why the fallback is worth asserting there too. The two `new` routes declare none and fall back to `staticData.title`, which is correct: a record being created has no label yet. It is the same channel §2's breadcrumb bullet needs for the trail's last crumb, which is why it is decided once here and built once.

  So: `dialog` and `drawer` keep their own `DialogTitle`/`SheetTitle` (Radix requires them for the accessible name anyway); `page` renders its `description` without a heading; and the shell's `<h1>` carries the record's label. The [ADR-0044](0044-record-routes-without-list-state.md) invariant survives exactly — the record's title is always a real heading, rendered by the surface in two variants and by the shell in the third, and there is always exactly one of it, on create and on edit alike.
- **The whole `AccountMenu` dropdown moves to `headerEnd`** — the slot's proving consumer. This **reverses the placement half of D6.3/D7.5 deliberately**: those steps put theme and locale in the account menu because a preference about the operator belongs in the menu named after them, and that reasoning survives — the menu is intact, `ThemeMenuItems`/`LocaleMenuItems` keep their `DropdownMenuRadioGroup` shape and its screen-reader semantics, and nothing about the two feature components changes. What changes is where the menu mounts, and the argument is D11's: **header chrome is exactly what the second app places differently**, so the shell's header must be able to hold it — a requirement written into `docs/plan/0011-customer-app.md` in the same change, per the slot-honesty rule. Moving the bare menu-item fragments instead would force both features out of the radio-group pattern; the cheap move is the whole menu.
- **The `breadcrumbs` slot is JSX, not data** — the app composes `Breadcrumb*` from its `shared/ui` door with `asChild` over the router's typed `Link`, and hands the finished trail in. A shell that took crumb labels and hrefs would emit plain anchors, i.e. a full document reload under TanStack Router, and would be a shell that knows about routing — the thing §2 opens by ruling out. The trail's items come from route `staticData` (which carries `title` and `fullHeight` today) plus **the record's own label through the loader-data reader the heading bullet above adds** — one channel, two consumers, built once. **The ancestor half needs a reader that does not exist yet, and it is named here rather than discovered**: `shared/lib/route-meta.ts` exports exactly `useRouteTitle` (the *deepest* declaring match, already translated, as one string) and `useRouteFullHeight` — nothing enumerates ancestors. `D8.6` adds a third export beside `useRouteRecordLabel`: it walks `useMatches()`, keeps the matches whose `staticData` declares a `title` (the pathless `_dashboard` declares none; `/staff` declares `staff:title`), translates each through `useKeyT`, and returns them in order with the path each crumb links to. Ancestor crumbs are `TranslationKey`s ([ADR-0046](0046-interface-localization.md) §8) because they are operator-facing copy; the record's own crumb is the `recordLabel` above, which is data rather than copy. `BreadcrumbEllipsis` is deliberately not among the six symbols `shared/ui` exports, so a trail that never collapses needs no door widening and the seventh export is owed by the first trail that does. **Amended 2026-08-26 (D8.6).** Two rules the build found, recorded here because `D8.10` and [D11](../plan/0011-customer-app.md) will both read this bullet as the source of truth. **A trail with no ancestor is not rendered at all**: one crumb repeats the `<h1>` a line above it and adds nothing, and shadcn's `BreadcrumbPage` is a `<span role="link" aria-disabled="true">`, so a lone crumb is a second link named for the page beside the sidebar's nav item of the same name. The ancestor/nav duplication survives on the routes that do render a trail, so a test reaching for a crumb scopes to the trail's `<nav>` rather than to the document. **And an ancestor crumb carries `closeSearch`**, the same [ADR-0044](0044-record-routes-without-list-state.md) carrier the record surface's own close uses: a crumb that navigated to the bare list would drop the page, filters and sort, and disagree with the Close button in the very surface it sits behind. **One consequence of proving it on the record routes is stated rather than discovered**: on the `dialog` and `drawer` variants the surface is modal, so the shell — trail included — is inside Radix's `aria-hidden` subtree while the surface is open. The trail is therefore asserted with `{ hidden: true }` queries, and an ancestor crumb's navigation is proved by its `Link` target and a `fireEvent` click rather than by `user-event`, which refuses a pointer-events-none subtree.
- **`widgets/dashboard-layout` survives as a thin adapter over `AppShell`** — it supplies the slots it is handed and stays the `_dashboard` layout component in the `widgets` layer. The shipped shape is kept: the `_dashboard` **route file** resolves the route meta (`useRouteTitle`, `useRouteFullHeight`, and now `useRouteRecordLabel`) and composes the two sibling widgets — `AppSidebar`, and `AccountMenu` from `D8.5` — and passes them down; the adapter places what it is given. The nav and its `can()` join do not move: they stay inside `AppSidebar`, which is handed over whole. That is the smaller diff and it is the shape `D8.5` and `D8.7` already need, since the route file is also where `AccountMenu` and the pseudo-notice value arrive. That placement is carried by **[ADR-0049](0049-admin-app-architecture.md)**, the supersession of frozen [ADR-0032](0032-admin-app-architecture.md) written for this deliverable and accepted at the head of `D8.1`: the layer still owns the composition's *contents*, the package owns its *geometry*, and the account block leaving `app-sidebar`'s footer is a divergence from 0032 that 0049 carries whole rather than a claim that 0032 is untouched.

**Deliberately out of scope, named so nobody wonders whether they were forgotten**: navigation as a typed data array (ADR-0042's containment carve-out keeps "which entries render" a per-app judgement); command palette; global search; tenant switcher; and everything D12 puts *in* the banner — the `impersonatedBy` field on the principal and the `ImpersonationBanner` itself are [D12](../plan/0012-impersonation.md)'s.

### 3. The banner: a dumb region and a hand-written component

- **The `banner` slot is a `shrink-0` in-flow sibling above the header, and it renders nothing at all — not an empty `div` — when handed nothing.** Its width is **the content column's, not the viewport's**: the region lives inside `SidebarInset`, which is the `<main>` landmark, so a banner spans the page beside the drawer rather than across the whole window. That is stated because [D12](../plan/0012-impersonation.md) will design an impersonation banner against it — a viewport-spanning bar above the sidebar would be a different element in a different place, and this chain does not provide one. It sits inside the `h-svh` box in full-height mode, so ADR-0037's flex budgeting absorbs it without arithmetic: chrome takes what it declares and the scroll body takes the rest. That is the existing argument restated, not a new one; an empty element that reserved space would shift every grid page's budget.
- **`Banner` is a generic component in the compositions path, hand-written rather than built on shadcn's alert primitive** (which the package does not carry): a `message`, a `dismissible` flag — included now because its first real consumer, D12's impersonation banner, needs `dismissible={false}` — and a variant set named here rather than left to the builder, because the slot-honesty rule is unreviewable against an unnamed set: **`info` and `warning`, one per consumer the repository can name today** (`info` for the dev-only pseudo-locale notice, `warning` for D12's impersonation banner). A third variant arrives with the notice that needs it. **An `action` slot is deliberately not in the v1 API** — neither named consumer has one, and it gets the same disposal `headerStart` and `pageActions` got: one prop wide when a screen names it. **`dismissible` exposes an `onDismiss` callback and the component holds no dismissed state of its own**: who is allowed to dismiss what, and whether it stays dismissed across a navigation, is a session question, and a composition that answered it would be the opposite of the next sentence. **Amended 2026-08-26 (D8.2).** The default is **`false`** — the open item this record left for the building step. The fail-safe direction is the one where forgetting the prop leaves a notice on screen rather than putting a dismiss control on a banner whose whole job is to stay, which is exactly D12's impersonation warning; opting in is a visible line in a diff, opting out is a line someone has to remember to write. **Both variants render `role="status"`** — a polite live region — and the variant is a visual fact plus `data-variant`, not an announcement level. The first draft of this amendment mapped `warning` to `role="alert"` and was refuted by its own next sentence: both named consumers are persistent chrome present at mount, and a live region reports *changes*, so an assertive region announces nothing there that a polite one does not. `role="alert"` is also the wrong container for the focusable control `dismissible` puts inside it. A consumer that genuinely needs to interrupt gets a prop with a name and a reason, added when it exists. It is **dumb by construction: no `@repo/contracts` import**, no principal, no session store — a checkable boundary, and the reason the shell never learns *why* a banner is showing.
- **The in-admin consumer is the dev-only pseudo-locale notice, and its condition is a prop with a named channel.** `VITE_I18N_PSEUDO` only sets the app's default. The channel is decided here rather than discovered at the step, because none exists: `renderApp`'s existing `pseudo` option means something else already (it selects the pseudo-locale *lens* and reaches only `createI18n`), and `createAppRouter`'s context is exactly `{session, queryClient, client}`, which no record here may widen. So the notice's visibility is **a prop on `widgets/dashboard-layout`, supplied by `app/routes/_dashboard.tsx` from a small `PseudoNoticeProvider` in `app/providers`** — mounted the way `app/providers/settings.tsx` mounts `shared/theme`'s `ThemeProvider` (the context itself lives in `shared/`, the `app` layer mounts it), and read only by `_dashboard.tsx`, which passes the value to the adapter as a prop — whose default is `config.VITE_I18N_PSEUDO` and which `renderApp` overrides through a **new option named `pseudoNotice`**, distinct from `pseudo`. Gating it on the config variable directly would render it in no test in the repository — the admin vitest config pins `VITE_I18N_PSEUDO` to `"false"` for the whole suite on purpose — which is the same unexercised-surface defect this repository has recorded twice about the `page` edit surface; and reusing `pseudo` would mount the notice on all nine routes of §14's pseudo-locale walk, whose copy would then have to survive `unaccented()`.

### 4. The record surface: one geometry-only container, three variants, both mounts

One content-agnostic container replaces the shells inside `app-form-surface.tsx` — fixed header, scrolling body, fixed footer:

```tsx
// packages/ui/src/compositions/record-surface.tsx — illustrative of shape and naming
type RecordSurfaceSize = "sm" | "md" | "lg" | "xl" | "full";

export const RecordSurface = ({
  variant,                  // "dialog" | "drawer" | "page"
  size = "md",              // token → a class string merged through cn onto
                            //   DialogContent / SheetContent; zero generated-file edits
  title, description,       // the fixed header; a real heading in dialog and drawer —
                            //   under `page` the shell's <h1> carries it (§2)
  footer,                   // the fixed footer — a slot, not a fixed set of actions
  open, onOpenChange,       // the controlled mount; omitted for the routed, always-open mount
  dismissible = true,       // false refuses dismissal — Escape, overlay, close — while a mutation is in flight
  column,                   // the inversion: a render prop the app fills with its <form> — see below
  children,                 // the scrolling body: overflow-y-auto min-h-0
}: RecordSurfaceProps) => …

// column?: (props: { className: string; children: ReactNode }) => ReactElement
//   Called with the container's geometry classes and its three rows.
//   Omitted → the container renders its own <div> as the column.
```

- **The `<form>` wraps header, body and footer, and only the body scrolls** — and the way it does so is an **inversion**, decided here because the obvious reading of "the container holds the frame" is unbuildable. This is what makes a `type="submit"` button work in a *fixed* footer and lets that footer read form state through context. It fights the primitives' own layout — `DialogContent` is `grid … gap-4 p-6`, `SheetContent` is `flex flex-col gap-4`, both laying out their direct children — so wrapping collapses them to a single child, and that child must be the element carrying the row template and the body's `min-h-0`.

  **`AppFormFrame` keeps the `<form>`** — `form.handleSubmit(onSubmit)` stays attached to it directly, as it is today — **and supplies it to the container as the container's inner column through the `column` render prop.** The container calls `column({ className, children })` with its geometry classes and its three rows, and the app returns `<AppFormFrame className={className} …>{children}</AppFormFrame>`. So the `<form>` really does wrap all three rows; the footer is inside it by construction and `type="submit"` keeps working.

  **The mechanism is a render prop, deliberately, and not `asChild`.** This repository's `asChild` is Radix `Slot.Root` throughout (`button.tsx:51`, `badge.tsx:36`, `breadcrumb.tsx:54`, `sidebar.tsx:424` and four more), and `Slot.Root` **clones its single child and merges props onto it — it does not render the parent's own children inside it**. The injection would need `Slot.Slottable`, which appears nowhere in this repository and would be a new package convention bought for one call site; and the element handed over is the `AppFormFrame` *component*, not a DOM node, so a clone would have to be trusted to forward `className` regardless. A render prop states both obligations in the type and needs no convention at all.

  `AppFormFrame`'s locked `FieldSet` — two of the three halves of [ADR-0035](0035-config-driven-resource-ui.md)'s submit lock — sits between the `<form>` and the rows and therefore must stop laying out (`display: contents`), so the rows remain the form's own grid children while every control, the footer's included, stays inside the lock. `display: contents` removes the box, not the element: `disabled` still propagates to every control and `aria-busy` is still on a node in the accessibility tree. The residual — that some assistive technology historically dropped `display: contents` elements from that tree — is checked once, on `D8.12`’s browser walk; if it bites, the `contents` display moves to an inner wrapper and the `FieldSet` keeps its box. **ADR-0035's one-form-frame ownership is untouched**: there is still exactly one `<form>`, still owned by the frame, and the footer still lands inside the disabled `FieldSet` — the property `app-form-surface.test.tsx`'s in-flight lock assertion checks in all three shells.

  The rejected reading, named so no step re-derives it: the container as the outer element with the frame rendered into `children`. It puts the container's `footer` slot outside both the `<form>` and the `FieldSet`, which breaks `type="submit"` and leaks the submit lock in one move.
- **The three-row frame is the `dialog` and `drawer` shape; under `page` the container is document-flow.** The `page` variant shares the slots, the header/body/footer structure and the size tokens, and has **no internal scroll element**: no `overflow-y-auto`, no `min-h-0`, header and footer in normal flow, the document scrolling as it does today. That is not a carve-out for tidiness but the only thing that works — a routed `page` surface renders with `fullHeight: editSurfaceOf(config) !== "page"`, i.e. `false`, so [ADR-0037](0037-grid-viewport-layout.md)'s chain gives it neither `h-svh` on the inset nor `min-h-0` on the page container, and an `overflow-y-auto min-h-0` body inside an unbounded parent is inert: it would scroll nothing and fix nothing, and jsdom would never say so. `fullHeight` keeps its meaning and its per-page opt-in untouched; §Definition of done's long-form promise is a `dialog` and `drawer` promise for the same reason.
- **Under `page` the size token maps to a `max-w-*` on the container's own element.** The variant renders neither a Dialog nor a Sheet, so it supplies its own element — the `Card` shape the page shell has today — and `md` maps to `max-w-2xl`, which is what `AppFormPage` hardcodes, so the shipped page surface's **width** is unchanged after the adoption; its own heading goes, per §2. That is what keeps "sizes are a token set" true of all three variants rather than two.
- **The inner column's own classes are `grid grid-rows-[auto_1fr_auto] min-h-0`** for `dialog` and `drawer` — **and the spacing `FieldSet` stops supplying has to land somewhere, or the inversion silently restyles every form.** `FieldSet` is `flex flex-col gap-6`, and `display: contents` removes its box, so that `gap-6` goes inert. **Its direct children are exactly two** — `FieldGroup` and, today, the footer (`app-form-frame.tsx:100-107` renders `<FieldSet><FieldGroup>{children}<AppFormError /></FieldGroup>{footer}</FieldSet>`) — so the inert `gap-6` is the fields-to-footer distance and nothing else. **`AppFormError` is inside `FieldGroup`, not beside it**, spaced by `FieldGroup`'s own `gap-7`, so the two move up one file **as a unit** with the error still nested: that distance is untouched, and the body row's content is the single `FieldGroup`, needing no wrapper and no gap of its own. What must be replaced is only the fields-to-footer distance, which ships as `gap-6` + `FOOTER`'s `mt-6` = **3rem**: with the footer now its own grid row and the row template supplying no gap, **`FOOTER`'s margin absorbs both halves (`mt-12`)**. The row template stays gapless because a row gap would also open one between the header and the body where none ships. This is the same class of defect as the `gap-4 p-4` residual §2 names: jsdom cannot see it and a class-presence assertion would pass over it: the row template because the primitives lay out their direct children and the column is now the only one; `min-h-0` on the column so the `1fr` body row may shrink below its content, which is what lets `overflow-y-auto` on that row scroll instead of growing the box. Under `page` the column is `flex flex-col` with no `min-h-0` and no scroll row, per the document-flow rule above.
- **The `dialog` variant's viewport bound goes on `DialogContent`, not on the column, and it is one class per variant rather than one per token**: `max-h-[calc(100svh-2rem)]`, matching the `max-w-[calc(100%-2rem)]` gutter `DialogContent` already carries, so the modal never exceeds the viewport at any size token. `DialogContent` carries **no `max-h` at all** (`packages/ui/src/components/dialog.tsx:75-78`: centred by transform, `grid`, `p-6`, `sm:max-w-lg`), so a `max-h` on the inner form bounds nothing — the dialog grows past the viewport and the body scrolls inside the padding, which is the dialog path's own shape of the defect §Context names. The size token's per-variant class therefore carries the `max-h` onto `DialogContent` itself through the `cn` merge — **and it needs one more class beside it, because `DialogContent` is `grid` and its implicit row track is `auto`, which sizes to the column's content rather than shrinking to the container's `max-height` the way a flex child does.** A `max-h` on the parent alone would leave the column's `1fr` body row resolving against content height and `overflow-y-auto` never engaging. So the dialog's per-variant class is `max-h-[calc(100svh-2rem)] grid-rows-[minmax(0,1fr)]`: the `minmax(0,1fr)` is what lets that single row shrink below its content, which is what makes the parent's bound reach the column at all. **The column's own classes are unchanged from the bullet above** — it keeps the row template and its `min-h-0`, because the primitives lay out their direct children and the column is the only one. Two classes on the parent, none moved off the column. The `drawer` needs no equivalent second half for the reason the asymmetry suggests: `SheetContent` is `flex flex-col` on a definite `inset-y-0 h-full`, so its child shrinks by default. Neither suite can see this — jsdom lays nothing out and `D8.8` asserts only class presence — so the dialog at a real viewport height is on `D8.12`'s browser-walk list. The `drawer` variant needs no equivalent bound: `SheetContent` is already `inset-y-0 h-full` on its `left`/`right` side variants, which is what the `drawer` uses — the size tokens do not map `top`/`bottom`. It does need the **gutters**, which `SheetContent` supplies none of: the app's wrapper pads the drawer today, so under the inversion the container's row template carries them on **the body and footer rows both** (`px-4` on each, `pb-4` on the footer) — what ships pads body and footer together and leaves the header self-padded by `SheetHeader`'s own `p-4`, so gutters on the body row alone would leave Cancel and Save flush to the drawer's edge, and `drawer`/`md` maps to `w-full sm:max-w-lg` so the shipped width is unchanged too.
- **The container is content-agnostic; the frame supplies the element, not the contents.** Container and form frame are fused today; split, the same surface serves a detail view, a confirmation with a long body, or a wizard — none of which hand it a `<form>` at all. Only the form case supplies a `column`; with none given the container renders its own `div` as the inner column. The behavioural halves stay in `apps/admin` as thin wrappers: the footer's `isPending`/`isDirty`/`isValid` reads through `useFormContext` in the app's wrapper, and the page variant's `useBlocker` (`enableBeforeUnload: false`) stays in the app's `AppFormPage` — a router hook has no business in a package whose shell "knows nothing about routing".
- **`AppFormFrame`'s signature changes, and it has two call sites, so the change is staged.** It gains a `className` it forwards to its `<form>`, its `FieldSet` gains the `contents` display, and it renders the container's rows as its `children`. That settles a question the inversion otherwise leaves ambiguous: the frame's `children` are the **rows**, so the field JSX cannot also be its `children`, and **`FieldGroup` and `AppFormError` move up one file, into `app-form-surface.tsx`, which passes them as the container's body content**. The frame keeps what [ADR-0035](0035-config-driven-resource-ui.md) makes load-bearing — the two providers and the submit lock. `AppFormError` moves, and the honest statement of why that owes 0035 nothing is narrower than "same module": **the frame has two call sites, and both are in `shared/form`**, so 0035's guarantee — the failure `applyServerErrors` could not land on a field is never rendered to nobody — still has exactly one implementation per shell rather than one per resource, which is the property 0035's D3.7 amendment was protecting. Both call sites take the wrapping **in the same step**: `app-form-surface.tsx` and `app-form-dialog.tsx` alike at `D8.9`, a two-line change to the second that leaves the rest of it alone until `D8.11`. And the invariant is stated as something a test can see rather than as a file location — **`FieldGroup` and `AppFormError` render inside the `<form>` and inside the disabled `FieldSet`** — which is a **new** structural assertion `D8.9` writes: `app-form-surface.test.tsx:178-197` pins the footer inside the lock, not the error's nesting, so the property needs its own test (a forced `root.server` error, its node a descendant of both the `<form>` and the `[data-slot="field-set"][disabled]`). Only `footer` becomes the container's own slot, because the container is what knows where a fixed footer goes. But `app-form-dialog.tsx` is a second call site that passes `footer=` and relies on the old layout, and it does not adopt the container until the step after. **So the frame's `footer` becomes optional — `readonly footer?: ReactNode` under `exactOptionalPropertyTypes` — and it gains `readonly className?: string`, which keeps the dialog call site **compiling** through the routed-mount step (it still takes the two-line `FieldGroup`/`AppFormError` wrapping there); the dialog step (`D8.11`) then retires the prop** — otherwise the routed-mount step cannot end green on `check-types`, which every step must. Its prop doc's rule — the footer "has to be *inside* the `<form>` and inside the locked `FieldSet`" — is preserved by the inversion rather than waived by it, in both shapes. **This is not a change to [ADR-0035](0035-config-driven-resource-ui.md) and owes it no supersession** — but the argument has to rest on the ground that survives the move, not on a claim the move falsifies. 0035's D3.7 amendment assigns the chrome to a *component* by name, and after `D8.9` the frame no longer renders `AppFormError` itself, so "the frame keeps all three" would be false. What is true, and sufficient: **what leaves the frame is layout**, which is not what 0035's D3.7 amendment was protecting — it names the chrome a resource would otherwise repeat (the providers, the submit lock, the error's single home), not the boxes that chrome sits in — and **both call sites stay in `shared/form`**, so 0035's guarantee — the failure `applyServerErrors` could not land on a field is never rendered to nobody — still has exactly one implementation per shell rather than one per resource, which is the property the D3.7 amendment was protecting. If a reader takes 0035's D3.7 sentence as placing `AppFormError` in the frame *element* rather than in the shell's chrome, the honest answer is ADR-0049's and not a sentence asserting the move did not happen: a fourth record superseding 0035, written before `D8.9` rather than after it.
- **The container serves both mounts.** The routed mount is always-open and closing is a navigation; but three shipped, deliberately non-routed ceremonies — profile change-password and both administrative password resets — consume `AppFormDialog` directly with `open`/`onOpenChange` state. A container that assumed the routed contract would break all three; `open`/`onOpenChange` are therefore part of its API, defaulted for the routed case.
- **Sizes are a token set, not free values**: `sm | md | lg | xl | full`, mapped per variant to a class string and merged through `cn` onto `DialogContent`/`SheetContent` — written with the `sm:` modifier (`sm:max-w-*`), because the primitives’ own caps are `sm:`-prefixed (`DialogContent`’s `sm:max-w-lg`, `SheetContent`’s `sm:max-w-sm`) and `tailwind-merge` will not drop a prefixed class in favour of an unprefixed one — both already merge `className`, so sizes cost **zero generated-file edits**. Any further generated-file edit carries the **ADR-0047** comment naming the rule that forced it — 0047 carries 0031's rule and 0031 is out of force from `D8.1`; the existing ADR-0031 comments stand as history and are not swept.
- **Every [ADR-0044](0044-record-routes-without-list-state.md)/[0035](0035-config-driven-resource-ui.md) invariant carries over as this container's job**: the URL is identical across all three variants; closing is a navigation for the routed mount; an in-flight mutation refuses dismissal in all three shells (the `dismissible` flag is how the wrapper says so); and the record's title is always exactly one real heading — the surface's own in `dialog` and `drawer`, the shell's `<h1>` under `page` (§2) — which is the defect `D4.2` found by testing the shells against each other, closed without creating a duplicate.
- **The structural pins hold**: the `dialog` variant keeps rendering a Radix Dialog (`role="dialog"`), the `drawer` variant the primitive `SheetContent` with `data-slot="sheet-content"` and still modal, and the `page` variant neither. **Three** suites name shells by exactly those and must keep passing unchanged — `app/__tests__/record-routes.test.tsx:98`, `shared/form/__tests__/app-form-surface.test.tsx:232` and `pages/users/__tests__/users-page.test.tsx:285-287` — and the third is the one that also depends on the drawer staying modal, since its hidden-row assertion rests on Radix's `aria-hidden` over the rest of the document.
- **`ConfirmDialog` does not adopt the container in D8.** It stays on `AlertDialog` — its own Radix root, no `showCloseButton` — and is named here as the future candidate for the container's "confirmation with a long body" case, decided when one exists rather than left to a step to discover.

### 5. Testing: geometry asserted in the package, behaviour asserted in the app

- **`@repo/ui`'s extended suite asserts roles, accessible names, `data-slot`/`data-*` attributes and the composition's own geometry classes** — and nothing behavioural: its harness is a `matchMedia` stub and Testing Library cleanup, with no form, no router, no MSW and **no `@testing-library/user-event`** (it is not among the package's devDependencies). The geometry half of that list is not a widening but the point: `data-full-height` is an attribute rather than a slot, and the size tokens are class strings, so a rule of "slots only" would forbid the assertions this record's own decisions need. What the missing `user-event` costs is stated rather than discovered: the controlled mount is asserted here **declaratively** — content present under `open`, absent after a rerender with `open={false}` — while `onOpenChange` actually firing from a dismissal gesture is asserted in `apps/admin`, where `user-event` lives.
- **The three-shell parity suite stays in `apps/admin` and is the `page` variant's exerciser.** It depends on `react-hook-form`, a real memory router and `@/test/render`, so it cannot follow the container into the package; extended to the new container it covers `dialog | drawer | page` without any shipped resource changing (the `dialog` variant reaches the container at `D8.11`, when `AppFormDialog` adopts it) — no resource declares the page edit surface, and the suite is what keeps that variant from being the third unexercised surface. Its harness mounts the shell around **the `page` variant only** — under `dialog` and `drawer` Radix hides the rest of the document from role queries, so a shell there adds cost and no assertion — and declares `staticData` (including `recordLabel`) on its own memory routes, feeding the shell through `route-meta.ts` rather than a literal `title` prop. **That channel is typed, and the step pays for it**: `staticData.title` is `title?: TranslationKey` over `ParseKeys<FlatNamespace[]>`, while the harness passes `title="Demo record"` as an ordinary string today — so the title becomes a `demo:` key declared on the harness route — the fixture's namespace is already augmented into `ResourceNamespaceMap`, and the demo resource already assigns bare `demo:` literals to `TranslationKey` fields, so no cast is needed, and because `useRouteTitle` wraps it in `t()`, the expected string in the retargeted assertions is the *resolved* translation. `recordLabel` bypasses `t()` and is asserted literally. Said here so the builder meets the type error in the record rather than in the compiler. **What that suite can claim is the shell's rendering: one heading, carrying the label, in the right element.** What it cannot claim is the route channel itself, because its routes are hand-built: that `/staff/$staffId` declares `recordLabel` and `route-meta.ts` reads it off the generated tree is asserted in `app/__tests__/`, where real `staticData` exists and where the breadcrumb's last-crumb assertion already reaches. Both halves are named because no shipped resource declares `editSurface: "page"` — the variant's exerciser is deliberately a harness, and saying so keeps the assertion from proving its own wiring.

## Consequences

- **Both SPAs get their frame from one package**, and D9's extraction stays mechanical: nothing behavioural moved, so its "no behaviour change" claim remains checkable by comparing test totals — minus the two-line file-count correction §Decision 1 charges.
- **Long forms keep their title and their Save button in every size token** — the defect that motivated the surface, closed structurally rather than per-screen.
- **The D6.3/D7.5 placement of theme and locale is reversed, on the record.** The account-menu *grouping* survives intact; its *mount* moves to `headerEnd`. Anyone reading D6.3's reasoning finds the counter-argument here rather than a silent contradiction.
- **The three pages that repeat their route title lose the duplicated `CardTitle`** — `staff`, `users` and `dashboard` — and the existing heading queries keep matching exactly one element; a page that reintroduces a second heading with the route's title breaks them, which is now a feature of the queries rather than an accident. The `page` surface variant is held to the same rule by §2's heading bullet, which is the only place the duplicate is armed in the *catalogue* rather than in a component.
- **The slot-honesty rule is enforceable at review, and this record was cut down by it**: a slot justified by D11 must point at a sentence in `docs/plan/0011-customer-app.md`, added in the same change — and D11's file states its needs only generically today, so the sentence is written by the step that cites it. Every slot in the v1 API has a today-consumer (`sidebar`, `headerEnd`, `breadcrumbs`, `banner`, `title`), and the three that did not — `brand`/`nav`/`sidebarFooter` as separate drawer regions, plus `headerStart` and `pageActions` — were struck rather than shipped unexercised.
- **Two coordinated edits per new package path** (exports entry, lint pattern) **plus one re-export per symbol** are now a stated pattern with two precedents; forgetting the lint pattern is one failure mode to check for, and a door line outliving its last consumer is the other.
- **The banner region is D12-ready and D12-free**: the slot, the component and `dismissible` ship now; the principal field, the session plumbing and the `ImpersonationBanner` content remain D12's, and the no-`@repo/contracts`-import rule is the boundary a review can check.
- **`widgets/dashboard-layout` thins rather than disappears**, and its `widgets`-layer placement is carried by [ADR-0049](0049-admin-app-architecture.md), which supersedes frozen [ADR-0032](0032-admin-app-architecture.md) whole at `D8.1` rather than leaving the account-block move as an unrecorded divergence; the same thinning holds for `shared/form`'s wrappers around the container.
- **What becomes harder**: the compositions are hand-maintained code in a package that was previously (almost) all generated — they are owned like `ui-strings.tsx`, with no upstream to diff against; and ADR-0031's upgrade-cadence coupling now covers layout, so a shell change is a both-apps change by construction, `"use client"` included.
- **Follow-ups owed to specific files**: the stale breadcrumb comment in `apps/admin/src/app/providers/ui-strings.tsx` (corrected by the first step that renders one); the `AppFormPage` docblock in `apps/admin/src/shared/form/app-form-surface.tsx:229-238`, which explains why the page shell renders a real `<h2>` — true until §2 gives the shell's `<h1>` the record's name, and rewritten by the step that makes that so; every comment that *states the `UiStrings` key count, or a number derived from it*, and says six or thirteen — the derived case is real: one comment counts the keys an `lv` fixture leaves in English, which becomes twelve when the fourteenth key lands. The five primitive owned-edit comments are rewritten **count-free** ("routes the primitives' operator-read strings through `UiStrings`"), per ADR-0047 §What-code, so they satisfy the predicate rather than needing an exception to it. ## Alternatives considered

- **The compositions stay per-app and the customer app forks them.** The default under frozen ADR-0031, and the drift argument that created `@repo/ui` applies with more force to layout than to buttons: two shells diverge at the first app-local fix. Rejected because the second consumer's requirements are nameable now; the honest trade-off is that this is the divergence that forces ADR-0047 at all.
- **A separate compositions package (`@repo/layouts`).** Avoids superseding 0031 and was considered and rejected by the operator in favour of **one door per app** — a second package is a second exports map, a second lint pattern set and a second version to keep in step, bought only to keep a frozen record unedited, which is not what the supersession mechanism is for.
- **Two additive ADRs — one for the shell, one for the surface.** They share the packaging path, the strings mechanism, the testing split and the slot-honesty rule; splitting them would state each twice or cross-reference itself into one record anyway. One record, at the cost of length.
- **`react-hook-form` and `@tanstack/react-router` enter `@repo/ui` so the whole surface moves.** The reading D9's plan currently assumes. Rejected: it contradicts the shell's own no-routing rule, hands the design system a form engine ADR-0031 §Field-family deliberately kept it agnostic of, and couples both apps to two more heavy dependencies. The honest trade-off is that "one container, three variants" covers **geometry only**, the behavioural wrappers stay app-side, and D9's table takes its correction.
- **A submit button outside the form, carrying `form="<id>"`.** Avoids fighting the primitives' layout, and needs id plumbing through every surface while still leaving the footer outside the `useFormContext` it reads — the wrong half of the problem solved.
- **`Banner` on shadcn's alert primitive.** The package has no `alert` today; generating one only to compose over it puts the banner's base under the regenerate-and-diff rule for no upstream benefit, since the banner's shape (spanning the content column, dismissible, session-scoped) is not the alert's. Hand-written, at the cost of owning its look outright.
- **The pseudo-locale notice gated on `config.VITE_I18N_PSEUDO` directly.** Renders in no test in the repository — the suite pins the variable to `"false"` on purpose — so the slot would be exercised only in a dev build. A prop with the env var as the app's default keeps the honest consumer honest.
- **ADR-0046 §13's `register(i18n)` for the compositions' strings.** The right mechanism for the packages D9 will extract, and the wrong one here — but not for the reason it is easy to give. §13 is dependency *injection*: the instance arrives as a parameter and the package calls `addResourceBundle` on it, so it adds no i18next import (`src/test/render.tsx` already runs that shape). What rules it out is the ordering [ADR-0047](0047-ui-package-scope.md) §Context sets: the package must render correct English with **no provider and no i18n mounted at all** — `apps/web` today — which `UiStrings` does by construction and §13 does not. That §13's `I18n` type is `apps/admin`-owned until D9 extracts it, so the package cannot import even the type, is the **secondary, mechanical blocker, and it expires at D9 while the first does not**. `UiStrings` already exists, already reaches every generated primitive, and grows by one key per string.
- **Prove `headerEnd` by moving only `ThemeMenuItems`/`LocaleMenuItems`.** They are bare `DropdownMenuRadioGroup` fragments, mountable only inside a `DropdownMenuContent`; moving them alone means restructuring both features away from the radio-group semantics D6.3 chose. The whole `AccountMenu` moves instead — cheaper, and it keeps the D6.3 reasoning intact while reversing only the mount point.
- **The page header renders its own heading beside the shell's `<h1>`.** The obvious composition and a shipped bug: the staff, users and dashboard heading queries would match two elements and throw. One owner of the `<h1>`, decided once; the three pages' pseudo-titles go, and §2's `page`-variant rule closes the same duplicate where it is armed in the catalogue rather than in a component.
- **`ConfirmDialog` adopts the container now.** Uniform, and premature: `AlertDialog` is its own Radix root with its own dismissal semantics, no shipped confirmation has a long body, and adopting the container would be the third change to a working surface in one deliverable. Named as the candidate instead, so the next long confirmation re-reads this bullet rather than re-deriving it.
